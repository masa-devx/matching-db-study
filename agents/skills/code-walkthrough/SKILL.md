# コードを解説する

目的：AI が書いたコードを、人が**自分の言葉で説明でき、突っ込まれても答えられる**ようにする。コードは直さない（気になる点は報告に挙げ、`pr-review` かチケットに回す）。

## 1. 読む

- PR の差分（`gh pr diff <番号>`）・チケット・`03-how.md`
- 差分のファイルだけでなく、呼ぶ所と呼ばれる所（ルート・テスト・使っている Model）も読む
- レガシー版の同じ処理：`git diff legacy-repo..HEAD -- <パス>`、または `git show legacy-repo:<パス>`

## 2. 書く（`06-walkthrough.md` に PR ごとの節）

[docs/process.md](../../../docs/process.md) の6章の見出しで書く。

| 見出し | 書き方 |
| --- | --- |
| ディレクトリの設計 | 足したファイルのツリーと、置き場の理由（`architecture-backend.md` のどの決まりか）。ほかに置ける場所と、置かなかった理由 |
| クラスの責務 | 1クラス1行：「〇〇を知っていて、〇〇をする。〇〇はしない」 |
| メソッドの表 | public のメソッドを全部。入力・戻り値・副作用・失敗のしかた・呼ぶ所。マスが長くなるときは、メソッドごとの見出しと箇条書きにする。コードの短い抜き出し（5〜10行）を2〜3か所 |
| 呼び出しの流れ | Mermaid の sequenceDiagram。リクエスト → middleware → コントローラー → 業務 → DB（流れる SQL を矢印に書く）→ 応答 |
| 名前 | 主な名前と、ほかの候補・選ばなかった理由 |
| 依存の向き | Mermaid の flowchart。矢印は「使う」向き。逆向きがあれば書く |
| レガシー版との違い | 前はどこに何行あったか、どう分かれたか |
| 直した課題と、現場での意味 | `05-problems.md` のこのチケットの節を指し、この PR で、現場の何が変わるか（だれが困らなくなるか・どう気づけるようになるか・測った前と後の数字）を3行で |

Mermaid のラベルに `"` `<` `>` を使うときは、引用符で囲むか言い換える。

## 3. 説明の練習（承認の前に、必ず）

承認を聞く前に、必ず1問やる。人が答えるまで、承認を聞かない（2026-11-18 に人が決めた。飛ばすと、説明できないまま取り込むことになるため）。短くてよい（1問・突っ込みは2〜3回まで）。

1. `リーダー：` と名乗り、「このメソッドが何をしているか、説明してください」と、大事なメソッドを1つ選んで頼む。問いは、なるべく現場の場面の形にする（例：「この不具合の問い合わせが来たら、このコードのどこから見ますか？」）
2. 人の説明のあとに、2〜3回突っ込む（なぜここに置いた・失敗したらどうなる・同時に来たら・どのテストで確かめている）
3. 合っているところ・ずれているところを返し、`06-walkthrough.md` の「説明の練習」と `docs/onboarding/quiz-log.md` に残す

### 3-2 面接の形の練習（大きなトピックに当たるとき）

設計の判断を、「なぜ？」と2段・3段と聞かれても、自分の言葉で答えられるようにする（2026-11-20 に人が決めた）。地図は [docs/onboarding/design-topics.md](../../../docs/onboarding/design-topics.md)。

- `docs/onboarding/design-topics.md` の地図で、このチケットが当たる小さな見出しを探す（なければ飛ばす）
- 練習のメモは、人の手元の非公開のリポジトリにある。置き場は `agents/notes.local.md` の「面接の練習の置き場」に書いてある（書いていなければ、この 3-2 は飛ばす）。このリポジトリの分は、その中の `projects/matching-db-study/tech/<分野>/<トピック>/`（なければ、そのリポジトリの `method/templates/topic.md` で作る）
- そのトピックの `questions.md` から1〜2問を、面接官の役で聞く。答えのあとに、合っている所・ずれている所・足りない所を返す。2回詰まったら、答えを出して説明する
- 答えと返しを `attempts.md` に残す（間違えた答えも消さない）。言えたら `decision.md` の判断の1枚を、本人の言葉で直す。そのリポジトリの `method/consistency.md` で一貫性を確かめる
- 練習のメモは非公開なので、このリポジトリの PR やチケットに中身を書かない
- 地図にない小さな見出しに当たったら、`design-topics.md` に足す

## 終わりの条件

- その PR の節が埋まり、図が描ける形になっている
- 人が大事なメソッドを1つ以上、自分の言葉で説明できた（承認の前）
- 書いた解説は、コミットの前に止まる（AGENTS.md の「コミットの前に」）
