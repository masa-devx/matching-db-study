# コードを解説する

目的：AI が書いたコードを、人が**自分の言葉で説明でき、突っ込まれても答えられる**ようにする。コードは直さない（気になる点は報告に挙げ、`pr-review` かチケットに回す）。

## 1. 読む

- PR の差分（`gh pr diff <番号>`）・チケット・`03-how.md`
- 差分のファイルだけでなく、呼ぶ所と呼ばれる所（ルート・テスト・使っている Model）も読む
- レガシー版の同じ処理：`git diff legacy-repo..HEAD -- <パス>`、または `git show legacy-repo:<パス>`

## 2. 書く（`06-walkthrough.md` に PR ごとの節）

[docs/process.md](../../../docs/process.md) の6章の見出しで書く。

| 見出し | 書き方 |
| --- | --- |
| ディレクトリの設計 | 足したファイルのツリーと、置き場の理由（`architecture.md` のどの決まりか）。ほかに置ける場所と、置かなかった理由 |
| クラスの責務 | 1クラス1行：「〇〇を知っていて、〇〇をする。〇〇はしない」 |
| メソッドの表 | public のメソッドを全部。入力・戻り値・副作用・失敗のしかた・呼ぶ所。コードの短い抜き出し（5〜10行）を2〜3か所 |
| 呼び出しの流れ | Mermaid の sequenceDiagram。リクエスト → middleware → コントローラー → 業務 → DB（流れる SQL を矢印に書く）→ 応答 |
| 名前 | 主な名前と、ほかの候補・選ばなかった理由 |
| 依存の向き | Mermaid の flowchart。矢印は「使う」向き。逆向きがあれば書く |
| レガシー版との違い | 前はどこに何行あったか、どう分かれたか |

Mermaid のラベルに `"` `<` `>` を使うときは、引用符で囲むか言い換える。

## 3. 説明の練習

1. `リーダー：` と名乗り、「このメソッドが何をしているか、説明してください」と、大事なメソッドを1つ選んで頼む
2. 人の説明のあとに、2〜3回突っ込む（なぜここに置いた・失敗したらどうなる・同時に来たら・テストはどこで守っている）
3. 合っているところ・ずれているところを返し、`06-walkthrough.md` の「説明の練習」と `docs/onboarding/quiz-log.md` に残す

## 終わりの条件

- その PR の節が埋まり、図が描ける形になっている
- 人が大事なメソッドを1つ以上、自分の言葉で説明できた
