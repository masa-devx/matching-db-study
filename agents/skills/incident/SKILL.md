# 割り込みの出来事を起こして、対応する

目的：計画どおりに進まない実務の場面を、手元で安全に練習する。

先に [docs/process.md](../../../docs/process.md) の5章を読む。

## 守ること（いつも）

- 壊してよいのは、開発用の DB（`matching_dev`）と、出来事のための作業用のブランチ（`incident/<日付>-<名前>`。push しない）だけ
- `main`・`legacy-repo`・`refactored-repo` のブランチ、テスト用の DB、秘密の値のファイル（`.env` など）は触らない
- データを壊す前に、必ずバックアップを取る：`docker compose exec db pg_dump -U postgres -Fc -f /tmp/matching_dev-before-incident.dump matching_dev`
- 何を壊したか（答え）は `agents/pm-secret.local.md`（git に入らない）にだけ書き、ポストモーテムまで人に言わない

## 1. 出来事を選ぶ

今のサイクルで触っている領域に近いものを選ぶ。

| 出来事 | 起こし方の例 |
| --- | --- |
| 障害 | `incident/` のブランチに、境界の条件を1つ壊すコミットを入れて切り替え、`docker compose restart app`／開発用の DB の行を壊す（例：プランの値段を NULL にする）／重い SQL を入れて遅くする |
| ユーザーの急増 | 「会員が10倍」と数字で知らせる。まず人に、増やすための道具（シーダーの倍率・負荷をかける道具）のチケットを考えてもらう |
| 急ぎの依頼 | PM の役で、期限つきの依頼を出す。今のサイクルから何を外すかを相談する |
| 外からの変化 | 「〇〇の版に脆弱性」と知らせる（作った例。実在の脆弱性の番号は使わない）。影響の調べ方と更新の手順を考えてもらう |

## 2. 知らせる

- ビジネス側か監視の役を名乗り、**症状だけ**を知らせる（例：「ビジネス側（サポート）：10時から、ログインできないと問い合わせが30件です」）。原因は言わない
- `ticket` で障害のチケット（`r-incident.md`）を作る案を出す。Priority は PM とリーダーの役で人と決める

## 3. 対応を進める

1. 人に、何から見るかを決めてもらう（ログ：`backend/client/storage/logs/`・SQL のログ・応答・画面）。詰まったら、ヒントを3段で1段ずつ出す（どこを見るか → 考え方 → 形）
2. 止血（暫定の対応）：`hotfix/` のブランチで直すか、設定やデータを戻す。直したら症状が止まったかを確かめる
3. 原因：なぜ起きたか・なぜ気づくのが遅れたかを、人に言ってもらう
4. 恒久の対応：再現するテストと直しを、不具合か改善のチケットにする（`ticket`）
5. チケットの「時間の流れ」を、その場で埋める

## 4. 片付けと、ポストモーテム

1. `refactored-repo` に戻し、`incident/` のブランチを消す（`git branch -D`。push していないもの）。データを壊したなら、バックアップから戻す：`docker compose exec db pg_restore -U postgres -d matching_dev --clean /tmp/matching_dev-before-incident.dump`
2. 答え（何を壊したか）を人に伝える
3. `docs/incidents/YYYY-MM-DD-<名前>.md` を `_template.md` から書く（人を責めない書き方）。「次に防ぐこと」はチケットの案にする
4. 今のサイクルで外したチケットを、PM の役で次へ回す

## 終わりの条件

- 症状が止まり、片付けが済み、ポストモーテムと恒久の対応のチケットがある
