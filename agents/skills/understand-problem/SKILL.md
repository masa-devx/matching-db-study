# 直す課題を理解する

目的：実装の前に、人が「何が問題で、現場では何が起き、どう直すか」を自分の言葉で説明できるようにする。AI が書くコードは、そのあとに読む。

先に [docs/process.md](../../../docs/process.md) の1章（話し合いの決まり）と4章を読む。2026-11-18 に人が決めた（改善の段階は、学習と現場を想定して、課題を理解しながら進む）。

## 1. 読む

- チケットの本文（`gh issue view <番号>`）・今のサイクルの `03-how.md`・関係する要件（`docs/requirements/`）
- レガシー版で測った結果：`docs/api/*.md` の「レガシー版で起きること」・`docs/onboarding/as-is-db.md`・`docs/data-model.md`・その一歩の解説のページの 9-2
- 原因のあるコード（ファイルと行）。レガシー版のコードは `git show legacy-repo:<パス>` でも読める
- 秘密の値のファイル（`.env` など）は読まない

## 2. 課題を見せる（リーダーの役。直し方の答えは、まだ言わない）

次の4つを、短く見せる。数字は、測ったものだけを書く。文書にない・古いときは、ここで測る（読むだけの SQL・`EXPLAIN (ANALYZE, BUFFERS)`・curl。書き込みは開発用の DB だけで行い、終わったら元に戻す）。

| 見せること | 中身 |
| --- | --- |
| 起きていること | 再現の手順と結果（入力 → 応答・DB の行）。測った数字（SQL の本数・時間・読んだページ・件数） |
| 現場ならどう見えるか | だれが困るか（会員・運営・サポート・お金）・どう気づくか（問い合わせ・ログ・アラート・数字の変化）・どのくらいの規模で起きるか（今の 2万人・10倍のとき・同時に何人） |
| 原因のある所 | ファイルと行を1〜3か所。コードの抜き出しは10行まで |
| 似た課題 | ほかの API にも同じ形があれば、場所だけ（直す範囲を広げない。広げるなら PM の役に戻す） |

- チケットが土台づくり（ツールの導入・テストの土台など）で、直す不具合がないときは、「これがないと、現場で何が困るか」（気づけない・戻せない・直すたびに怖い・遅くなる）を、同じ表で見せる
- 作った数字（測っていない数字）を、測ったように書かない。分からないことは「分からない」と書く

## 3. 人に答えてもらう（問いは3つまで）

1. なぜ起きるか（原因を、自分の言葉で）
2. どう直すか（案を1つ。DB の制約・トランザクション・置き場・インデックスなど）
3. 直ったことを、どう確かめるか（テスト・測る数字）

- 答えを先に言わない。人の答えのあとに、合っているところ・ずれているところ・足りないところを返し、弱いところと代わりの案を必ず1つ出す
- 2回詰まったら、ヒントを1段ずつ出す
- 人の案と `03-how.md` の設計が違ったら、どちらにするかを人が決める。設計を変えるなら、`tech-lead` の「3 どう作るか」に戻る

## 4. 残す

`docs/cycles/<番号>-<名前>/05-problems.md`（なければ `docs/cycles/_template/05-problems.md` をコピーする）に、チケットごとに1節を書く。

- 2の4つ（起きていること・現場での見え方・原因の場所・似た課題）。表にせず、1つずつ見出しと箇条書きで書く
- 人の答えの要点と、リーダーが返したこと（合っている・ずれている・足りない）
- 決めたこと（直し方・確かめ方）。設計と違えば、その理由
- 書いたら、コミットの前に止まる（AGENTS.md の「コミットの前に」）

## 終わりの条件

- `05-problems.md` にそのチケットの節があり、人が、原因と直し方と確かめ方を、自分の言葉で答えた
- ここで初めて、`implement` の「テストから書く」に進む

## エラー時

- 測れない（データがない・API がまだない）ときは、測れないことと理由を書く。推測の数字は書かない
- 人が「今回は飛ばす」と決めたときは、`05-problems.md` に「飛ばした（理由）」と1行残してから進む
