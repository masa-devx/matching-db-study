# PR レビューのコメントのひな形

行ごとのコメントは使わない。**1つのレビュー（`event: COMMENT`）の本文に、見出しと図でまとめる。** 人は番号で、ターミナルで答える。直し終わったら、PR に「対応のまとめ」を1つ書く。

## 決まり

- 指摘に番号を付ける：`M`（must）・`S`（should）・`A`（ask）・`N`（nits）＋数字。答えも直しも番号で指す
- 1つの指摘に書くのは、**場所・何が起きるか・現場で起きること・どう直すか・根拠**の5つ。図は、文で分かりにくいときだけ足す
- 「現場で起きること」は、だれが困るか（会員・運営・サポート・お金）・どう気づくか（問い合わせ・ログ・アラート・数字）・どのくらいの規模で起きるか、を1〜2行で。学習のために書く（2026-11-18 に人が決めた）。分からないときは「要確認」と書き、作った数字を書かない
- 図の選び方（Mermaid。GitHub の PR でそのまま描ける）

| 見せたいもの | 図 |
| --- | --- |
| 依存の向き・置き場・判断の分かれ道 | `flowchart` |
| 同時に2回来るとき・API と DB のやり取り | `sequenceDiagram` |
| 表の形・制約 | `erDiagram` |

- Mermaid のラベルに `"`・`<`・`>` を使うときは引用符で囲むか言い換える（壊れて描けなくなる）
- 公開のリポジトリなので、実務の言葉・社名・秘密の値を書かない
- 文は `agents/rules/writing.md` の書き方と言葉で書く。レビュー役の報告に、使わないと決めた言い方が入っていたら、まとめるときに直す
- 範囲を人が絞ったとき（例：ルールと書き方だけ）は、外した指摘を「今回は外したもの」に1行ずつ残す

## 本文のひな形

````markdown
## レビュー：<PR のタイトル>

### 結論
- 出してよいか：直してから／このままでよい
- 件数：must <n>・should <n>・ask <n>・nits <n>
- 見た角度：<要件・設計・…>

| # | 指摘（短く） | 現場で起きること（短く） | 場所 | 角度 |
| --- | --- | --- | --- | --- |
| M1 | … | … | `path:行` | … |
| S1 | … | … | `path:行` | … |

### この PR の全体像（図）
```mermaid
flowchart LR
  …（変えた層・ファイルと依存の向き。DB を変える PR なら erDiagram）
```

---

### M1 <タイトル>（must・<角度>）
**場所**：`path:行`
**何が起きるか**：<具体的な入力と結果>
**現場で起きること**：<だれが困るか・どう気づくか・どのくらいの規模で>
**図**：（必要なときだけ）
**どう直すか**：<直し方。案が2つあれば (a)・(b)>
**根拠**：<要件 ID・ルールのファイルと行>

---

（S・A・N も同じ形。N は1行ずつでよい）

### 今回は外したもの
### 確かめたこと・確かめていないこと
### 答え方
ターミナルで、番号で答えてください（例：「M1 直す」「S2 直さない：理由」「A1 (a)」）。
````

## 対応のまとめ（直し終わったら、PR のコメントに1つ）

```markdown
## 対応のまとめ

| # | 扱い | 中身 |
| --- | --- | --- |
| M1 | 直した | <コミット> で… |
| S2 | 直さない | 理由：… |
| S3 | チケットにした | #<番号>（Inbox） |
```
