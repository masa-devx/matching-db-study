# PR をいろいろな角度からレビューする

目的：実務の PR レビューと同じく、角度ごとに別の目で見て、出してよいかを人が決められるようにする。レビュー中はコードを直さない。

先に [docs/process.md](../../../docs/process.md) の7章を読む。

## 1. 集める

- PR の番号・差分（`gh pr diff <番号>`、ブランチを開いているなら `git diff refactored-repo...HEAD` と未追跡のファイル）・チケットの本文・`03-how.md`
- 実装の会話や経緯は、レビュー役に渡さない

## 2. レビュー役を選んで、並列に頼む

| いつも | 差分にあれば足す |
| --- | --- |
| `requirements-reviewer`・`design-reviewer`・`edge-case-reviewer`・`security-reviewer`・`test-reviewer` | マイグレーション・クエリ・Model → `db-reviewer`／ログ・例外・設定・マイグレーション・compose → `ops-reviewer`／`frontend/` → `frontend-reviewer` |

- 1つのメッセージで、選んだ全員に同じ資料を渡す（Agent ツールの並列）。プロンプトに「報告は日本語で。指摘ごとに、現場で起きること（だれが困るか・どう気づくか・どのくらいの規模で）を書く」と書く
- `edge-case-reviewer`・`security-reviewer` は P0〜P2 で返すので、P0 → `[must]`・P1 → `[should]`・P2 → `[nits]` に読み替える。比較元は `refactored-repo` と伝える

## 3. 確かめて、まとめる

1. 同じ指摘をまとめる（いちばん重い印にする）
2. 指摘ごとに、コードを読んで本当に起きるかを確かめる。起きないものは落とす。確かめきれないものは「要確認」を付けて残す
3. 印ごとに表にしてチャットで見せる：印・ファイルと行・何が起きるか・現場で起きること・直し方・どの角度か
4. 何を確かめたか（角度ごとに1行）も添える

## 4. PR にコメントを残す

人が決めた（2026-11-15）ので、まとめを見せたら、聞かずにコメントにしてよい。ただし公開のリポジトリなので、実務の言葉・社名・秘密の値が入っていないかを先に見直す。

- 本文は [review-template.md](review-template.md) の形で書く（番号・見出し・図）。行ごとのコメントは使わない（人が決めた。2026-11-15）
- 1つのレビューとして出す：`gh api repos/masa-devx/matching-db-study/pulls/<番号>/reviews -X POST --input <JSON>`
  - JSON：`{"event": "COMMENT", "body": "<本文>"}`
- `event` は `COMMENT` だけにする。承認（`APPROVE`）と変更の要求（`REQUEST_CHANGES`）は AI がしない
- `docs/cycles/<番号>/07-review.md` に、扱いのまとめ（印・指摘を短く・扱い）を書く

## 5. 人のレビューと、直し

1. 人に「自分でも差分を読み、コメントを書いてください。気になる所は [ask] で聞いてください」と頼む
2. 人は、指摘への答えをターミナルで番号で返す（「M1 直す」「S2 直さない：理由」）。人の `[ask]` には、実装の担当として答える
2-1. 直し終わったら、PR に「対応のまとめ」を1つ書く（形は [review-template.md](review-template.md)）
3. `[must]` は `implement` の手順で直し、直したらもう一度このスキルを回す（変わったところだけでよい）。`[should]` は直すか、`ticket` で Inbox に入れるかを人と決める。直さない `[should]`・`[nits]` のうち、性能・設計の改善になるものは、`docs/onboarding/design-topics.md` の「改善の候補」に置くかも人と決める（つながるトピックは、人に先に答えてもらう）。直したら、コミットの前に止まり、差分を見せる（AGENTS.md の「コミットの前に」）
4. 3回まわっても同じ指摘が行き来したら、人が決める
5. must がなくなったら、承認を聞く前に、`code-walkthrough` の「説明の練習」を済ませる（1問。人が答えるまで、承認を聞かない）。そのあと、人が承認する。GitHub は自分の PR を承認できないので、人が PR に「承認」とコメントするか、チャットで「承認」と言ったら、承認とみなす
5-1. 承認は、そのとき見せた差分にだけ当てはまる。承認のあとにファイルを変えたら（レビューの直し・解説の追記を含む）、差分を見せて、もう一度承認をもらう（2026-11-18。承認のあとに、見せていない直しを入れて取り込んだことがあったため）
6. 承認と CI が通ったら取り込み、チケットを閉じ、ボードを Done にする（取り込みは確かめてから）

## 終わりの条件

- PR にレビューのコメントがあり、`07-review.md` に扱いが書け、must がなく、人が承認した

## エラー時

- レビュー役が差分を読めなかったら、その角度を「問題なし」にしない。読めなかったことを伝える
- 投稿のあと、PR を開いて Mermaid の図が描けているかを見る。描けていなければ、その図を直して出し直す
