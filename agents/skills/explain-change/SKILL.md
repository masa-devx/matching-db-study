# 実装したことを解説して、記録する

目的：AI が書いたコードを、読んで理解したうえで次へ進む。このスキルでは**コードを直さない**（気になる点は報告に挙げる）。

## 1. 対象を決める

- どの一歩か、どの段階かを確かめる（言われなければ、目次で状態が「解説だけ」か「レガシー版まで」の一歩を提案する）
  - レガシー版のあと → 9-1（レガシー版）と 9-2（測った問題と数字）を書く
  - 改善したあと → 9-3（足したテスト）と 9-4（改善版と、前と後の数字）を書く
  - 00・05b は分けずに、9章に1つの記録として書く
- 差分を取る：`git status --short` と `git diff`（コミット済みなら、その一歩のコミットの範囲）
- その一歩の解説のページ（`explanations/<番号>-*.html`）を読む
- 秘密の値のファイル（`.env` など）は読まない。差分に含まれていても中身を出さない

## 2. 確かめる

- テストを実行して、結果をそのまま記録する（コマンドは AGENTS.md の「主要コマンド」）。実行していないものを通ったことにしない
- 解説のページの「6. どう確かめるか」に書いたもの（クエリの数・EXPLAIN・同時に送ったときの結果）を実行し、数字を取る。レガシー版のあとは「前」の数字、改善したあとは「後」の数字として記録する
- レガシー版の段階ではテストがないので、テストの結果の代わりに、測った問題をそのまま記録する

## 3. ページの「9. 実装の記録」を書く

その段階の見出し（9-1〜9-4）の下の `<p>【まだ実装していない】</p>` を置き換える。書くこと（その段階に合うものだけ）：

| 見出し | 中身 |
| --- | --- |
| 書いたもの | ファイルの一覧（パス）と、それぞれの役割を1行 |
| 大事な行の読み方 | 3〜5か所。コードの短い抜き出しと、「何をしていて、なぜそう書くのか」 |
| 実際に流れる SQL | Eloquent が流した SQL（クエリログ）・改善したあとの SQL・マイグレーションの要点。インデックスや制約が効くところ |
| テストで確かめたこと | テストの名前・何を確かめたか・実行の結果（通った・落ちた） |
| 数字 | EXPLAIN の前と後・実行時間・読んだ行の数（性能の一歩だけ） |
| 解説から変えたこと | 「4. 選択肢」で選んだ案から変えたところと、その理由。なければ「なし」 |
| 図 | 実装した形のテーブルや流れが、解説の図と違えば、新しい図を1枚足す（Mermaid） |
| 気になる点 | 直していないが気づいたこと（次の一歩や、リファクタリングの候補） |

改善したあとは、[docs/decisions.md](../../../docs/decisions.md) の「一歩で決めたこと」に1行足す（決めたこと・ほかの案・理由・前と後の数字・このページへのリンク）。要件（`docs/requirements/<機能>.md`）の「関連する設計・テスト」に、このページとテストへのリンクを足す。

あわせて、ページの先頭と `explanations/index.html` の目次の状態を、レガシー版のあとは「レガシー版まで」、改善したあとは「実装済み」にする。

## 4. claude.ai に載せ直す

記録を書いたページを、[explain-step](../explain-step/SKILL.md) の「5. claude.ai に載せる」と同じ手順で載せ直す。`agents/notes.local.md` にある URL を使い、同じリンクのまま更新する。

## 5. チャットで伝えて、止まる

- 変えたこと・大事な行の読み方・テストの結果を短く伝える
- 理解を確かめる問いを2〜3個出す（例：「この UNIQUE を外すと、どのテストが落ちるか」「この JOIN を LEFT にすると、結果はどう変わるか」）。答えは聞かれたら出す
- 次の一歩を1つ提案し、「次の一歩の予定をカレンダーに入れますか？」と聞いて止まる。入れると言われたら [study-calendar](../study-calendar/SKILL.md) で進める。コミットは頼まれたときだけ行う

## 終わりの条件

- ページの「9. 実装の記録」が埋まり、テストの結果が実際の出力と合っている
- 目次とページの状態が「実装済み」になっている
