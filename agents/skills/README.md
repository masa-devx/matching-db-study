# スキルの一覧

このフォルダのスキルと、その呼び出し方。Claude Code では `/<名前>` で呼ぶか、「」の言い方で頼む。`.claude/skills` と `.agents/skills` はこのフォルダへのリンクなので、Codex からも使える。

## 一覧

| コマンド | 何をするか | いつ使う | 頼み方の例 |
| --- | --- | --- | --- |
| `/explain-step` | 次の一歩の解説と図を `explanations/<番号>-*.html` に作る。コードは書かない | 新しい一歩に入る前 | 「次の一歩を解説して」「02 を解説して」 |
| `/explain-change` | 書いたコード・SQL・テスト・EXPLAIN の数字を解説し、その一歩のページの「9. 実装の記録」に書く | 一歩の実装が終わったとき | 「実装を解説して」「記録して」 |
| `/issue-plan` | 親 Issue と子 Issue の下書きを作り、確認を取ってから GitHub に作る | 新しい一歩や改善に入る前 | 「02 の Issue を作って」「N+1 を直す Issue を作って」 |
| `/study-calendar` | 一歩を 30〜60 分のタスクに分け、確認を取ってから Google カレンダーに入れる | 予定を立てたいとき。explain-step・explain-change の終わりに聞かれたとき | 「カレンダーに入れて」「02 の予定を作って」 |
| `/review` | 差分を、確かめたいこと・開発ルールと照らしてレビューする | 区切りごと | 「レビューして」 |
| `/harness-setup` | 残っている【記入】を数え、質問しながら順番に埋める | セットアップの途中 | 「セットアップを進めて」「技術が決まったので反映して」 |
| `/harness-extend` | スキル・ルール・サブエージェントを型どおりに下書きし、確認を取ってから足す | 新しい手順やルールを足したいとき | 「この手順をスキルにして」「ルールを足したい」 |

`/issue-plan` は、機能や改善の Issue を作る。子 Issue は DB・API・フロント・今の動きを確かめるテストに分け、作った Issue はマイルストーンと Project につなぐ。

### 改訂版（refactored-repo）の開発サイクル

回し方の正本は [../../docs/process.md](../../docs/process.md)。

| コマンド | 何をするか | いつ使う | 頼み方の例 |
| --- | --- | --- | --- |
| `/pm` | PM とビジネス側の役で話し合う。今の段階を見て次の一手を出す | サイクルの頭・なぜ／何を作るか・振り返り | 「次は何をする？」「サイクルを始めて」「仕分けして」 |
| `/tech-lead` | リーダーの役で設計を話し合い、チケットに分け、理解度チェックをする | どう作るか・チケットを切る・PR のあと | 「どう作るか話そう」「理解度チェックして」 |
| `/ticket` | 10種類のひな形でチケットを作り、ボードの項目を付ける | チケットを作る・Inbox に入れる | 「チケットを作って」「Inbox に入れて」 |
| `/understand-problem` | 実装の前に、直す課題（レガシー版で起きていること・現場での見え方・原因）を人が理解する。人が先に答え、リーダーが弱いところを返す | Ready のチケットに入るとき（`/implement` の最初） | 「#120 の課題を理解したい」「課題を説明して」 |
| `/implement` | チケット1つを設計どおりに実装し、PR を作る。コミットの前に、人が差分を見る | 課題を理解したあと | 「#120 を実装して」 |
| `/code-walkthrough` | PR のディレクトリとメソッドの設計を解説し、説明の練習をする | PR を作ったあと | 「この PR を解説して」 |
| `/pr-review` | いろいろな角度のレビュー役に見せ、PR にコメントを残す | 解説のあと | 「PR をレビューして」 |
| `/release` | 手元でリリースする | サイクルの終わり | 「リリースして」 |
| `/incident` | 割り込みの出来事を起こして対応する | pm が予告なしに呼ぶ・練習したいとき | 「障害の練習をしたい」 |
| `/proposal` | 人からの提案を相談する | いつでも | 「提案です：…」 |

```text
/pm（仕分け → なぜ → 何を）
  → /tech-lead（どう作るか → 設計のレビュー → チケットに分ける）→ /ticket
  → チケットごとに：/understand-problem → /implement → /code-walkthrough（説明の練習）→ /pr-review → /tech-lead（理解度チェック）
  → /release → /pm（振り返り）→ 次のサイクル
  （途中に /incident・いつでも /proposal）
```

## 一歩の流れで使う順番（レガシー版）

```text
/issue-plan（親と子の Issue を作る）
  → /study-calendar（予定を入れる）
  → /explain-step（解説を読む）
  → 「実装して」（レガシーコードで作る：Fat Controller・テストなし）
  → /explain-change（レガシー版と、測った問題を記録）
  → 「直して」（今の動きを確かめるテストを足して直し、もう一度測る）
  → /explain-change（前と後の数字を記録）
  → /review（区切りごとに見直す）
```

## スキルを足したとき

1. このフォルダに `<名前>/SKILL.md` を置く（手順は `/harness-extend`）
2. この表と、[../README.md](../README.md) の「作業手順を呼び出す」に1行ずつ足す
