# チケットを実装する

目的：決めた設計とチケットの範囲だけを、レビューできる形の PR にする。設計を変えたくなったら、実装を止めてリーダーの役で相談する。

## 1. 読む

- チケットの本文（`gh issue view <番号>`）・今のサイクルの `03-how.md`・関係する要件（`docs/requirements/`）と `docs/api/`
- AGENTS.md の「作業前に読むルール」の表で、触る領域のルールをすべて読む（`agents/rules/architecture.md` は改訂版の設計。古いコードを触るときは、その10章（移し方）に従う。Larastan の目標はレベル 9（D-016）だが、今の `phpstan.neon` はレベル 6。上げるのは別のチケットにし、足したコードはレベル 9 でも通る書き方にする）
- 秘密の値のファイル（`.env` など）は読まない

## 2. ブランチを切る

- `refactored-repo` を最新にしてから、種類に合うブランチを切る（process.md の2章：`feature/`・`refactor/`・`fix/`・`hotfix/`・`chore/`）
- ボードの Status を In progress にする（`ticket` の「ボードの項目を付ける」）

## 3. テストから書く

- 改善：今の振る舞いを固定するテストを先に足し、**直す前のコードで通る**ことを確かめる
- 不具合：再現するテストを先に足し、**落ちる**ことを確かめる
- 機能：受け入れの条件ごとのテスト（要件 ID を名前に入れる）
- テストの決まりは `agents/rules/testing.md`。本物の PostgreSQL（テスト用の DB）で流す

## 4. 実装する

- `03-how.md` の「ディレクトリとクラス」の表のとおりに置く。表にないファイルを足すときは、理由を PR の「見てほしいところ」に書く
- チケットにないこと（気づいた別の直し）は足さず、Inbox のチケットの案として報告に挙げる
- コメントは「なぜ」だけを書く

## 5. 確かめる

AGENTS.md の「主要コマンド」で、次を流して結果をそのまま残す。

- テスト（Pest。画面なら Vitest）・Pint・Larastan（画面なら lint・build）
- 測る：流れる SQL の本数（クエリログ）・EXPLAIN・時間。改善なら前と後
- 受け入れの条件を、テストのほかに curl か画面でも1回確かめる

## 6. PR を作る

- 本文は `.github/pull_request_template.md` の見出しを埋める（何を・なぜ・ディレクトリとクラス・流れる SQL・テスト・前と後の数字・リリースと戻し方・見てほしいところ）
- コミット・push・PR の作成は、人に確かめてから行う。行き先は `refactored-repo`
- PR を作ったらボードの Status を In review にする
- 続けて `code-walkthrough`（解説）と `pr-review`（レビュー）に進むことを伝える

## 終わりの条件

- PR ができ、テスト・静的検査が通り、測った数字が PR にある

## エラー時

- テストや検査が通らないときは、設定を緩めて通さない。原因と、試したことを伝えて止まる
