# 雛形の【記入】を順番に埋める

写した雛形を、このプロジェクトの事実で埋めていく。推測で埋めない。分からないところは【記入】のまま残し、何が決まれば埋められるかを伝える。1回の依頼で進めるのは1つの手順だけにする。

最初のコミットの前は、`main` の上で埋めてよい。最初のコミットのあとは、`main` の上での編集をフック（main-guard）が止めるので、残りは worktree で埋める（例：Issue「セットアップの残り」を立てて `wt <番号> setup chore`）。

最初に埋め終えたら、このスキルの役目は終わる。そのあとスキル・ルール・サブエージェントを足すときは [harness-extend](../harness-extend/SKILL.md) を使う。

## 1. 進み具合を調べる

次を実行し、残っている【記入】と目印を数える。

```sh
grep -rn '【記入】\|__NODE_LTS__\|【アプリ名】' --exclude-dir=.git --exclude-dir=node_modules --exclude-dir=worktrees . | grep -v -e 'skills/harness-' -e 'plans/template.md' -e 'requirements/template.md' -e 'docs/operations.md'
```

外しているもの（数えない）:
- harness-setup と harness-extend の SKILL.md（説明のための文字）
- ひな形の `agents/plans/template.md` と `docs/requirements/template.md`（Issue や機能のたびにコピーして使うので、【記入】が残っているのが正しい）
- `docs/operations.md`（公開の前に埋める。残っていることだけ伝える）

残った行のうち、言葉として【記入】や目印に触れているだけの説明の行（`docs/README.md` の「各ひな形の【記入】と記入例を…」、`mise.toml` の注釈）も数えない。
- `docs/` がないとき（アウトプット（学習）で消したとき）は、手順 1 を AGENTS.md の冒頭だけにする

下の手順ごとに、残りの数とファイルを表にして見せ、まだ終わっていない手順のうち一番前のものを「次の1つ」として示す。

## 2. 手順

順番どおりに進める。前の手順が決まらないと決められないものがあるため。ただし、ユーザーが別の手順を指定したら、それに従う。

| 手順 | 決めること | 埋めるところ |
| --- | --- | --- |
| 1 目的 | 誰の何を解決するか・利用者と場面・主要な機能・成功基準・不変条件・対象外・用語 | docs/product.md、AGENTS.md の冒頭（1〜2文の要約だけ） |
| 2 技術スタック | 言語・フレームワーク・DB と ORM・テスト・静的検査・デプロイ先と版 | AGENTS.md の「技術スタック」、mise.toml、.gitignore の生成物、database.md の冒頭 |
| 3 ディレクトリ構成 | 実装・テスト・スキーマの置き場所 | AGENTS.md の「ディレクトリ構成」、architecture.md の「構造」、各ルールの `paths:`、testing.md の置き場所 |
| 4 主要コマンド | セットアップ・起動・テスト・静的検査・ビルド | AGENTS.md の「主要コマンド」、testing.md の表とシード、.claude/settings.json の `permissions.allow` |
| 5 ルールを選ぶ | 使わないルール（DB がない・ログを共通化しない など）と、残すルールの【記入】 | agents/rules/、agents/README.md の「ルールの目次」、AGENTS.md の「作業前に読むルール」、.claude/hooks/prod-db-guard.mjs の道具 |
| 6 スキルとサブエージェントを選ぶ | 使わないスキル（エラー監視がなければ debug-issue）、モデルと道具 | agents/skills/、.claude/agents/、agents/README.md の表と一覧、agents/prompts/workflow.md の表 |
| 7 秘密の値のファイル | 使う秘密の値のファイルの名前（値は聞かない・読まない） | .gitignore、.worktreeinclude、.claude/settings.json の `deny`、環境変数の見本（名前だけ） |
| 8 骨組みに入る | 同時に動かすとぶつかるもの（ポート・DB・Docker のプロジェクト名） | AGENTS.md の「作業の場所」。最初のコミットと、骨組みの Issue を勧める |

## 3. 1つの手順の進め方

1. その手順で決めることを、まとめて質問する。選択肢があるものは、選択肢とおすすめを示す
2. 答えをもとに、埋めるところを書き換える案を出し、確認を取ってから書く
3. 埋めた節の「> 記入例」の行は消す（このプロジェクトの事実に置き換わったため）。まだ埋めていない節の記入例は残す
4. 書いたあとに確かめる
   - 手順 3：`paths:` の glob が、実際のファイルに合うか（`git ls-files` で、合うファイルが1つ以上あるか。まだファイルがなければ、その旨を伝える）
   - 手順 4：書いたコマンドを実際に実行し、動いたものだけを残す。動かなかったものは【記入】に戻し、理由を伝える。`permissions.allow` に足すのは、何度実行しても何も壊さないコマンドだけにする
   - 手順 5・6：外したファイルへの言及とリンクが残っていないか（`grep` と `find . -type l` で、切れたリンクがないか）
   - 手順 7：3か所の名前がそろっているか。秘密の値のファイルの中身は読まない
   - どの手順も：.claude/settings.json を変えたら、JSON として正しいか
5. 残りの数と、次の1つを伝える

## 4. 手順 8 で行うこと

- 最初のコミットを勧める（コミットは頼まれたときだけ行う）。worktree はコミットがないと作れない
- 骨組みの Issue の下書きを出し、確認を取ってから `gh issue create` で作る。題は「骨組み：起動・テスト・Lint・CI」、本文には、起動・テスト・Lint・CI が通る状態にすることと、手順 4 で【記入】に残ったコマンドを埋めることを書く。本文の形は `.github/ISSUE_TEMPLATE/feature.md` に合わせる
- 最初のコミットのあとは、`main` の上での編集とコミットがフックで止まることを伝える
- そのあとの作業は、AGENTS.md の「作業の流れ」に従う

## 終わりの条件

- 手順 1〜8 の【記入】がなくなった（docs/operations.md と、決まっていないと伝えたものを除く）
- 最初のコミットと、骨組みの Issue ができた

終わったら、残したもの（docs/operations.md・決まっていない【記入】）を一覧にして伝える。

## エラー時

- 質問に答えが出ないものは、【記入】のまま残し、何が決まれば埋められるかを書いて次へ進んでよいか確認する
- コマンドが動かないときは、出たエラーをそのまま伝える。動かないコマンドを主要コマンドに書かない
