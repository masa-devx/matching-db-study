## ルールを足す・変える

ルールは作業のたびに読まれるので、密度を保つ。

- 新しいルールは、次の3つをすべて満たすものだけ足す
  1. 自明でない：慣れた人でも、書かれていなければ間違える
  2. 繰り返す：同じ間違いが2回以上起きた（1回の作業での複数回を含む）
  3. 具体的：守り方が1つに決まる指示であり、漠然とした原則ではない
- 構造の説明（ディレクトリの中身、データの流れ）は書かない。コードを読めばわかり、すぐ古くなる。書くのは避けるべき罠である
- まず、同じカテゴリの既存ファイルに足せないかを考える。足せないとき、または1つのファイルが長くなりすぎたときだけ、新しいファイルに分ける
- 新しいファイルの名前は `<カテゴリ>-<内容>.md`（英小文字の kebab-case）にする
  - カテゴリは `architecture`・`testing`・`logging`・`database`・`api`・`quality`・`performance`・`ci`・`security` から選ぶ。合うものがなければ、足す理由を添えて新しいカテゴリを提案する
  - 例：`api-no-breaking-changes.md`（公開している API の互換性を壊さない）・`testing-timezone.md`（時刻と時間帯に依存させない）
- 1つの領域にしか効かないルールは、ファイルの先頭に `paths:` を付けて置く
- 各ルールには、守り方と一緒に「なぜ」を1行で書く。間違いやすい書き方と正しい書き方の例を、短く並べてよい
- ファイルを足したら、この目次の該当カテゴリに1行足す
- エージェントは通常の作業中にルールを直接書き換えない。追加案は PR 本文やレビュー報告に書き、足すかは人間がレビューで決める。足すときは、なぜ必要かを添えて専用のコミットにする
- 既存ルールの言い換えや明確化は、いつでも歓迎する

## 相互レビューを依頼する

実装とは別のセッションで、差分と判定の基準を渡す。実装の対話履歴や経緯は渡さない。別のセッションは、実装の会話を持たないサブエージェントで代えてよい。8ステップの Step 2・3（プランのレビュー）も同じ。

スキルは作業の手順、サブエージェント定義は担当の役割・モデル・使用ツールを記述する。review スキルでレビューの準備と報告を揃え、観点別の担当を使う場合は .claude/agents/ の3体（実装のレビュー）へ依頼する。スキルを読み込むだけで、実装から独立したレビューになるわけではない。

レビュー役には `isolation: worktree` を付けない。付けると、作業中の変更を持たない worktree が作られ、レビューしたい変更が見えなくなる。レビューは、変更のある worktree の中から呼ぶ。

定義は .claude/agents/ にある（Claude Code 向け）。8ステップのどこで使うかで並べる。
