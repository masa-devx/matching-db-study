# マイグレーション規律と守備範囲

【記入】使う DB・ORM・マイグレーションの道具（記入例: PostgreSQL 17・Prisma）。コマンドは AGENTS.md の「主要コマンド」に書く。

## マイグレーション規律

- 適用済みのマイグレーションファイルは編集しない。修正は新しい
  マイグレーションで行う
- 本番・ステージングはロールバックせず、前進のみ（forward-only）で
  修正する。開発DBだけはリセットしてよい
- UNIQUE / NOT NULL などの制約を既存テーブルへ追加する前に、
  違反する行がないか読み取り専用の検査クエリで確認する
- 値が変わる業務設定（税率・料金表）は関数にハードコードせず、
  設定テーブルを参照する（変更のたびのデプロイをなくす）
- 列名を変えると、ORM によっては「削除と追加」のマイグレーションが生成されてデータが消える。
  生成された SQL を必ず読む（記入例: Prisma なら `@map` で旧名を残すか、`RENAME COLUMN` を手書きする）

## クエリと型の罠

- トランザクションの中で外部APIやメール送信を呼ばない。ロックを持ったまま待つうえ、
  ロールバックしても送ったものは取り消せない。コミット後に実行する
  （記入例: Prisma の `$transaction`）
- 金額は小数の型（Decimal）か最小単位（円）の整数で持つ。浮動小数点（Float）にしない
  （0.1 + 0.2 のような丸め誤差が請求額に出る）
- 持ち主（ユーザー・組織）ごとのデータを持つテーブルへのクエリには、必ず持ち主のIDの条件を入れる。
  IDだけで1件を引くクエリは、他人の行も返す（記入例: Prisma の `findUnique({ where: { id } })`）

## DBが守るもの／アプリが守るもの

| DB（制約で守る） | アプリ（コードで守る） |
| --- | --- |
| 一意性（UNIQUE） | 認可（誰がどの行を見られるか） |
| 参照整合（FK）・値域（CHECK） | 業務フロー（ステータス遷移の順序） |
| 同時実行で破れる不変条件 | 外部サービスとの整合 |

判断基準: 「UIを通らない書き込み（バッチ・手動SQL・バグ）でも
絶対に壊れてはいけないか？」→ Yesなら DB制約、Noならアプリに置く。
