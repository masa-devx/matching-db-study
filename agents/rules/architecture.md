# architecture

置き場所・責務・機能の境界を決めるときの判断基準。ディレクトリの中身の説明は書かない（AGENTS.md の「ディレクトリ構成」は索引だけ）。

## 構造（どこに何を置くか）

迷ったらこの順で問う:

1. 特定機能の業務ロジック → 【記入】機能ごとのフォルダ（記入例：`src/features/<機能名>/`）
2. どの機能にも属さない基盤（DB の接続・ログ・認証の共通処理など） → 【記入】基盤のフォルダ（記入例：`src/lib/`）
3. 複数機能で共有したい処理 → 安易に共通化せず、まず各機能に置く。同じ事実だと分かってから、基盤へ移す

機能は、画面・API・DB の層で横に切らず、機能ごとに縦に切る。1つの機能を変えるときに、触るフォルダが1か所にまとまるようにするためである。

## SSoT（1つの事実は1箇所に）

- 定義（ステータス・定数・金額の計算式・バリデーション）を書く前に、既存の定義を検索して使う。見つからないときだけ新しく書く
- 共通化するのは「同じ事実」だけ。見た目が似ているだけの処理は、各機能に置いたままにする
- 型・スキーマ・API の形は、生成元を1つに決め、そこから生成する。手で写した定義を2か所に置かない（記入例：DB のスキーマから型を生成し、API の定義から型付きのクライアントを生成する）

## 過剰設計の禁止

- 要件にない汎用化・設定項目・抽象化を足さない。1箇所でしか使わないものにインターフェースや共通関数を作らない
- 起こりえない入力への防御を足さない。検証は外部からの入力の境界で行う
- 凝った書き方より、読んですぐ分かる書き方を選ぶ。1行に詰め込むより、手順を分けて書く

## 1ファイル1責務

- ファイルの担当を一文で言えること。「請求書の金額計算」は合格、
  「請求書まわりの処理いろいろ」は失格
- ファイルが肥大したら、責務の境界で割る

## 機能境界

- 他機能のテーブルへ直接クエリしない。所有機能の公開している関数を経由する
  （例: 入金処理がユーザー情報を更新するときは user の関数を呼ぶ）
- 入口（ルート・コントローラー・画面のイベント）に業務ロジック・クエリを直書きしない。業務の関数を呼ぶだけにする
- 【記入】言語に特有の罠を足す（記入例：TypeScript では barrel export（index.ts への集約・再エクスポート）を使わず、実ファイルへ直接 import する。循環参照と読み込みの遅さを避けるため）

## 副作用の分離（Functional Core / Imperative Shell）

- 業務判断・計算・変換は純粋関数に集める（Functional Core）
- DBの読み書き・外部API・時刻・乱数・環境変数参照は外側の薄い層へ寄せ、
  Coreが返した結果を実行するだけに近づける（Imperative Shell）
- 狙いは、複雑なロジックを外部依存なしでテストできる形に保つこと
