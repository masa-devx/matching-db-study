# 文書の書き方と、使う言葉

ルール・スキル・チケット・議事録・PR の文は、初めて読む人にも分かるように書く。このリポジトリだけで通じる言い方（たとえや、作った言葉）は使わない（2026-11-17 に人が決めた）。

## 書き方

- 1文に1つのことを書く。条件が3つ以上並ぶときは、箇条書きにする
- 専門用語は、初めて出てくる所で1文で説明してから使う
- たとえより、実物（URL・ファイル・画面・テストの名前）を主語にする
- 業務の言葉（会員・マッチ・トークルームなど）は、[docs/glossary.md](../../docs/glossary.md) の名前にそろえる

## 使う言葉

| 使う言い方 | 意味 | 使わない言い方 |
| --- | --- | --- |
| 今の動きを確かめるテスト | 直す前に、今の動きをそのまま（要件と違う所も含めて）確かめるテスト。直したあとも同じ動きかを比べるために使う。バックエンドでは、ふつう API テストで書く（`architecture-backend.md` の10章）。画面や単体のテストでも、同じ目的ならこう呼ぶ | 固めるテスト・固定するテスト・（テストで）固める |
| API テスト | API を呼び、状態コード・応答・DB の変化を確かめるテスト | ― |
| API テストがある・API テストで確かめている | その API に、少なくとも成功が1本と、`docs/api/` に書いた失敗ごとに1本の API テストがあること（`architecture-backend.md` の10章） | （テストで）守るテスト・守っている |
| テストを弱めて通す | 確かめる中身を減らしたり、期待値を実装に合わせたりして、テストを無理に通すこと | 骨抜き |
| コピーする・書き足す | コード・ファイルを同じ形で複製すること／ルールや文書に、決めたことを足すこと | 写す |
| 変えずに残す | 今の URL の中身を、直さずにそのまま置いておくこと | 凍結 |
| 分かっている不具合 | 要件と違うと分かっているが、そのチケットでは直さない動き。テストには「分かっている不具合：…」とコメントを書く | 既知のリスク |
| Repository（画面） | 画面で、データの出どころ（REST・Firestore）を隠す型の約束（`repository.ts` の `XxxRepository`）と、その実装（`features/*/repositories/`）。`architecture-frontend.md` の2章。バックエンドの DB とのやり取りの意味ではない | Source・Adapter・Interface（約束と実装の呼び名として） |
| 業務のまとまり | Auth・Members・Matching のような、業務ごとの分け方。フォルダ・ルートの名前・OpenAPI の `tags` にそろえて使う。ファイルの中で2回目からは「まとまり」と書いてよい | （初めて出てくる所で、説明なしの）まとまり |

## 決まりを保つ仕組み

| 仕組み | 見るもの |
| --- | --- |
| AGENTS.md の「応答と報告」 | 返事・チケット・PR・議事録・ルールの文を書くとき、この決まりを読む |
| `python3 -I agents/tools/check-words.py`（CI の `docs.yml` でも流れる） | 上の表の「使わない言い方」のうち、意味が1つに決まる言葉。古い言い方を説明のために引くときは「」で囲む |
| レビュー役（`design-reviewer`・`requirements-reviewer`・`test-reviewer`） | 文脈で決まる言葉（守る・入口・まとまり）と、説明のない新しい言い方 |
| `ticket`・`implement`・`pr-review` のスキル | チケットの本文・PR の本文・レビューのコメント（GitHub にあり、機械の検査が届かない） |

表に言葉を足したら、`agents/tools/check-words.py` の `WORDS` にも足す（意味が1つに決まる言葉だけ）。

## 言葉の範囲

- 「守る」は、テストの意味で使わない。「決まりを守る」「要件を守る」のような普通の意味では使ってよい
- 「入口」は、層の名前（HTTP・コマンド・キュー・Webhook のような、外から呼ばれる所）としては使ってよい。ルートやコントローラーそのものを指すときは、その名前で書く（例：「501 を返すだけのコントローラー」）
- 今あるコードのコメントは、この決まりの対象の外。その API を移すチケットで直す。新しく書くコメント（テストの「分かっている不具合：…」など）には、この表の言葉を使う
- `explanations/`（レガシー版の解説）は、記録として残すので書き換えない
