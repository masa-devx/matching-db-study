# 文書の書き方と、使う言葉

ルール・スキル・チケット・議事録・PR の文は、初めて読む人にも分かるように書く。このリポジトリだけで通じる言い方（たとえや、作った言葉）は使わない（2026-11-17 に人が決めた）。

## 書き方

- 1文に1つのことを書く。条件が3つ以上並ぶときは、箇条書きにする
- 専門用語は、初めて出てくる所で1文で説明してから使う
- たとえより、実物（URL・ファイル・画面・テストの名前）を主語にする
- 業務の言葉（会員・マッチ・トークルームなど）は、[docs/glossary.md](../../docs/glossary.md) の名前にそろえる

## 使う言葉

| 使う言い方 | 意味 | 使わない言い方 |
| --- | --- | --- |
| 今の動きを確かめるテスト | 直す前に、今の動きをそのまま（要件と違う所も含めて）確かめるテスト。直したあとも同じ動きかを比べるために使う。API テストの1つ | 固めるテスト・固定するテスト・（テストで）固める |
| API テスト | API を呼び、状態コード・応答・DB の変化を確かめるテスト | ― |
| API テストがある・API テストで確かめている | その API に、少なくとも成功が1本と、`docs/api/` に書いた失敗ごとに1本の API テストがあること（`architecture.md` の10章） | （テストで）守るテスト・守っている |
| テストを弱めて通す | 確かめる中身を減らしたり、期待値を実装に合わせたりして、テストを無理に通すこと | 骨抜き |
| コピーする・書き足す | コード・ファイルを同じ形で複製すること／ルールや文書に、決めたことを足すこと | 写す |
| 変えずに残す | 今の URL の中身を、直さずにそのまま置いておくこと | 凍結 |
| 分かっている不具合 | 要件と違うと分かっているが、そのチケットでは直さない動き。テストには「分かっている不具合：…」とコメントを書く | 既知のリスク |
| 業務のまとまり | Auth・Members・Matching のような、業務ごとの分け方。フォルダ・ルートの名前・OpenAPI の `tags` にそろえて使う。ファイルの中で2回目からは「まとまり」と書いてよい | （初めて出てくる所で、説明なしの）まとまり |

## 言葉の範囲

- 「守る」は、テストの意味で使わない。「決まりを守る」「要件を守る」のような普通の意味では使ってよい
- 「入口」は、層の名前（HTTP・コマンド・キュー・Webhook のような、外から呼ばれる所）としては使ってよい。ルートやコントローラーそのものを指すときは、その名前で書く（例：「501 を返すだけのコントローラー」）
- コードのコメントは、この決まりの対象の外。その API を移すチケットで直す
- `explanations/`（レガシー版の解説）は、記録として残すので書き換えない
