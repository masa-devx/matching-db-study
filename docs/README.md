# プロジェクトのドキュメント

「何を作るか」と「なぜその設計にしたか」の正本。AGENTS.md・background.md・解説のページには書き写さず、ここへリンクする。両方のブランチ（`legacy-repo`・`refactored-repo`）に共通なので、`main` で直して取り込む。

## 文書の使い分け

| 文書 | 記録すること | 使う場面 |
| --- | --- | --- |
| [product.md](product.md) | 何を作るか・主要な機能・不変条件・対象外・用語（コードでの名前つき） | 機能の範囲と言葉をそろえる |
| [requirements/template.md](requirements/template.md) | 機能の振る舞いと受け入れ条件（要件 ID つき）のひな形 | 一歩に入る前に、何ができれば合格かを決める |
| [api.md](api.md) | API の全体の決まり（パス・ステータス・エラーの形）と、API ごとの設計（入力・応答・失敗・流れる SQL の目安・curl の例） | API を作る前に設計を書き、確かめてもらう。画面の型を手で書くとき |
| [ci.md](ci.md) | CI で何を・いつ・どこで動かすか。マージの決まり | CI を足す・変えるとき。CI が落ちたとき |
| [decisions.md](decisions.md) | なぜその設計・技術にしたか（ほかの案・理由・前と後の数字） | 選んだ理由を説明するとき。直したあとに1行足す |

あとで足すもの（中身ができたときに作る。空のファイルは置かない）:

| 文書 | 記録すること | 作るとき |
| --- | --- | --- |
| `data-model.md` | 今の全体の ER 図と、表の一覧 | 01 で最初の表を作ったとき |

## 作成と更新

- 機能を足すときは、requirements/template.md を写し、`requirements/<機能名>.md`（英小文字の kebab-case。例：`likes.md`）として保存する。1つの機能を長く表すファイルで、一歩ごとには作らない
- 要件は、一歩の解説（`explain-step`）を作る前に、質問しながら決める（状態：草案 → 確定）
- 直す段階で足す「振る舞いを固定するテスト」は、要件 ID（`FR-001` など）に対応させる。素朴な版も直した版も、同じ要件を守る
- 直したら、decisions.md に1行足す（`explain-change`）
- 未確定のことは「要確認」と書く。文書を足したら、この目次に1行足す

## 文書と学習の記録の関係

| 置き場 | 中身 |
| --- | --- |
| docs/ | 何を作るか（product・requirements）と、なぜそうしたか（decisions） |
| explanations/ | どう学んだか（一歩ごとの解説・図・実装の記録・数字） |
| AGENTS.md | 使う道具と版・置き場所・コマンド（結論だけ） |
| agents/background.md | 背景・作業の決まり・進め方の好み |
