## #106 アーキテクチャのテスト（管理画面の分。2026-11-18）

会員の側は PR #231 で入れた。この節は、管理画面にコピーする分。土台づくりのチケットなので、「これがないと、現場で何が困るか」を見た。

### 課題（リーダーが見せたもの）

| 見せること | 中身 |
| --- | --- |
| 起きていること | 管理画面のコントローラーは 13個・1,305行。同じ処理がコピーされている：トークンを読む処理 23か所・役割（owner）の確かめ 5か所・監査ログの書き込み 6か所。DB を直接呼ぶ行が 147行。層の決まりを確かめるテストは 0本（会員の側は 15本） |
| 現場ならどう見えるか | 書き込みの API のうち、「停止を解く」（`SuspensionController::destroy`）と「対応のメモを書く」（`MemberNoteController::store`）は、役割の確かめも監査ログもない（見るだけの管理者でも `204`・`201`）。運営から「ある会員の停止が解かれていた。だれが解いたか調べてほしい」と頼まれても、監査ログに記録がなく、答えられない。気づくのは、問題が起きたあと |
| 原因のある所 | `backend/admin/app/Http/Controllers/SuspensionController.php` の `destroy`（`store` をコピーして作り、役割の確かめと監査ログを落とした。コメントにも「写し忘れている」）。決まりは `agents/rules/architecture.md` の「管理画面での当てはめ」に書いてあるが、確かめる仕組みが管理画面にない |
| 似た課題 | 会員の側のコントローラー 19個も、同じくトークンを読む処理をコピーしている（会員の側のテストは入れた） |

### 人の答え

| 問い | 人の答え（要点） | リーダーが返したこと |
| --- | --- | --- |
| なぜ起きるか | 認証情報の管理を定義していないので、バグが起きている | 合っている：決まりを1か所に定義していないのが芯。ずれている：「認証」（だれか。トークンを読む）と「認可」（何をしてよいか。役割の確かめ）を分ける。抜けたのは認可。足りない：監査ログも抜けている。抜けたのは「役割を確かめる → 書く → 同じトランザクションで監査ログ」の手順のまとまり |
| 3つの手順を、どこに1か所にするか | UseCase に置いて、そこで役割を確かめる | 合っている。足すと、3つの手順を全部 UseCase に置く。役割の決まりの中身は Domain（`AdminRole`）。トークンを読むのは Middleware の1か所 |
| どう入れるか（2つのテストのずれ） | テストの中身（決まり）を、会員の側と同じにする | 方向は合っている。弱いところ：コピーは片方だけ直すとずれる（#231 で会員の側を3回直した）。違えるのは、古いコントローラーの一覧と `App\Models` などの一覧だけ。代わりの案 (a) 決まりの部分が同じかを比べるテスト (b) 1つのファイルを両方から読む (c) レビューだけ。人が (a) を選んだ |
| このテストがあると、なぜ「停止を解く」と同じ抜けが起きにくいか | 分からない（ヒントのあとも） | 答えを出した：新しい Controller が DB を直接使うとテストが落ちるので、書き込むには UseCase を通すしかなくなる。UseCase には3つの手順がある。ただし、UseCase の中の書き忘れは、このテストでは見られない（API テストで確かめる。#107）。仕組みごとに確かめる範囲を決めて重ねる |

### 決めたこと

- 直し方：管理画面の `tests/Arch/LayersTest.php` に、会員の側のテストをコピーする。違うのは、ファイルの上の3つの一覧だけ。印より下（決まり）が同じかを、`tests/Arch/SameRulesAsClientTest.php` が比べる（人が (a) を選んだ）
- 確かめ方：管理画面に違反を置いて、落ちるのを見る（とくに「停止を解く」と同じ形：新しい Controller が `DB::table()->update()` で直接書く）。片方のファイルだけ直すと、比べるテストが落ちるのを見る
- 設計（`03-how.md`）と違うこと：なし
- **リーダーの説明のまちがい（実装の前に見つけた）**：3の答えで「新しい Controller が DB を直接使うと、テストが落ちる」と説明したが、会員の側で入れたテスト（#231）は、Model と Repository だけを止めていて、`DB::table()->update()` で直接書く Controller も、トークンを読む Controller も通っていた。設計のルール（4-1：Controller は SQL を書かない・トークンを読むのは Middleware だけ）には書いてあったので、このチケットで、その2つを止めるテストを足した（会員の側と管理画面の両方。決まりの部分なので、2つのファイルで同じ）

## #236 設計の決まりを「Controller → Service → Model」に直す

土台のチケット（直す不具合はない）なので、「この決まりがないと、現場で何が困るか」を見せた（2026-11-18）。

### 課題（リーダーが見せたもの）

| 見せること | 中身 |
| --- | --- |
| 起きていること | Controller の中にロジックと DB の処理が全部ある。会員の側は Controller 20個・1611行、管理画面は14個・1319行（2026-11-18 に数えた）。いちばん長いメソッドは `UserController::index`（会員の検索）の142行、管理画面の `MemberController::index` の117行。DB を直接使う所は `LikeController` に21か所、管理画面の `MemberActivityController` に28か所 |
| 決まりはあったのに | `architecture.md`（865行。4層）は 11-15 からあったが、見本の実物がなく、新しい形のコードは1行もなかった |
| 現場ならどう見えるか | 新しく入った人が「検索の年齢の条件はどこ？」と聞かれ、142行のメソッドを上から読む。1か所を直すと、別の所が壊れないか不安になる。検索が遅くなっても、SQL がどこで組み立てられているかを探すところから始まる |
| 原因のある所 | `backend/client/app/Http/Controllers/UserController.php` の `index`・`LikeController.php` の `store`・`backend/admin/app/Http/Controllers/MemberController.php` の `index` |
| 似た課題 | 画面の側も同じ形（`frontend/client/src/HomePage.tsx`）。エピック #112 で扱う |

### 人の答え

| 問い | 人の答え（要点） | リーダーが返したこと |
| --- | --- | --- |
| なぜ起きるか | `api.php` から Controller への導線が分かりやすく、Controller に書けば、とりあえず動く機能が簡単に作れるから | 合っている（Fat Controller が生まれるいちばんの理由）。足りない：このリポジトリでは、レガシー版はわざと Fat Controller で作った（D-003）。問題は「見本と、書いている時に止める仕組み（機械）がない」こと。現場でも、文書の決まりは書く人がその場で読むとは限らない |
| どう直すか | ロジックは Service に、Model には DB との接続周りとクエリの処理を書く | 前に決めた「DB の処理も Service」とずれていたので、人に選んでもらった。人は「検索などのクエリの組み立ては Model」（B）を選んだ。弱いところ：検索・一覧・集計が増えるたびに `User` が太る（Rails の Fat Model）。代わりの案：条件はスコープで Model、組み合わせは Service |
| どう確かめるか | 仕様で決めたことは機械が確かめ、人はディレクトリを見て判断する | 合っている。足りない：ディレクトリを見るだけでは、正しい場所に置いたファイルの中身（Controller に `if` の判断が残る）は分からない。代わりの案：レビューで「Controller に判断が残っていないか」を見る（`design-reviewer` に足した） |

### 決めたこと

- 形：Controller → Service → Model（D-025）。検索などのクエリの組み立ては Model（人が B を選んだ）
- 確かめ方：アーキテクチャのテストを新しい形で書き直し、違反を置いて落ちることを見る（会員の側と管理画面の両方。違反21種類と、通るはずの4つ。#239 のレビューのあとは、違反31種類と、通るはずの8つ）。中身（Controller の判断）はレビューで見る
- 設計（`03-how.md`）と違うこと：4層から変えた。`03-how.md` に見直したことを書き、前の決定は記録として残した

## #237 ホームのプロフィールの API を Service に移す

動きを変えずに移すチケット（直す不具合はない）なので、「移すと、決まりと今の動きがどこでぶつかるか」を見せた（2026-11-19）。手で動かす確かめは、Bruno（`bruno/client/profile/`）で行った。記録は、PR #240 のレビューのあとに書いた。

### 課題（リーダーが見せたもの）

| 見せること | 中身 |
| --- | --- |
| 起きていること | `ProfileController`（55行）に、JWT を読む・SQL 5本・書き換えが全部ある。`update` はトークンを読まないので、だれが送ったかが分からない（Bruno で、トークンなしの書き換えが 200 になった） |
| 似た課題 | トークンを読むコードが、17の Controller に29か所コピーされている。壊れたトークンは、どこも 500 |
| 現場ならどう見えるか | 401 にする・鍵や期限の決まりを変える、のたびに29か所を直すことになり、直し漏れが起きる |
| ぶつかる所 | ① トークンを読む所（決まり：Middleware だけ）② 応答の形（決まり：Resource で項目を選ぶ）③ 書き換えの入力（決まり：`validated()`）。②③を決まりどおりにすると、今の動きを確かめるテストが落ちる |

### 人の答え

| 問い | 人の答え（要点） | リーダーが返したこと |
| --- | --- | --- |
| `update` で、だれが送ったかは、コードのどこで分かるか | `update` の中では分からない | 合っている。分かるのは URL の番号（だれのものか）だけで、比べる材料が片方しかない |
| `show` の JWT を読む行を `update` にもコピーして比べる案の、弱いところ | 全部の Controller にコピーが要り、直し漏れが起きる | 合っている。今も29か所ある。401 の処理を足すときも、29か所を直すことになる。だから Middleware の1か所で読む |
| 見る API（トークンなしでも通る）と書き換え（ログインが要る）の違いを、Middleware でどう扱うか | ログインしないと見られない（要件）なら、トークンなしでも通す Middleware は意味がないのでは | 要件から見れば合っている（FR-AUTH-020 なら、401 で止める Middleware で足りる）。ただ、このチケットは動きを変えないので、今の「トークンなしでも通る」を残す必要がある |
| ①②③をどうするか | ①は Middleware、②③は今のまま | ― |

### 決めたこと

- ① トークンは、新しい Middleware（`IdentifyMember`）で読む。トークンがあれば読み、なくても通す。壊れたトークンの 500 は今のまま（分かっている不具合）
- ② 応答は、今と同じく全部の列を返す。Resource は作らない（返す項目を選ぶときに作る。`architecture.md` に1行足した）
- ③ 書き換えの入力は `all()` のまま。`validated()` は、直すチケットで入れる
- PR #240 のレビューで決めたこと
  - Service のメソッドの名前は「何ができるか」にする（`showProfile`・`updateProfile`）。「だれが呼べるか」は名前に入れない（`architecture.md` の3章に足した）
  - 移す前と違う動き（3つ）は、コードを変えずに PR に書く
  - 消した `SentLikesListTest.php`・`SupportFunctionsTest.php` は、消したままにする。その API を移すチケットで、今の動きを確かめるテストを書く
  - トークルームとマッチングのまわりの改善は、その機能を直すときに一緒に行う

## #241 エラーハンドリングと例外処理の土台

不具合の8枚（#128〜#158）を調べると、どれも「共通の確かめを、ある API で書き忘れた」形だった。共通の仕組みを先に作る5つ（エラー → ログインの Middleware → 管理画面の役割 → 返す・受け取る項目 → 持ち主の確かめ）のうち、最初のもの（2026-11-19）。

### 課題（リーダーが見せたもの）

| 見せること | 中身 |
| --- | --- |
| 起きていること | エラーの応答を、Controller ごとに手で書いている（会員の側：401 が30か所・403 が9か所・404 が7か所）。業務の例外のクラスがない。`bootstrap/app.php` は「`api/*` なら JSON」だけ |
| 現場ならどう見えるか | 古いブックマークから、いない会員を開くと、応答に Model の名前（`App\Models\User`）が出る。書き換えは 500 になり、運営のログで、不具合か古い URL かを見分けられない。「ログインしてください」の文を変えるには、30か所を直す |
| やること・やらないこと | やる：業務の例外の親と最初の例外・`bootstrap/app.php` の1か所・ログに出さない・API テスト。やらない：今の30か所の書き換え（API を移すときに）・ログインの Middleware（次の作業） |

### 人の答え

| 問い | 人の答え（要点） | リーダーが返したこと |
| --- | --- | --- |
| Service が `abort(404)` ではなく、例外のクラスを投げるのはなぜか | HTTP を知らないので、500・403・401 のエラーハンドリングしかできないから | 一部。Service は、どの状態コードも知らない。`abort(404)` をコマンドから呼ぶと、返す相手がいない。例外は「会員がいない」という業務で起きたことを伝え、何に変えるかは呼んだ側が決める |
| 最初に作る例外はどれか | 500 から例外にする。403・401 は、認証の情報がないときと、本人かどうか | ずれていた。500 は業務の例外にしない（思っていなかった失敗は握りつぶさない）。401 は Middleware の受け持ち。本人でないときは、403 ではなく 404 にする（403 だと、会員がいるかどうかが分かってしまう） |
| （もう一度）Service が投げるのはどれか | 403 | 一部。Service が投げるのは 403・409（業務の決まり）と 404（見つからない）。今いちばん要るのは 404（`ProfileService` の `firstOrFail()` と `RuntimeException`） |
| どう確かめるか | 解説を頼んだ | #237 で残した分かっている不具合の2本を、要件どおりに変えて落ちる（Red）のを見てから直す。`bootstrap/app.php` の行を消すと落ちることも見る |

### 決めたこと

- 最初の例外は「会員が見つからない」の1つだけ。403・409 の例外は、業務の決まりを移すときに足す（9章：過剰設計の禁止）
- 管理画面には、まだ作らない（Service がなく、投げる所がない）
- 会員の側のコードでは、会員を `User` と呼ぶ（案A。`MemberNotFoundException` → `UserNotFoundException` など）
- エラーの文は `lang/ja/errors.php` にだけ書く（案B）。言語は `config/app.php` で `ja` に決める（(a)。環境変数で変えない）
- try-catch は、基本は書かない。意味のある別の動きができるときだけ書く（`architecture.md` の7章に足した）
- テストでは、エラーの文を文字で書く（`testing-style.md` に足した）
- PR #242 のレビューで決めたこと：いくつものまとまりで使う例外は `app/Exceptions/` の直下に置く。業務の例外の `render` と文の書き忘れは、テスト（`BusinessExceptionsTest.php`）で見つける。FR-004 を「見る・書き換える」に広げる
