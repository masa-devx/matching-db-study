# 課題の理解

チケットを実装する前に、直す課題を人が理解した記録。チケットごとに1節（手順は `agents/skills/understand-problem/SKILL.md`）。

## #106 アーキテクチャのテスト（管理画面の分。2026-11-18）

会員の側は PR #231 で入れた。この節は、管理画面にコピーする分。土台づくりのチケットなので、「これがないと、現場で何が困るか」を見た。

### 課題（リーダーが見せたもの）

#### 起きていること

- 管理画面のコントローラーは 13個・1,305行
- 同じ処理がコピーされている
  - トークンを読む処理 23か所
  - 役割（owner）の確かめ 5か所
  - 監査ログの書き込み 6か所
- DB を直接呼ぶ行が 147行
- 層の決まりを確かめるテストは 0本（会員の側は 15本）

#### 現場ならどう見えるか

- 書き込みの API のうち、次の2つは、役割の確かめも監査ログもない（見るだけの管理者でも `204`・`201`）
  - 「停止を解く」（`SuspensionController::destroy`）
  - 「対応のメモを書く」（`MemberNoteController::store`）
- 運営から「ある会員の停止が解かれていた。だれが解いたか調べてほしい」と頼まれても、監査ログに記録がなく、答えられない
- 気づくのは、問題が起きたあと

#### 原因のある所

- `backend/admin/app/Http/Controllers/SuspensionController.php` の `destroy`
  - `store` をコピーして作り、役割の確かめと監査ログを落とした。コメントにも「写し忘れている」とある
- 決まりは `agents/rules/architecture-backend.md` の「管理画面での当てはめ」に書いてあるが、確かめる仕組みが管理画面にない

#### 似た課題

- 会員の側のコントローラー 19個も、同じくトークンを読む処理をコピーしている（会員の側のテストは入れた）

### 人の答え

#### 問い1：なぜ起きるか

- 人の答え：認証情報の管理を定義していないので、バグが起きている
- リーダーが返したこと
  - 合っている：決まりを1か所に定義していないのが芯
  - ずれている：「認証」（だれか。トークンを読む）と「認可」（何をしてよいか。役割の確かめ）を分ける。抜けたのは認可
  - 足りない：監査ログも抜けている。抜けたのは「役割を確かめる → 書く → 同じトランザクションで監査ログ」の手順のまとまり

#### 問い2：3つの手順を、どこに1か所にするか

- 人の答え：UseCase に置いて、そこで役割を確かめる
- リーダーが返したこと
  - 合っている
  - 足すと、3つの手順を全部 UseCase に置く
  - 役割の決まりの中身は Domain（`AdminRole`）
  - トークンを読むのは Middleware の1か所

#### 問い3：どう入れるか（2つのテストのずれ）

- 人の答え：テストの中身（決まり）を、会員の側と同じにする
- リーダーが返したこと
  - 方向は合っている
  - 弱いところ：コピーは片方だけ直すとずれる（#231 で会員の側を3回直した）
  - 違えるのは、古いコントローラーの一覧と `App\Models` などの一覧だけ
  - 代わりの案
    - (a) 決まりの部分が同じかを比べるテスト
    - (b) 1つのファイルを両方から読む
    - (c) レビューだけ
  - 人が (a) を選んだ

#### 問い4：このテストがあると、なぜ「停止を解く」と同じ抜けが起きにくいか

- 人の答え：分からない（ヒントのあとも）
- リーダーが返したこと（答えを出した）
  - 新しい Controller が DB を直接使うとテストが落ちるので、書き込むには UseCase を通すしかなくなる
  - UseCase には3つの手順がある
  - ただし、UseCase の中の書き忘れは、このテストでは見られない（API テストで確かめる。#107）
  - 仕組みごとに確かめる範囲を決めて重ねる

### 決めたこと

- 直し方：管理画面の `tests/Arch/LayersTest.php` に、会員の側のテストをコピーする。違うのは、ファイルの上の3つの一覧だけ。印より下（決まり）が同じかを、`tests/Arch/SameRulesAsClientTest.php` が比べる（人が (a) を選んだ）
- 確かめ方：管理画面に違反を置いて、落ちるのを見る（とくに「停止を解く」と同じ形：新しい Controller が `DB::table()->update()` で直接書く）。片方のファイルだけ直すと、比べるテストが落ちるのを見る
- 設計（`03-how.md`）と違うこと：なし
- **リーダーの説明のまちがい（実装の前に見つけた）**：3の答えで「新しい Controller が DB を直接使うと、テストが落ちる」と説明したが、会員の側で入れたテスト（#231）は、Model と Repository だけを止めていて、`DB::table()->update()` で直接書く Controller も、トークンを読む Controller も通っていた。設計のルール（4-1：Controller は SQL を書かない・トークンを読むのは Middleware だけ）には書いてあったので、このチケットで、その2つを止めるテストを足した（会員の側と管理画面の両方。決まりの部分なので、2つのファイルで同じ）

## #236 設計の決まりを「Controller → Service → Model」に直す

土台のチケット（直す不具合はない）なので、「この決まりがないと、現場で何が困るか」を見せた（2026-11-18）。

### 課題（リーダーが見せたもの）

#### 起きていること

- Controller の中にロジックと DB の処理が全部ある
- 大きさ（2026-11-18 に数えた）
  - 会員の側は Controller 20個・1611行
  - 管理画面は14個・1319行
- いちばん長いメソッド
  - `UserController::index`（会員の検索）の142行
  - 管理画面の `MemberController::index` の117行
- DB を直接使う所
  - `LikeController` に21か所
  - 管理画面の `MemberActivityController` に28か所

#### 決まりはあったのに

- `architecture-backend.md`（865行。4層）は 11-15 からあった
- ただし、見本の実物がなく、新しい形のコードは1行もなかった

#### 現場ならどう見えるか

- 新しく入った人が「検索の年齢の条件はどこ？」と聞かれ、142行のメソッドを上から読む
- 1か所を直すと、別の所が壊れないか不安になる
- 検索が遅くなっても、SQL がどこで組み立てられているかを探すところから始まる

#### 原因のある所

- `backend/client/app/Http/Controllers/UserController.php` の `index`
- `LikeController.php` の `store`
- `backend/admin/app/Http/Controllers/MemberController.php` の `index`

#### 似た課題

- 画面の側も同じ形（`frontend/client/src/HomePage.tsx`）。エピック #112 で扱う

### 人の答え

#### 問い1：なぜ起きるか

- 人の答え：`api.php` から Controller への導線が分かりやすく、Controller に書けば、とりあえず動く機能が簡単に作れるから
- リーダーが返したこと
  - 合っている（Fat Controller が生まれるいちばんの理由）
  - 足りない：このリポジトリでは、レガシー版はわざと Fat Controller で作った（D-003）
  - 問題は「見本と、書いている時に止める仕組み（機械）がない」こと
  - 現場でも、文書の決まりは書く人がその場で読むとは限らない

#### 問い2：どう直すか

- 人の答え：ロジックは Service に、Model には DB との接続周りとクエリの処理を書く
- リーダーが返したこと
  - 前に決めた「DB の処理も Service」とずれていたので、人に選んでもらった
  - 人は「検索などのクエリの組み立ては Model」（B）を選んだ
  - 弱いところ：検索・一覧・集計が増えるたびに `User` が太る（Rails の Fat Model）
  - 代わりの案：条件はスコープで Model、組み合わせは Service

#### 問い3：どう確かめるか

- 人の答え：仕様で決めたことは機械が確かめ、人はディレクトリを見て判断する
- リーダーが返したこと
  - 合っている
  - 足りない：ディレクトリを見るだけでは、正しい場所に置いたファイルの中身（Controller に `if` の判断が残る）は分からない
  - 代わりの案：レビューで「Controller に判断が残っていないか」を見る（`design-reviewer` に足した）

### 決めたこと

- 形：Controller → Service → Model（D-025）。検索などのクエリの組み立ては Model（人が B を選んだ）
- 確かめ方：アーキテクチャのテストを新しい形で書き直し、違反を置いて落ちることを見る（会員の側と管理画面の両方。違反21種類と、通るはずの4つ。#239 のレビューのあとは、違反31種類と、通るはずの8つ）。中身（Controller の判断）はレビューで見る
- 設計（`03-how.md`）と違うこと：4層から変えた。`03-how.md` に見直したことを書き、前の決定は記録として残した

## #237 ホームのプロフィールの API を Service に移す

動きを変えずに移すチケット（直す不具合はない）なので、「移すと、決まりと今の動きがどこでぶつかるか」を見せた（2026-11-19）。手で動かす確かめは、Bruno（`bruno/client/profile/`）で行った。記録は、PR #240 のレビューのあとに書いた。

### 課題（リーダーが見せたもの）

#### 起きていること

- `ProfileController`（55行）に、JWT を読む・SQL 5本・書き換えが全部ある
- `update` はトークンを読まないので、だれが送ったかが分からない（Bruno で、トークンなしの書き換えが 200 になった）

#### 似た課題

- トークンを読むコードが、17の Controller に29か所コピーされている
- 壊れたトークンは、どこも 500

#### 現場ならどう見えるか

- 401 にする・鍵や期限の決まりを変える、のたびに29か所を直すことになり、直し漏れが起きる

#### ぶつかる所

- ① トークンを読む所（決まり：Middleware だけ）
- ② 応答の形（決まり：Resource で項目を選ぶ）
- ③ 書き換えの入力（決まり：`validated()`）
- ②③を決まりどおりにすると、今の動きを確かめるテストが落ちる

### 人の答え

#### 問い1：`update` で、だれが送ったかは、コードのどこで分かるか

- 人の答え：`update` の中では分からない
- リーダーが返したこと
  - 合っている
  - 分かるのは URL の番号（だれのものか）だけで、比べる材料が片方しかない

#### 問い2：`show` の JWT を読む行を `update` にもコピーして比べる案の、弱いところ

- 人の答え：全部の Controller にコピーが要り、直し漏れが起きる
- リーダーが返したこと
  - 合っている。今も29か所ある
  - 401 の処理を足すときも、29か所を直すことになる
  - だから Middleware の1か所で読む

#### 問い3：見る API（トークンなしでも通る）と書き換え（ログインが要る）の違いを、Middleware でどう扱うか

- 人の答え：ログインしないと見られない（要件）なら、トークンなしでも通す Middleware は意味がないのでは
- リーダーが返したこと
  - 要件から見れば合っている（FR-AUTH-020 なら、401 で止める Middleware で足りる）
  - ただ、このチケットは動きを変えないので、今の「トークンなしでも通る」を残す必要がある

#### 問い4：①②③をどうするか

- 人の答え：①は Middleware、②③は今のまま
- リーダーが返したこと：―

### 決めたこと

- ① トークンは、新しい Middleware（`IdentifyMember`）で読む。トークンがあれば読み、なくても通す。壊れたトークンの 500 は今のまま（分かっている不具合）
- ② 応答は、今と同じく全部の列を返す。Resource は作らない（返す項目を選ぶときに作る。`architecture-backend.md` に1行足した）
- ③ 書き換えの入力は `all()` のまま。`validated()` は、直すチケットで入れる
- PR #240 のレビューで決めたこと
  - Service のメソッドの名前は「何ができるか」にする（`showProfile`・`updateProfile`）。「だれが呼べるか」は名前に入れない（`architecture-backend.md` の3章に足した）
  - 移す前と違う動き（3つ）は、コードを変えずに PR に書く
  - 消した `SentLikesListTest.php`・`SupportFunctionsTest.php` は、消したままにする。その API を移すチケットで、今の動きを確かめるテストを書く
  - トークルームとマッチングのまわりの改善は、その機能を直すときに一緒に行う

## #241 エラーハンドリングと例外処理の土台

不具合の8枚（#128〜#158）を調べると、どれも「共通の確かめを、ある API で書き忘れた」形だった。共通の仕組みを先に作る5つ（エラー → ログインの Middleware → 管理画面の役割 → 返す・受け取る項目 → 持ち主の確かめ）のうち、最初のもの（2026-11-19）。

### 課題（リーダーが見せたもの）

#### 起きていること

- エラーの応答を、Controller ごとに手で書いている（会員の側：401 が30か所・403 が9か所・404 が7か所）
- 業務の例外のクラスがない
- `bootstrap/app.php` は「`api/*` なら JSON」だけ

#### 現場ならどう見えるか

- 古いブックマークから、いない会員を開くと、応答に Model の名前（`App\Models\User`）が出る
- 書き換えは 500 になり、運営のログで、不具合か古い URL かを見分けられない
- 「ログインしてください」の文を変えるには、30か所を直す

#### やること・やらないこと

- やる
  - 業務の例外の親と最初の例外
  - `bootstrap/app.php` の1か所
  - ログに出さない
  - API テスト
- やらない
  - 今の30か所の書き換え（API を移すときに）
  - ログインの Middleware（次の作業）

### 人の答え

#### 問い1：Service が `abort(404)` ではなく、例外のクラスを投げるのはなぜか

- 人の答え：HTTP を知らないので、500・403・401 のエラーハンドリングしかできないから
- リーダーが返したこと
  - 一部合っている
  - Service は、どの状態コードも知らない
  - `abort(404)` をコマンドから呼ぶと、返す相手がいない
  - 例外は「会員がいない」という業務で起きたことを伝え、何に変えるかは呼んだ側が決める

#### 問い2：最初に作る例外はどれか

- 人の答え：500 から例外にする。403・401 は、認証の情報がないときと、本人かどうか
- リーダーが返したこと
  - ずれていた
  - 500 は業務の例外にしない（思っていなかった失敗は握りつぶさない）
  - 401 は Middleware の受け持ち
  - 本人でないときは、403 ではなく 404 にする（403 だと、会員がいるかどうかが分かってしまう）

#### 問い3：（もう一度）Service が投げるのはどれか

- 人の答え：403
- リーダーが返したこと
  - 一部合っている
  - Service が投げるのは 403・409（業務の決まり）と 404（見つからない）
  - 今いちばん要るのは 404（`ProfileService` の `firstOrFail()` と `RuntimeException`）

#### 問い4：どう確かめるか

- 人の答え：解説を頼んだ
- リーダーが返したこと
  - #237 で残した分かっている不具合の2本を、要件どおりに変えて落ちる（Red）のを見てから直す
  - `bootstrap/app.php` の行を消すと落ちることも見る

### 決めたこと

- 最初の例外は「会員が見つからない」の1つだけ。403・409 の例外は、業務の決まりを移すときに足す（9章：過剰設計の禁止）
- 管理画面には、まだ作らない（Service がなく、投げる所がない）
- 会員の側のコードでは、会員を `User` と呼ぶ（案A。`MemberNotFoundException` → `UserNotFoundException` など）
- エラーの文は `lang/ja/errors.php` にだけ書く（案B）。言語は `config/app.php` で `ja` に決める（(a)。環境変数で変えない）
- try-catch は、基本は書かない。意味のある別の動きができるときだけ書く（`architecture-backend.md` の7章に足した）
- テストでは、エラーの文を文字で書く（`testing-style.md` に足した）
- PR #242 のレビューで決めたこと：いくつものまとまりで使う例外は `app/Exceptions/` の直下に置く。業務の例外の `render` と文の書き忘れは、テスト（`BusinessExceptionsTest.php`）で見つける。FR-004 を「見る・書き換える」に広げる

## #244 の5 確認用の文字が応答に出る（元の #133）

不具合の8件（#244）のうち、ほかの土台を待たずに直せる1件（2026-11-20）。土台4（返す・受け取る項目）のうち、`#[Hidden]` に1語足すところだけをする。

### 課題（リーダーが見せたもの）

#### 起きていること

- 開発用の DB で再現した
- 他人のメールアドレスで `POST /api/users` を送ると、`201` の応答に `verification_token`（40文字）が入る
- その文字で `GET /api/email-verifications/{文字}` を開くと `200` になり、メールを開かずに確認済みになる
- `GET /api/me` の応答にも入る
- 相手のプロフィール（`GET /api/users/{user_id}`）でも、ログインしていない人に、他人の文字が出る
  - `tests/Feature/Profile/ShowTest.php` が、分かっている不具合として確かめていた
- 開発用の DB で、確認用の文字を持つ会員は 11人（全部で 20030人）

#### 現場ならどう見えるか

- メールアドレスを勝手に使われた人が困る。登録した覚えのないサービスに「確認済み」の会員ができる
- 運営は、確認済みの数を本人確認の数として使えない
- エラーにもログにもならず、「登録した覚えがない」という問い合わせで初めて分かる

#### 原因のある所

- `app/Models/User.php:16` の `#[Hidden]` が `password`・`remember_token` だけ
- 次の3か所が Model をそのまま返す
  - `UserController.php:44`
  - `AuthController.php:72`
  - `ProfileController.php:26`

#### 似た課題

- 管理画面の会員の一覧（#244 の4）
- `DB::table('users')` で読むので、Model を通らず、この直しでは直らない

### 人の答え

#### 問い1：なぜ、`password` は出ないのに、`verification_token` は出るか

- 人の答え：`#[Hidden]` に入っていないから
- リーダーが返したこと
  - 合っている
  - もう一段：Model を JSON にすると、`#[Hidden]` に書いた列以外は全部出る（隠すものを書く作り）
  - 新しい秘密の列を足したとき、書き忘れると黙って出る

#### 問い2：どう直すか

- 人の答え：`#[Hidden]` に足す
- リーダーが返したこと
  - 合っている
  - `#[Hidden]` は JSON にするときだけ効く
  - なので、確認の API の `where()` と、確認のメールの `$user->verification_token` は変わらない

#### 問い3：どう確かめるか

- 人の答え：テストを先に変えて Red
- リーダーが返したこと
  - 合っている
  - 足りないところ：登録と自分の情報には API テストがない
  - 変えるテスト1本と、足すテスト2本で Red を見る
  - 直したあと、足した1語を消して落ちるのも見る

#### 弱いところと代わりの案

- 弱いところ：隠すものを書く作りのままなので、次の秘密の列でまた書き忘れうる
- 代わりの案：API ごとに返す項目を書く（Resource）
- 応答の形が変わり、画面も確かめ直しになるので、土台4のチケットでやる

### 決めたこと

- 今回は案A（`#[Hidden]` に足す）。返す項目を書く案B（Resource）は、土台4のチケットでやる
- テストの置き場：登録は `tests/Feature/Auth/RegisterTest.php`、自分の情報は `tests/Feature/Profile/ShowAccountTest.php`
- 「自分」の名前

- `backend/client/app/Http/Controllers/AuthController.php:55`：30日の JWT を作り、JSON で返す
- `backend/client/app/Http/Controllers/AuthController.php:69`：ログアウトで、何もしない
- `frontend/client/src/shared/session/session.ts:10`：トークンを、JavaScript から読める所に置く

#### 似た課題

- 管理画面も JWT。範囲の外（#246 の「入れない」）

### 人の答え

#### 問い1：セッションにすると、なぜログアウトのあとが 401 になるか

- 人の答え：JWT はサーバーに行がないから消せない。セッションなら行を消せる
- 合っている：そのとおり
- 足りない：消したあとも、ブラウザは同じ Cookie（セッションの番号）を送ってくる。サーバーは表 `sessions` でその番号を探し、見つからないので「ログインしていない」として 401 を返す

#### 問い2：トークンを JavaScript から読めない所に置くと、どう伝えるか。新しく要る守りは何か

- 人の答え：セッションを見て判断する
- 合っている：サーバーがセッションを見て、だれかを決める
- 足りない
  - ブラウザが HttpOnly の Cookie を自動で付ける。画面に要るのは `credentials: 'include'` だけ
  - Cookie は自動で付くので、よそのサイトの画面から書き込みを送らせられる（CSRF）。Sanctum の CSRF のトークン（`/sanctum/csrf-cookie` と `X-XSRF-TOKEN`）で守り、ないものは `419`（FR-AUTH-018）

#### 問い3：どう確かめるか

- 人の答え：セッションがあるかどうかで確かめる
- 合っている：セッションで確かめる
- 足りない（リーダーの案）
  - ログイン → ログアウト → 同じ Cookie で `GET /api/me` が 401（FR-AUTH-016）
  - `X-XSRF-TOKEN` なしの書き込みが 419（FR-AUTH-018）。Laravel のテストはふだん CSRF の確かめを飛ばすので、飛ばさない形のテストか curl で確かめる
  - ログインの応答の JSON に `token` がない。Cookie に `HttpOnly` が付いている

#### 人からの問い：JWT を HttpOnly の Cookie に入れればよいのでは

- リーダーの返し：XSS で持ち出される問題は解けるが、「ログアウト・停止・パスワードの変更のあとも使える」は残る。止めるには、使えなくしたトークンの一覧を DB に持つ（セッションと同じ重さになる）か、期限を短くして取り替え用のトークンを足す（D-014 で考え、D-027 で今は考えないと決めた）ことになる
- 人の答え：JWT を HttpOnly にし、CSRF のトークンを入れれば、CSRF は防げる → 合っている。違いは CSRF ではなく「止められるか」に出る

#### 人からの問い：セッションと JWT は、サービスによって使い分けがあるのでは

- リーダーが出した、選ぶときの4つの問い：だれが API を呼ぶか・すぐに止める必要があるか・だれが本物かを確かめるか・状態をどこに置くか
- 人の答え
  - このサービスで効くのは「自分のサイトのブラウザだけ」と「アカウントを停止するので、すぐに止める必要がある」
  - 設計のトピックの地図では 1-4 だと考えた
- リーダーの返し
  - いちばん効くのは「すぐに止める」。「自分のサイトだけ」はセッションを選べる条件、「すぐに止める」は JWT では足りない理由
  - 方式を選ぶ話は 1-1。1-4 は、選んだあとの守り方（Cookie にしたので CSRF を守る）の話

### 決めたこと（人が決めた。2026-11-21）

- D-027（Sanctum のセッション）のまま進める。理由：通報や運営の対応でアカウントを停止したとき、次のリクエストから止める必要があるため
- 直し方と確かめ方は、#259 の本文と `03-how.md` の「認証をセッションに移す」のとおり
- あとで方式を変えるとき（人からの問い：セッションから JWT に移すのは簡単か）
  - 直す所を少なく保つため、#259 でも次の形を崩さない：認証を読むのは Middleware（`AuthenticateUser`）だけ・Service は会員の番号だけを受け取る・画面は `client.ts` の1か所
  - 難しいのはコードの外：止める仕組みの作り直し（一覧か取り替え用のトークン）・ログインしている人の移し方（#258 のメンテナンスで全員にログインし直してもらう）・守り方（Cookie なら CSRF、ヘッダーなら XSS）
  - 先の形は「セッションに Sanctum の API トークンを足す」が多い（スマホのアプリを作るとき。#246 の「入れない」）

### 2つ目の PR：パスワードの変更・再設定・退会でセッションを消す（2026-11-21）

#### 起きていること（コードを読んだ。測っていない）

- パスワードの変更（`PUT /api/me/password`）・再設定（`PUT /api/password-resets/{token}`）・退会（`DELETE /api/me`）は、パスワードやメールアドレスを書き換えるだけで、表 `sessions` を触らない
- 3つとも、レガシー版の Controller（`app/Http/Controllers/` の直下）。今の動きを確かめるテストもない

#### 現場ならどう見えるか

- 「スマホを落とした」会員がパソコンでパスワードを変えても、拾った人のスマホはログインしたまま使える（操作が続けば24時間ごとに延びる）
- 退会は、次のリクエストで `AuthenticateUser` が 401 にする。ただし行は残る

#### 原因のある所

- `app/Http/Controllers/PasswordController.php`・`PasswordResetController.php` の `update`・`UserController.php` の `destroy`
- `AuthenticateUser` は「行に会員の番号があるか」と「使える会員か」だけを見る。パスワードを変えたかは見ない

#### 人の答え

- 問い1（なぜほかの端末が使えるか）：`sessions` にデータがあるので、認証情報を持ったまま使える → 合っている。足りないのは、ログインの確かめがパスワードの変化を見ていないこと
- 問い2（どう直すか）：Service か Controller に置く → まだ決まっていない。行を消すのは DB の操作（Service の側）、`logoutOtherDevices()` はガード（Controller の側）。古い Controller に機能を足さない決まりとの関係も要る
- 問い3（どう確かめるか）：2回とも、状態コードまで言えなかった。リーダーが答えを出した（下の「確かめ方」）

#### 決めたこと（人が決めた）

- 置き場は A：3つの API を新しい形（Controller → Service）に移してから、消す処理を足す。移す前に、3つの今の動きを確かめるテストを足す。移すコミットと、消す処理を足すコミットを分ける
  - ほかの案：B（古い Controller に消す行だけ足す。決まりを破る）・C（出来事と Listener。Controller を読んでも消すことが見えない）
- 変えた端末を残す方法はイ：今の端末の番号を除いて、その会員の行を消す（`delete from sessions where user_id = ? and id <> ?`）
  - 設計（`03-how.md`）で決めていたア（`logoutOtherDevices()` と `AuthenticateSession`）から変えた。行が残らず、テストで行が消えたことを確かめられるため
  - 弱いところ：管理画面など、ほかの所でパスワードを変えたときは効かない。今の端末の番号は作り直さない（PR で扱いを書く）
  - 2026-11-22 の Q1（`explanations/auth-edge-cases.html` の10章）で、変えた端末の番号は作り直すと決め直した（`03-how.md` の「#259 の2つ目で決めたこと」）

#### 確かめ方

- 端末 A・B を `DummyAuth::loginFromScreen()` で作り、操作のあとに `GET /api/me` を呼ぶ
  - A でパスワードを変える：A は 200・B は 401。B の行がなく、A の行はある
  - 再設定のリンクで変える：A も B も 401。その会員の行が0
  - A で退会する：A も B も 401。その会員の行が0
- 比べる相手：ほかの会員のセッションは残る
- 消す行を外して、テストが落ちることを見る

## #269 アカウント停止された会員を、ほかの会員から見えなくする
