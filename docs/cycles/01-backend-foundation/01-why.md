## 届いた声

- 人（新しく入ったエンジニアとして）：「当時は技術力がなく、設計・性能・ログ管理がなかった。まずこのプロジェクトを改善するところから入りたい」
- 数字（2026-11-15 に数えた）
  - 会員の側の API は24本、管理画面の API は14本。テストは health の1件だけ
  - JWT を読む処理のコピーが、会員の側に16か所・管理画面に14か所
  - `backend/client/app` の PHP は26ファイル。業務の処理はほぼコントローラーの中にある

## 困りごと（1文）

エンジニアが、どこにどんなファイルがあり、どんな処理をしているかを掴めず、変えたときに何が壊れるかを確かめる手段（テスト）もないので、開発が遅く、不具合を出しやすい。

## 今どれくらい起きているか

- API のテストで守られている振る舞い：24本中 0本（health を除く）
- 置き場の決まり（`agents/rules/architecture.md`）はあるが、今のコードはレガシー版の形（Fat Controller）のまま

## 作らないとどうなるか

- 次の機能を足すたびに、コントローラーのコピーが増える（JWT の読み方のように）
- 直したときに、別の API を壊しても気づけない
- 会員や運営に見える影響は、今はまだない。ただし次のサイクルから、機能を出す速さと不具合の数に効いてくる

## 決めたこと

- サイクル 01 のテーマは「バックエンドの土台の改善（開発者体験）」。会員向けの機能は足さない
- 設計書を読むのは、エンジニアリーダーとメンバーのエンジニア
- 開発者体験がよくなったと言える状態：開発が速い・不具合が起きない・どこにどんなファイルがあり、どんな処理をしているかをエンジニアが分かる
- 最初はバックエンド。ディレクトリの設計（どんな処理・ファイルをどこに置くか）を整理する
- 一気に移さない。段階的に、触る機能に関係するところだけを新しい形にする
- このサイクルでは、中身のコードは変えない
- テストはバックエンドの API テストから。テストのゴール・パターン・何が成功で何が失敗かを、理解しながら進める
- このサイクルのねらいは、これから改善していくときに不具合とデグレ（前に動いていたものが壊れること）を出さないこと
- まずテストの土台を整える。一気に全部の API のテストは書かない（何をしているか・動いているかを確かめられなくなるため）。API ごとのテストは、必要に応じて分けるか、その API を触る機能や改善のチケットで一緒に足す
- 前提：今は不具合の報告は出ていない。今の振る舞いを正しいものとして、そこから改善する
- 範囲は会員の側（`backend/client`・API 24本）と管理画面（`backend/admin`・API 14本）の両方
- #51〜#55（04 の検索の改善）は、いったんボードに移したが、02-what の話し合いで要らないと決め、予定なしで閉じた
