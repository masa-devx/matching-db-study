# 何を作るか

日付：2026-11-15
出た役：PM・リーダー・人

## 範囲

- 入れる
  - バックエンドの棚卸し（会員の側 API 24本・管理画面 API 14本）
  - バックエンドの設計書の第1版（目標のディレクトリと、どこにどんな処理を置くか）
  - API テストの土台（会員の側と管理画面。テストデータの作り方・ログインした状態の作り方・書き方の決まり・CI）
  - 見本の API テストを1〜2本
  - 「既存の API を触るチケットは、先にその API の振る舞いを固めるテストを足す」の決まり
- 入れない
  - 中身のコードを変えること（ファイルを移すことも含む）
  - 全部の API のテスト（その API を触るチケットで足す）
  - 単体テスト・同時実行・負荷・ミューテーションのテスト（業務の処理を切り出したあと、または出来事のときに）
  - フロントエンドの設計書（次のサイクル以降）

## 受け入れの条件

- [ ] 38本の API それぞれについて、コントローラーのメソッド・読む表・書く表・主な処理が `docs/onboarding/feature-map.md` にある
- [ ] バックエンドの設計書に、目標のディレクトリと、各ディレクトリに置く処理・置かない処理が書いてある。今のファイルが目標のどこに移るかの地図がある
- [ ] 会員の側で、用意した部品（テストデータの作り方・ログインした状態の作り方）だけを使って、API テストを1本書ける
- [ ] 管理画面でも同じことができ、テストが CI で回る
- [ ] 見本の API テストが、成功の場合と失敗の場合を両方確かめている
- [ ] 「触る API には先にテストを足す」が、`docs/process.md` の Ready の条件と PR のひな形にある

## 成功の指標

| 指標 | 今 | 目標 | 測り方 |
| --- | --- | --- | --- |
| テストを足しやすい | 部品がない | 用意した部品だけで1本書ける。かかった時間を記録する | 見本のテストを書くときに測る |
| どこに何があるか分かる | 測っていない | 地図の問い10問のうち8問 | 棚卸しのあとに、リーダーが問いを出す（`tech-lead` の理解度チェック） |
| デグレに気づける | 会員の側だけ CI で回る | 会員の側と管理画面の両方で回る | CI の結果 |
| （記録だけ）守っている API | 38本中 0本 | 目標なし | 数える |

## 既知のリスクの扱い

- 測って分かっている危ないところ（停止した会員のトークンが使える・期限が切れても有料のまま、など。各一歩の解説の 9-2）は、不具合として直さない
- テストでは今の振る舞いをそのまま固め、テストの中に「既知のリスク」とコメントを残す
- 危ないところは「改善」のチケットとして Inbox に入れ、次のサイクルの仕分けで優先度を決める

## 優先度と、このサイクルのチケット

| 順 | 種類 | チケット |
| --- | --- | --- |
| 1 | 調査 | バックエンドの棚卸し：API → コントローラー → 表 → 処理の地図 |
| 2 | 雑務 | バックエンドの設計書の第1版：目標のディレクトリと置く処理・移行の地図 |
| 3 | ツールの導入 | 会員の側の API テストの土台 |
| 4 | ツールの導入 | 管理画面の API テストの土台と CI |
| 5 | 改善 | 見本の API テストを1〜2本 |
| 6 | 雑務 | 「触る API には先にテストを足す」を Ready の条件と PR のひな形に |

Size・順番の入れ替え・チケットの分け方は、リーダーが「どう作るか」で決める。
