# 何を作るか

日付：2026-11-15
出た役：PM・リーダー・人

## 範囲

- 入れる
  - バックエンドの棚卸し（会員の側 API 24本・管理画面 API 14本）
  - バックエンドの設計書の第1版（目標のディレクトリと、どこにどんな処理を置くか）
  - API テストの土台（会員の側と管理画面。テストデータの作り方・ログインした状態の作り方・書き方の決まり・CI）
  - 見本の API テストを1〜2本
  - 「既存の API を触るチケットは、先にその API の今の動きを確かめるテストを足す」の決まり
  - アーキテクチャのテスト（Pest の `arch()`。会員の側と管理画面。`03-how.md` で範囲に入れると決めた）
  - OpenAPI の土台（#125）と契約テストの土台（#126）。2026-11-16 の提案 #124 で足した（下の「追加の決定」）
  - 改訂版のルートの骨組み（#127）。新しい URL のルートと、501 を返すだけのコントローラーを作る。`bootstrap/app.php`・CORS の設定も変える（「中身のコードを変えない」の例外。今のコントローラーの中身には触らない）
- 入れない
  - 中身のコードを変えること（ファイルを移すことも含む）
  - 全部の API のテスト（その API を触るチケットで足す）
  - 単体テスト・同時実行・負荷・ミューテーションのテスト（業務の処理を切り出したあと、または出来事のときに）
  - フロントエンドの設計書（次のサイクル以降）
  - `oasdiff`（破壊的な変更の検出。このサイクルの最後か 02）・Schemathesis（ファジング。02 以降）・`openapi-typescript`（使わない）
  - 新しい URL への契約テスト（その API を移すチケットで足す。今の URL には契約テストをかけない）

## 受け入れの条件

- [ ] 38本の API それぞれについて、コントローラーのメソッド・読む表・書く表・主な処理が `docs/onboarding/feature-map.md` にある
- [ ] バックエンドの設計書に、目標のディレクトリと、各ディレクトリに置く処理・置かない処理が書いてある。今のファイルが目標のどこに移るかの地図がある
- [ ] 会員の側で、用意した部品（テストデータの作り方・ログインした状態の作り方）だけを使って、API テストを1本書ける
- [ ] 管理画面でも同じことができ、テストが CI で回る
- [ ] 見本の API テストが、成功の場合と失敗の場合を両方確かめている
- [ ] 「触る API には先にテストを足す」が、`docs/process.md` の Ready の条件と PR のひな形にある
- [ ] Domain にわざと `Illuminate` のクラスを use するか `now()` を書くと、アーキテクチャのテストが落ちる（会員の側と管理画面の両方。CI で流れる）
- [ ] OpenAPI 3.1 の仕様書（会員の側と管理画面）の lint が CI で回り、わざと `security` のない操作を書くと落ちる（#125）
- [ ] `GET /api/health`（両方）が契約テストで確かめられ、仕様書にない項目を返すと落ちる（#126）
- [ ] #107 の2本の API の、目標の仕様書がある

## 分かっている不具合の扱い

（決めたとき（2026-11-15）の言い方は「既知のリスク」。2026-11-17 に、`agents/rules/writing.md` の言い方に直した。決めた中身は変えていない）

- 測って分かっている危ないところ（停止した会員のトークンが使える・期限が切れても有料のまま、など。各一歩の解説の 9-2）は、不具合として直さない
- テストでは今の振る舞いをそのまま確かめ、テストの中に「分かっている不具合：…」とコメントを残す
- 危ないところは「改善」のチケットとして Inbox に入れ、次のサイクルの仕分けで優先度を決める
