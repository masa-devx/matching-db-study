# 設計の判断の地図

このプロジェクトで決めたこと・直したことを、大きなトピックと小さな見出しに分けた地図。「なぜそうしたか」を、2段・3段と聞かれても、自分の言葉で説明できるようにするために使う（2026-11-20 に人が決めた）。

- 実装がトピックに当たったら、`code-walkthrough` の説明の練習のあとに、そのトピックの問いに答える（`agents/skills/code-walkthrough/SKILL.md` の 3-2）
- 問いへの答えと、練習の記録は、人の手元の非公開のメモに置く（置き場は `agents/notes.local.md` に書く。git に入らない）。この地図には、トピックと、記録のある場所だけを書く
- 決めたことの理由の正本は、それぞれの記録（`docs/decisions.md`・`docs/cycles/`・解説の HTML）。この地図は、その入口

### トピックが増える流れ

現場と同じく、PM の役がビジネスの困りごと・不具合・次の機能の提案を出し、リーダーの役が機能とアーキテクチャを見直す。そのたびに、話したことを地図に結ぶ（2026-11-21 に人が決めた）。

1. PM の役・リーダーの役・レビューが、困りごとや改善の案を出す
2. 人が先に「地図のどのトピックに当たるか」を答える。役は、そのあとで合っているかを返す（答えを先に言わない）
3. どの見出しにも当たらなければ、人が新しい小さな見出しの名前を考え、この表に足す
4. すぐにはやらないものは、下の「改善の候補」に置く。やると決めたら、チケットにして候補から消し、表の「主な記録」にチケットの番号を書く
5. やり終えたら、`code-walkthrough` の 3-2 で、そのトピックの問いに答える

## 説明するときの流れ

1. 困りごと：だれの・どんな場面で・どのくらい（数字）
2. 原因：なぜ起きていたか
3. 案：2つ以上。何で比べたか
4. 選んだ案と、決め手
5. 弱い点と、その手当て
6. 結果：前と後の数字・何が変わったか
7. 今ならどうするか

続けて聞かれる「なぜ？」の種類：

| 種類 | 例 |
| --- | --- |
| 基本 | なぜそれを選んだのか |
| 別の案 | 〇〇にしていたら、何が違ったか |
| 規模 | 会員が10倍・100倍になったら、どうなるか |
| 失敗 | 困ったこと・あとから気づいたことは。どう気づいたか |
| サービス | 利用者や運営にとって、何が良くなったか |

気をつけること：

- 「そう決まっていたので」「AI がそう言ったので」で終わらせない
- このプロジェクトは学習用。前の現場で見た問題を、実務のコードを持ち込まずに再現し、測って直したことを話す。仕事でしたことと、学習で確かめたことを分ける
- 仮説で終わらせない。測った数字・壊して確かめたテストで話す

## 改善の候補（まだやっていない）

PM の役・リーダーの役・レビューで出た「直したい・試したい」を、トピックに結んで置く。1つの候補を1つの見出しにする。中は、困りごと・つながるトピック・どこで起きるか（画面・API・DB）・測り方・出どころ。

### 画面が、同じ API を何度も呼ぶ

- 困りごと
  - 画面を開くたびに、同じデータを取り直す
  - ホームは、`GET /api/me` の応答を待ってから、`GET /api/users/{user_id}` を呼ぶ（行き来を2回待つ）
  - トークの画面は、5秒ごとに新しいメッセージを取りに行く（FR-MSG-015）
- つながるトピック：5-6・7-3・7-5
- どこで：画面と API の両方
- 測り方：1つの画面を開いたときの、API の本数と待ち時間（ブラウザの開発ツールの Network）
- 出どころ：リーダー（#257 の課題の理解）

### キャッシュを使うか（どの置き場で）

- 困りごと：変わらないデータを、毎回 DB から読む
- キャッシュの置き場は4つある
  - 画面：取ったデータを、画面をまたいで使い回す（7-6）
  - HTTP：`Cache-Control`・`ETag` で、ブラウザに「まだ新しい」と伝える（5-7）
  - サーバー：計算した結果を Redis などに置く（3-5）
  - DB：PostgreSQL が、読んだページを覚えている（何もしなくても効く）
- 候補になる API：プランの一覧（`GET /api/plans`。ほとんど変わらない）
- 弱い点：古いデータを見せる。アカウント停止された会員・有料の期限のように、すぐ変わってほしいものには使いにくい。いつ消すかを決める必要がある
- つながるトピック：3-5・5-7・7-6
- どこで：画面・API・DB のどれでもありうる。置き場ごとに、効く所と弱い点が違う
- 測り方：同じ API を何度も呼んだときの、時間と SQL の本数（前と後）
- 出どころ：人（2026-11-21）

### アカウント停止された会員が、ほかの会員から見えたまま

- 困りごと
  - 検索・いいね・マッチ・トークの一覧は、退会した会員だけを除いている
  - アカウント停止・強制退会の会員は出たままなので、返事の来ない相手に、いいねやメッセージを送り続ける
- 決めたこと：退会した会員と同じく、見えなくする（人が決めた。2026-11-21）
- 弱い点：アカウント停止を解いたときに、一覧へ急に戻る。トークの相手が消えたように見える
- つながるトピック：11（業務の決まりとデータの整合）・2-3（状態の持ち方）
- どこで：API と DB（除く条件を、どの API でもそろえる。Model のスコープの `active()` など）
- 測り方：アカウント停止された会員が、検索・一覧に出ないことを API テストで確かめる
- 出どころ：人（PR #268 のレビューの S7 の話し合い）

### 1回のリクエストで、同じ会員の行を2回読む

- 困りごと：ログインを確かめる Middleware が `users` の行を読んだあと、Controller がもう一度読む（9つの API）
- 今の重さ：主キーで1行を読むだけ（1本 0.03ms 足らず）。会員が10倍でも、ほとんど変わらない
- 直すなら：Middleware が読んだ会員を Controller に渡す・Service に移すときに読み方をやめる
- つながるトピック：3-2・6-2
- どこで：API
- 測り方：API ごとの SQL の本数（`db.summary` のログ）
- 出どころ：PR #268 のレビュー（DB と性能）

### ブロックの表を、全部読む SQL

- 困りごと：「自分をブロックした人」を探す SQL（`blocks where blocked_id = ?`）に索引がなく、表を全部読む
- 今の重さ：752ページ・0.93ms（開発用の DB）。表の行の数に比例して遅くなる
- 使う API：マッチの一覧・いいねの一覧・検索など、ブロックした相手を除く API
- つながるトピック：3-1
- どこで：DB
- 測り方：`EXPLAIN (ANALYZE, BUFFERS)` の読んだページの数（前と後）
- 出どころ：PR #268 のレビュー（DB と性能）
