# 決めたことと、その理由

なぜその設計・技術にしたかの一覧。結論（使う道具と版）は [AGENTS.md](../AGENTS.md) の「技術スタック」に、作業の決まりは [background.md](../agents/background.md) に書く。

- 1つの判断に、1つの見出し（`### D-xxx 名前`）を作る。中は「状態・決めたこと・ほかの案・理由・数字・リンク」の箇条書きにする
- 番号は `D-001` から順に振り、消さない。変えたら新しい見出しを足し、古い見出しの「状態」を「置き換え（D-xxx）」にする
- 足し方：下の「一覧」の表に1行（番号・名前・状態・一歩）を足し、「準備で決めたこと」か「一歩で決めたこと」に見出しを1つ足す。スキルや文書の「decisions.md に1行足す」は、この2つを足すことを指す
- 一歩で直したら、`explain-change` が「一歩で決めたこと」に足す。「数字・リンク」には、前と後の数字と、解説のページへのリンクを書く

## 準備で決めたこと

### D-001 バックエンドは Laravel と PostgreSQL

- 状態：有効
- 決めたこと：バックエンドは Laravel（API）＋PostgreSQL
- ほかの案：
  - Go＋sqlc（SQL を全部自分で書く）
  - Rails（`lock_version`・`strong_migrations` がある）
- 理由：
  - 使い慣れた ORM（Eloquent）で書き、裏で流れる SQL を見て直す経験を、測った事実として残す
  - 09（楽観ロック）・10（止めずに変えるマイグレーション）は、道具に頼らず自分で作るので、仕組みを説明できる
- 数字・リンク：―

### D-002 ORM は Eloquent。流れた SQL と直し方を残す

- 状態：有効
- 決めたこと：
  - ORM は Eloquent
  - 各一歩で「流れた SQL → 問題 → 直し方 → 前と後の数字」を残す
  - Rails（ActiveRecord）・Prisma ならどう書くかも並べる
- ほかの案：ORM を使わない（sqlc）
- 理由：ORM の便利さと罠（N+1・with と join）を、どの ORM でも説明できるようにする
- 数字・リンク：―

### D-003 最初は Fat Controller で作り、測って直す

- 状態：有効
- 決めたこと：
  - 最初は、Laravel を入れたときの形の MVC・Fat Controller（Laravel 5 系のころの書き方）で、テストも性能も考えずに作る
  - 一歩ごとに測って直す
  - Laravel 本体は最新
- ほかの案：
  - 初めから層を分ける（クリーンアーキテクチャなど）
  - Laravel 5 系をそのまま使う
- 理由：
  - 古いコードを引き継いで直す力を、前と後の数字つきで説明できるようにする
  - 5 系は保守が終わり、PHP 8.5 で動かない
- 数字・リンク：―

### D-016 レガシー版から PHP の型を書く

- 状態：有効
- 決めたこと：
  - レガシー版（`legacy-repo`）から、PHP の型を書く
    - `declare(strict_types=1)`
    - 引数と戻り値とプロパティの、言語の型
    - 配列やリレーションの中身は PHPDoc
    - Model の列の型は、Laravel IDE Helper でマイグレーションから作る
  - PHPStan（Larastan）のレベルは、`legacy-repo` が 6
  - `refactored-repo` は、直す一歩ごとにレベルを上げ、最後は 9
- ほかの案：レガシー版は型を書かず、改善する段階で足す（Laravel 5 系のころの形に近い）
- 理由：
  - 関数の型と PHPDoc で管理する書き方に、早くから慣れる
  - レガシー版でもレベル 8（NULL の扱い）は見ない。そのため、「`null` に書こうとして `500`」のようなレガシー版の問題は、残して測れる
- 数字・リンク：[quality-types.md](../agents/rules/quality-types.md)

### D-017 CI は GitHub Actions

- 状態：有効
- 決めたこと：
  - CI は GitHub Actions
  - PR と push で、次の3つを別々のジョブで動かす
    - 整形の確かめ（Pint）
    - 静的解析（PHPStan）
    - テスト（Pest。GitHub の上の PostgreSQL 18.6）
  - 設定は `legacy-repo` に置く
  - CI が通らない PR はマージしない
- ほかの案：
  - CI を使わず、手元だけで確かめる
  - Docker のイメージを CI でも作る
- 理由：
  - 手元で忘れても、毎回同じ確かめが動く
  - Docker のイメージを作り直すと遅いので、PHP は setup-php で用意する
  - `main` には `backend/client/` がないので、`legacy-repo` に置く
- 数字・リンク：[ci.md](ci.md)

### D-018 画面も 03b からレガシー版と改善版に分ける

- 状態：有効

  - 画面も、03b からレガシー版と改善版に分ける

  - 表示速度は、04 の一覧で測る（[frontend.md](frontend.md)）

- 数字・リンク：改善したあとに足す

### D-020 「直した版」を「改善版」と呼ぶ

- 状態：有効
- 決めたこと：
  - レガシー版の対になる形を「直した版」から「改善版」に変える。作ることは「改善する」と呼ぶ
  - 改善の中では、次の2つを分けて書く
    - **リファクタリング**：振る舞いを変えずに中を直す（Fat Controller を分ける・container／presenter に分ける）。今の動きを確かめるテストは通ったまま
    - **修正**：振る舞いを変える（入力の確かめ・認可・トランザクション・インデックス）。問題をそのまま確かめていたテストを、要件どおりの期待に書き換える
  - ブランチ・マイルストーン・ラベルの名前（`refactor`）は変えない
- ほかの案：
  - 直した版
  - リファクタ版
  - モダン版
- 理由：
  - 『レガシーコード改善ガイド』の進め方とそろう。この本では、テストのないコードをレガシーコードと呼び、今の動きを確かめるテストを足してから変える
  - リファクタ版だと、振る舞いを変える修正が含まれることと合わない
  - モダン版だと、技術を入れ替える意味に取られる
- 数字・リンク：―

### D-012 性別と都道府県はマスタの表と外部キー

- 状態：有効
- 一歩：01
- 決めたこと：
  - 性別と都道府県は、マスタの表（`genders`・`prefectures`）と外部キーで持つ
  - 性別の値は、男性・女性・その他・回答しない

### D-013 身長の範囲はバックエンドで確かめる

- 状態：有効
- 一歩：01
- 決めたこと：
  - 身長は、DB では型（`smallint`）だけを守る
  - 範囲（120〜220）は、バックエンドのバリデーションで守る
- ほかの案：DB の CHECK でも範囲を守る

### D-014 認証は JWT と取り替え用のトークン

- 状態：置き換え（D-027）
- 一歩：01b・03b
- 決めたこと：
  - 認証は JWT
  - レガシー版：
    - ログインの応答（JSON）で、有効期限の長い JWT を返し、止める仕組みを持たない
    - 03b の画面は sessionStorage に置く
  - 改善版：
    - JWT（15分）と取り替え用のトークン（30日）を、どちらも HttpOnly の Cookie に置く
    - 取り替え用のトークンは、DB にハッシュで保存し、取り替えのたびに作り直す。使い回しを見つけたら、家族ごと止める
    - Cookie は `HttpOnly`・`SameSite=Lax`、本番だけ `Secure`
  - BFF は作らず、画面から API を直接呼ぶ
  - リリースするときは、画面と API を同じサイトに置く
- ほかの案：
  - Sanctum の SPA 認証（セッション）
  - Sanctum の API トークン
  - BFF（画面専用のサーバーがトークンを預かる）
  - トークンを localStorage に置く
- 理由：
  - JWT の形（だれでも読める中身・止められない期限・取り替え用のトークン）を、レガシー版の失敗から学ぶ
  - HttpOnly の Cookie にすると、XSS があってもトークンを持ち出されにくい
  - 取り替え用のトークンの表で、DB の設計（ハッシュ・期限・家族）も学べる
  - 画面と API が別のサイトだと、ブラウザがよそのサイトの Cookie を止める。そのため、同じサイトに置くことを条件にする
- 数字・リンク：改善したあとに足す（[認証とトークンの絵本](https://claude.ai/artifact/EW5HWFdTJgLd3JYewyP4bE)）
- 置き換えたもの：D-007
- 置き換えられた：D-027

### D-015 `users` と `profiles` に分ける

- 状態：有効
- 一歩：01
- 決めたこと：
  - レガシー版も改善版も、次の2つの表に分け、`profiles.user_id` で `users` につなぐ
    - `users`：アカウント（メールアドレス・パスワード・確認）
    - `profiles`：その会員についての情報（性別・生年月日・ニックネーム・都道府県・身長・自己紹介・画像）
  - ひな形の `users.name` は、`profiles.nickname` に移して消す
  - レガシー版の `profiles` は、自分の `id` と、外部キーも UNIQUE もない `user_id`、文字の列で、制約なし
  - 改善版は、`user_id` を主キー兼外部キーにし、性別（`gender_code`）と生年月日（`birthdate`）も `profiles` に置く
- ほかの案：
  - レガシー版は `users` 1つにまとめる（初めの形）
  - 改善版で、性別と生年月日を `users` に置く
- 理由：
  - アカウントと、その人についての情報は、使う処理・更新の多さ・守り方が違う
  - 04 の検索の条件（性別・生年月日・都道府県・身長）が `profiles` にそろうので、複合インデックスを1つ作れる（表をまたぐ複合インデックスは作れない）
  - レガシー版も分けておくと、「分けたのに守りがない」問題（1人にプロフィールが2つ・ない会員を指すプロフィール）を測れる
- 数字・リンク：改善したあとに足す（[01](../explanations/01-members.html)）

### D-021 JWT を作る道具は `firebase/php-jwt`

- 状態：有効
- 一歩：01b
- 決めたこと：
  - JWT を作る道具は `firebase/php-jwt`（v7.2.1）
  - レガシー版は、コントローラの中で `encode`・`decode` を書き、鍵は `APP_KEY` を使い回す

### D-022 URL で指す ID は `public_id`（UUID）

- 状態：有効
- 一歩：04
- 決めたこと：
  - URL で1つのものを指す ID（ユーザー詳細の会員・05 のトークルームなど）は、その表に足す `public_id` にする
    - `uuid`・`NOT NULL`・`UNIQUE`・既定は DB の `uuidv7()`
  - 一覧の応答で相手を指す `user_id` も、詳細へのリンクに使うので `public_id` にする
  - 中の主キー `id`（`bigint`）・表どうしのつながり（外部キー）・JWT の `sub` は、中の `id` のまま
  - あわせて、相手の詳細の API を `/api/users/{id}/profile` から `/api/users/{public_id}` に変える
    - `users` と `profiles` に分けたのは DB の都合で、画面から見ると1つのもの
    - 検索の `GET /api/users` と、一覧と1件の対になる
  - 自分の編集は、次のようにする
    - レガシー版は `PUT /api/users/{public_id}` のまま（だれでも書き換えられる問題を測る）
    - 改善版で `PATCH /api/me` に移す
  - レガシー版から入れる
- ほかの案：
  - 主キーごと UUID にする
  - 連番のまま、認可だけで守る
  - 連番を別の文字に変えて見せる（Hashids など）
  - JWT の `sub` も UUID にする
  - `/profile` を残す
- 理由：
  - 連番だと、ID を順に変えて他人のページを開ける。会員の数と増え方も分かる
  - 主キーを UUID にすると、すべての表の外部キーとインデックスの幅が2倍になり、今の表とコードを全部変えることになる
  - v7 は時刻の順に並ぶので、v4 よりインデックスへの書き込みが散らばらない
  - DB の既定の値にすると、どこから行を入れても必ず入る
  - JWT の `sub` から分かるのは自分の番号だけで、それで他人のページは開けない
  - JWT の `sub` を UUID にすると、JWT を読むコントローラごとに、中の `id` を引き直す SQL が増える
  - UUID にしても、認可の代わりにはならない（UUID を知っていれば書き換えられる問題は、レガシー版で測る問題として残す）
- 数字・リンク：[#46](https://github.com/masa-devx/matching-db-study/issues/46)

### D-023 メッセージの表を3つに分ける

    - `talk_room_members`：ルームの中の一人ひとりの状態。`(talk_room_id, user_id)` の UNIQUE・既読の位置

  - 表示速度（#295）とテスト（#290）は、画面をまたぐので別のチケットにする。試しの1画面は届いたいいね（#294）
- ほかの案：
  - 1つの領域を全部の画面に広げる（例：状態管理を全部の画面で直す）：PR が大きくなり、何が良くなったかが数字で見えない
  - 全部の画面を先に棚卸ししてから移す：棚卸しが古くなる前に移しきれない
- 理由：
  - 「なぜ入れるのか・何が良くなるのか」を、毎回本物の1画面と前と後の数字で確かめられる
  - 人が決めた（2026-11-23）
- 弱いところ：
  - しばらく、レガシー版と改善版の画面が並び、書き方が2つある
  - 触らない画面は、いつまでも移らないことがある
