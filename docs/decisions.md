## 準備で決めたこと

| # | 状態 | 決めたこと | ほかの案 | 理由 | 数字・リンク |
| --- | --- | --- | --- | --- | --- |
| D-001 | 有効 | バックエンドは Laravel（API）＋PostgreSQL | Go＋sqlc（SQL を全部自分で書く）・Rails（`lock_version`・`strong_migrations` がある） | 使い慣れた ORM（Eloquent）で書き、裏で流れる SQL を見て直す経験を、測った事実として残す。09（楽観ロック）・10（止めずに変えるマイグレーション）は道具に頼らず自分で作るので、仕組みを説明できる | ― |
| D-002 | 有効 | ORM は Eloquent。各一歩で「流れた SQL → 問題 → 直し方 → 前と後の数字」を残し、Rails（ActiveRecord）・Prisma ならどう書くかも並べる | ORM を使わない（sqlc） | ORM の便利さと罠（N+1・with と join）を、どの ORM でも説明できるようにする | ― |
| D-003 | 有効 | 最初は Laravel を入れたときの形の MVC・Fat Controller（Laravel 5 系のころの書き方）で、テストも性能も考えずに作り、一歩ごとに測って直す。Laravel 本体は最新 | 初めから層を分ける（クリーンアーキテクチャなど）・Laravel 5 系をそのまま使う | 古いコードを引き継いで直す力を、前と後の数字つきで説明できるようにする。5 系は保守が終わり、PHP 8.5 で動かない | ― |
| D-004 | 有効 | 画面は React＋TypeScript＋Vite。00〜03 は API だけで、03b から足す | 最初から作る・画面を作らない | DB を学ぶ時間を先に取り、画面が学びにつながる一歩（04・05・08・09）から使う | ― |
| D-005 | 有効 | 画面の状態は、まず React の Context。描き直しが気になったら Zustand に移す（05b） | 最初から Zustand・TanStack Query・Redux Toolkit | 標準の仕組みの限界を体験してから移すと、移した理由を説明できる | ― |
| D-006 | 有効 | OpenAPI は使わない。画面の型は手で書き、API の返す形に合わせる | OpenAPI から型を作る | 道具を増やさない。ずれはテストで見つける | ― |
| D-007 | 有効 | 認証：01b の素朴な版は自分で書いたトークン（`users` の列に平文）、直した版は Sanctum の API トークン。03b の素朴な版は画面で sessionStorage に置き、直した版は Sanctum の SPA 認証（HttpOnly の Cookie）に移す | JWT・最初から Sanctum | 素朴な形の危うさ（なりすまし・平文・XSS で盗まれる）を試してから直す。JWT は Laravel の標準でない | ― |
| D-008 | 有効 | メッセージは PostgreSQL（05）。05c で同じものを Firebase Emulator（手元の Firestore）で作って比べる | 最初から Firestore・解説で比べるだけ | RDB とドキュメント DB の違いを、同じ題材で説明できるようにする。Emulator ならクラウドのアカウントと秘密の鍵が要らない | ― |
| D-009 | 有効 | デプロイしない。11 で DB の引っ越しを手元で試す。クラウドに載せるかは、すべての一歩のあとに決める | AWS（RDS）に載せる | お金と秘密の値の管理を増やさない | ― |
| D-010 | 有効 | テストは本物の PostgreSQL に対して実行する（Pest） | SQLite のメモリ DB | SQLite ではロックや UNIQUE の動きが違い、確かめたいことが確かめられない | ― |
