# 改訂版の回し方（開発サイクル）

`refactored-repo` で、実務と同じ開発サイクルを回すときの正本。スキル（`pm`・`tech-lead` など）とレビュー役は、このファイルを読んでから動く。レガシー版（`legacy-repo`）の進め方は AGENTS.md の「作業の流れ」のまま変えない。

## 1. 登場人物

人は1人なので、ほかの役は AI が受け持つ。AI は話すときに役を名乗る（例：`PM：`・`リーダー：`・`ビジネス側（サポート）：`）。

| 役 | 受け持ち | しないこと |
| --- | --- | --- |
| ビジネス側（運営・サポート・営業・マーケ） | 困りごと・お客さまの声・数字（問い合わせの件数・売上・継続率）を出す。聞かれたことに答える | 技術の答えを先に言う |
| PM（プロダクトマネージャー） | **なぜ・何を・いつ**。バックログと優先度・範囲・成功を何で測るか・リリースの範囲・お知らせ | どう作るかを決める |
| プロジェクトリーダー（テックリード） | **どう作るか**。設計・タスクの分け方・見積もり・技術の負債・品質の基準・PR の最終判断・理解度チェック | 要件を勝手に変える |
| 実装の担当（AI） | 決めた設計とチケットのとおりにコードを書き、PR を作る | チケットにないことを足す |
| レビュー役（サブエージェント） | 実装の会話を持たずに、差分を角度ごとに見る（`.claude/agents/`） | コードを直す |
| 人（エンジニア） | 話し合いで決める・設計に意見を出す・提案を出す・コードの解説を受けて説明できるようになる・PR をレビューして承認する | ― |

話し合いの決まり：

- 1回の返事で人に出す問いは3つまで
- 役は答えを知っていても先に言わない。人の案を聞いてから、弱いところを聞き返す
- 役は人の案をそのまま褒めない。弱いところと代わりの案を必ず1つ出す。人は役の案に反対してよい
- 決まったことは、その場で `docs/cycles/` の議事録に「決めたこと・決めなかったこと・宿題」として残す
- 実務のコード・社名・サービス名・お客さまのデータは持ち込まない。困りごとと数字は作った例で出す

## 2. ブランチ

| ブランチ | 役割 |
| --- | --- |
| `main` | どのブランチでも使う共通のもの。取り込んで AGENTS.md などがぶつかったら、`refactored-repo` の書き方を優先して手で合わせる |
| `legacy-repo` | レガシー版をそのまま残す。`refactored-repo` から戻さない |
| `refactored-repo` | 改訂版の本線。リリースのタグ（`v0.x.0`）はここに打つ |

作業用のブランチは `refactored-repo` から切り、PR で `refactored-repo` に戻す。チケット1つにブランチ1つ・PR 1つ。

| ブランチ名 | 使うとき |
| --- | --- |
| `feature/<番号>-<名前>` | 機能・小さな機能 |
| `refactor/<番号>-<名前>` | 改善（振る舞いを変えない） |
| `fix/<番号>-<名前>` | 不具合・障害の恒久の対応 |
| `hotfix/<番号>-<名前>` | 障害の暫定の対応（急ぐ。レビュー役は security と edge-case だけでよい） |
| `chore/<番号>-<名前>` | ツールの導入・CI・依存の更新・雑務 |
| `spike/<番号>-<名前>` | 調査。取り込まない（結論だけ Issue と文書に残す） |
| `harness/<番号>-<名前>` | AGENTS.md・スキル・サブエージェント・この文書 |

## 3. チケット（Issue）

### 3-1. 種類

ひな形は `.github/ISSUE_TEMPLATE/`（GitHub の画面の「New issue」は既定のブランチ（main）のひな形を出すので、改訂版のチケットは `ticket` スキルが、このブランチのひな形から作る）。

| 種類 | 何か | 大きさ | ひな形 |
| --- | --- | --- | --- |
| エピック | 大きな追加機能。子のチケットを束ねる（sub-issue）。1〜3サイクル | XL | `r-epic.md` |
| 機能 | 中くらいの追加機能。PR 1〜3つ（3つなら子に分ける） | M〜L | `r-feature.md` |
| 小さな機能 | PR 1つで終わる追加 | XS〜S | `r-small.md` |
| 改善 | 振る舞いを変えずに直す・速くする・設計や DB を直す | S〜L | `r-improvement.md` |
| 不具合 | 決めた振る舞いと違う | S〜M | `r-bug.md` |
| ツールの導入 | 開発や運用の道具を入れる | S〜M | `r-tool.md` |
| 調査 | 答えを出すために調べる。時間を区切る（2〜4時間） | 時間 | `r-spike.md` |
| 雑務 | 文書・設定・小さな掃除 | XS〜S | `r-chore.md` |
| 障害 | 今まさに使えない・データが壊れている。サイクルに割り込む | 時間 | `r-incident.md` |
| 提案 | 人が出す「こうしたい」。相談して採るかを決める | 相談のあと | `r-proposal.md` |

### 3-2. ボード（GitHub Projects「matching-db-study 改訂版」）

| 項目 | 値 | 決める役 |
| --- | --- | --- |
| Status | Inbox（届いたまま）→ Backlog（仕分け済み）→ Ready（始めてよい）→ In progress → In review → Done | だれでも |
| 種類 | 3-1 の10種類 | PM |
| Priority | P0（すぐ・止まっている）・P1（今のサイクル）・P2（次のサイクル）・P3（いつか） | PM |
| Size | XS（〜1時間）・S（〜半日）・M（〜1日）・L（〜3日）・XL（エピックにして分ける） | リーダー |
| Cycle | サイクル 01・02…（2週間ずつ） | PM とリーダー |
| Area | 会員・認証・検索・いいね・メッセージ・有料・管理画面・基盤 | リーダー |

- ラベルは領域（`db`・`api`・`frontend`・`auth`・`docs`）だけを付ける。種類と優先度はボードの項目で持つ（2か所に書かない）
- マイルストーンは使わない（サイクルで区切る）
- Ready にしてよい条件：受け入れの条件と確かめ方が書いてある・Size と Priority が付いている・依存するチケットが Done か、順番が決まっている
- Done にしてよい条件：PR が取り込まれた・受け入れの条件をすべて確かめた・文書（要件・API・データモデル）を直した

## 4. サイクル（1リリース）

1サイクルは2週間・チケット5〜8枚。記録は `docs/cycles/<番号>-<名前>/` に置く（ひな形は `docs/cycles/_template/`）。

| 段階 | 話す役 | 話し合うこと | 残すもの | 次へ進んでよい条件 | スキル |
| --- | --- | --- | --- | --- | --- |
| 0 仕分け | PM・リーダー | Inbox を見て、種類・優先度・大きさを付けるか閉じる。今回のサイクルに入れるものを選ぶ | ボード | 今回のチケットが決まった | `pm` |
| 1 なぜ作るか | ビジネス側・PM | だれの・どんな困りごとか。今どれくらい起きているか。作らないとどうなるか | `01-why.md` | 困りごとを1文で言える・数字が1つある | `pm` |
| 2 何を作るか | PM | 範囲と範囲の外・受け入れの条件・成功を何で測るか | `02-what.md`・`docs/requirements/` | 受け入れの条件が書けた・外すものが決まった | `pm` |
| 3 どう作るか | リーダー | DB（表・制約・インデックス・移行）・API（入力・応答・失敗・互換）・ディレクトリとクラスの置き場・ログとエラー通知・戻し方。案を2つ以上比べる | `03-how.md`・`docs/api/`・`docs/decisions.md` の案 | リーダーと design-reviewer・db-reviewer の must がない | `tech-lead` |
| 4 チケットを切る | リーダー・PM | PR 1つの大きさに分ける・順番・見積もり。改善と不具合は、最初に「固定するテスト」 | Issue | すべてのチケットが Ready | `ticket` |
| 5 実装 | 実装の AI | チケットのとおりに書く。テスト → 実装 → 測る | PR | CI が通る・測った数字がある | `implement` |
| 6 コードの解説 | リーダー | ディレクトリとメソッドの設計（6章） | `06-walkthrough.md` | 人が説明し直せた | `code-walkthrough` |
| 7 PR レビュー | レビュー役・人 | 角度ごとに見る（7章）。人も自分のコメントを書く | PR のコメント・`07-review.md` | must がなくなり、人が承認した | `pr-review` |
| 8 理解度チェック | リーダー | 「なぜそこに置いた？」「ほかの案は？」「壊れたらどう気づく？」「10倍になったら？」 | `docs/onboarding/quiz-log.md` | 8割に答えられた。残りは次の課題にした | `tech-lead` |
| 9 リリース | PM・リーダー | 出す順番・確かめ・戻し方・お知らせ | `09-release.md`・タグ | 出したあとの確かめが通った | `release` |
| 10 振り返り | PM・リーダー | 指標は良くなったか・良かったこと・困ったこと・次に試すこと・ハーネスの直し | `10-retro.md`・`docs/roadmap.md` | 次のサイクルの候補が決まった | `pm` |

5〜8 はチケットごとに回す。7 で must が出たら 5 に戻る。

## 5. 割り込み

### 5-1. 出来事

AI（ビジネス側・監視の役）が、サイクルの途中に出来事を起こす。1サイクルに0〜1回。いつ起こすかは前もって言わない。進め方は `incident` スキル。

| 出来事 | 例 | 手元での再現 |
| --- | --- | --- |
| 障害 | 「朝から、ログインできないと問い合わせが30件」 | 作業用のブランチに壊すコミットを入れる・設定を変える・開発用の DB のデータを壊す |
| ユーザーの急増 | 「紹介されて、会員が10倍の20万人に」 | シーダーで10倍にする・負荷をかける道具で同時に送る（費用のかからないもの） |
| 急ぎの依頼 | 「来週のキャンペーンまでに、初月半額を入れたい」 | PM が期限つきで依頼する |
| 外からの変化 | 「使っているライブラリに脆弱性が見つかった」 | 依存の版を指定して直す |

- 壊してよいのは、開発用の DB（`matching_dev`）と、出来事のための作業用のブランチだけ。`main`・`legacy-repo`・`refactored-repo` と、テスト用の DB と、秘密の値のファイルは触らない
- 優先度は PM とリーダーが決める。P0 は今の作業を止めて対応（暫定の対応 → 原因 → 恒久の対応のチケット → ポストモーテム）。P1 は今のサイクルの範囲を入れ替える。P2 以下は Inbox
- 障害の記録は `docs/incidents/YYYY-MM-DD-<名前>.md`（ひな形は `docs/incidents/_template.md`）。人を責めない書き方にする

### 5-2. 人からの提案

人は「提案です：…」といつでも出してよい。進め方は `proposal` スキル。PM は価値を、リーダーは作り方・危なさ・大きさを聞き返し、採る・形を変えて採る・保留・採らない、を決めて理由を残す。

## 6. コードの解説（code-walkthrough）

AI が書いたコードを、人がレビューで説明し、突っ込まれても答えられるようにする。PR ごとに次を書く。

| 見出し | 中身 |
| --- | --- |
| ディレクトリの設計 | 足したファイルの置き場と、なぜそこか（`agents/rules/architecture.md` のどの決まりか）。ほかに置ける場所と、置かなかった理由 |
| クラスの責務 | クラスごとに「何を知っていて・何をするか・何をしないか」 |
| メソッドの表 | 入力・戻り値・副作用（DB の書き込み・ログ・通知）・失敗のしかた・呼ぶ所 |
| 呼び出しの流れ | リクエストから応答まで、どのメソッドがどの順で呼ばれ、どの SQL が流れるか（sequenceDiagram） |
| 名前 | なぜその名前か。ほかの候補 |
| 依存の向き | だれがだれを使うか。逆向きになっていないか |
| レガシー版との違い | 同じ処理がレガシー版ではどこにあったか（`git diff legacy-repo..HEAD -- <パス>`） |
| 説明の練習 | 人が説明し、リーダーが2〜3回突っ込む |

## 7. PR レビュー（pr-review）

角度ごとに別のレビュー役が見て、最後に人とリーダーが判断する。レビュー役どうしは互いの結果を見ない。

| 角度 | 見ること | 担当 |
| --- | --- | --- |
| 要件 | 受け入れの条件を満たすか・範囲の外が混ざっていないか | `requirements-reviewer` |
| 設計 | 責務・ディレクトリ・依存の向き・名前・重複・やりすぎ | `design-reviewer` |
| DB と性能 | 制約・インデックス・ロック・マイグレーションの戻し方・SQL の本数・N+1 | `db-reviewer` |
| 異常系と境界値 | 空・0件・上限・同時に2回・期限の境目・時間帯 | `edge-case-reviewer` |
| セキュリティ | 認証・認可・入力の確かめ・秘密の値 | `security-reviewer` |
| 運用 | ログ・エラー通知・監視・リリースの順番・戻し方 | `ops-reviewer` |
| テスト | 要件 ID との対応・骨抜き・テスト同士の依存 | `test-reviewer` |
| 画面 | 状態・読み込みと失敗の表示・アクセシビリティ・API とのずれ（画面を触る PR だけ） | `frontend-reviewer` |
| 全体 | 今出してよいか。何を今直すか | 人とリーダー |

指摘の印：

| 印 | 意味 | 扱い |
| --- | --- | --- |
| `[must]` | 直さないと出せない（不具合・セキュリティ・データが壊れる・要件を満たさない） | この PR で直す |
| `[should]` | 直した方がよい（設計・性能・読みやすさ・テストの抜け） | この PR で直すか、チケットにして Inbox へ |
| `[ask]` | 意図が分からないので聞きたい | 答えを PR に残す |
| `[nits]` | 細かい好み | 直さなくてよい |

- どの指摘にも「どこ（ファイルと行）・何が起きるか（具体的な入力と結果）・どう直すか」を書く
- 指摘は PR にコメントとして残す（リポジトリは public。実務の言葉・社名・秘密の値を書かない）。承認は人だけがする
- 3回まわっても同じ指摘が行き来したら、人が決める

## 8. リリース（手元だけ）

デプロイ先はないので、本番に出すのと同じ順番を手元でやる。手順は `release` スキル。

1. 開発用の DB をバックアップする
2. 取り込み、マイグレーションを流す。かかった時間とロックを見る
3. 出したあとの確かめ（health・決めた操作・エラーの通知が Mailpit に届くか）
4. 戻し方を1回試す → もう一度出す
5. タグ `v0.x.0` を打ち、リリースノートを書く（タグと push は確かめてから）

エラー通知は手元だけで終わらせる（構造化ログと、Mailpit へのメール）。外のサービスは使わない。

## 9. 文書の置き場

| パス | 中身 |
| --- | --- |
| `docs/process.md` | このファイル |
| `docs/roadmap.md` | エピックの並び・次の候補・成長の見通し |
| `docs/onboarding/` | 入ってきた人として読む：読む順番・機能の地図・今の表の形・理解度の記録 |
| `docs/cycles/<番号>-<名前>/` | サイクルごとの議事録と記録 |
| `docs/incidents/` | 障害の記録（ポストモーテム） |
| `docs/requirements/`・`docs/api/`・`docs/data-model.md`・`docs/decisions.md` | 今までと同じ。サイクルの中で直す |
