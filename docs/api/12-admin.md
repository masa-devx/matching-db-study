状態：**実装済み（レガシー版）**（PR は #90 の PR）

決まり（パス・ステータス・エラーの形）と一覧は [README.md](README.md)。

要件：[requirements/admin.md](../requirements/admin.md)（FR-ADMIN-001〜012・NFR-ADMIN-001〜004）。表は会員の側と共通（`admins`・`admin_audit_logs`・`users.suspended_at` も含めて、作りは `backend/client` のマイグレーション。[data-model.md](../data-model.md)）。解説：`explanations/12-admin.html`（`legacy-repo`）。

会員の側（`backend/client`）では、アカウント停止された会員を断る：

- レガシー版：ログインの API だけで断る（ほかの API にはコピーしない）
- 改善版：ログインした会員を読むミドルウェア（`AuthenticateMember`）で断る
  - ルートに付けるときの名前は `auth.member`

レガシー版の作り：

- Fat Controller
- だれが使うかは、管理者の JWT を読んで決める処理を、コントローラごとにコピーする（会員の側の 16か所と同じ形を、管理画面の中にもう一度作る）
- 役割（`viewer` を断る）と監査ログの書き込みも、コントローラごとにコピーする（コピーし忘れを測る）
- 入力は確かめず、エラーの扱いは考えない

## 前提：管理画面の鍵（人が作る）

管理者の JWT は、管理画面の `APP_KEY` で署名する（会員の側の鍵とは別。会員の JWT では管理画面の API を使えないようにするため）。`APP_KEY` は秘密の値なので、AI は作らない・読まない。実装の前に、人が次の2つを実行する：

1. `cp backend/admin/.env.example backend/admin/.env`
2. `docker compose run --rm admin-app php artisan key:generate`

DB の接続先などは compose の環境変数が `.env` より優先されるので、`.env.example` の DB の行（sqlite）は直さなくてよい。

## #211 で足すこと（A1：停止の履歴。状態：**実装済み（レガシー版）**）

要件は FR-ADMIN-019。止める・解く API（`POST`・`DELETE /api/members/{publicId}/suspension`）の入力と応答は変えない。会員の詳細（`GET /api/members/{publicId}`）の応答に、`suspensions`（新しい順。`reason`・`suspended_at`・`suspended_by`・`lifted_at`・`lifted_by`）が増える。

### 今の状態（止めているか）

- レガシー版（legacy-repo）：前からある `users.suspended_at`・`suspended_reason` に持つ
  - **同じ日時と理由を、`suspensions` にも書く（2か所）**
  - トランザクションがないので、片方だけ書けることがある
- 改善版（refactored-repo）：履歴（`suspensions`）を正にする
  - 「止めているか」は、解いていない行があるかで決める
  - 会員の側が毎回読むので、`users.suspended_at` を残すなら、同じトランザクションで書く

### 外部キー

- レガシー版：なし（いない会員・いない管理者を指す行が入る）
- 改善版：`user_id`・`suspended_by`・`lifted_by` に外部キー（`restrict`）

### まだ解いていない停止は、会員に1つ

- レガシー版：止めるものがない。**止めている会員をもう一度止めると、解いていない行が増える**

### インデックス

- レガシー版：主キーだけ（会員の履歴を探すと、表を全部読む）

```sql
select count(*) from users
where id in (select user_id from profiles where gender = 'female')
  and id in (select user_id from profiles where prefecture = '東京都')
  and id in (select user_id from profiles
             where extract(year from now())
```

```sql
join profiles p on p.user_id = u.id
where p.prefecture = '東京都' and p.gender = 'female'
  and p.birthday >  current_date - interval '35 years'   -- 今日の時点で 34歳まで
  and p.birthday <= current_date - interval '25 years'   -- 今日の時点で 25歳から
```

## #227 で足すこと（A1・A7：会員ごとの、やり取り・違反・ブロック。状態：**実装済み（レガシー版）**）

要件は FR-ADMIN-030〜033。API を4本足す（どれも `GET`。`viewer` も読める）。

| API | 何を返す |
| --- | --- |
| `GET /api/members/{publicId}/talk-rooms` | その会員のルームの配列 |
| `GET /api/members/{publicId}/violations` | 通報された案件と、通報した記録 |
| `GET /api/members/{publicId}/blocks` | ブロックした相手・された相手 |
| `GET /api/block-ranking` | ブロックされた人数の多い順に 50人 |

### `GET /api/members/{publicId}/talk-rooms` の応答

その会員のルームの配列（最後のメッセージの新しい順）。1つのルームは次のもの：

- `room_id`
- `partner`（`user_id`・`nickname`・`state`）
- `message_count`・`sent_count`
- `last_message`（`body`・`created_at`・`mine`）
- `created_at`

### `GET /api/members/{publicId}/violations` の応答

- `cases`（通報された案件：`id`・`status`・`action`・`report_count`・`reasons`・`created_at`・`closed_at`）
- `reports_made`（その会員が通報した記録：`reported`・`case_id`・`reason`・`created_at`）

### `GET /api/members/{publicId}/blocks` の応答

- `made`（ブロックした相手）・`received`（ブロックされた相手）
- 1行は `user_id`・`nickname`・`state`・`blocked_at`・`matched`

### `GET /api/block-ranking` の応答

ブロックされた人数の多い順に 50人。1行は `user_id`・`nickname`・`state`・`blocked_count`・`last_blocked_at`・`report_count`・`open_case`。

注意のお知らせ・利用の停止・強制退会は、会員の詳細の API（`notices`・`suspensions`・`banned_at`）が返しているものを、画面の「違反」のタブが使う。
