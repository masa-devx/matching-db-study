# 07 有料会員

状態：**実装済み（レガシー版）**（PR は #81 の PR）

決まり（パス・ステータス・エラーの形）と一覧は [README.md](README.md)。

要件：[requirements/paid-members.md](../requirements/paid-members.md)（FR-PAID-001〜017・NFR-PAID-001〜004）。表は `users.is_paid`・`paid_until`・`plans`・`purchases`（[data-model.md](../data-model.md)）。解説：`explanations/07-paid-members.html`（`legacy-repo`）。

購入は「ログインした本人がしたもの」なので `/api/me/purchases` の下に置く。プランの一覧は、だれにでも同じなので `/api/plans`（ログインが要る）。画面は、プランの一覧（`/plans`）で期間を選び、購入の画面（`/plans/:id`）で「購入する」を押す。

購入まわり（プランの一覧・購入する・購入の記録）は、レガシー版でも**男性の会員だけ**が使える。バックエンドでは3つの API で性別を確かめ、男性でなければ `403`。画面でも、男性にだけ入口を出す。

| API | 中身 | レガシー版 | 改善版 |
| --- | --- | --- | --- |
| `GET /api/plans` | 期間と値段の一覧 | 作る（`PlanController::index`） | 作る |
| `POST /api/me/purchases` | 購入する | 作る（`PurchaseController::store`） | 作る |
| `GET /api/me/purchases` | 購入の記録 | 作る（`PurchaseController::index`） | 作る |
| `GET /api/me` | 自分の情報（画面の出し分けに使う） | 変えない（`users` の行に `is_paid`・`paid_until` が増えて出る） | `features`（使える機能）を足す |
| 送る・いいね・検索（05・02・04） | 男性の無料の会員を断る | 入口ごとに `if` を写す（下の「今ある API に足すこと」） | 1つの関数（`Features::allows()`） |

レガシー版は、設計を考えずに「とりあえず使える」形で作る。だれが使うかは、これまでと同じく JWT を読んで決める（`AuthController::me()` の処理を写す。3つ足して 14〜16か所目）。性別の確かめも、3つの API に同じものを写す。入力は確かめず、トランザクションもない。

## `GET /api/plans`（期間と値段の一覧）

| 項目 | レガシー版（legacy-repo） | 改善版（refactored-repo） |
| --- | --- | --- |
| だれが使えるか | 正しい JWT を持つ男性の会員。男性でなければ `403` `{"message": "有料会員は男性の会員だけです"}` | 正しい `access` の Cookie を持つ男性の会員 |
| 応答（成功） | `200`。`plans` の行の配列（`id`・`name`・`months`・`price`・日時）。`id` の順 | `200` `{"data": [{"plan_id": 2, "name": "3か月", "months": 3, "price_yen": 9800}]}`（`months` の順） |
| 応答（失敗） | `401`：`Authorization` がない。`403`：男性でない。`500`：JWT が壊れている | `401`・`403` |
| 流れる SQL の目安 | 2本（自分のプロフィール・プラン） | 1本＋ガード1本 |

## `POST /api/me/purchases`（購入する）

| 項目 | レガシー版（legacy-repo） | 改善版（refactored-repo） |
| --- | --- | --- |
| だれが使えるか | 正しい JWT を持つ男性の会員（男性でなければ `403`）。確認していない会員・退会した会員の JWT でも買える | 正しい `access` の Cookie を持ち、メールアドレスを確認した男性の会員（FR-PAID-012・015） |
| 入力（JSON） | `{"plan_id": 2}`。確かめない | `plan_id`：必須・ある（表にある）プラン |
| 何をするか | 購入の記録を1行入れ（プランを指すだけ）、`users` の `is_paid` を true に、`paid_until` を「今の `paid_until`（なければ今）＋プランの月」にする。**期限が過ぎていても、古い期限から足す**。月は `addMonths()`（1月31日＋1か月は3月3日）。トランザクションなし | 会員の行を押さえ、「今と最後の期限の遅いほう」から、`addMonthsNoOverflow()` で足した期間を、値段と一緒に記録に写す（FR-PAID-001・003・004） |
| 応答（成功） | `201` `{"is_paid": true, "paid_until": "…"}` | `201` `{"data": {"paid_until": "…", "purchase": {"months": 3, "price_yen": 9800, "starts_at": "…", "ends_at": "…"}}}` |
| 応答（失敗） | `401`：`Authorization` がない。`403`：男性でない。`500`：JWT が壊れている・**ないプラン**（`$plan` が `null`） | `401`・`403`（男性でない・確認していない）・`422`（ないプラン） |
| 流れる SQL の目安 | 5本（自分のプロフィール・プラン・会員・insert・update） | 4本＋begin・commit（行ロック・プラン・最後の期限・insert） |
| curl の例 | `curl -X POST http://127.0.0.1:8000/api/me/purchases -H 'Authorization: Bearer <JWT>' -H 'Content-Type: application/json' -d '{"plan_id":2}'` | `-b cookies.txt` で同じ |

## `GET /api/me/purchases`（購入の記録）

| 項目 | レガシー版（legacy-repo） | 改善版（refactored-repo） |
| --- | --- | --- |
| だれが使えるか | 正しい JWT を持つ男性の会員（自分の分だけ。男性でなければ `403`） | 同じ（Cookie） |
| 応答（成功） | `200`。配列。新しい順。1件は `{"name": "3か月", "months": 3, "price": 9800, "bought_at": "…"}`。**`price` と `months` は今のプランから読む**（値段を変えると前の記録も変わる。いつからいつまでの分かは出せない） | `200` `{"data": [{"months": 3, "price_yen": 9800, "starts_at": "…", "ends_at": "…"}]}`（買ったときの値） |
| 応答（失敗） | `401`・`403`（男性でない）・`500`（JWT が壊れている） | `401`・`403` |

## 今ある API に足すこと（レガシー版）

送る・いいね・検索のコントローラに、同じ判断を写す（2本ずつ増える）。

```php
// 07：男性の無料の会員は使えない（is_paid だけを見る。paid_until は見ない）
$myProfile = Profile::where('user_id', $payload->sub)->first();
$myUser = User::find($payload->sub);
if ($myProfile?->gender === 'male' && ! $myUser->is_paid) {
    return response()->json(['message' => '有料会員になると使えます'], 403);
}
```

| API | いつ断るか | 流れる SQL の目安 |
| --- | --- | --- |
| `POST /api/me/talk-rooms/{public_id}/messages`（05） | 男性で `is_paid` でなければ、いつも `403`（読む `GET` は断らない） | 2本足す（断るときは 2本で終わる） |
| `POST /api/me/likes`（02） | 男性で `is_paid` でなく、**今日（UTC の日付）のいいねが 10回以上**なら `403`。数えてから入れる（ロックなし） | 3本足す（プロフィール・会員・数える）。数えるのは `created_at::date = ?`（索引なし・列に関数） |
| `GET /api/users`（検索。04） | `height_min` か `height_max` を送ったときだけ、男性で `is_paid` でなければ `403` | 2本足す（身長の条件があるときだけ。04 ですでに自分のプロフィールを読んでいるが、もう一度読む） |

断るときの応答は `403` `{"message": "有料会員になると使えます"}`。要件の `code: paid_required` は返さない（画面はステータスだけで見分ける）。

`GET /api/me` は変えない。`users` の行をそのまま返すので、`is_paid`・`paid_until` も出る（性別は出ないので、画面はプロフィールの API も読んで、同じ判断を写す）。

## レガシー版で起きること（#81 で測った。改善する段階で要件 ID のテストにする）

開発用の DB（会員 2万人・有料にしたことがある男性 3000人・購入 23,594件）に、手元から本物の HTTP（`127.0.0.1:8000`）を送り、SQL はクエリログの増えた行で数えた。会員は、男性の無料 `search00001`・期限の中 `search00304`・期限が過ぎた `search00306`・女性（ルームがある会員）。JWT は外に出していない。書いたもの（メッセージ・いいね・マッチ・購入・値段・性別）は消すか戻し、最後に `PaidMembersSeeder` を流し直した。

| 送るもの・すること | レガシー版 | 要件 |
| --- | --- | --- |
| 男性の無料の会員：送る・読む・身長の条件で検索・条件なしの検索 | `403`（`有料会員になると使えます`。SQL 2本で終わる）・`200`・`403`（SQL 2本）・`200`（SQL 25本） | FR-PAID-007・009 |
| 期限の中の会員：送る・身長の条件で検索 | `201`（SQL 4本）・`200`（SQL 27本。04 より2本多い） | FR-PAID-010 |

| 女性の会員：送る・身長の条件で検索 | `201`・`200` | FR-PAID-011 |
| 男性の無料の会員が、今日 0回から 11回いいね | 10回目まで `201`（1本目は SQL 6本）・11回目 `403`（SQL 3本で終わる） | FR-PAID-008 |
