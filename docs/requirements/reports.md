# 要件：通報

状態：確定
元資料：ユーザーとの会話で決めたこと（2026-11-17）。[blocks.md](blocks.md)・[admin.md](admin.md) の「次の段階」・[backlog.md](../backlog.md) の M7・A7
一歩：M7（会員の側）と A7（管理画面）。バックログのまとまりで進める
目的：[product.md](../product.md) の「安全」

このファイルは、会員が困った相手を運営に伝える（通報）と、運営が通報を見て対応する、を長く表す。レガシー版も改善版も、この要件を守る（レガシー版で守れていないものは、改善する段階のテストの対象になる）。要件 ID は `FR-REPORT-` で始める。画面の要件は [screens.md](screens.md) に `FR-UI-` で書き足す。

## 目的と対象

今は、困った相手（しつこい連絡・勧誘・お金の要求 など）に出会った会員にできるのは、ブロックだけ。ブロックは自分から見えなくするだけで、運営には何も伝わらず、その相手はほかの会員に同じことを続けられる。会員が運営に伝える手段と、運営が、通報の重なっている会員を見つけて対応を残す手段を作る。

## ユーザーストーリーと優先度

- 会員として、困った相手を、理由を付けて運営に伝えたい。困った発言があれば、その発言を指して伝えたい
- 会員として、通報と一緒に、その相手をブロックするかを選びたい
- 運営として、通報の重なっている会員を先に見つけ、通報の中身を読んで、対応の状態と、何をしたかを残したい

優先度ごとの範囲：

- 必須（M7・A7）
  - 会員を通報する
  - メッセージを指して通報する
  - 理由（選択肢と自由な文）
  - 通報と一緒にブロックするかを選ぶ
  - 管理画面で会員ごとにまとめて見る
  - 対応の状態（まだ・対応中・済み）
  - 済みにするときに何をしたかとメモを残す
- 必須（A7 の続き。#213）：運営から会員へのお知らせで注意を届ける・従わないときの強制退会（FR-REPORT-018〜023）
- 次の段階：通報した会員に結果を知らせる・気をつける言葉を自動で拾う・全員へのお知らせ（メンテナンスなど）
- 対象外：写真だけを指す通報・通報の取り消し・通報した会員への報酬や評価

## 機能要件と受け入れ条件

通報は、会員（通報された側）ごとに1つの「案件」にまとまる。対応の状態は、案件に付ける（通報1件ずつには付けない。2026-11-17 に人が決めた）。

理由の選択肢は6つ：しつこい連絡・迷惑な行い／勧誘・営業／お金の要求・詐欺の疑い／不適切な写真・プロフィール／なりすまし・年齢や独身でない疑い／その他。自由な文は 0〜1000文字。「その他」を選んだときは、自由な文が要る。

済みにするときに残す「何をしたか」は4つ：問題なし／注意した／利用を止めた／強制退会にした（4つ目は、#213 で足した）。

### FR-REPORT-001 会員を通報できる

- 前提：ログインした会員 A。会員 B がいる
- 操作：A が、B を、理由「勧誘・営業」で通報する
- 期待結果
  - `201`
  - 通報が1件できる
  - B への案件がなければ、状態「まだ」の案件が1つでき、通報はその案件に入る

### FR-REPORT-002 メッセージを指して通報できる

- 前提：A と B がマッチしていて、B が A にメッセージ M を送った
- 操作：A が、M を指して通報する
- 期待結果：`201`。通報に、M が入る。通報された会員は、M を送った B になる

### FR-REPORT-003 指せるメッセージは、自分のいるルームで、相手が送ったものだけ

- 前提：A のいないルームのメッセージ N。A が自分で送ったメッセージ O
- 操作：A が N・O を指して通報する
- 期待結果：`404`（N）・`422`（O）。通報はできない

### FR-REPORT-004 理由の誤りが分かる

- 前提：なし
- 操作：理由なし・選択肢にない理由・1001文字の文・「その他」で文なし、で通報する
- 期待結果：`422`。どれが違うかを返す。通報はできない

### FR-REPORT-005 自分・いない会員は通報できない

- 前提：なし
- 操作：A が、A 自身・ない ID を通報する
- 期待結果：`422`（自分）・`404`（いない）

### FR-REPORT-006 通報と一緒に、ブロックするかを選べる

- 前提：A が B をブロックしていない
- 操作：A が「ブロックもする」を付けて通報する。付けずに通報する
- 期待結果
  - 付けたときは、通報とブロックの両方ができる（片方だけにはならない）
  - 付けないときは、通報だけ
  - もうブロックしていても、通報は `201`

### FR-REPORT-007 同じ相手を、何度も通報できる

- 前提：A が B を1回通報した
- 操作：A が、もう一度 B を通報する
- 期待結果：`201`。通報は2件。案件は1つのまま。案件の「通報の件数」は 2、「通報した人数」は 1

### FR-REPORT-017 済みにしたあとの通報は、新しい案件になる

- 前提：B への案件が、済みになっている
- 操作：A が B を通報する
- 期待結果
  - `201`
  - 状態「まだ」の新しい案件が1つでき、通報はそこに入る
  - 済みの案件は変わらない（何をしたか・メモが残る）
  - B の案件は2つ

### FR-REPORT-008 通報されたことは、相手に伝わらない

- 前提：A が B を通報した
- 操作：B が、自分の情報・A のプロフィール・トークを見る
- 期待結果：通報される前と同じ。通報した会員がだれかは、会員の API のどこにも出ない

### FR-REPORT-009 ログインしていない・利用を止められた会員は通報できない

- 前提：なし
- 操作：トークンなし・止められた会員のトークンで通報する
- 期待結果：`401`・`403`

### FR-REPORT-010 管理者は、案件の一覧を見られる

- 前提：案件が3つ（まだ 2・済み 1）
- 操作：管理者が一覧を見る。状態「まだ」で絞る
- 期待結果
  - `200`
  - 1件は、通報された会員・状態・通報の件数・通報した人数・いちばん新しい通報の日時
  - 新しい通報のある順
  - 絞ると2つ
  - `viewer` も見られる

### FR-REPORT-011 管理者は、案件の中身を見られる

- 前提：B への案件に、通報が3件（1件はメッセージを指す）
- 操作：管理者が案件を開く
- 期待結果
  - `200`
  - 通報ごとに、通報した会員・理由・自由な文・日時
  - メッセージを指す通報には、そのメッセージの中身と送った日時
  - B の今の状態（利用中・停止中・退会）と、B の詳細へ行ける ID
  - `viewer` も見られる

### FR-REPORT-012 `owner` は、案件の状態を変えられる

- 前提：状態「まだ」の案件
- 操作：`owner` が「対応中」にする
- 期待結果：`200`。状態が変わり、だれが・いつ変えたかが残る。監査ログに1行入る

### FR-REPORT-013 済みにするときは、何をしたかを残す

- 前提：状態「対応中」の案件
- 操作：`owner` が、「注意した」とメモを付けて済みにする。何をしたかを付けずに済みにする
- 期待結果：付けたときは `200`。何をしたか・メモ・済みにした管理者と日時が残る。付けないときは `422`

### FR-REPORT-014 `viewer` は、状態を変えられない

- 前提：Y は `viewer`
- 操作：Y が状態を変える
- 期待結果：`403`。画面ではボタンが出ない（FR-ADMIN-010 と同じ）

### FR-REPORT-015 会員が退会しても、通報は残る

- 前提：A が B を通報したあと、A が退会した。別の案件で、通報された B が退会した
- 操作：管理者が案件を見る
- 期待結果：どちらも、通報が残っている。退会した会員は「退会」と出る

### FR-REPORT-016 「利用を止めた」は、記録だけ。止める操作は、今ある仕組みで行う

- 前提：案件を開いた `owner`
- 操作：会員の詳細から B を止め（FR-ADMIN-006）、案件を「利用を止めた」で済みにする
- 期待結果：止める操作と、案件を済みにする操作は別。案件を済みにしただけでは、B は止まらない

### FR-REPORT-018 `owner` は、会員にお知らせを送れる（#213）

- 前提：X は `owner`。会員 B がいる
- 操作：X が、B に、種類「注意」・題・本文を送る
- 期待結果
  - `201`
  - B のお知らせが1つできる
  - 種類は「注意」か「お知らせ」
  - 題（1〜100文字）・本文（1〜2000文字）がない・長すぎるときは `422`
  - `viewer` は `403`
  - 監査ログに1行入る（本文は入れない）

### FR-REPORT-019 会員は、自分に届いたお知らせを読める

- 前提：B にお知らせが2つ届いた
- 操作：B が一覧を見る
- 期待結果
  - `200`
  - 新しい順に2つ（種類・題・本文・届いた日時・読んだかどうか）
  - ほかの会員のお知らせは出ない

### FR-REPORT-020 読んだことが残り、運営から分かる

- 前提：B に、まだ読んでいないお知らせがある
- 操作：B が読む。X が B の詳細を見る
- 期待結果
  - B の画面の帯が消える
  - X には、読んだ日時が出る
  - ほかの会員が、B のお知らせを読んだことにはできない（`404`）

### FR-REPORT-021 通報の案件を「注意した」で済みにするとき、注意の文を一緒に送れる

- 前提：状態「まだ」の B への案件
- 操作：X が、「注意した」と注意の文を付けて済みにする
- 期待結果
  - 案件が済みになり、B に種類「注意」のお知らせが届く
  - お知らせに、もとの案件が残る
  - 文を書かなければ、記録だけ

### FR-REPORT-022 `owner` は、会員を強制退会にできる

- 前提：X は `owner`。B は会員
- 操作：X が、B を理由つきで強制退会にする
- 期待結果
  - `200`
  - B はログインできず（`403`。「強制退会になっています」）、持っているトークンでも会員の API を使えない
  - ほかの会員から B は見えない
  - B のメールアドレスでは、登録し直せない
  - 元に戻す操作はない
  - `viewer` は `403`
  - 監査ログに1行入る

### FR-REPORT-023 強制退会と、自分での退会を、運営は見分けられる

- 前提：B は強制退会。C は自分で退会した
- 操作：X が B・C の詳細を見る
- 期待結果：B は「強制退会」と、日時・理由が出る。C は「退会」と出る

## 成功基準・非機能要件・制約

- 成功基準：運営が、通報の重なっている会員を一覧のいちばん上で見つけ、通報の中身（指されたメッセージを含む）を読んで、何をしたかを残せる
- NFR-REPORT-001：まだ済みでない案件は、会員1人に1つまで。同時に何件の通報が来ても、案件が2つにならない
- NFR-REPORT-002：通報とブロックを一緒に行うときは、両方できるか、どちらもできないかのどちらか
- NFR-REPORT-003：案件の一覧を読む SQL は、件数に関係なく決まった本数（件数と人数を、案件ごとに1本ずつ数えない）
- NFR-REPORT-004：通報の自由な文と、指されたメッセージの中身を、ログに出さない
- NFR-REPORT-005：同じ会員から同じ相手への通報は、短い時間に続けて送れない（上限の数は、改善する段階で決める）

## 前提と要確認事項

- 前提：通報できる入口は、相手のプロフィールと、トーク画面（相手のメッセージを長く押す・メニューから）の2か所
- 前提：通報した会員には、対応の結果を知らせない。通報の画面に「結果はお知らせしません」と書く（お知らせの置き場ができたら見直す）
- 前提
  - 「注意した」は記録
  - 会員に届けるのは、運営からのお知らせ（FR-REPORT-018・021）
  - 従わないときは、強制退会（FR-REPORT-022）
  - 2026-11-17 に「あとで作る」と決め、2026-11-18 に #213 で作った
- 前提（#213。AI が置いた。違えば変える）
  - お知らせは、1人の会員に送るもの（全員へのお知らせは、次の段階）
  - 送ったあとは、直せない・消せない
  - 会員は、返事を書けない
  - 未読があるあいだ、どの画面にも帯を出す
  - 強制退会は、戻す操作を作らない
  - 強制退会にしても、通報・お知らせ・メッセージは消さない
- 前提
  - 表は2つ
  - `reports`（通報。通報した会員・通報された会員・指したメッセージ（なくてよい）・理由・自由な文・入っている案件）
  - `report_cases`（案件。通報された会員・状態・何をしたか・メモ・対応した管理者・済みにした日時）
- 前提：表の作り（マイグレーション）は `backend/client` に置く。通報する API は会員の側、見る・対応する API は管理画面の側
- 前提：レガシー版は、設計を考えずに「とりあえず使える」形で作り、次を測る
  - 案件を「あるかを見てから作る」だけで止める（ロックも UNIQUE もない）→ 同時に通報が来ると、同じ会員の案件が2つできる（NFR-REPORT-001）
  - 指されたメッセージの持ち主を確かめない → 自分のいないルームのメッセージを指して通報でき、管理画面でその中身が読める（FR-REPORT-003）
  - 理由・文の長さ・自分かどうかを確かめない（FR-REPORT-004・005）
  - 通報とブロックを、トランザクションなしで順に行う → 片方だけできることがある（NFR-REPORT-002）
  - 案件の一覧で、件数と人数を案件ごとに数える（1＋2N 本。NFR-REPORT-003）。人数は、件数と同じ数を出す（FR-REPORT-007）
  - 何回でも続けて通報できる（NFR-REPORT-005）
  - 外部キーを付けない（数の列だけ）→ いない会員・ないメッセージ・ない案件を指す行が入る。会員を DB で直接消すと、だれへの通報かが分からない行が残る（FR-REPORT-005・015）
- 前提：済みにした案件のある会員に新しい通報が来たら、新しい案件を作る（前の対応の記録は、済みの案件にそのまま残る。済みの案件を「まだ」に戻すことはしない。2026-11-17 に人が決めた）
- 前提：ログインした会員なら、だれでも、どの会員でも通報できる（検索で見ただけの相手も。2026-11-17 に人が決めた）
- 前提：管理者（`owner` も `viewer` も）は、通報した会員がだれかを見られる（嫌がらせの通報をくり返す会員を見つけるため。2026-11-17 に人が決めた）
- 要確認：なし
