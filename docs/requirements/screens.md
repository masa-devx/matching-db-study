このファイルは、画面（`frontend/client/`）を長く表す。あとの一歩で画面を足すときは、ここに書き足す。レガシー版も改善版も、この要件を守る（レガシー版で守れていないものは、改善する段階のテストの対象になる）。要件 ID は `FR-UI-` で始める。

## 目的と対象

01〜03 で作った API（登録・ログイン・プロフィール・いいね・マッチ）を、ブラウザの画面から使えるようにする。会員を探す一覧はまだないので、相手は URL（`/users/<相手の public_id>`）で開く。URL で会員を指す ID は UUID（`public_id`）で、連番は使わない（D-022。#46）。

## ユーザーストーリーと優先度

- 会員として、画面から登録・ログインしたい
- 会員として、自分のプロフィールを画面で直したい
- 会員として、相手のプロフィールを見て、いいねを送り、マッチしたらその場で知りたい
- 会員として、送ったいいねとマッチした相手を、一覧で見返したい

優先度ごとの範囲：

- 必須（03b）：
  - ログイン・登録・自分のプロフィール（見る・直す）・相手のプロフィール（いいねのボタン）・送ったいいねの一覧・メッセージ（マッチした相手の一覧）の6画面
  - 画面の切り替え（React Router）・ログアウト
- 次の段階：
  - 会員を探す一覧（04。検索のタブ）
  - トーク画面（05。メッセージのタブでマッチした相手を押すと開く）
  - 見た目と動き（03c。モーダル・トースト・スケルトン・マッチの演出など。[design.md](../design.md)）
  - 状態を Zustand に移す（05b）
  - 有料会員の表示（07）
- 対象外：画像のアップロード・通知・ダークモードの切り替え・多言語

## 画面の一覧

| 画面 | パス | 呼ぶ API | ログインが要るか | 要件 |
| --- | --- | --- | --- | --- |
| ログイン | `/login` | `POST /api/auth/login` | 要らない | ― |
| 登録 | `/register` | `POST /api/users` | 要らない | ― |
| 自分のプロフィール（ホーム） | `/home` | `GET /api/me`・`GET /api/users/{public_id}`・`PUT /api/users/{public_id}`・`POST /api/auth/logout` | 要る | ― |
| 相手のプロフィール | `/users/:publicId` | `GET /api/users/{public_id}`・`POST /api/me/likes` | 要る | ― |
| 送ったいいね | `/likes` | `GET /api/me/likes` | 要る | ― |
| メッセージ（マッチした相手の一覧） | `/messages` | `GET /api/me/matches` | 要る | ― |
| 検索（04） | `/search` | `GET /api/users` | 要る | [search.md](search.md) |
| ブロックした相手（06） | `/blocks` | `GET /api/me/blocks`・`DELETE /api/me/blocks/{public_id}` | 要る | [blocks.md](blocks.md) |
| プランの一覧（07。男性だけ） | `/plans` | `GET /api/plans`・`GET /api/me`・`GET /api/me/purchases` | 要る | [paid-members.md](paid-members.md) |
| 購入（07。男性だけ） | `/plans/:planId` | `GET /api/plans`・`POST /api/me/purchases` | 要る | ― |

ログインしたあとの画面は、四角の枠の中に、画面（上）とタブ（下）を入れる。上の帯は置かない。

- タブは左から「検索・いいね・メッセージ・ホーム」。検索（`/search`）は 04 で作る（それまでは「準備中」）
- マッチだけの画面は作らない。マッチした相手は、メッセージのタブで見る。05 で、相手を押すとトーク画面に移る（03b のあいだは、相手のプロフィールに移る）
- ログアウトは、ホームのいちばん下に置く
- 枠の幅：スマホ（〜767px）は画面いっぱい、タブレット（768〜1023px）は 600px、PC（1024px〜）は 640px で真ん中に置く。どの幅でも同じ形にする
- ログイン・登録の画面は、真ん中に幅 480px の1列

## 機能要件と受け入れ条件

要件ごとに、前提・操作・期待結果を書く。

### FR-UI-001 ログインできる

- 前提：登録した会員
- 操作：`/login` でメールアドレスとパスワードを入れて送る
- 期待結果：
  - 自分のプロフィール（`/home`）に移る
  - 再読み込みしても、ログインしたまま

### FR-UI-002 ログインに失敗したら分かる

- 前提：なし
- 操作：違うパスワードで送る
- 期待結果：画面に「メールアドレスかパスワードが違います」と出て、`/login` のまま

### FR-UI-003 登録できる

- 前提：なし
- 操作：`/register` でメールアドレス・パスワード・ニックネーム・性別・生年月日を入れて送る
- 期待結果：「確認のメールを送りました」と出る（メールは Mailpit で見る）

### FR-UI-004 登録の入力の誤りが分かる

- 前提：なし
- 操作：18歳未満・同じメールアドレスで送る
- 期待結果：項目ごとに、何が違うかが出る（API の `422` の `errors`）

### FR-UI-005 自分のプロフィールを見て直せる

- 前提：ログインした
- 操作：`/home` で項目を直して保存する
- 期待結果：
  - 保存した値が表示される
  - 再読み込みしても残る

### FR-UI-006 相手のプロフィールを見られる

- 前提：
  - ログインした
  - 会員 B がいる
- 操作：`/users/<B の public_id>` を開く
- 期待結果：ニックネーム・年齢・都道府県・自己紹介・画像が出る

### FR-UI-007 いいねを送れる。マッチしたらその場で分かる

- 前提：相手が先に自分にいいねしている
- 操作：相手のプロフィールで「いいね」を押す
- 期待結果：
  - 「マッチしました」と出る
  - マッチしなければ「いいねしました」
  - ボタンは「いいね済み」になり、押せない

### FR-UI-008 もういいねした相手には送れない

- 前提：もういいねした
- 操作：相手のプロフィールを開く・押す
- 期待結果：
  - ボタンが「いいね済み」で押せない
  - 押せた場合も「もういいねしています」（`409`）と出る

### FR-UI-009 送ったいいねの一覧を見られる

- 前提：B・C に送り、B とはマッチした
- 操作：`/likes` を開く
- 期待結果：
  - 新しい順に C・B
  - B に「マッチ済み」の印
  - 名前を押すと相手のプロフィールに移る
- 変えたこと（M3。#184）：いいねのタブは届いたいいねにしたので、この一覧は設定の「送ったいいね」（`/likes/sent`）から開く

### FR-UI-010 マッチした相手を、メッセージのタブで見られる

- 前提：B とマッチした
- 操作：メッセージのタブ（`/messages`）を開く
- 期待結果：
  - B が出る
  - 押すと相手のプロフィールに移る（05 からはトーク画面）
  - 0人なら「まだマッチした相手はいません」

### FR-UI-011 ログインしていないと、ログインが要る画面は見られない

- 前提：ログインしていない
- 操作：`/home`・`/users/<public_id>`・`/likes`・`/messages` を開く
- 期待結果：
  - `/login` に移る
  - ログインしたら、開こうとした画面に戻る
  - 分かっている不具合：開こうとした画面を覚えず、ログインのあとはいつもホームへ移る（#257 の 2-2 の時点。`app/RequireAuth.tsx`）

### FR-UI-012 ログアウトできる

- 前提：ログインした
- 操作：ホームのいちばん下の「ログアウト」を押す
- 期待結果：
  - `/login` に移る
  - 戻るボタンで戻っても、ログインが要る画面は見られない

### FR-UI-013 読み込み中と失敗が分かる

- 前提：なし
- 操作：API の応答が遅い・失敗した（`500`・つながらない）
- 期待結果：
  - 読み込み中は「読み込み中…」が出る
  - 失敗したら「読み込めませんでした」と、もう一度試すボタンが出る
  - 真っ白にならない

### FR-UI-014 メールアドレスを確認していない会員に、確認を促す

- 前提：ログインしたが、確認していない
- 操作：ログインが要る画面を開く
- 期待結果：
  - 「メールアドレスを確認してください」と出る（API の `403`。FR-AUTH-021）
- 変えたこと（M2。#193）：枠のいちばん上に帯を出す形にした
  - 帯には、「メールアドレスが未確認です。確認すると、機能を使えるようになります」と、「もう一度送る」のボタンが出る（#263 で文を変え、設定へのリンクを外した）
  - 帯はどの画面にも出て、確認が済むと消える
- 変えたこと（#263。2026-11-21 に人が決めた）
  - ログインが要る画面の代わりに、「確認待ち」の画面を出す：「この機能は使えません」「メールアドレスを確認すると、使えるようになります」と、「確認のメールをもう一度送る」「確認した」「ログアウト」のボタン
  - 「確認した」を押すと、確認したかを読み直し、済んでいれば画面に戻る
  - 確認が要る API が 403（`code: "email_unverified"`）を返しても、画面はその応答を置かずに止まる（真っ白にならない）
  - タブのバーの数とお知らせは、確認していない会員には読まない

### FR-UI-015 検索のタブで、相手を2列のカードで見られる（04）

  - 一覧の画面に戻り、条件に合う相手に変わる

### FR-UI-100 ログインしたあとの画面で、ログインが切れたら、理由を付けてログインの画面に移る（#257）

- 補足：2026-11-21 に人が決めた。ログインしたあとの API が 401 を返したときの、画面の動き
- 前提：ログインが切れた（期限切れ）・アカウント停止された・退会した・強制退会になった
- 操作：ログインしたあとの画面を開く・押す
- 期待結果
  - ログインした自分の情報（前の検索の条件・前の JWT）を消し、ログインの画面へ移る
  - アプリを開いたとき（`GET /api/me` が 401）も同じ。アカウント停止なら、理由を付けて移る（2026-11-21 に足した。#259）
  - アカウント停止のとき：ログインの画面の題の下に「ログインはできません。このアカウントは停止されています」と出る（API の 401 の `code` が `account_suspended`）
  - ほかのとき：「ログインが切れました。もう一度ログインしてください」と出る（退会・強制退会は、理由を言わない。強制退会は、ログインし直すと FR-UI-099 の文が出る）
  - 何本の API が同時に 401 を返しても、移るのは1回
  - 自分でログアウトしたときは、どちらの文も出ない
  - パスワードを間違えたときの文と、同時には出ない
  - ログインの API・登録・確認・再設定の 401 では移らない（パスワードの誤りを画面に出すため）

## 成功基準・非機能要件・制約

- NFR-UI-001：幅 375px（スマホ）から 1280px までで、横にはみ出さず使える
- NFR-UI-002：入力にはラベルがあり、キーボードだけで送れる（`<label>`・`<button>`・Enter で送る）
- NFR-UI-008：読み上げ（スクリーンリーダー）で区別できる。モーダルの見出しは、モーダルごとに別のものを読む。押して選ぶ選択肢のまとまりは、項目の名前（体型・タバコ など）を読む。同じ名前のボタンが並ぶとき（名前を直す・消す）は、対象の名前を読む（#162）
- NFR-UI-003：API の送り先は1か所で決める（Vite の環境変数 `VITE_API_URL`。既定は `http://localhost:8000`。読むのは `src/api/client.ts` だけ）
- NFR-UI-004（03c）：OS で「視差効果を減らす」を選んだ人には、動きを止める（`prefers-reduced-motion: reduce`）。出る・消えるだけにする
- NFR-UI-005（03c）：押せる場所は 44×44px 以上。キーボードで動かしたとき、今いる場所に枠が出る（`:focus-visible`）。文字と地のコントラストは 4.5 以上（[design.md](../design.md)）
- NFR-UI-006（03c）：動かすのは `transform` と `opacity` だけ。Lighthouse（スマホ）の CLS を 0.1 以下に保つ。03c の前と後で、LCP・INP・CLS と `vite build` の大きさを測って残す
- NFR-UI-007（03c）：動きと部品のために、新しい依存（ライブラリ・Web フォント）を入れない。ブラウザの標準（`<dialog>`・View Transitions・CSS）と React 19 の標準（`useOptimistic` など）で作る
- 制約：React 19・TypeScript・Vite・React Router。Node は mise の版（26.13.0）。置き場所は `frontend/client/`。OpenAPI は使わず、型は `docs/api/` に合わせて手で書く（D-006）
- 制約：CSS は、レガシー版はひな形の `index.css`・`App.css` に書く。改善版は部品ごとの CSS Modules と、色・余白・文字の大きさを CSS の変数（カスタムプロパティ）にまとめる

## 前提と要確認事項

- 前提：レガシー版は、ログインの JWT を sessionStorage に置き、`Authorization: Bearer` で送る（D-014）。改善版は HttpOnly の Cookie
- 前提：レガシー版は、1画面に1つの大きな部品で書き、テスト・画面の CI を持たない（D-018）。改善版で Vitest・Biome（`npm run lint:rules`）・型の検査（`npm run build`）を CI に入れる
- 前提：API の CORS は、Laravel の標準の設定（`api/*` をどこからでも呼べる）で、Vite の開発サーバー（`http://localhost:5173`）から呼べるかを確かめる。呼べなければ、API の子 Issue で直す
- 前提（M2。#193 で変えた）：メールアドレスの確認のリンクは、画面（`/verify/<確認用の文字>`）を開く。画面が、今の API（`GET /api/email-verifications/{token}`）を呼んで、結果を出す（FR-UI-085）。前は、リンクが API をそのまま開き、JSON が出ていた
- 前提：見た目（色・余白・文字・角丸・影・動き）と部品の見た目は、[design.md](../design.md) を正とする（03c で決めた）
- 前提：03c のレガシー版は、見た目と動きだけを足す。失敗・`401`・連打・`422` の扱い（FR-UI-004・013 など）は直さず、改善する段階で直す
- 決まった（M3。#187）：いいねの応答に `room_id` を足し、その相手のトーク画面に直接移るようにした（FR-UI-069）。前の記述：FR-UI-028 の「メッセージを送る」で、そのトーク画面に直接移るには、いいねの応答にルームの `public_id` が要る。今の応答にはないので、03c は `/messages` に移る

## スコープ外

- 会員を探す一覧・ページ送り（04）。それまでは、相手を URL で開く
- 画像のアップロード（プロフィール画像は、シードのデモ画像のパスを選ぶ）
- E2E のテスト（道具は改善する段階で決める）
- ダークモード・Web フォント・音・振動（03c でも入れない）
