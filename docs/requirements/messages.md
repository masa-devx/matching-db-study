# 要件：メッセージ

状態：確定
元資料：ユーザーとの会話で決めたこと（2026-11-13）。[product.md](../product.md) の不変条件 6・8。[matches.md](matches.md)・[screens.md](screens.md)・D-022
一歩：05（ブロックした相手を出さないのは 06、Firestore と比べるのは 05c）
目的：[product.md](../product.md) の「メッセージ」

このファイルは、マッチした相手とメッセージを送り合う・トークの一覧で相手ごとの最新の1件と未読の数を見る、を長く表す。レガシー版も改善版も、この要件を守る（レガシー版で守れていないものは、改善する段階のテストの対象になる）。要件 ID は `FR-MSG-` で始める。画面の要件は [screens.md](screens.md) に `FR-UI-` で書き足す。

## 目的と対象

マッチした2人が、文字のメッセージを送り合えるようにする。メッセージのタブでは、マッチした相手ごとに最新の1件と未読の数を見て、どの相手と話すかを選べるようにする。

## ユーザーストーリーと優先度

- 会員として、マッチした相手に文字のメッセージを送りたい
- 会員として、相手から届いたメッセージを、画面を開いたまま数秒のうちに見たい
- 会員として、メッセージのタブで、相手ごとの最新の1件と、まだ読んでいない数を見たい
- 会員として、トーク画面を上までさかのぼって、古いメッセージを読みたい

| 優先度 | 範囲 |
| --- | --- |
| 必須（05） | マッチした相手に送る・トークの履歴（新しい50件と、古い続き）・新しいメッセージを数秒ごとに取りに行く・トークの一覧（最新の1件・未読の数）・開いたら読んだことにする |
| 次の段階 | ブロックした・された相手を一覧とトークに出さない（06）・有料会員だけが送れる（07）・Firestore で同じものを作る（05c）・管理者がメッセージを見る（12） |
| 対象外 | 写真・スタンプ・ファイル・相手に見せる「既読」の印・送ったメッセージの取り消しと編集・グループのトーク・通知（メール・プッシュ）・WebSocket で押し出す |

## 機能要件と受け入れ条件

トークルームは、マッチしたときに1つ作る（マッチ1つにルーム1つ）。マッチ（関係）とトークルーム（やり取りの場所）は別のものとして扱う（D-023）。URL でルームを指す ID は、トークルームの `public_id`（UUID。D-022）にする。

| ID | 機能要件 | 前提 | 操作 | 期待結果 |
| --- | --- | --- | --- | --- |
| FR-MSG-001 | マッチした相手にメッセージを送れる | A と B がマッチした | A が A と B のルームに「こんにちは」を送る | `201`。送ったメッセージ（ID・本文・送った人・送った日時）を返す。B のトークにも出る |
| FR-MSG-002 | マッチしていない相手には送れない（不変条件 6） | A と C はマッチしていない | A が、A と C のルームがあるつもりで送る・ない ID のルームに送る | `404`。メッセージは増えない |
| FR-MSG-003 | 他人のルームは見られず、送れない（不変条件 8） | B と C がマッチした。A はどちらともマッチしていない | A が B と C のルームを見る・送る | `404`（ルームがあることも分からない）。メッセージは増えない |
| FR-MSG-004 | 本文は1〜1000文字 | ― | 空・空白だけ・1001文字を送る | `422`。どこが違うかを返す。1000文字ちょうどは `201` |
| FR-MSG-005 | トークの履歴を、新しい50件ずつ読める | A と B のルームに 120件ある | A がルームを開き、上までさかのぼって続きを2回読む | 50・50・20件。画面では古い順に並ぶ。最後に「もうない」と分かる |
| FR-MSG-006 | さかのぼるあいだに新しいメッセージが来ても、重ならず・抜けない | A が新しい50件を読んだあと、B が送った | A が古い続きを読む | 1回目に出たメッセージは、続きに出ない。古い続きから抜けるものはない |
| FR-MSG-007 | 新しいメッセージを、数秒ごとに取りに行ける | A がルームを開いている | B が送る | 5秒ほどのうちに A の画面に出る。取りに行くたびに、前に受け取ったものはもう返さない（改善版）|
| FR-MSG-008 | トークの一覧に、相手ごとの最新の1件が出る | A は B・C・D とマッチした。B と C とはやり取りがあり、D とはまだない | A がメッセージのタブを開く | `200`。最新のメッセージ（なければマッチした日時）の新しい順。相手ごとに、相手の会員の ID（`public_id`）・ニックネーム・年齢・画像・ルームの ID・最新の1件の本文と日時（D は空）・未読の数 |
| FR-MSG-009 | 未読の数が分かる | B が A に3件送り、A はまだそのルームを開いていない | A がトークの一覧を見る | B の未読が 3。自分が送ったものは数えない |
| FR-MSG-010 | ルームを開くと、読んだことになる | B の未読が 3 | A が B とのルームを開き、トークの一覧に戻る | B の未読が 0。ルームを開いているあいだに届いたものも、読んだことになる |
| FR-MSG-011 | 相手に「既読」は見せない | A が B のメッセージを読んだ | B がトークを見る | B には、A が読んだかは出ない |
| FR-MSG-012 | ログインしていないと使えない | ― | トークンなしで一覧・履歴・送る | `401` |
| FR-MSG-013 | メールアドレスを確認していないと使えない（不変条件 2） | A は確認していない | 一覧・履歴・送る | `403`（FR-AUTH-021） |
| FR-MSG-014 | 会員が消えたら、その会員とのルームとメッセージも消える（ルームを閉じて残すかは 06 の退会で決め直す） | A と B がやり取りした | B を消す（DB で直接。退会は 06） | A の一覧に B は出ない。A と B のメッセージは残らない |

## 成功基準・非機能要件・制約

- NFR-MSG-001：トークの一覧を見るときの SQL は、相手の数が増えても本数が増えない（3本以内。相手ごとの最新の1件と未読の数で N+1 にしない）
- NFR-MSG-002：ルームの新しい50件・古い続き・新しいものだけを取るとき、そのルームのメッセージを全部読まない（メッセージが増えても読む量が増えない）
- NFR-MSG-003：数秒ごとに取りに行くとき、新しいメッセージがなければ、返すものも読むものもほとんどない
- 測るときの試しのデータ：マッチ 1000組・メッセージ 10万件（多い組と少ない組を混ぜる）。速さの目標は決めず、記録する

## 前提と要確認事項

- 前提：表は `talk_rooms`（やり取りの場所。`public_id`・マッチを指す `match_id`）・`talk_room_members`（ルームの中の一人ひとりの状態。どこまで読んだか）・`messages`（やり取りの中身）の3つ（D-023）。`user_matches` は 03 のまま「お互いにいいねした関係」を表す。ブロック（`blocks`）・通報（`reports`）は 06 で別の表にする
- 前提：マッチしたとき（いいねを送った API の中）に、トークルームと2人の `talk_room_members` を作る。03 より前からあるマッチのルームは、シーダーで作る
- 前提：レガシー版の3つの表は、主キー・UNIQUE・外部キーを持ち、インデックスは足さない（PostgreSQL は外部キーの列にインデックスを自動で作らない）。03 の `user_matches`（同じ組が2行になることがある）の上にそのまま作り、組が2行あるときにどうなるかを測る
- 前提：レガシー版は、だれが使うかをコントローラの中で JWT を読んで決める（6か所目）。新しいものを取りに行くのは、画面が5秒ごとに履歴を全部読み直す形にする。改善版で「最後に受け取ったものより新しいものだけ」に直す
- 前提：レガシー版の続きは OFFSET、改善版はカーソル（04 と同じ。カーソルにも連番の ID を出さない）
- 前提：メッセージのタブ（`/messages`）は 03b の「マッチした相手の一覧」を、トークの一覧に置き換える。相手を押すとトーク画面（`/messages/:roomId`）に移る（FR-UI-010 の「05 からはトーク画面」）
- 要確認：なし

## スコープ外

- 写真・スタンプ・ファイル・リンクのプレビュー
- 相手に見せる「既読」の印・入力中の表示
- 送ったメッセージの取り消し・編集・消す
- 通知（メール・プッシュ）・WebSocket で押し出す（リアルタイムは 05c の Firestore と比べる）
- ブロック（06）・有料会員だけが送れる（07）
