# 要件：検索と一覧

状態：確定
元資料：ユーザーとの会話で決めたこと（2026-11-12）。[product.md](../product.md) の「検索と一覧」・不変条件 2・7。[members.md](members.md)・[likes.md](likes.md)・[screens.md](screens.md)
一歩：04（ブロックした・された相手を除くのは 06、有料会員の表示は 07）
目的：[product.md](../product.md) の「検索と一覧」

このファイルは、会員を探す・一覧で見る、を長く表す。レガシー版も改善版も、この要件を守る（レガシー版で守れていないものは、改善する段階のテストの対象になる）。要件 ID は `FR-SEARCH-` で始める。画面の要件は [screens.md](screens.md) に `FR-UI-` で書き足す。

## 目的と対象

会員が、相手のプロフィールの項目（年齢の幅・都道府県・身長と、#153 で足した体型・お仕事・年収・タバコ・お酒・結婚歴）で絞り込み、有料の機能（こだわり条件：最終ログイン・登録して間もない会員・フリーワード・登録が新しい順。#150）も使って、最近ログインした相手から順に見て、いいねを送る相手を見つけられるようにする。03b までは、相手を URL（`/users/<public_id>`）で開くしかなかった。

会員は 2万人を目安にする。速さの目標は置かず、実行計画・SQL の本数・かかった時間・画面の表示速度は、記録だけする（改善する段階で、前と後を比べるため）。

## ユーザーストーリーと優先度

- 会員として、条件を選んで相手を探し、気になった人のプロフィールを開きたい
- 会員として、もういいねした相手や、まだ使い始めていない会員は、探すときに見たくない
- 会員として、一覧を下まで見たら、続きが自然に出てきてほしい

優先度ごとの範囲：

- 必須（04）
  - 検索の API（絞り込み・並び・続き）
  - 最終ログインを残す
  - 検索の画面（検索のタブ・2列のカード・絞り込み・下までスクロールで続き）
  - 2万人の試しのデータ
- 次の段階：ブロックした・された相手を除く（06）・有料会員の印（07）
- 対象外：おすすめの順（並び方を選ぶ・キーワードで探す・有料の条件は #150 で作った。条件を保存するのは 04b で作った：[saved-searches.md](saved-searches.md)）

#### FR-SEARCH-001 条件で絞り込める

- 前提：ログインした会員
- 操作：性別・年齢の幅・都道府県（1つ以上）・身長の幅を送る
- 期待結果
  - `200`
  - すべての条件に合う会員だけを返す
  - 1件は、会員の ID（`public_id`。UUID。ユーザー詳細へのリンクに使う）・ニックネーム・年齢・都道府県・身長・画像（メールアドレス・生年月日は返さない）

#### FR-SEARCH-002 性別を選ばなければ、自分と違う性別を返す

- 前提：自分の性別が女性
- 操作：性別を送らずに探す
- 期待結果：男性だけを返す。性別を送れば、その性別を返す

#### FR-SEARCH-003 自分は出ない

- 前提：なし
- 操作：自分に合う条件で探す
- 期待結果：自分は結果に出ない

#### FR-SEARCH-004 もういいねした相手は出ない

- 前提：B にいいねした
- 操作：B に合う条件で探す
- 期待結果：B は出ない。いいねしていない C は出る

#### FR-SEARCH-005 メールアドレスを確認していない会員は出ない

- 前提：D は確認していない
- 操作：D に合う条件で探す
- 期待結果：D は出ない

#### FR-SEARCH-006 並び替えを選ばないとき（「ログインが新しい順」を選んだときも）、最終ログインが新しい順に並ぶ

- 前提：3人が違う時刻にログインした
- 操作：探す
- 期待結果：新しい順。同じ時刻なら、会員の `public_id` の大きい順（並びがいつも同じになる）

#### FR-SEARCH-007 20件ずつ、続きを読める

- 前提：合う会員が 45人
- 操作：続きを2回読む
- 期待結果：20・20・5件。最後に「もうない」と分かる

#### FR-SEARCH-008 続きを読むあいだに、ほかの会員がログインしても、重ならず・抜けない

- 前提：1回目を読んだあと、まだ見ていない会員がログインした
- 操作：続きを読む
- 期待結果：1回目に出た会員は2回目に出ない。まだ見ていない会員が抜けない

#### FR-SEARCH-009 条件の誤りが分かる

- 前提：なし
- 操作：年齢 17・年齢の下が上より大きい・身長 300・都道府県 48 を送る
- 期待結果
  - `422`
  - どの条件が違うかを返す（年齢は 18〜99、身長は 120〜220、都道府県は 1〜47）

#### FR-SEARCH-010 ログインしていないと使えない

- 前提：ログインしていない
- 操作：探す
- 期待結果：`401`

#### FR-SEARCH-011 ログインするたびに、最終ログインが新しくなる

- 前提：なし
- 操作：ログインする
- 期待結果：会員の最終ログインの時刻が、そのときになる

#### FR-SEARCH-012 最終ログインで絞り込める（有料の機能。#150）

- 前提：有料の機能を使える会員
- 操作：「24時間以内・3日以内・1週間以内」のどれかを付けて探す
- 期待結果
  - `200`
  - その時間の中にログインした会員を返す
  - 登録したばかりで、まだ一度もログインしていない会員は、登録した日時を最終ログインの代わりに見て出す（2026-11-17 に人が決めた。#162）

#### FR-SEARCH-013 登録して間もない会員だけに絞り込める（有料の機能。#150）

- 前提：有料の機能を使える会員
- 操作：「登録して1週間以内の会員だけ」を付けて探す
- 期待結果：`200`。登録して1週間以内の会員だけを返す

#### FR-SEARCH-014 フリーワードで絞り込める（有料の機能。#150）

- 前提：有料の機能を使える会員
- 操作：言葉（1〜50文字）を付けて探す
- 期待結果
  - `200`
  - 自己紹介かニックネームに、その言葉が入っている会員だけを返す
  - `%` や `_` は、ただの文字として探す（全員に当たらない）
  - 英字の大文字と小文字は区別しない
  - 51文字以上は `422`

#### FR-SEARCH-015 登録が新しい順に並べられる（有料の機能。#150）

- 前提：有料の機能を使える会員
- 操作：並び替えに「登録が新しい順」を選んで探す
- 期待結果
  - `200`
  - 登録が新しい順
  - 同じ時刻なら、会員の `public_id` の大きい順
  - 続きを読んでも、重ならず・抜けない（FR-SEARCH-008）

#### FR-SEARCH-016 有料の機能は、男性の無料の会員は使えない（#150）

- 前提：男性の無料の会員
- 操作：FR-SEARCH-012〜015 のどれかを付けて探す
- 期待結果
  - `403`（`paid_required`。FR-PAID-009）
  - 身長・年齢・都道府県だけなら `200`

#### FR-SEARCH-017 プロフィールの6項目で絞り込める（無料。#153）

- 前提：ログインした会員
- 操作：体型・お仕事・タバコ・お酒・結婚歴のそれぞれで、選択肢を1つ以上選び、年収は幅を選んで探す
- 期待結果
  - `200`
  - 同じ項目の中は「どれか」、項目どうしは「すべて」に合う会員だけを返す（例：年収が 500〜700万円か 700〜1000万円で、タバコが吸わない）
  - 年収だけは、区分をいくつか選ぶのではなく、「◯◯万円 から ◯◯万円」の幅で選ぶ（下限・上限は 300・500・700・1000万円か、なし。2026-11-17 に人が決めた。#162）
  - 幅の中に入る区分の会員を返す（例：500万円〜1000万円なら、500〜700万円と 700〜1000万円）

#### FR-SEARCH-018 条件を付けた項目に答えていない会員は出ない（#153）

- 前提：B は年収に答えていない
- 操作：年収の条件を付けて探す
- 期待結果：B は出ない。年収の条件を外せば出る

#### FR-SEARCH-019 選択肢にない値は誤りになる（#153）

- 前提：なし
- 操作：年収に「1億円」を送る・配列でなく文字で送る
- 期待結果：`422`。どの条件が違うかを返す

#### FR-SEARCH-020 スキップした相手は出ない（M3。#184）

- 前提：A が B をスキップした
- 操作：A が、B に合う条件で探す
- 期待結果
  - B は出ない
  - スキップを元に戻すと、また出る
  - B が A を探すときは、A は出る（スキップは、した側からだけ隠す。FR-LIKE-012）

#### FR-UI-015 検索のタブで、相手を2列のカードで見られる

- 前提：ログインした
- 操作：検索のタブ（`/search`）を開く
- 期待結果：写真を大きく、ニックネーム・年齢・都道府県を重ねたカードが2列に並ぶ。押すと相手のプロフィールに移る

#### FR-UI-016 絞り込みを選べる

- 前提：なし
- 操作：絞り込みを開き、条件を選んで「この条件で探す」を押す
- 期待結果：条件に合う相手に変わる。選んだ条件は、相手のプロフィールから戻っても残る

#### FR-UI-017 下までスクロールすると、続きが出る

- 前提：合う相手が 45人
- 操作：いちばん下までスクロールする
- 期待結果：続きの20人が足される。最後まで出たら「これで全員です」

#### FR-UI-018 0人なら分かる

- 前提：なし
- 操作：だれにも合わない条件で探す
- 期待結果：「条件に合う相手がいません」と、条件を変えるボタン

## 成功基準・非機能要件・制約

- NFR-SEARCH-001：1回の検索で流れる SQL は、件数が増えても本数が増えない（3本以内）
- 速さ（API の時間・実行計画・Lighthouse の LCP と CLS）は、目標を置かない。会員 2万人で、1ページ目と深い続き（5,000件目のあたり）を測って、記録だけする
- 制約：試しの会員 2万人は、シーダーで作る（`users`・`profiles`。性別・生年月日・都道府県・身長はばらつかせる）。開発用の DB にだけ入れ、テスト用の DB には入れない

## 前提と要確認事項

- 前提：最終ログインは、`users` に時刻の列を足して、ログインのたびに書き換える
- 前提：年齢は、生年月日から、その日の時点で数える（誕生日の前なら1つ少ない）
- 前提
  - レガシー版は、続きを OFFSET（`?page=2`）で読み、改善版で「最後に見た会員の最終ログインと `public_id`」から続ける形（カーソル）に直して比べる
  - カーソルにも連番の ID を出さない（D-022）
  - FR-SEARCH-008 はレガシー版では守れない見込み
- 前提：レガシー版の生年月日・身長は文字の列（01 のまま）。文字で比べる問題も、レガシー版で測る
- 要確認：なし
