# 要件：会員の側のメンテナンス

状態：確定
元資料：ユーザーとの会話で決めたこと（2026-11-20）。認証をセッションに移すリリース（#246・D-027）で使う
一歩：改善版（サイクル 01。#246 の子のチケット）
目的：リリースや DB の作業のあいだ、会員の側だけを止め、作業を終えたあとに全員をログインし直させる

このファイルは、会員の側（`backend/client` と会員の画面）のメンテナンスを長く表す。管理画面（`backend/admin`）は止めない。

## 目的と対象

- 認証の切り替えのようなリリースでは、切り替えの瞬間に、古い状態（古いトークン・古い画面）の会員がいると、画面が止まったり、戻したときに古いトークンがまた使えたりする
- 作業のあいだは会員の側を止め、入れたときに全員をログアウトさせれば、その瞬間をなくせる
- 作業の確かめ（ログイン・CSRF・エラーの扱い）は、メンテナンス中に、開発者だけが本物の画面で行う

## ユーザーストーリーと優先度

- 開発者として、リリースのあいだ会員の側を止め、全員をログアウトさせて、確かめが済んでから開けたい（必須）
- 会員として、メンテナンス中は、何が起きているかが分かる画面を見たい（必須）
- 運営として、メンテナンス中も管理画面を使いたい（必須）

## 機能要件と受け入れ条件

| ID | 機能要件 |
| --- | --- |
| FR-MAINT-001 | 開発者が、コマンドで会員の側をメンテナンスにできる |
| FR-MAINT-002 | メンテナンスに入れたとき、全員をログアウトさせる |
| FR-MAINT-003 | メンテナンス中に、確かめる開発者だけが通れる |
| FR-MAINT-004 | メンテナンス中も、動いているかの確かめ（`GET /up`）は止まらない |
| FR-MAINT-005 | 管理画面は止めない |
| FR-MAINT-006 | 会員の画面は、メンテナンス中であることを表示する |
| FR-MAINT-007 | 開発者が、コマンドでメンテナンスを解ける |

### FR-MAINT-001 開発者が、コマンドで会員の側をメンテナンスにできる

- 前提：会員の側が動いている
- 操作：開発者が `php artisan down`（抜け道を付けるときは `--with-secret`）を流す
- 期待結果：会員の API は、どれも `503` `{"message": "ただいまメンテナンス中です"}` を返す

### FR-MAINT-002 メンテナンスに入れたとき、全員をログアウトさせる

- 前提：会員 A がログインしている
- 操作：開発者がメンテナンスに入れる
- 期待結果
  - 表 `sessions` の行が全部消える（ログインの前の行も含む）
  - メンテナンスを解いたあと、A の前の Cookie で呼ぶと `401`

### FR-MAINT-003 メンテナンス中に、確かめる開発者だけが通れる

- 前提：`--with-secret` で入れた。コマンドが抜け道の URL を出した
- 操作：開発者のブラウザで、抜け道の URL を一度開く
- 期待結果
  - そのブラウザにだけ確かめ用の Cookie が付き、会員の画面と API を、いつもどおり使える（ログインもできる）
  - 開いていないブラウザは `503`

### FR-MAINT-004 メンテナンス中も、動いているかの確かめ（`GET /up`）は止まらない

- 前提：メンテナンス中
- 操作：`GET /up` を呼ぶ
- 期待結果：`200`（Laravel がもとから、メンテナンスの外にしている）
- 会員の側の動いているかの確かめは、`GET /up` の1つだけ。自分で作った `GET /api/health` は消した（消すことは 2026-11-21 に人が決めた）
  - 理由：監視からも CI からも呼んでいなかった（2026-11-21 に確かめた）。返していた DB の名前とマイグレーションの数は、外から見えなくてよい情報だった
- 弱いところ：`GET /up` は DB につながるかを見ないので、DB が落ちても `200` を返す（`docs/api/00-health.md` の「弱いところ」）
- 監視を入れるとき（#287）に、DB の確かめを足すかと、メンテナンス中の `GET /up` の扱いを、一緒に決め直す
- 前の形：`GET /api/health` を、ほかの会員の API と同じに `503` で止めていた（2026-11-21 に決めた形。消したので、なくなった）

### FR-MAINT-005 管理画面は止めない

- 前提：会員の側がメンテナンス中
- 操作：管理者が管理画面を使う
- 期待結果：いつもどおり使える

### FR-MAINT-006 会員の画面は、メンテナンス中であることを表示する

- 前提：メンテナンス中
- 操作：会員が画面を開く・操作する
- 期待結果：「ただいまメンテナンス中です」の画面が出る。JSON の文字は出ない。ログインの画面には移らない

### FR-MAINT-007 開発者が、コマンドでメンテナンスを解ける

- 前提：メンテナンス中
- 操作：開発者が `php artisan up` を流す
- 期待結果：会員の API が、いつもどおりに戻る。会員は、ログインし直してから使う

## 成功基準・非機能要件・制約

- NFR-MAINT-001
  - 抜け道の秘密の文字は、リポジトリ・チケット・PR・ログに書かない
  - コマンドの履歴に残さないため、自分で決めた文字（`--secret`）ではなく、Laravel に作らせる（`--with-secret`）
  - 例外：抜け道の URL を開いた行は、PHP の組み込みのサーバーのアクセスのログ（`docker compose logs app`）に残る。手元だけで動かし、解けば文字が使えなくなり、`--with-secret` で毎回変わるので、残ってよいとする。ログを貼るときは、その行を消す（2026-11-21 に人が決めた）
- NFR-MAINT-002
  - メンテナンスの状態は、Laravel の標準の置き場（ファイル。設定の `maintenance.driver` は `file`）に置く
  - 会員の側のサーバーを2台以上にするときは、共通の置き場（`cache`）に替える
  - 替えるときは、置き場のストアが `database` だと、メンテナンス中かを読むたびに SQL が流れ、SQL のログ（`db.summary` の `path`）に抜け道の文字が出る。替えるチケットで確かめる
- 入れる・解くのは、開発者だけ（サーバーでコマンドを流せる人）。管理画面にボタンは作らない

## 前提と要確認事項

- 前提：強制ログアウト（FR-MAINT-002）が効くのは、会員の認証をセッションに切り替えたあと（#246 の4）。それより前は、会員は JWT を持っているので、メンテナンスを解くと前のトークンがそのまま使える
- 前提
  - 抜け道の Cookie は API（`localhost:8000`）に付く
  - 画面を通して抜け道を使えるのは、画面が Cookie を送るようになってから（#246 の4 の `credentials: 'include'`）
  - それより前は、curl で確かめる
- 前提：表 `sessions` には、会員のセッションだけを入れる。管理画面をセッションでのログインに移すときは、別の表にする（FR-MAINT-005。メンテナンスで管理者まで追い出さないため。2026-11-21 に人が決めた）
- 前提：FR-MAINT-005（管理画面は止めない）は、テストでなく、手元の curl で確かめる（別のアプリで、置き場も別なので、今の作りでは止まりようがないため。2026-11-21 に人が決めた）
- 分かっている不具合（2026-11-21 に人が決めた）
  - 画面がポーリング（トークの画面は5秒ごと）で 503 を受けると、画面ごとメンテナンスの画面に入れ替わり、書きかけの文が消える。メンテナンス中は送れないので、受け入れる
  - Firestore 版のトークは API を通らないので、メンテナンスに入ってから、タブのバーの数え直し（30秒ごと）が 503 を受けるまで送れる。範囲の外とする
- 要確認：なし
