# 要件：保存した検索条件と、検索の画面の URL

状態：確定
元資料：ユーザーとの会話で決めたこと（2026-11-17）。[search.md](search.md)・[paid-members.md](paid-members.md)・[screens.md](screens.md) の FR-UI-016
一歩：04b（検索 04 の続き。08 は「決済の通知」で決まっているので使わない）
目的：[product.md](../product.md) の「検索」

このファイルは、検索の条件に名前を付けて保存する・保存した条件で検索する・直す・消す、と、検索の画面の URL に今の条件を出す、を長く表す。レガシー版も改善版も、この要件を守る（レガシー版で守れていないものは、改善する段階のテストの対象になる）。要件 ID は `FR-SAVED-` で始める。画面の要件は [screens.md](screens.md) に `FR-UI-` で書き足す。

## 目的と対象

今の検索は、条件をブラウザのタブの中（sessionStorage）にだけ置く。タブを閉じる・ログインし直す・別の端末で開く、のどれでも条件が消え、会員は毎回同じ条件を入れ直している。条件に名前を付けてサーバーに保存し、どの端末でも選ぶだけで同じ条件で検索できるようにする。あわせて、今の条件を検索の画面の URL（`/search?age_min=20…`）に出し、再読み込み・ブックマーク・ブラウザの「戻る」で同じ条件に戻れるようにする（2026-11-17 に、同じ一歩で作ると決めた）。

## ユーザーストーリーと優先度

- 会員として、よく使う検索の条件に名前を付けて保存し、次からは選ぶだけで検索したい
- 会員として、条件の違うパターン（例：「東京・20代」「関西・30代」）をいくつか持ち、切り替えて検索したい
- 会員として、別の端末でログインしても、保存した条件を使いたい
- 運営として、有料の機能（身長の条件）を、保存した条件を通しても無料の会員に使わせたくない

| 優先度 | 範囲 |
| --- | --- |
| 必須（04b） | 保存する（名前と条件）・一覧を見る・名前と条件を直す・消す・保存した条件で検索する（画面）・1人5件まで・有料の条件の制限・検索の画面の URL に今の条件を出す（画面の要件は [screens.md](screens.md) の FR-UI-041〜048） |
| 次の段階 | 検索の条件の項目を増やす |
| 対象外 | 条件に合う新しい会員の通知・「いつも使う」条件を自動で当てる・最後に使った条件を自動で当てる・検索の履歴 |

## 機能要件と受け入れ条件

保存する条件の中身は、検索（FR-SEARCH-001）で送れる項目と同じ：性別・年齢の幅・都道府県（1つ以上）・身長の幅。値の範囲も検索と同じ（FR-SEARCH-009）。検索の項目が増えたら、保存できる項目も同じだけ増える。

有料の条件（今は身長の幅）を使えるかどうかは、検索と同じ決まりで決める（FR-PAID-005・009・011：男性の無料の会員だけが使えない。期限が過ぎたら無料に戻る）。

| ID | 機能要件 | 前提 | 操作 | 期待結果 |
| --- | --- | --- | --- | --- |
| FR-SAVED-001 | 条件に名前を付けて保存できる | ログインした会員 A | 名前「東京・20代」と、年齢 20〜29・都道府県「東京都」を保存する | `201`。A の保存した検索条件が1つできる。応答に、その ID（`public_id`。UUID）・名前・条件が入る |
| FR-SAVED-002 | 自分の保存した検索条件の一覧を見られる | A が2つ保存した | A が一覧を見る | `200`。保存した順（古い順）に2つ。1件は、ID・名前・条件・今の自分が使えるかどうか |
| FR-SAVED-003 | 名前と条件を直せる | A が「東京・20代」を保存した | 名前を「東京・30代」、年齢を 30〜39 に直す | `200`。直した値が一覧に出る。件数は変わらない |
| FR-SAVED-004 | 消せる | A が2つ保存した | 1つを消す | `204`。一覧は1つになる。もう一度消すと `404` |
| FR-SAVED-005 | 1人5件まで | A が5つ保存した | 6つ目を保存する | `422`（上限）。5つのまま。同時に何回送っても、6つ目以上は入らない。1つ消せば、また1つ保存できる |
| FR-SAVED-006 | 他人の保存した検索条件は、見られない・直せない・消せない | B が1つ保存した | A が、B の条件の ID で直す・消す。A が一覧を見る | 直す・消すは `404`。B の条件は変わらない。A の一覧に B の条件は出ない |
| FR-SAVED-007 | 条件の誤りが分かる | ― | 年齢 17・年齢の下が上より大きい・身長 300・都道府県 48・知らない項目を入れて保存する | `422`。どの条件が違うかを返す。保存されない（FR-SEARCH-009 と同じ範囲） |
| FR-SAVED-008 | 名前の誤りが分かる | ― | 名前なし・31文字以上で保存する | `422`。保存されない（名前は1〜30文字） |

## 成功基準・非機能要件・制約

- 成功基準：会員が、別の端末でログインして、保存した条件を選ぶだけで（条件を入れ直さずに）検索できる
- NFR-SAVED-001：上限（5件）は、同時に保存しても破れない（数えてから入れるまでのあいだに、ほかの保存が入らない）
- NFR-SAVED-002：条件の値の範囲と、有料の条件を使えるかの判断は、検索と保存で同じものを使う（決まりをコピーして増やさない。NFR-PAID-004）
- NFR-SAVED-003：検索の項目を1つ足すとき、保存した検索条件の表の作りを変えなくてよい
- NFR-SAVED-004：一覧を読む SQL は、件数に関係なく2本以内（自分を読む・条件を読む）

## 前提と要確認事項

- 前提：検索そのもの（`GET /api/users`）は変えない。画面が、選んだ条件を検索のクエリにして送る
- 前提：検索のタブを開いたとき、保存した条件を自動では当てない。会員が選ぶ
- 前提：今の条件の正は、検索の画面の URL のクエリにする。URL にクエリがないとき（タブのリンクから `/search` を開いたとき）だけ、タブの中で覚えた最後の条件（FR-UI-016。sessionStorage）に戻す
- 前提：URL のクエリの名前は、検索の API のクエリと同じにする（`gender`・`age_min`・`age_max`・`prefecture`（くり返す）・`height_min`・`height_max`）。ページの番号は URL に出さない
- 前提：有料でも無料でも、上限は5件（件数では分けない。分けるのは、使える項目だけ）
- 前提：条件の中身は、表の1つの列（`jsonb`）にまとめて持つ（NFR-SAVED-003。持ち方の比較は解説の「選択肢」）
- 前提：レガシー版は、設計を考えずに「とりあえず使える」形で作り、次の4つを測る
  - 上限を、数えてから入れるだけで止める（ロックなし）→ 同時に送ると6件目が入る（FR-SAVED-005・NFR-SAVED-001）
  - 送られた条件を、確かめずにそのまま入れる → 年齢 17・身長 300・知らない項目が保存される（FR-SAVED-007）
  - 有料かどうかの確かめを、検索のコントローラーからコピーする（`is_paid` だけを見る）→ 期限が過ぎた会員が、身長の入った条件を保存でき、検索もできる（FR-SAVED-009・010。FR-PAID-005）
  - 持ち主を確かめずに、ID だけで直す・消す → 他人の条件を変えられる・消せる（FR-SAVED-006）
- 前提：Firestore 版（05c）には足さない
- 前提：同じ会員が、同じ名前の条件を2つ持てる（名前は会員が見分けるためのもので、ID は別にあるため）
- 前提：条件を1つも入れずに（名前だけで）保存できる（「条件なし」も1つのパターン）
- 要確認：なし

## スコープ外

- 条件に合う新しい会員の通知
- 「いつも使う」条件・最後に使った条件を、検索のタブを開いたときに自動で当てる
- 検索の履歴
