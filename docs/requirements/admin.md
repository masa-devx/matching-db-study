# 要件：管理画面

状態：確定
元資料：ユーザーとの会話で決めたこと（2026-11-13）。[product.md](../product.md) の不変条件 8（管理者を除く）・用語「管理者」。[members.md](members.md)・[messages.md](messages.md)・[paid-members.md](paid-members.md)・[withdrawal.md](withdrawal.md)
一歩：12（M3 追加機能）
目的：[product.md](../product.md) の「管理者」

このファイルは、運営の人（管理者）が、会員・メッセージ・有料会員と売上を見て、数をグラフで確かめ、会員の利用を止められる管理画面を長く表す。レガシー版も改善版も、この要件を守る。要件 ID は `FR-ADMIN-` で始める。

## 目的と対象

運営の人が、ふだんの数（登録・マッチ・メッセージ・有料会員・売上）をグラフで見て、問題のある会員を調べ、利用を止められるようにする。会員の画面と API とは別のもの（`admin/` の中の別の Laravel と別の React）として作り、会員の側を変えても管理画面が壊れにくく、管理画面を足しても会員の側に手を入れずに済むようにする。サイドバーの項目（ドメイン）は、あとから足せる形にする。

## ユーザーストーリーと優先度

- 管理者として、ダッシュボードで、登録・マッチ・メッセージ・有料会員・売上の数と、日ごと・月ごとの移り変わりをグラフで見たい
- 管理者として、会員をメールアドレス・ニックネーム・状態で探し、詳細（プロフィール・いいね・マッチ・購入・ブロック）を見て、利用を止めたい
- 管理者として、メッセージの一覧を見て、問題のあるやり取りを調べたい
- 管理者として、購入の一覧と月ごとの売上を見て、プランの値段を変えたい
- 運営の責任者として、だれが・いつ・どの会員の何を見た／変えたかを、あとから確かめたい
- 見るだけの役割の人には、止める・値段を変えるをさせたくない

| 優先度 | 範囲 |
| --- | --- |
| 必須（12） | 管理者のログイン（会員とは別のアカウント）と役割・サイドバー（ダッシュボード・会員・メッセージ・有料会員と売上）・ダッシュボードのグラフ・会員の一覧と詳細と利用の停止・メッセージの一覧・購入の一覧と月ごとの売上とプランの値段の変更・監査ログ |
| 次の段階 | 通報（会員からの通報を見る）・ブロックの一覧・管理者の追加と役割の変更を画面で・CSV の書き出し・二段階認証 |
| 対象外 | 会員の代わりにログインする（なりすまし）・メッセージを消す／書き換える・決済の返金 |

## 機能要件と受け入れ条件

管理者は `admins` の表で持ち、会員（`users`）とは別にログインする。役割は「すべてできる（`owner`）」と「見るだけ（`viewer`）」の2つ。

| ID | 機能要件 | 前提 | 操作 | 期待結果 |
| --- | --- | --- | --- | --- |
| FR-ADMIN-001 | 管理者だけがログインできる | 管理者 X・会員 A | X と A が管理画面にログインする | X は `200`。A は会員のメールアドレスとパスワードでも `401`。会員の JWT では管理画面の API を使えない（`401`） |
| FR-ADMIN-002 | サイドバーから、ドメインごとの画面に移れる | X がログインした | サイドバーの「ダッシュボード」「会員」「メッセージ」「有料会員・売上」を押す | それぞれの画面に移る。今いる項目が分かる。項目を1つ足すときは、画面の決まった1か所に足すだけでよい（ほかの画面を直さない） |
| FR-ADMIN-003 | ダッシュボードで、数と移り変わりを見られる | ― | ダッシュボードを開く | 会員の数（今・退会を除く）・今日の登録・マッチの数・メッセージの数・有料会員の数（今、期限の中）・今月の売上。直近 30日の日ごとの登録・マッチ・メッセージの折れ線、直近 12か月の月ごとの売上の棒のグラフ。日付の区切りは日本時間 |
| FR-ADMIN-004 | 会員を探せる | 会員 2万人 | メールアドレス（部分一致）・ニックネーム（部分一致）・状態（すべて・有料・停止中・退会）で探す | 条件に合う会員が、登録の新しい順に 50人ずつ出る。全部の件数も出る |
| FR-ADMIN-005 | 会員の詳細を見られる | ― | 一覧で会員 A を押す | A のアカウント（メールアドレス・登録日・最終ログイン・状態）・プロフィール・いいね（送った・もらった）とマッチの数・購入の記録・ブロックした／された数 |
| FR-ADMIN-006 | 会員の利用を止められる・止めたのを解ける | X は `owner`。A は会員 | X が A を理由つきで止める・解く | 止めると、A はログインできず、持っているトークンでも会員の API を使えない（`403`）。ほかの会員から A は見えない。解くと元に戻る |
| FR-ADMIN-007 | メッセージの一覧を見られる | メッセージ 10万件 | メッセージの画面を開く・送った会員・期間・本文の語で絞る | 新しい順に 50件ずつ。1件に、送った人・相手・ルーム・本文・送った日時。件数が多くても数秒以内に出る |
| FR-ADMIN-008 | 購入の一覧と、月ごとの売上を見られる | 購入 2万件 | 有料会員・売上の画面を開く | 購入の新しい順の一覧（会員・プラン・値段・日時）と、月ごとの売上の表とグラフ。売上は買ったときの値段で数える |
| FR-ADMIN-009 | プランの値段を変えられる | X は `owner` | 1か月を 4,500円にする | 新しく買う人から 4,500円。前に買った記録と過去の売上は変わらない（FR-PAID-004） |
| FR-ADMIN-010 | 見るだけの役割は、変える操作をできない | Y は `viewer` | Y が会員を止める・値段を変える | API は `403`。画面ではボタンが出ない |
| FR-ADMIN-011 | だれが何を見た／変えたかが残る | ― | X が会員 A の詳細を見る・メッセージの一覧を見る・A を止める・値段を変える | 監査ログに、管理者・操作・対象・日時が1行ずつ残る。監査ログは画面から消せない・書き換えられない。監査ログの画面で、新しい順に見られる |

## 成功基準・非機能要件・制約

- NFR-ADMIN-001：会員・メッセージ・購入の一覧は、件数が増えても SQL の本数が増えない（N+1 にしない）
- NFR-ADMIN-002：ダッシュボードの数とグラフは、会員 2万人・メッセージ 10万件・購入 2万件で、数秒以内に出る（測って記録する）
- NFR-ADMIN-003：管理画面の API と画面は、会員の側（`backend/`・`frontend/`）のコードを読み込まない・呼ばない。共有するのは DB だけ。会員の側の表の作りは会員の側（`backend/` のマイグレーション）が持ち、管理画面は自分の表（管理者・監査ログ）だけを自分のマイグレーションで持つ
- NFR-ADMIN-004：サイドバーの項目は、1か所の一覧（どの項目・どの画面・どの役割が見られるか）から作る
- 測るときの試しのデータ：これまでのシーダー（会員 2万人・マッチ・メッセージ 10万件・ブロック・退会・有料会員と購入）をそのまま使う。管理者は試しの2人（`owner` と `viewer`）

## 前提と要確認事項

- 前提：`admin/backend`（Laravel。API。別のコンテナと別のポート）と `admin/frontend`（React と Vite。別のポート）。同じ PostgreSQL（`matching_dev`）を読み書きする
- 前提：会員の利用の停止は、会員の側の表（`users`）に止めた日時を持つ。列は会員の側のマイグレーションで足し、止めたときに会員の側の API が断るのも会員の側で行う（レガシー版では、会員の側が見ない場所が残るかを測る）
- 前提：レガシー版は、構成（`admin/` の分け方・サイドバーの1か所の一覧）は最初から整え、中の API は Fat Controller で作る。一覧の N+1・集計の遅さ・監査ログの抜けを測ってから直す
- 前提：グラフの道具は、解説の「選択肢」で決める
- 要確認：なし

## スコープ外

- 通報・ブロックの一覧（次の段階）
- 会員になりすましてログインする・メッセージを消す
- 管理者を画面で増やす（試しの管理者はシーダーで入れる）
