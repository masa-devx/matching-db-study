# 要件：有料会員

状態：確定
元資料：ユーザーとの会話で決めたこと（2026-11-13）。[product.md](../product.md) の不変条件 9・用語「有料会員」。[messages.md](messages.md)・[likes.md](likes.md)・[search.md](search.md)・[members.md](members.md)
一歩：07（プランを一般とプラチナに分けるのは 07b、決済の通知は 08）
目的：[product.md](../product.md) の「有料会員」

このファイルは、有料会員になる（購入する）・有料かどうかで使える機能を分ける・期限が過ぎたら無料に戻る、を長く表す。レガシー版も改善版も、この要件を守る。要件 ID は `FR-PAID-` で始める。画面の要件は [screens.md](screens.md) に `FR-UI-` で書き足す。

## 目的と対象

男性の会員は、有料会員になると、メッセージを送る・いいねを数の上限なく送る・検索の詳しい条件を使う、ができるようになる。男性以外の会員は、これらを無料で使える。決済会社にはつながず、画面の「購入する」で、すぐ有料会員になる（08 で決済の通知に置き換える）。

## ユーザーストーリーと優先度

- 男性の会員として、期間（1か月・3か月・6か月）を選んで購入し、マッチした相手にメッセージを送りたい
- 男性の無料の会員として、使えない機能を押したときに、有料会員になれば使えると分かりたい
- 男性の有料会員として、いつまで有料かを知りたい。続けて購入したら、今の期限から延びてほしい
- 女性の会員として、お金を払わずに、すべての機能を使いたい
- 運営として、値段を変えても、前に買った人がいくらで買ったかを残したい

| 優先度 | 範囲 |
| --- | --- |
| 必須（07） | 購入する（期間を選ぶ）・今の状態（有料か・期限）を見る・期限が過ぎたら無料に戻る・男性の無料の会員だけ、メッセージを送る／いいねの上限なし／検索の詳しい条件を使えない・購入した記録（いつ・どの期間・いくらで）を残す |
| 次の段階 | プランを一般とプラチナに分ける（07b）・決済の通知で有料にする（08）・もらったいいねの一覧（有料の機能にするかは 07b で決める）・解約・自動の更新 |
| 対象外 | 本当の決済・返金・日割り・キャンペーンの値引き・領収書 |

## 機能要件と受け入れ条件

有料会員かどうかは「今の時刻が、有料の期限より前か」で決める。無料・有料で分けるのは男性の会員だけで、ほかの性別（女性・その他・回答しない）は、有料の機能をいつも使える。

| ID | 機能要件 | 前提 | 操作 | 期待結果 |
| --- | --- | --- | --- | --- |
| FR-PAID-001 | 期間を選んで購入できる | 男性の無料の会員 A | A が「1か月」を購入する | `201`。A は有料会員になり、期限は今から1か月後。購入の記録（期間・値段・始まり・終わり）が1つ残る |
| FR-PAID-002 | 期間と値段の一覧を見られる | ― | 購入の画面を開く | 1か月 3,980円・3か月 9,800円・6か月 16,800円（値段はアプリの外の設定で変えられる） |
| FR-PAID-003 | 有料のあいだに購入すると、今の期限から延びる | A の期限は 10日後 | A が「1か月」を購入する | 期限は「10日後＋1か月」。購入の記録は2つ |
| FR-PAID-004 | 値段を変えても、前に買った記録の値段は変わらない | A が 3,980円で「1か月」を買った | 運営が 1か月を 4,500円に変える | A の記録は 3,980円のまま。次に買う人は 4,500円 |

| FR-PAID-007 | 男性の無料の会員は、メッセージを送れない（読むことはできる） | 男性の無料の会員 A が、B とマッチしている | A が B に送る・トークの履歴を読む | 送るは `403`（`code`: `paid_required`）。読むは `200` |

| FR-PAID-011 | 男性以外は、3つとも無料で使える | 女性の会員 C（購入していない） | 送る・11回目のいいね・身長の条件で検索 | `201`・`201`・`200` |
| FR-PAID-012 | 男性以外は購入できない | 女性の会員 C | 購入する | `403`。記録は残らない |
| FR-PAID-013 | 性別を変えて、有料の機能を使うことはできない | 男性の無料の会員 A | プロフィールの編集で性別を女性にして送る | 性別は変わらない（FR-010）。A は無料のまま |
| FR-PAID-014 | ログインしていないと、購入も状態の確かめもできない | ― | トークンなしで購入・状態を見る | `401` |

## 成功基準・非機能要件・制約

- NFR-PAID-001：有料かどうかを確かめるために、機能ごとに SQL を何本も足さない（会員を読むときに一緒に分かる。1本以内）
- NFR-PAID-002：いいねの1日の上限は、同時に送っても破れない（数えてから入れるまでのあいだに、ほかのいいねが入らない）
- NFR-PAID-003：購入の記録は消さない・書き換えない（あとから値段や期間を確かめられる）
- NFR-PAID-004：有料かどうか・使える機能かの判断は1か所にあり、API と画面が同じものを使う（機能を足しても、確かめる場所を写して増やさない）
- 測るときの試しのデータ：04 の会員 2万人のうち、男性の一部を有料会員にする（期限が過ぎた人・これから切れる人・続けて買った人を混ぜる）。購入の記録を数万件

## 前提と要確認事項

- 前提：決済はしない。「購入する」を押したら、その場で有料会員になる（08 で、決済の通知を受けてから有料にする形に置き換える）
- 前提：値段は 1か月 3,980円・3か月 9,800円・6か月 16,800円（試しの値段）。1か月は「同じ日付の翌月」（1月31日の1か月後は2月28日。月末にそろえる）
- 前提：日付の区切りは日本時間（いいねの「今日」・期限の表示）
- 前提：レガシー版は `users.is_paid`（真偽値）で持つ（product.md の用語）。期限・購入の記録・値段の持ち方は、解説の「選択肢」で決める
- 前提：レガシー版は、設計を考えずに「とりあえず使える」形で作る。有料かどうかの確かめは、コントローラと画面ごとに `if` で写す（どの機能が有料かがコードに散らばり、FR-PAID-017 は守れない。06 の写し忘れと同じ形を測る）。改善版で、使える機能の判断を1か所（設定と1つの関数）にまとめ、`GET /api/me` から画面に渡す
- 前提：Firestore 版（05c）には足さない
- 要確認：なし
