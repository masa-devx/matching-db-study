06 ブロックと退会

作成: 2026-11-13 ／ 状態: レガシー版まで ／ 要件: docs/requirements/blocks.md（FR-BLOCK-001〜015・NFR-BLOCK-001〜002）・docs/requirements/withdrawal.md（FR-WD-001〜011・NFR-WD-001〜002）・screens.md の FR-UI-034〜037

この一歩でできるようになること
  • 「ない行だけを残す」を、NOT IN と NOT EXISTS で書き分け、なぜ NOT EXISTS を選ぶかを説明できる
  • 論理削除（deleted_at）にしたとき、UNIQUE とぶつかる理由と、部分インデックスで直す方法が分かる
  • 「消さずに隠す」条件を、すべての読み取りに漏れなく入れる仕組み（1か所にまとめる）を作れる

1. 何を作るか

ブロック：会いたくない相手をブロックすると、検索・いいね・マッチ・トーク・プロフィールのどこにも、お互いが出なくなります。マッチやメッセージは消さずに残し、読むときに除きます。解除すれば元に戻ります。

退会：会員が自分でやめられます。行は消さずに、やめた日時（deleted_at）を入れます（論理削除）。やめた人はどこにも出ず、ログインもできず、持っていたトークンも使えなくなります。同じメールアドレスで、新しい会員として登録し直せます。

どちらも「行はあるのに、ないことにする」機能です。だから難しいのは書くときではなく、読むときのすべての場所に、除く条件を入れることです。今の API には、会員を読む場所が 10 以上あります（検索・いいね・マッチ・トークの一覧・履歴・送る・プロフィール・ログイン・JWT を読む 9か所）。

2. 先に知っておく言葉

言葉意味（1〜2文）
論理削除行を消さずに「消した」印（ここでは deleted_at に日時）を入れること。行を本当に消すのは物理削除。
NOT EXISTS「条件に合う行が1つもなければ真」。サブクエリが行を返すかだけを見るので、結果の行は増えない。
NOT IN「並べた値のどれとも違えば真」。並べた中に NULL が1つあると、どの行も真にならず、何も返さない。
アンチ結合「相手の表に対応する行がない行」だけを残す結合。PostgreSQL は NOT EXISTS をこれにして、インデックスで相手を探す。
部分インデックス条件（WHERE）に合う行だけを集めたインデックス。UNIQUE にすると「その条件の行のなかで重ならない」になる。
SoftDeletesLaravel のモデルに付けると、delete() が deleted_at を入れるだけになり、そのモデルの読み取りに deleted_at is null が自動で足される（グローバルスコープ）。
グローバルスコープそのモデルのすべてのクエリに、自動で足される条件。ほかのモデル（Profile::）や DB::table() には足されない。

4. 設計の選択肢を比べる

ブロックの持ち方

案良いところ弱いところ向いている場面
A. blocks に1行足し、読むときに除く（消さずに隠す）解除で元に戻る。通報や管理画面（12）で、ブロックの前のやり取りを見られるすべての読み取りに「除く」条件が要る。書き忘れると見える今回（FR-BLOCK-011）
B. ブロックしたら、マッチ・ルーム・メッセージを消す読み取りは何も変えなくてよい解除しても戻らない。いいねの一覧や検索には、やはり除く条件が要る。証拠が残らないやり取りを残す必要がないとき
C. 1回のブロックで、向きを変えた2行を入れる（A→B と B→A）除く条件が「自分が blocker の行」の1つで済む「どちらがブロックしたか」「片方だけ解除」（FR-BLOCK-013）が分かりにくい。行が2倍向きを問わない関係（友だち）

除く条件の書き方

案良いところ弱いところ向いている場面
A. ID を PHP に持ってきて whereNotIn（04 のいいねと同じ）書きやすいSQL が3本・ブロックが増えるほど長くなる。NULL が混ざると何も返さないレガシー版
B. NOT EXISTS（向きごとに2つ）SQL 1本・長さが変わらない。アンチ結合になり、索引で相手を探す。NULL の罠がないサブクエリを読み慣れる必要がある改善版
C. LEFT JOIN blocks … WHERE b.id IS NULLB と同じ結果・同じ計画になることが多い2方向なら JOIN が2つ。結合の条件を間違えると行が増えるJOIN で書くほうが読みやすい人

退会とメールアドレスの UNIQUE

案良いところ弱いところ向いている場面
A. deleted_at ＋ メールアドレスを書き換えて空ける（…#deleted#時刻）UNIQUE を変えなくてよい。よく見る手元のメールアドレスが残らない。長いと 255 文字を超える。メールを送る処理が、書き換えた宛先に送るレガシー版
B. deleted_at ＋ 部分インデックスの UNIQUE（where deleted_at is null）元のメールアドレスが残る。DB が「会員のなかで重ならない」を守る（同時に登録しても2人にならない）PostgreSQL の機能（MySQL には部分インデックスがない。生成列で代わりを作る）改善版
C. UNIQUE を外して、PHP で「あるか」を見るDB を変えなくてよい同時に2回登録すると2人になる（02 の二重のいいねと同じ）選ばない
D. 退会した行を別の表（withdrawn_users）へ移すusers に除く条件が要らないいいね・マッチ・メッセージが指す先が消える（FK）。移す処理が重いほかの表から指されていないとき
この一歩で選ぶもの：ブロックは A（blocks に1行・消さずに隠す）、除く条件は B（NOT EXISTS を向きごとに2つ・1か所のスコープにまとめる）、退会は B（deleted_at と部分インデックスの UNIQUE・SoftDeletes・トークンを読むところで退会を見る）。要件で「解除で戻る」「同じメールアドレスで登録し直す」を決めたので、行を残し、DB の制約で重なりを防ぐ形にします。

5. 見本：レガシー版と改善版

レガシー版（Fat Controller・テストなし）

表は 05 と同じく、主キー・UNIQUE・外部キーを持ち、インデックスは足しません。users に deleted_at を足しますが、SoftDeletes は使わず、思い出した場所にだけ whereNull('deleted_at') を書きます。

// BlockController::store（JWT の処理を写す。10か所目）
$to = User::where('public_id', $request->input('user_id'))->value('id');
Block::create(['blocker_id' => $payload->sub, 'blocked_id' => $to]);   // 2回目は 500

// 一覧（検索・いいね・マッチ・トーク）ごとに、同じ3行を写す
$blocked = Block::where('blocker_id', $me)->pluck('blocked_id');
$blockedMe = Block::where('blocked_id', $me)->pluck('blocker_id');
$query->whereNotIn('id', $blocked->merge($blockedMe));

// UserController::destroy（退会）
if (! Hash::check($request->input('password'), $user->password)) { /* 422 */ }
$user->update(['email' => $user->email.'#deleted#'.time(), 'deleted_at' => now()]);
  • 写し忘れ：一覧には除く3行を写すが、直接開く場所（プロフィール・いいねを送る・トークの履歴・送る）には写さない。ブロックした相手のプロフィールが URL で開け、メッセージも送れる
  • 退会した人が見える：deleted_at を見るのは検索だけ。マッチやトークの一覧は Profile::where('user_id', …) で相手を読むので、退会した人が名前つきで残る
  • トークンが生きている：JWT を読むだけで会員を見ないので、退会した人の JWT が30日使える（FR-WD-004）
  • 索引がない：「私をブロックした人」（blocked_id = ?）は、UNIQUE の先頭の列ではないので、blocks を全部読む
  • 二重のブロック：UNIQUE が止めるが、例外をつかまえないので 500（FR-BLOCK-002）
  • メールアドレスの書き換え：元のメールアドレスが残らない。255文字を超えると 500

改善版

// User：退会は SoftDeletes（delete() が deleted_at を入れる・読むときに自動で除く）
class User extends Authenticatable { use SoftDeletes; }

// 「私に見せてよい会員」を1か所に（検索・いいね・マッチ・トークの一覧・プロフィールで使う）
public function scopeVisibleTo(Builder $q, int $me): void
{
    $q->whereNotExists(fn ($s) => $s->selectRaw('1')->from('blocks as b')
            ->where('b.blocker_id', $me)->whereColumn('b.blocked_id', 'users.id'))
      ->whereNotExists(fn ($s) => $s->selectRaw('1')->from('blocks as b')
            ->whereColumn('b.blocker_id', 'users.id')->where('b.blocked_id', $me));
}

// マイグレーション
$table->index(['blocked_id', 'blocker_id']);                       // 私をブロックした人
DB::statement('create unique index users_email_active_unique
    on users (email) where deleted_at is null');                     // 退会していない人だけで UNIQUE

大事なのは3つです。① 除く条件を1か所（スコープ・ミドルウェア）にまとめ、写さない。② NOT EXISTS を向きごとに分け、それぞれに索引を用意する（(blocker_id, blocked_id) は UNIQUE がそのまま使え、(blocked_id, blocker_id) を足す）。③ 重なりは PHP ではなく、部分インデックスの UNIQUE で DB に守らせる。

注意：SoftDeletes の自動の条件は User:: のクエリにだけ付きます。Profile::where('user_id', …) や DB::table('users')、JOIN した users には付きません（7章の罠）。

Eloquent が発行する SQL（レガシー版と改善版を並べる）

左がレガシー版、右が改善版です。SQL は Laravel に作らせて確かめたもので（blocks の表と deleted_at はまだないので、すべて DB::pretend() で、流さずに SQL だけを取り出した。改善版の SoftDeletes は、トレイトを付けたその場のモデルで作らせた）、例は会員 1（search00001）が会員 3 をブロックする・会員 1 が退会する場合です。中身は explanations/sql/06-blocks-withdrawal.json にあり、explanations/tools/compare-block.py で作り直せます。

ログ（sql-*.log）では、値は ? になり、別に渡されます（プリペアドステートメント）。読みやすいよう、ここでは値を入れて、行を分けて書きました。

on conflict do nothing;

  • deleted_at is null は、モデルの SoftDeletes が自動で足す

  and "id" != 1

7. 気をつけること（罠）

  • NOT IN と NULL：id not in (3, null) は、どの行でも真にならず、検索の結果が0件になる。列に NULL が入りうるなら、NOT EXISTS を使う
  • グローバルスコープが効かない場所：SoftDeletes は User:: にだけ効く。Profile::where('user_id', …)・DB::table('users')・JOIN した users・withTrashed() では、退会した人が出る
  • 片方の向きだけ除く：「私がブロックした人」だけを除くと、ブロックされた側からは、ブロックした人が見えたまま（FR-BLOCK-005 は両方）
  • OR でまとめる：not exists (… where (blocker = 私 and blocked = X) or (blocker = X and blocked = 私)) は正しいが、索引を使いにくくなる。向きごとに分ける
  • 部分インデックスの条件と、クエリの条件をそろえる：where deleted_at is null の索引は、クエリにも同じ条件がないと使われない。ログインの where email = ? は、SoftDeletes が deleted_at is null を足すので使える
  • 件数と中身のずれ：検索の件数（count(*)）にも、同じ除く条件を入れる。中身だけに入れると「20件中 18件」のように数が合わない
  • 退会しても残るもの：相手のトークの一覧に、退会した人とのルームが残っていると、未読の数（タブのバッジ）に数えられる。未読の数にも除く条件が要る

8. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？（消さずに隠す・論理削除にする）

ブロックは「解除で元に戻る」と決めたので、マッチやメッセージを消せない。退会も、相手とのやり取りや、あとで通報・管理画面で見るための記録として行を残す。消さないので、「ない」ことにするのは読むときの条件になる。条件がばらけると写し忘れが起きるので、1か所のスコープとミドルウェアにまとめる。

ほかの方法は？なぜ選ばなかったか？

ブロックでマッチやルームを消す形は、解除で戻せない。ブロックを2行（両方向）で持つ形は、除く条件が1つで済むが、どちらがブロックしたか・片方だけ解除が分かりにくい。NOT IN は SQL が長くなり、NULL の罠がある。退会でメールアドレスを書き換える形は、元のメールアドレスが残らない。UNIQUE を外して PHP で見る形は、同時の登録で2人になる。退会した行を別の表へ移す形は、いいね・マッチ・メッセージが指す先が消える。

弱点は？

すべての読み取りに NOT EXISTS が2つ足され、少し重くなる（索引で1回ずつ探すだけなので、増え方は小さい）。SoftDeletes の効かない書き方（Profile::・DB::table()・JOIN）では、自分で条件を足す必要が残る。退会した行が増え続けるので、期間が過ぎたら消す（個人情報）仕組みが、いずれ要る。部分インデックスは PostgreSQL の機能で、MySQL に移すなら生成列で代わりを作る。

問題が起きたら、どう調べて直すか？

「ブロックした相手が見える」と言われたら、その画面の API のクエリログ（sql-*.log）を見て、blocks を読んでいるかを確かめる。読んでいなければ、スコープを通していない場所（Profile:: から読んでいるなど）を探す。遅いなら EXPLAIN (ANALYZE, BUFFERS) で、blocks が Seq Scan になっていないか・アンチ結合になっているかを見る。登録で 500 なら、どの UNIQUE の違反かを例外の制約の名前で見る。

データが10倍・100倍になったら？

レガシー版は、ブロックが増えるほど not in (…) が長くなり、SQL を送る・読む時間が増える。「私をブロックした人」は Seq Scan なので、blocks が 100倍なら読む行も 100倍。改善版は、向きごとの索引で1回ずつ探すので、blocks が増えても1会員あたりの手間はほとんど変わらない。退会した行が会員の大半になったら、users のほかの索引も部分インデックス（where deleted_at is null）にすると、索引が小さくなる。

Eloquent でどんな SQL が流れ、どう直したか？ Rails（ActiveRecord）・Prisma ならどう書くか？

レガシー版は pluck() で ID を2回持ってきて whereNotIn()（3本）。改善版は whereNotExists() を2つ（1本）。退会は SoftDeletes で deleted_at is null が自動で付き、UNIQUE は部分インデックスにする。

やることLaravel（Eloquent）Rails（ActiveRecord）Prisma
ブロックした・された相手を除くwhereNotExists(fn ($q) => …) を2つwhere.not(Block.where(...).where('blocks.blocked_id = users.id').arel.exists)、または where.not(id: Block.where(blocker_id: me).select(:blocked_id))（サブクエリの NOT IN）where: { blocksReceived: { none: { blockerId: me } }, blocksMade: { none: { blockedId: me } } }（none は NOT EXISTS になる）
論理削除use SoftDeletes（自動で除く）標準にはない。discard の gem や default_scope（使いすぎに注意）標準にはない。クライアントの拡張（$extends）で deletedAt: null を足す
部分インデックスの UNIQUEDB::statement('create unique index … where deleted_at is null')add_index :users, :email, unique: true, where: 'deleted_at IS NULL'スキーマでは書けない。マイグレーションの SQL を手で直す
