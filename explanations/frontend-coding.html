2. React の書き方

2-1. 描く間は、外を変えない（R1・R2）

  • React は、同じ props・state なら同じ JSX が返ると決めて、描く回数を自分で決める。開発中の StrictMode は、わざと2回描く（どちらのアプリも main.tsx で入れている）
  • props・state は書き換えず、新しい値を setXxx に渡す
  • hook は一番上で呼ぶ。use で始まる名前は hook だけに付ける。今のコードでは、SearchConditionsPage.tsx の useSaved（ふつうの関数）が、lint の誤りを2件出している

2-2. Effect が要るかを決める（R3）

React の文書は、Effect を「React の外に出るための出口」と呼んでいる。外（API・DOM・タイマー）がないなら、Effect は要らない。

flowchart TD
  A["Effect を書きたい"] --> B{"React の外に合わせるか？
（API・Firestore・DOM・タイマー）"}
  B -- "合わせない" --> C{"何をしたいか"}
  C -- "props・state から値を作る" --> D["描く間に計算する（重いときだけ useMemo）"]
  C -- "押した・送ったときの処理" --> E["イベントの処理に書く"]
  C -- "props が変わったら state を戻す" --> F["親で key を変える"]
  C -- "state を見て別の state を変える" --> G["1つのイベントの処理で、次の state を全部決める"]
  B -- "合わせる" --> H{"データを取るか？"}
  H -- "取る" --> I["hook の中に書き、片付けで古い応答を捨てる（R4）"]
  H -- "取らない" --> J["Effect に書き、片付けで外したものを戻す"]

今のコードの Effect は 44。中身で分けると、データを取る 34・外に合わせる 8・Effect でなくてよい 2。

// 今（VerifyBanner.tsx）：取った値を見て、別の Effect が retry() を呼ぶ
useEffect(() => {
  if (me?.email_verified_at && sessionSaysUnverified) retry()
}, [me, sessionSaysUnverified, retry])

// 案：取ったときの処理の中で決める（Effect のつながりをなくす）
const onLoaded = (me: AccountResponse) => {
  setMe(me)
  if (me.email_verified_at !== null && sessionSaysUnverified) retry()
}

2-3. データを取る Effect は、古い応答を捨てる（R4・R5）

  • 会員の id が A から B に変わったとき、A の応答があとから届くと、B の画面が A で上書きされる（race condition）
  • 片付けで印を立てれば、最後に頼んだもの以外の応答は捨てられる。StrictMode で2本呼ばれても、1本目は捨てられる
  • React の文書は、AbortController だけでは、fetch のあとに続く await を止められないと書いている
useEffect(() => {
  let ignore = false
  getUser(publicId).then((user) => {
    if (!ignore) setUser(user)
  })
  return () => {
    ignore = true
  }
}, [publicId])
  • 今のコードで片付けがあるのは、SessionProvider.tsx（番号で見分ける）の1つだけ。残りの 33 にはない
  • 依存の配列は、コードから決まる。「1回だけ動かしたい」ために依存を省かない。React の文書は、依存の lint を止めることを「React に嘘をつく」と書いている
  • 依存を減らしたいときは、値を部品の外に出すか、Effect の中で作るか、useEffectEvent（React 19.2）に出す。管理画面の biome-ignore 12件は、どれも依存を選んでいる

2-4. key と &&（R6・R8）

// 番号の key：行を消すと、入力中の値や開いている状態が、隣の行に付く
{rows.map((r, i) => <Row key={i} row={r} />)}
// データの id
{rows.map((r) => <Row key={r.publicId} row={r} />)}

// count が 0 のとき「0」と出る
{count && <Badge>{count}</Badge>}
// 真偽にする
{count > 0 && <Badge>{count}</Badge>}
  • 番号でよいのは、数が決まっていて並びが変わらない一覧（Skeleton.tsx）だけ

2-5. state の形（R7）

  • 計算できる値は state にしない。props を state の初めの値にするなら、名前を initialXxx にする
  • 同時に true になってはいけない真偽（isLoading と isError）は、1つの status にする
  • 管理画面の MembersPage.tsx:158 は、URL のクエリを入力欄の state にも持ち、Effect で合わせている

4. TypeScript と型の書き方

4-1. 外から来る値の流れ（T1〜T4）

  • res.json() と JSON.parse は any を返す。Biome の noExplicitAny は、書いた any しか見つけない
  • 今のコードの res.json() は 58。型を付けて受けているのは2か所
  • 見本になるのは shared/api/client.ts の codeOf
// unknown で受けて、調べてから使う（client.ts の codeOf と同じ形）
function readRole(text: string | null): Role | null {
  try {
    const value: unknown = JSON.parse(text ?? 'null')
    if (typeof value === 'object' && value !== null && 'role' in value && isRole(value.role)) {
      return value.role
    }
  } catch {
    // JSON でない
  }
  return null
}

4-2. as と !、satisfies（T3）

  • TypeScript の文書は、言い切りは動くときに何も調べず、違っていても例外も null も出ないと書いている
  • 書いてよいのは、DOM（HTML を見れば確かめられる）と、api.ts で API の応答を XxxResponse として受ける1か所だけ
  • useParams() の値に ! を付けない（TalkFsPage.tsx に4つ）。if (!roomId) return で絞る
  • 定数の形を確かめたいときは satisfies。形が合わないと誤りにし、値の細かい型も残す
const PLAN_LABELS = {
  monthly: '1か月',
  yearly: '12か月',
} satisfies Record<PlanKind, string>   // キーの抜け・打ち間違いを誤りにする

4-3. type と interface（T5。決まりには入れていない）

  • TypeScript の文書は「ほとんどの場合、好みで選んでよい。迷ったら interface」と書いている
  • 違いは2つ。interface は同じ名前で書くと宣言が足される。type は union（'loading' | 'error'）を名前にできる
  • このリポジトリは状態の union が多く、今のコードも type だけ（13・interface 0）なので、type にそろえる案にした。interface は Window・ImportMetaEnv に宣言を足すときだけ使う
// src/vite-env.d.ts：import.meta.env.VITE_API_URL に型を付ける
interface ImportMetaEnv {
  readonly VITE_API_URL?: string
}

4-4. 状態の抜けを never で見つける（T6。決まりには入れていない）

function label(s: SessionState): string {
  switch (s.status) {
    case 'loading': return '読み込み中…'
    case 'signedIn': return s.account.email
    case 'signedOut': return 'ログインしていません'
    case 'error': return '読み込めませんでした'
    default: {

5. 書き方の道具（Biome）

  • 整形と import の並びは、Biome が直した形を正とする（B1）。Biome の文書は、整形の話し合いを終わらせるために、選べる項目を少なくしていると書いている。PHP の Pint と同じ考え方
  • npm run lint（biome lint）は import の並びを見ない。見るのは biome check。今は管理画面の3ファイルが並んでいない
  • noExplicitAny・noNonNullAssertion は recommended では warn で、lint を止めない。overrides で、改訂版の置き場（app/・features/・shared/）だけ error にした（B2。#114）
{
  "overrides": [
    {
      "includes": ["src/app/**", "src/features/**", "src/shared/**"],
      "linter": {
        "rules": {
          "suspicious": { "noExplicitAny": "error" },
          "style": { "noNonNullAssertion": "error" }
        }
      }
    }
  ]
}
  • biome-ignore には、規則の名前と理由を書く。useExhaustiveDependencies は止めない（B3）
  • a11y の規則は recommended のまま使う（B4）。画面のレビュー役が見るもの（ラベル・キーボードの操作）を、レビューの前に機械で止める

7. 気をつけること（罠）

  • noExplicitAny が 0 になっても、res.json()・JSON.parse から来る any は残る。lint では見つからない
  • as XxxResponse も const x: XxxResponse = await res.json() も、動くときには何も調べない。正しさは、docs/api/ の例を入れるテスト（architecture-frontend.md の7章）で確かめる
  • <form action> は、誤りの文を返しても入力欄を空にする。入力を残したい欄は defaultValue を state から渡す
  • useEffectEvent は、依存を隠すために使わない。React の文書は「依存を書かないために使うと、不具合を隠す」と書いている
  • strict を書いていなくても、TypeScript 7 では入っている。"strict": false と書いた所がないかを見る
  • CI は、まだ画面の全体の lint を流していない（作業中の frontend.yml も、置き場の決まりだけ）。warn の規則は、だれも止めない

8. 理解を確かめる問い

先に自分で答えてから、開いて見る。

会員のプロフィールを読む Effect に片付けがないと、何が起きるか？

会員 A から B にすぐ移ると、A の応答があとから届き、B の画面を A で上書きすることがある。片付けで印を立て、最後に頼んだもの以外の応答を捨てる。

「開いたときに1回だけ読みたい」ので依存の配列を [] にし、lint を止めた。何が困るか？

Effect の中で使う値（props の id など）が変わっても、動き直さない。古い値のまま表示が残る。依存は選べないので、値を外に出すか、Effect の中で作るか、useEffectEvent に出す。

一覧の key に配列の番号を使うと、どんなときに困るか？

行を足す・消す・並べ替えるとき。React は番号で同じ行と見なすので、入力中の値や開いている状態が、別の行に付いたまま残る。

noExplicitAny の指摘が 0 なら、any はないと言えるか？

言えない。res.json() と JSON.parse は any を返すので、書かなくても any が入る。unknown か XxxResponse で受ける。

as と satisfies は、何が違うか？

as は調べずに型を決め、違っていても誤りにならない。satisfies は形が合うかを調べて誤りにし、値の細かい型も残す。

なぜ noUncheckedIndexedAccess を、any を消す前に足すのか？

今は読み出しの多くが any の上なので、誤りは3件だけで済む。any を消すと読み出しに型が付き、足したときに直す所が増える。
