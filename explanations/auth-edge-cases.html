認証のエッジケース（パスワード・退会・アカウント停止・端末）

作成: 2026-11-21 ／ 状態: 仕様の確認中（#259 の2つ目の PR）

このページの状態
  • 「前」は、今の refactored-repo（PR #280 を取り込んだあと。会員のログインは表 sessions の行）
  • 「後」は、#259 の2つ目の PR を出したあとの予定（docs/cycles/01-backend-foundation/05-problems.md の #259 の2つ目で決めた形）
  • どれもコードを読んで書いた。実際に動かして確かめたものは「確かめた」、まだのものは「確かめていない」と書く
  • 最後の「10. 決めてほしいこと」に、仕様を決める必要があるものを集めた
このページでわかること
  • パスワードの変更・再設定・退会・アカウント停止・強制退会・端末やタブを変えたときに、ほかの端末のログインがどうなるか
  • 2つ目の PR で、何が変わり、何が変わらないか
  • 同時に2つのことが起きたとき（ログインと再設定など）に残る穴
  • 要件に書いていない所と、決める必要がある所

1. 先に知っておく言葉

言葉意味
セッションの行表 sessions の1行。1つのブラウザのログイン
端末セッションの Cookie を1つ持つブラウザ。同じブラウザのタブは、同じ端末
行を消す行がなくなり、その Cookie は次から 401
ログインの確かめAuthenticateUser。行の会員の番号と、会員の状態を見る
ポーリング決まった間隔で API を呼ぶこと
同時に起きる2つのリクエストが、DB の上で重なること
  • ログインの確かめ（AuthenticateUser）が見るのは、次の2つだけ
    • セッションの行に、会員の番号があるか
    • その会員が使える状態か（退会・アカウント停止・強制退会でないか。users の列を毎回読む）
  • 「パスワードを変えたか」は見ない。そのため、パスワードを変えたときは、行を消さないと、ほかの端末が使えたままになる
  • アカウント停止・強制退会・退会は、users の列で毎回見るので、行を消さなくても次のリクエストで 401 になる

2. 全体の図：だれが行を消すか

2つ目の PR のあとに、どの操作が表 sessions のどの行を消すか。

flowchart LR
  pw["パスワードの変更"] --> others["その会員の、ほかの端末の行を消す"]
  reset["パスワードの再設定"] --> all["その会員の行を全部消す"]
  wd["退会"] --> all
  logout["ログアウト"] --> one["その端末の行を消す"]
  down["メンテナンスに入れる"] --> every["全員の行を消す"]
  susp["アカウント停止・強制退会"] --> keep["行は消さない。毎回 users を見て 401"]
  email["メールアドレスの変更"] --> none["API がない"]
  • 2つ目の PR で足すのは、上の3つ（パスワードの変更・再設定・退会）だけ
  • ログアウトとメンテナンスは、PR #278・#280 でできている

3. パスワードの変更（PUT /api/me/password。FR-AUTH-033）

P1. 端末 A でパスワードを変える。端末 B もログインしている

例：スマホを落とした会員が、パソコンでパスワードを変える。

前B は 200 のまま

  • パスワードを書き換えるだけで、表 sessions を触らない
  • 拾った人のスマホ（B）は、ログインしたまま使える
  • 使い続ければ、24時間ごとに期限が延びる

後B は 401

  • 今の端末（A）の番号を除いて、その会員の行を消す（delete from sessions where user_id = ? and id <> ?）
  • B は、次のリクエストで 401「ログインしてください」になり、ログインの画面に移る
  • テスト：A は 200・B は 401。B の行がなく、A の行はある

P2. パスワードを変えた端末 A そのもの

前200

  • ログインしたまま。セッションの番号は変わらない

後200

  • ログインしたまま（要件：変えた端末のものは除く）
  • セッションの番号は、作り直さない予定
決めること（Q1）
  • パスワードを変えたときに、A のセッションの番号も作り直すか
  • 作り直すと、A の番号を前に盗まれていても、それも使えなくなる（ログインのときと同じ考え方）
  • 作り直さないと、A の番号を知っている人は使い続けられる

P3. 同じブラウザの、別のタブ

  • Cookie はタブのあいだで1つなので、同じ端末（A）として扱う。前も後も、ログインしたまま

P4. 変えたちょうどそのとき、端末 B が書き込みをしている

例：B がメッセージを送るリクエストと、A のパスワードの変更が重なる。

sequenceDiagram
    participant B as 端末 B
    participant L as Laravel
    participant DB as PostgreSQL
    participant A as 端末 A
    B->>L: POST メッセージを送る
    L->>DB: select from sessions（B の行がある）
    A->>L: PUT /api/me/password
    L->>DB: delete from sessions where user_id = ? and id は A でない
    L->>DB: insert into messages（B のリクエストは、そのまま最後まで動く）
    L->>DB: update sessions（B の行はもうないので、0行）
    L-->>B: 201
    B->>L: 次のリクエスト
    L-->>B: 401

前通る

  • どちらも通り、B はそのまま使える

後そのリクエストだけ通る

  • 行を読んだあとのリクエストは、最後まで動く（メッセージは送られる）
  • 終わりの保存は、消えた行を作り直さない。Laravel の DatabaseSessionHandler::write() は、読めた行を update するだけで、0行なら何もしない（コードを読んだ。確かめていない）
  • B は、次のリクエストから 401

P5. 今のパスワードを間違える

  • 前も後も、422「今のパスワードがちがいます」。何も変わらない。行も消さない
  • 分かっている不具合：何回でも試せる（要件は「何回も続けて間違えたら、しばらく止める」）。回数の上限は #281 と同じ形で考える

P6. 新しいパスワードを送らない・1文字にする

前通る・500

  • 1文字でも通る（要件は8〜64文字。FR-AUTH-004）
  • 送らないと、NOT NULL の違反で 500

後変えない予定

  • 新しい形に移すだけで、動きは変えない予定（移すコミットと、直すコミットを分ける決まり）
  • テストに「分かっている不具合」と書いて残す

P7. 再設定のメールを頼んだあとに、設定の画面でパスワードを変える

  • 前も後も、再設定のリンクは使えるまま。あとでリンクを使うと、もう一度パスワードを変えられる
  • 例：メールを盗み見られていたら、会員が設定で変えても、リンクから変え直されてしまう
決めること（Q3）
  • パスワードを変えたら、その会員の再設定用の文字（表 password_reset_tokens の行）も消すか

4. パスワードの再設定（PUT /api/password-resets/{token}。FR-AUTH-035）

R1. 端末 A・B でログインしたまま、リンクから再設定する

前A も B も 200

  • パスワードを書き換えるだけ
  • 前のパスワードでログインしていた端末は、全部使えたまま

後A も B も 401

  • その会員の行を全部消す（delete from sessions where user_id = ?）
  • テスト：A も B も 401。その会員の行が0

R2. リンクを開いたブラウザが、ログインしている

  • 再設定はログインが要らない API なので、どのブラウザから開いても同じ
  • 後：そのブラウザの行も消すので、再設定のあとはログインの画面になる。自動でログインさせない（要件どおり）

R3・R4. 同じリンクを2回使う・60分を過ぎたリンクを使う

  • 前も後も、どちらも通る（分かっている不具合。要件は「60分で切れ、1回しか使えない」）
  • 後：移すだけで直さない予定。テストに「分かっている不具合」と書く

R5. 再設定のメールを2回頼む

  • 前も後も、前のリンクは使えなくなる（表 password_reset_tokens は、メールアドレスごとに1行。書き換える）

R6. 退会した会員が、退会の前に届いたリンクを使う

  • 前：500（退会でメールアドレスを書き換えるので、会員が見つからず、null に update() する）
  • 後：移すだけで直さない予定（分かっている不具合）

R7. アカウント停止中の会員が、再設定する

  • 前も後も、パスワードは変わる。ログインは、停止のあいだ 403「利用を停止しています」のまま
  • 後：行は全部消す（停止を解いたあと、前の端末がパスワードなしで戻らない）
決めること（Q4）
  • アカウント停止のあいだも、再設定を受け付けてよいか（今のまま受け付けるか）

R8. 前のパスワードでのログインと、再設定が重なる

例：パスワードを知った人がログインするのと同時に、本人が再設定する。

sequenceDiagram
    participant X as 前のパスワードを知る人
    participant L as Laravel
    participant DB as PostgreSQL
    participant M as 本人
    X->>L: POST /api/auth/login（前のパスワード）
    L->>DB: select from users（前のハッシュ）
    L->>L: 照合が通る
    M->>L: PUT /api/password-resets/{token}
    L->>DB: update users（新しいパスワード）
    L->>DB: delete from sessions where user_id = ?
    L->>DB: insert into sessions（X の行。消したあとにできる）
    L-->>X: 200（ログインできてしまう）

前そもそも消さない

  • 再設定で行を消さないので、X は、重ならなくてもログインしたまま

後重なると残る

  • 照合のあと、行を書くまでのあいだに消すと、X の行が残る（コードから考えた。確かめていない）
  • 間は短い（照合の bcrypt が数十ミリ秒）。ただ、狙ってくり返されると起きうる
  • 設計の前の案（ア：セッションにパスワードのハッシュを持たせる AuthenticateSession）なら、X の次のリクエストで切れる。イを選んだときに、手放したもの
決めること（Q5）
  • この重なりを、分かっている不具合として受け入れるか
  • 受け入れないなら、ア（AuthenticateSession）を足すか、ログインと再設定を、会員の行のロック（select ... for update）で順番にするか

R9. 登録されていないメールアドレスで、再設定のメールを頼む

  • 前：404「会員が見つかりません」（要件は同じ 200 を返し、登録されているかを教えない。FR-AUTH-034）
  • 後：200 を返し、メールは送らない。強制退会の会員も同じに扱う（Q4）ので、再設定の PR で、メールを送る API（POST /api/password-resets）も直す（2026-11-22 に人が決めた）

5. メールアドレスの変更

M1. API がない

  • 会員の側に、メールアドレスを変える API はない（要件の対象外。docs/requirements/auth.md:32）
  • 作るときに決めること
    • ほかの端末の行を消すか（パスワードの変更と同じ扱いにするか）
    • 再設定用の文字を消すか（表 password_reset_tokens は、メールアドレスで行を持つので、古いアドレスの行が残る）
    • 新しいアドレスを確認するまで、機能を止めるか（今の「確認していない会員は 403」と同じにするか）
    • 古いアドレスに「変わりました」と知らせるか

6. 退会（DELETE /api/me）

W1. 端末 A で退会する。端末 B もログインしている

前B は 401・行は残る

  • deleted_at を入れるので、B は次のリクエストで 401（ログインの確かめが users を見る）
  • 行は消さない。24時間たって掃除されるまで残る

後B は 401・行は0

  • その会員の行を全部消す
  • テスト：A も B も 401。その会員の行が0

W2. 退会した端末 A そのもの

  • 前も後も、API は 204。画面は自分の情報を消して、ログインの画面に移る
  • 後：A の行も消すので、同じ Cookie は 401

W3. 退会のちょうどそのとき、端末 B が書き込みをしている

  • P4 と同じ。行を読んだあとのリクエストは最後まで動き、次から 401
  • 例：退会と同時に送ったメッセージは、相手に届く

W4. 退会したあと、同じメールアドレスで登録し直す

  • 前も後も、登録できる（退会でメールアドレスを書き換えて空けるため）
  • 新しい会員の番号は別なので、前の会員のセッションとは関係しない

7. アカウント停止・強制退会（管理画面）

2つ目の PR では、ここは変えない。今の動きと、気になる所だけを書く。

S1. ログインしているあいだに、運営がアカウント停止にする

  • 前も後も、次のリクエストで 401（code: account_suspended）。画面は、理由を付けてログインの画面に移る（「このアカウントは停止されています」）
  • 行は消さない

S2. アカウント停止のあいだも、開いたままのタブがポーリングする

  • タブのバーは30秒ごと、トーク画面は5秒ごと、メッセージ一覧は10秒ごとに API を呼ぶ（TabBar.tsx・TalkPage.tsx・MessagesPage.tsx）
  • 401 の応答でも、Laravel はセッションを保存するので、行の last_activity が延び続ける（コードを読んだ。確かめていない）
  • ただし、画面は 401 でログインの画面に読み込み直すので、ふつうはポーリングも止まる

S3. 運営がアカウント停止を解く

  • 前も後も、行が残っていれば、その端末はパスワードなしで、すぐにログインした状態に戻る
  • 「24時間たったら戻らない」とは言い切れない（S2 で延び続けることがあるため）
  • 本人がログアウトしていれば、行は消えている（PR #280 の A1。停止中でもログアウトできる）
決めること（Q6）
  • アカウント停止・強制退会のときに、その会員の行を消すか
  • 消すなら、管理画面（backend/admin）が、同じ DB の表 sessions を消す。管理画面を移すチケットで扱うのが自然

S4. アカウント停止中に、ログインする

  • 前も後も、403「利用を停止しています」（code: account_suspended）。セッションを作らない（テストあり）

S5. 強制退会にする

  • 前も後も、次のリクエストで 401「ログインしてください」（理由は言わない）。ログインし直すと 403「強制退会になっています」
  • 行は残るが、戻ることはない（強制退会は解けない）
  • アカウント停止と強制退会の両方なら、強制退会として扱う

8. 端末・タブ・ブラウザ

D1. 2つ以上の端末で、同時にログインする

  • 前も後も、どれも使える。数の上限はない

D2. 新しい端末に変える（古い端末はそのまま）

前古い端末も使える

  • 古い端末は、24時間使わなければ切れる。使えば延びる
  • 自分で古い端末を切る方法は、その端末でログアウトするか、メンテナンスだけ

後パスワードの変更で切れる

  • 新しい端末でパスワードを変えれば、古い端末は切れる（P1）
  • 「ほかの端末をすべてログアウト」のボタンは、ない
決めること（Q9）
  • 端末の数に上限を付けるか
  • パスワードを変えずに「ほかの端末をすべてログアウト」できる機能が要るか

D3. 同じブラウザの別のタブで、別の会員がログインする

  • Cookie は1つなので、上書きされる
  • 前のタブに戻ると、GET /api/me を読み直し、会員が違えば画面を読み込み直す（PR #280 の S3。テストあり）
  • 残る弱いところ：戻ってすぐに押した書き込みが、読み直しの前に、新しい会員として送られることがある（確かめていない）

D4. タブを開いたまま、何もしないで24時間

  • タブのバーが30秒ごとに API を呼ぶので、期限は延び続け、切れない
  • 要件は「操作がないまま24時間たつと切れる」（FR-AUTH-013）。人が何もしていなくても、画面が開いていれば「操作がある」ことになる
決めること（Q7）
  • 画面を開いているだけで延びるのを、要件どおりとするか
  • よしとするなら、要件の言葉を「画面を使っていないまま」に直す。よしとしないなら、ポーリングを期限の延長に数えない仕組みが要る（大きい）

D5. ブラウザを閉じて、また開く

  • 前も後も、ログインしたまま（設定の expire_on_close が false。Cookie が残る）
  • 共有のパソコン（ネットカフェなど）では、次に使う人が開けてしまう
決めること（Q8）
  • ブラウザを閉じたら切れるようにするか（「ログインしたままにする」の選択を、ログインの画面に足すか）

D6. 127.0.0.1 で画面を開く

  • Cookie が API に届かず、ログインのあとに「ログインできませんでした。画面を読み込み直してください」が出る（PR #280 の A3）。localhost で開く

D7. セッションの Cookie を盗まれる

  • Cookie は HttpOnly なので、画面のスクリプトからは読めない。盗まれるのは、端末のマルウェアや、落とした端末から
  • 前：その端末でログアウトするか、アカウント停止か、メンテナンスでしか止まらない
  • 後：本人がほかの端末でパスワードを変えれば止まる（P1）

9. ログアウト・メンテナンス・Firebase

L1. ログアウトの API が失敗する

  • ホームのまま「ログアウトできませんでした。もう一度お試しください」が出る。画面の自分の情報は消さない（Cookie が生きたままなので。テストあり）

L2. ほかのタブでログアウトする

  • 前のタブに戻ると、読み直して、ログインしていない状態になる（テストあり）

L3. メンテナンスに入れる

  • 全員の行を消す。解いたあとは、どの端末もログインの画面になる（FR-MAINT-002。テストあり）

F1. ログアウトしても、Firebase のログインが残る

  • トークの一部の画面（MessagesFsPage.tsx・TalkFsPage.tsx）は、Laravel からカスタムトークンをもらい、Firebase にログインする（firebase.ts の signInFirebase）
  • 画面のどこにも、Firebase から抜ける処理（signOut(auth)）がない。ログアウトしても、ブラウザに前の会員の Firebase のログインが残る（コードを読んだ。確かめていない）
  • 決まり（architecture-frontend.md の5章）には「ログアウトのときは消し、Firebase からも抜ける」とあり、今のコードと違う
  • 今は手元の Emulator だけなので、本物の会員のデータは関係しない

F2. パスワードの変更・退会・アカウント停止でも、Firebase のログインは止まらない

  • Firebase のログインは Laravel のセッションと別なので、2つ目の PR のあとも止まらない
決めること（Q10）
  • Firebase から抜ける処理を、2つ目の PR に入れるか、別のチケット（不具合）にするか
