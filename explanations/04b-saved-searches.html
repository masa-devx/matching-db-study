04b 保存した検索条件と、検索の画面の URL

作成: 2026-11-17 ／ 状態: レガシー版まで

この一歩でできるようになること
  • 項目があとから増えるデータを、列で持つか jsonb でまとめるかを、「だれが・どう読むか」で決められる
  • 「1人5件まで」のような件数の上限を、同時に送られても破れない形（行ロック）で作れる
  • 「自分のものだけ直せる・消せる」を、SQL の where で確かめる形にできる

1. 何を作るか

検索の条件（性別・年齢の幅・都道府県・身長の幅）に名前を付けて、サーバーに保存します。会員は、検索の画面で「東京・20代」「関西・30代」のようなパターンを選ぶだけで、同じ条件で検索できます。保存できるのは1人5件までです。別の端末でログインしても、同じパターンが出ます。

今の検索は、条件をブラウザのタブの中（sessionStorage）にだけ置いています。タブを閉じる・ログインし直す・別の端末で開く、のどれでも消えるので、会員は毎回同じ条件を入れ直しています。

有料の条件（身長）の決まりは、検索と同じです。男性の無料の会員は、身長を入れた条件を保存できません。有料のときに保存した条件は、無料に戻っても消えませんが、その条件での検索はできません。もう一度有料になれば、そのまま使えます。

あわせて、今の条件を検索の画面の URL（/search?age_min=20&prefecture=東京都）に出します。再読み込み・ブックマーク・ブラウザの「戻る」で、同じ条件に戻れます。役割は2つに分かれます。URL は「今の条件」、サーバーの表は「名前を付けて取っておく条件」です。保存した条件を選ぶと、その条件が URL に入り、URL の条件で検索します。

レガシー版は、設計を考えずに「とりあえず使える」形で作ります。上限は数えてから入れるだけ、条件は確かめずに入れる、有料かどうかの確かめは検索のコントローラーからコピーする、持ち主は確かめない、の4つです。要件は docs/requirements/saved-searches.md（FR-SAVED-001〜015）にあります。

2. 先に知っておく言葉

言葉意味（1〜2文）
jsonbPostgreSQL の、JSON を入れる列の型。{"age_min": 20} のような入れ子のデータを1つの列に持てる。入れるときに形を整えて保存するので、中の項目で探すこともできる。
スキーマ（表の作り）表にどんな列があり、それぞれがどんな型か、という決まり。列で持つと DB が型を確かめるが、jsonb の中身は DB が確かめない。
EAV（1項目1行）「どの条件の・どの項目が・どんな値か」を1行ずつ持つ形（Entity・Attribute・Value）。項目は自由に増やせるが、値が全部文字になり、1件を読むのに行を集め直す。
行ロック（for update）トランザクションの中で行を読みながら押さえ、ほかのトランザクションがその行を押さえるのを、終わるまで待たせる。同じ会員の処理を1つずつにできる（07 でも使った）。
数えてから入れる（check-then-act）「今4件だから入れてよい」と確かめてから入れる書き方。確かめてから入れるまでのあいだに、ほかの処理が入れるので、同時に来ると上限を超える。
IDORID を知っていれば、他人のデータを読める・変えられる不具合（Insecure Direct Object Reference）。持ち主を確かめないと起きる。
一括代入（mass assignment）送られてきた項目を、そのまま全部 Model に入れること。user_id のような、変えられては困る列まで書き換えられる。

4. 設計の選択肢を比べる

どこに持つか

案良いところ弱いところ向いている場面
A. 画面の URL（/search?age_min=25）ブックマーク・共有・ブラウザの「戻る」が効く。サーバーは変えないほかのタブから戻ると消える。「毎回入れ直す」は解決しない条件を人に見せたいとき（通販・検索サイト）
B. ブラウザの localStorage画面だけで済む。閉じても残る別の端末では残らない。同じ端末で別の会員がログインすると、前の人の条件が出るログインのないサービス
C. サーバーの表どの端末でも、ログインすれば残る表・API・テストが増えるログインして使うサービス

何件持つか

案良いところ弱いところ向いている場面
A. 1人に1件（最後の条件を自動で覚える）会員は何もしなくてよい。表は1対1条件の違うパターンを切り替えられない条件が「その人の好み」で、あまり変わらないとき
B. 名前を付けて複数（上限あり）パターンを切り替えられる保存・直す・消すの操作と、上限の決まりが要る違う条件を並べて探すとき（求人・不動産に多い）

条件の中身の持ち方

案良いところ弱いところ向いている場面
X. 列で持つ（age_min・age_max…）＋都道府県は別の表DB が型と範囲を確かめる（CHECK）。ほかの会員の条件をまたいで集計しやすい検索の項目を足すたびに、マイグレーション・Model・API を直す項目が決まっていて、条件をまたいで調べたいとき
Y. jsonb の1列項目が増えても表を変えない。中身を検索のクエリと同じ形にできるDB は中身を確かめない。項目をなくすと、古い形のデータが残る持ち主が読んでフォームに戻すだけで、項目が増えるとき
Z. 1項目1行（EAV）項目ごとに行で持てる値が全部文字になる。1件を読むのに行を集め直す。型も範囲も確かめられない項目を運営が画面から足すような、特別なとき

5件の上限の止め方

案良いところ弱いところ向いている場面
A. 数えてから入れる（ロックなし）短い同時に送ると上限を超えるレガシー版
B. 会員の行を for update で押さえてから数える分かりやすい。いいねの1日の上限（07）と同じ形同じ会員のほかの書き込みが、そのあいだ待つ改善版
C. 番号の列（1〜5）と UNIQUE (user_id, slot)DB の制約だけで6件目が入らない。ロックが要らない空いている番号を探す処理が要る。上限を変えにくい上限が小さく、変わらないとき
この一歩で選ぶもの：取っておく条件はサーバーの表に持ち（C）、今の条件は画面の URL に出し（A。役割が違うので両方使う）、名前を付けて5件まで（B）、条件の中身は jsonb の1列（Y）。決め手は、この条件を読むのが「持ち主がフォームに戻して検索するとき」だけで、検索の項目があとから増えることです。jsonb の弱いところ（DB が中身を確かめない）は、保存するときに検索の API と同じ検証を通し、読むときに今の決まりに合わない項目を捨てて補います。上限は、改善版では行ロック（B）で止めます。レガシー版は、数えてから入れるだけ（A）・検証なし・持ち主を確かめない形で作り、何が困るかを測ります。

表の作り（レガシー版と改善版）

同じ表を、レガシー版と改善版でどう作るかを並べます。レガシー版はマイグレーション（#140）で作った実物、改善版は直す段階で作る予定の形です。

-- レガシー版：とりあえず使える形
create table search_conditions (
  id         bigserial primary key,
  public_id  uuid not null default uuidv7() unique,
  user_id    bigint not null,          -- 外部キーなし・インデックスなし
  name       varchar(255) not null,    -- 長さは確かめない
  conditions jsonb not null,           -- 何でも入る
  created_at timestamp(0),
  updated_at timestamp(0)
);
-- 改善版：DB が確かめられることは、DB で確かめる
create table search_conditions (
  id         bigint generated always as identity primary key,
  public_id  uuid not null default uuidv7() unique,
  user_id    bigint not null references users (id) on delete cascade,
  name       varchar(30) not null check (char_length(name) between 1 and 30),
  conditions jsonb not null check (jsonb_typeof(conditions) = 'object'),
  created_at timestamptz not null,
  updated_at timestamptz not null
);
-- 自分の一覧を、保存した順に読む
create index search_conditions_user_id_id_index on search_conditions (user_id, id);
項目レガシー版改善版違いで起きること
持ち主（user_id）数の列だけ外部キー（on delete cascade）レガシー版は、会員を消しても条件が残り、いない会員を指せる（FR-SAVED-014）
インデックス主キーと public_id だけ(user_id, id)レガシー版は、自分の一覧を読むのに表を全部読む（6万件で 1549 ページ・Seq Scan）。改善版は、自分の行だけを保存した順に読める
名前varchar(255)varchar(30) と CHECKレガシー版は、空の名前も 255文字の名前も入る（FR-SAVED-008）
条件の中身何でも入る「オブジェクトであること」だけ CHECK。項目と範囲はアプリレガシー版は、配列・数・文字だけの JSON も入る。項目ごとの CHECK を書かないのは、項目が増えるたびに制約を直すことになるため（NFR-SAVED-003）
1人5件なし（アプリが数えるだけ）なし（アプリが、会員の行を押さえてから数える）「1人5件まで」は、行をまたぐ決まりなので CHECK では書けない
日時timestamp（時間帯なし）timestamptzほかの表と同じ（database.md）

検索の項目を足すときの、表・SQL・インデックス（#153）

2026-11-17 に、検索に使う6項目（体型・お仕事・年収・タバコ・お酒・結婚歴）をプロフィールに足しました。レガシー版は実物、改善版は直す段階で作る予定の形です。改善版の SQL は、まだ Laravel に作らせていません（表がないため）。直す段階で、作らせて確かめます。

表の作り

-- レガシー版：選択肢の名前（文字）を、そのまま列に入れる
alter table profiles

項目レガシー版（文字）改善版（コードとマスタ）
選択肢にない値入る（「1億円」も保存される）外部キーが断る
選択肢の名前を変える前に保存した行と合わなくなる（全部の行を書き換える）マスタの1行を直すだけ
年収「500万円以上」比べられない。当てはまる区分を全部選んでもらうincome_code >= 3 で比べられる
選択肢の一覧の置き場ホーム・条件の画面・試しのデータの3か所に同じ一覧マスタの表の1か所。画面は API から読む
1行の大きさ文字（「ややぽっちゃり」は 21バイト）smallint（2バイト）。表が小さくなり、全部読むときも速い
項目を足すとき列を足し、画面の一覧を3か所直すマスタの表と列を足す（どちらもマイグレーションは要る）

インデックス：レガシー版には足していません。年収2区分・タバコ・体型で探すと、profiles を全部読みます（57人を見つけるのに 19,972行を捨て、3,986 ページ）。改善版でどうするかは、次の案を測って決めます。

案中身良いところ弱いところ
A. 項目ごとに1つずつ(income_code)・(smoking_code) … を別々に作る分かりやすい。PostgreSQL が複数のインデックスを組み合わせて使える（ビットマップ）選択肢が3〜11個しかない列は、1つの値に当たる行が多く、インデックスを使っても読む行があまり減らない。書き込みのたびに6つを直す
B. よく使う組を1つにまとめる(gender_code, prefecture_code, …) の複合インデックスその組で探すときは速い条件の組み合わせは会員ごとに違う（6項目の付け方だけで64通り）。全部の組は作れない。並びの左の列を条件に付けないと使えない
C. 並びのインデックスをたどるusers (last_login_at, public_id) を新しい順にたどり、条件に合う行を20人見つけたら止める条件に合う会員が多いときは、少し読むだけで終わる。インデックスを足さない条件に合う会員が少ないと、最後までたどることになり、かえって遅い
D. 複数の列を1つの索引で（GIN・bloom）btree_gin や bloom で、6項目をまとめた1つのインデックスどの組み合わせでも使える拡張を入れる必要がある。並び（最終ログイン順）には使えないので、合った行を並べ直す

直す段階で確かめること：条件に合う会員が多いとき（例：タバコ＝吸わない）と少ないとき（例：6項目を全部付ける）の両方で、EXPLAIN (ANALYZE, BUFFERS) の読んだページの数を、案ごとに比べます。「どの列にインデックスを張るか」は、列の値の種類の数（選択肢の数）と、条件に合う行の割合で決まります。

5. 見本：レガシー版と改善版

レガシー版（Fat Controller・テストなし）

// SearchConditionController::store（JWT の処理をコピーする）
// 07 の検索からコピー：身長が入っていて、男性で is_paid でなければ 403（期限は見ない）
$conditions = $request->input('conditions');

}

}
$row = SearchCondition::create(['user_id' => $me, 'name' => $request->input('name'), 'conditions' => $conditions]);

  • 上限を超える：数えてから入れるまでのあいだに、ほかの保存が入れる。同時に送ると6件目が入る（FR-SAVED-005）
  • 何でも保存できる：条件を確かめないので、年齢 17・身長 300・知らない項目・とても大きい JSON が入る（FR-SAVED-007）。名前の長さも確かめない
  • 期限切れでも有料の条件を保存できる：検索からコピーした確かめは is_paid だけを見る。期限（paid_until）が過ぎた会員が、身長の入った条件を保存でき、検索もできる（FR-SAVED-009・010）。同じ確かめが、これで4か所目
  • 他人の条件を直せる・消せる：ID（UUID）を知っていれば、だれのものでも変えられる（FR-SAVED-006）。$request->all() で user_id も書き換えられる
  • 会員を消しても残る：外部キーがないので、持ち主のいない行が残る（FR-SAVED-014）

改善版

// 条件の決まりは1か所（検索の API と保存の両方が使う）
final readonly class SearchConditions
{
    public static function fromArray(array $input): self { /* 範囲を確かめる。違えば 422 */ }
    public static function fromStored(array $stored): self { /* 今の決まりに合わない項目を捨てる */ }
    public function usesPaidFeature(): bool { return $this->heightMin !== null || $this->heightMax !== null; }
}

// 保存：検証 → 有料の判断（07 の1つの関数）→ ロックして数える → 入れる
$conditions = SearchConditions::fromArray($request->validated('conditions'));
if ($conditions->usesPaidFeature() && ! $features->canUse($me, 'search_detail')) {
    throw new PaidRequired;   // 403
}
DB::transaction(function () use ($me, $name, $conditions) {
    DB::table('users')->where('id', $me->id)->lockForUpdate()->value('id');
    if (SearchCondition::where('user_id', $me->id)->count() >= 5) {
        throw new SavedSearchLimitExceeded;   // 422
    }
    SearchCondition::create(['user_id' => $me->id, 'name' => $name, 'conditions' => $conditions->toArray()]);
});

大事なのは3つです。条件の決まり（SearchConditions）が1か所にあり、検索と保存が同じものを使うこと。有料かどうかの判断が、07 で作る1つの関数（期限を見る）であること。数える前に、会員の行を押さえること。直す・消すは、where に持ち主（user_id）を入れ、変わった行が 0 なら 404 にします（下の SQL）。

6. どう確かめるか

段階確かめること
① レガシー版で問題を見る
  • 同時に保存する：4件ある会員で、保存を10本同時に送る（xargs -P 10 で curl）。select count(*) from search_conditions where user_id = … が 5 を超える
  • 確かめない条件：{"age_min": 17, "height_min": 300, "x": "y"} を保存して、201 が返る
  • 期限切れ：paid_until が過ぎた男性（is_paid は true のまま）で、身長を入れて保存し、201 が返る
  • 他人の条件：会員 A のトークンで、会員 B の条件の ID を PUT・DELETE し、B の行が変わる・消える
  • 索引：EXPLAIN (ANALYZE, BUFFERS) select * from search_conditions where user_id = …。レガシー版は user_id に索引がなく、表を全部読む（Seq Scan）。試しのデータ（会員 2万人 × 平均3件 = 6万件）で見る
② 振る舞いを固定するテスト
  • FR-SAVED-001 条件に名前を付けて保存できる
  • FR-SAVED-005 6つ目は保存できない（順に6回送る。同時に送るテストは、改善のときに足す）
  • FR-SAVED-006 他人の条件は直せない・消せない（レガシー版では落ちる。分かっている不具合として、今の動きをコメントに残す）
  • FR-SAVED-009 男性の無料の会員は、身長を入れて保存できない
  • FR-SAVED-010 無料に戻ると、身長の入った条件では検索できない
③ 改善したあとに比べる数字同時に10本送ったあとの件数（6以上 → 5）・確かめない条件が保存される数（入る → 422）・他人の条件を変えられるか（変わる → 404）・一覧の EXPLAIN（Seq Scan → Index Scan。読んだ行の数）・直すときの SQL の本数（2本 → 1本）

7. 気をつけること（罠）

  • jsonb に入れる前に確かめる：DB は中身を確かめません。送られたものをそのまま入れると、検索の API が受け付けない値や、とても大きいデータが入ります。保存のときに検索と同じ検証を通します
  • 読むときも信用しない：検索の項目をなくしたり範囲を変えたりすると、前に保存した条件に古い形が残ります。読むときに、今の決まりに合わない項目を捨てます（FR-SAVED-015）
  • 決まりを2か所に書かない：条件の範囲（年齢 18〜99 など）を検索と保存の両方に書くと、片方だけ直してずれます。1か所に置き、両方から使います
  • 上限は「数える」だけでは止まらない：数えてから入れるまでのあいだに、ほかの処理が入れます。行を押さえるか、DB の制約で止めます
  • UUID は秘密ではない：ID が推測しにくくても、持ち主の確かめの代わりにはなりません。画面の通信やログから知られることがあります
  • 保存した時点の「使えるか」を持たない：有料かどうかは変わります。保存するときに「使える」と行に書くと、無料に戻ったあとも使えてしまいます。読むたびに、今の状態で判断します
  • 無料に戻った会員の条件を消さない：消すと、もう一度有料になったときに作り直しになります。残して「使えない」と見せます
  • URL の値は、だれでも書き換えられる：/search?age_min=1 のように、画面の欄では選べない値を入れて開けます。URL の値をそのまま信用せず、API の検証（422）に任せ、画面は誤りを見せます。ページの番号や、秘密にしたい値は URL に出しません
  • 画面で隠すだけでは止まらない：画面が身長の条件を出さなくても、API を直接呼べば送れます。止めるのは API です

8. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？

条件を jsonb の1列にするのは、この条件を読むのが「持ち主がフォームに戻して検索するとき」だけで、検索の項目があとから増えるからです。列で持つと、項目を足すたびに表・Model・API を直します。jsonb なら表は変えず、条件の決まり（SearchConditions）だけを直します。サーバーに持つのは、タブを閉じても・別の端末でも残すためです。上限を行ロックで止めるのは、数えてから入れるまでのあいだに、同じ会員のほかの保存が入らないようにするためです。

ほかの方法は？なぜ選ばなかったか？

列で持つ案は、DB が型と範囲を確かめてくれますが、項目が増えるたびに直す所が多くなります。ほかの会員の条件をまたいで集計する使い方（「25歳を探している人は何人か」）があるなら、列のほうが向いています。1項目1行（EAV）は、値が全部文字になり、型も範囲も確かめられないので選びません。画面の URL や localStorage は、別の端末で残らないので、「毎回入れ直す」を解決できません。上限を番号の列と UNIQUE で止める案は、ロックが要らない代わりに、空いている番号を探す処理が要り、上限を変えにくくなります。

弱点は？

DB が jsonb の中身を確かめないので、アプリの検証を通らずに入ったデータ（手で直した・古い版が入れた）は、形が違うことがあります。読むときに捨てる処理が、その受け皿です。行ロックは、同じ会員のほかの書き込み（プロフィールの保存・いいね・購入など、会員の行を押さえる処理）を、そのあいだ待たせます。保存は短いので、ふつうは問題になりません。また、検索の項目の名前を変えると（height_min → min_height など）、前に保存した条件からその項目が消えます。名前を変えるときは、保存したデータも書き換えるマイグレーションが要ります。

問題が起きたら、どう調べて直すか？

「6件ある」と言われたら、select user_id, count(*) from search_conditions group by user_id having count(*) > 5 で、上限を超えた会員を数えます。同じ秒に2件入っていれば、同時に送られたと分かります。直すのは、保存の処理（行ロック）で、超えた分をどうするかは運営と決めます。「保存した条件で検索すると 422 になる」と言われたら、その行の conditions を読み、今の決まりに合わない値がないかを見ます。読むときに捨てる処理が抜けている項目があれば、そこを直します。「知らないうちに条件が変わった・消えた」と言われたら、直す・消すの SQL の where に持ち主が入っているかを、クエリログで確かめます。

データが10倍・100倍になったら？

1人5件までなので、会員が20万人で最大100万件、200万人で最大1000万件です。読むのはいつも「自分の5件」なので、user_id の索引があれば、件数が増えても速さはほとんど変わりません。索引がないレガシー版は、表を全部読むので、件数に比例して遅くなります。jsonb は1行が大きくなりやすいので、条件の大きさに上限を付けます（検証を通せば、項目の数で自然に決まります）。行ロックは会員ごとなので、会員が増えても、待ちは増えません。もし「この条件に合う新しい会員を通知する」を足すなら、すべての条件を読んで検索することになり、jsonb のままでは重くなります。そのときは、通知に使う項目を列に出すか、別の仕組み（条件ごとの検索を順に流すジョブ）を考えます。

Eloquent でどんな SQL が流れ、どう直したか？ Rails（ActiveRecord）・Prisma ならどう書くか？

レガシー版の「直す」は、where("public_id" = ?) で読んでから update … where "id" = ? の2本で、持ち主を見ません。改善版は、update … where "user_id" = ? and "public_id" = ? の1本にして、変わった行が 0 なら 404 にします。保存は、select … for update で会員の行を押さえてから数えます。
