03 マッチ

作成: 2026-11-12 ／ 状態: レガシー版まで ／ Issue: #29 ／ 要件: docs/requirements/matches.md（FR-MATCH-001〜010・NFR-MATCH-001〜003）

この一歩でできるようになること
  • 向きのない組（A と B）を1行で持ち、「小さい ID を先に」の CHECK と組の UNIQUE で「1組に1つ」を DB に守らせる理由を説明できる
  • 自己結合・INNER JOIN・LEFT JOIN で、結果の行がどう変わるかを説明できる（LEFT JOIN の相手の条件は ON に書く）
  • 「書いてから相手の行を読む」処理が同時に来たとき、トランザクションなしでは二重に、トランザクションだけではマッチが抜けることと、ロックで順番に進める直し方を説明できる

1. 何を作るか

お互いにいいねした会員どうしを「マッチ」にします。いいねを送り返したその場で「マッチしました」と分かり、マッチした相手の一覧と、送った相手の「マッチ済み」の印も見られるようにします。05 のメッセージは、マッチした相手にだけ送れる（不変条件 6）ので、その土台になります。

作るもの中身要件子 Issue

送ったときのマッチ相手からのいいねがあればマッチを作り、応答で「マッチしたか」を返すFR-MATCH-001〜004・NFR-MATCH-003#31

送った一覧の印02 の送った一覧に「マッチ済み」を足すFR-MATCH-006・NFR-MATCH-001#31

API のパス（マッチの一覧は GET /api/me/matches の予定）と応答の形は、子 Issue #31 の最初に docs/api/03-matches.md に書き、確かめてもらってから作ります。

2. 先に知っておく言葉

言葉意味（1〜2文）
自己結合同じ表を、別の名前（likes as l1・likes as l2）を付けて2回使い、行どうしをつなぐこと。「A から B」の行と「B から A」の行を1行に並べられる。
INNER JOIN両方の表に相手が見つかった行だけを残す結合。相手がいない行は結果から消える。
LEFT JOIN左の表の行は全部残し、右の表に相手がなければ右の列を null で埋める結合。「マッチしていない相手も一覧に出す」ときに使う。
向きのない組「A と B」と「B と A」を同じものとみなす組。いいね（A から B）には向きがあるが、マッチにはない。小さい ID を先に並べると、1通りの書き方にそろう。
least・greatestPostgreSQL の関数。並べた値のうち、一番小さい・一番大きいものを返す。least(23, 5) は 5。組を「小さい ID・大きい ID」に並べ替えるのに使う。
READ COMMITTEDPostgreSQL の標準の分離レベル。SQL を1本流すたびに、その時点でコミット済みの行を見る。ほかのトランザクションがまだコミットしていない行は見えない。
行ロック（FOR UPDATE）select … for update で読んだ行を、トランザクションが終わるまで押さえる。同じ行を押さえようとした別のトランザクションは、終わるまで待つ。Laravel では lockForUpdate()。
デッドロック2つのトランザクションが、お互いが押さえた行を待ち合って、どちらも進めなくなること。PostgreSQL は見つけると片方をエラー（40P01）にする。押さえる順をそろえると起きない。
BitmapOr実行計画の段の1つ。a = ? or b = ? のとき、a のインデックスと b のインデックスで見つけた行を合わせる。片方にでもインデックスがないと、表を全部読む。

4. 設計の選択肢を比べる

マッチの持ち方

案良いところ弱いところ向いている場面
A. 表を持たず、毎回 likes を自己結合する正（本当の値）が likes の1つだけで、二重もずれも起きない。表が増えない一覧のたびに結合が走る。05 のメッセージが「どのマッチか」を指す ID がない。解除・マッチの状態を持てないマッチを読むだけで、ほかの表から指さないとき
B. user_matches に向きつきで2行（A から B・B から A）一覧は user_id = 自分 の1本のインデックスで済み、相手の列が決まっている2行をいつも一緒に書き・消す必要があり、片方だけ残ると壊れる。行の数が2倍一覧の読み込みがとても多く、書き込みを1か所にまとめられるとき
C. user_matches に1行。小さい ID を user1_id に（CHECK user1_id < user2_id＋組の UNIQUE）「1組に1行」を DB が守る。(B, A) は CHECK で入らない。05 から user_matches.id を指せる一覧は「どちらかの列が自分」の OR になり、インデックスが2つ要る。相手の列を CASE で選ぶ向きのない組を持つとき（友だち・マッチ・対戦の組）
この一歩で選ぶもの：改善版は C。レガシー版は、C と同じ1行の形だが順の決まりがなく（送り返した人を user1_id に入れる）、UNIQUE も CHECK もインデックスもない。改善版は、先に行の向きをそろえ、重なった行を消してから制約を足す（01・02 と同じ「先に直してから制約」の手順）。

同時にお互いへ送ったときの守り方

案良いところ弱いところ向いている場面
A. トランザクションなし（レガシー版）書くのが簡単。1本ずつすぐ確定するので、どちらかは必ず相手のいいねを見る（0行にはならない）両方が相手のいいねを見ると、マッチが2行になる。いいねを入れたあとに落ちると、マッチだけ抜ける使わない
B. トランザクションで包むだけいいねとマッチが、そろって入るか、そろって入らないかになるREAD COMMITTED では、相手のまだコミットしていないいいねが見えない。両方が「ない」と読んで、マッチが0行になる（2枚目の図）同時に来ない処理だけ
C. トランザクション＋2人の users の行を ID の小さい順に FOR UPDATE＋組の UNIQUE同じ2人の処理が1つずつ進むので、抜けも二重もない。ロックで会員がいるかも確かめられる。UNIQUE が最後の守りになる同じ会員への送信が重なると、少し待つ。users の行を書き換えるほかの処理も待たされる「読んでから書く」を、ある組について順番にしたいとき
D. 分離レベルを SERIALIZABLE にして、失敗したらやり直す書き方を変えずに、順番に流したのと同じ結果になる失敗（40001）のやり直しを、呼ぶ側すべてに書く必要がある。混んでくると失敗が増える守りたい決まりが多く、ロックの場所を決めきれないとき
この一歩で選ぶもの：改善版は C。ロックするのは「組」についての行がまだない（いいねもマッチもこれから入る）ので、すでにある2人の users の行を押さえる。押さえる順を ID の小さい順にそろえて、デッドロックを防ぐ。pg_advisory_xact_lock（行ではなく番号を押さえる）でも同じことができるが、会員がいるかを同時に確かめられる FOR UPDATE にする。ロックの種類の比べ方は 09 で深める。

ほかに決めること

決めること改善版理由
表と列の名前表は user_matches（Model は UserMatch）。列は user1_id・user2_id（レガシー版も同じ）match は PHP の予約語なので Model を UserMatch にし、表もそれにそろえる（Laravel が Model から探す名前と同じなので、$table を書かずに済む）。列は意味を持たない番号にして、レガシー版（送り返した人が先）と改善版（小さい ID が先）で入れ方が変わっても、名前とずれないようにする。決まりは CHECK（user_matches_user1）とコメントで示す
「マッチ済み」の印の正user_matches を正にして、送った一覧から LEFT JOIN する印を逆向きのいいねから決めると、正が2つになる。マッチが抜けたときに、印と一覧が食い違う。05 のメッセージも user_matches を見る
03 より前の「お互いのいいね」改善版のマイグレーションで、likes の自己結合からマッチを埋める（insert … select … on conflict do nothing）レガシー版の同時の送信で抜けたマッチも、ここで埋まる
自分とのマッチCHECK user1_id < user2_id で入らないレガシー版は、自分あてのいいねが自分の行を「逆向き」として見つけ、自分とのマッチができる。02 の CHECK（自分あてのいいね）とあわせて、二重に止める
会員を消したとき2つの列から users.id への外部キー（ON DELETE CASCADE）FR-MATCH-010。06 の退会で論理削除にするなら、CASCADE は働かない（06 で考える）
マッチの一覧の取り方JOIN で1本（user_matches と profiles）NFR-MATCH-001。with() は「自分でないほう」をリレーションにしにくい（組のどちら側かが行ごとに違う）

5. 見本：レガシー版と改善版

レガシー版（Fat Controller・テストなし）

// マイグレーション：組の2人と日時だけ。UNIQUE・CHECK・外部キー・インデックスなし
Schema::create('user_matches', function (Blueprint $table) {
    $table->id();
    $table->unsignedBigInteger('user1_id');   // 送り返した人
    $table->unsignedBigInteger('user2_id');   // 先に送っていた人
    $table->timestamps();
});

// LikeController::store に足す（02 の Like::create のすぐあと）
$reverse = Like::where('from_user_id', $request->input('user_id'))
    ->where('to_user_id', $payload->sub)->first();
$matched = false;
if ($reverse) {
    UserMatch::create(['user1_id' => $payload->sub, 'user2_id' => $request->input('user_id')]);
    $matched = true;
}
return response()->json(array_merge($like->toArray(), ['matched' => $matched]), 201);
  • 二重のマッチ：トランザクションも組の UNIQUE もないので、同時にお互いへ送ると (A, B) と (B, A) の2行が入りうる。一覧に同じ相手が2回出る
  • 自分とのマッチ：02 のレガシー版は自分あてのいいねを入れる。そのあと「自分から自分へのいいね」（今入れた行）が逆向きとして見つかり、自分とのマッチができる
  • 途中で落ちる：いいねを入れたあと、マッチを入れる前に落ちると、お互いにいいねしているのにマッチがない
  • 一覧：user_matches にインデックスがなく、user1_id = ? or user2_id = ? は表を全部読む。相手のプロフィールは1件ごとに読む（1＋N 本）
  • 印：送った一覧の印を、1件ごとに逆向きのいいねを読んで決める（1＋2N 本）。user_matches と食い違っても気づかない
  • 会員を消す：外部キーがないので、マッチが残る

改善版

// マイグレーション：先に行を直す（向きをそろえる → 重なりと自分とのマッチを消す）
DB::statement('update user_matches set user1_id = user2_id, user2_id = user1_id where user1_id > user2_id');
DB::statement('delete from user_matches a using user_matches b
    where a.user1_id = b.user1_id and a.user2_id = b.user2_id and a.id > b.id');
DB::statement('delete from user_matches where user1_id = user2_id');
// 次に制約を足す
Schema::table('user_matches', function (Blueprint $table) {
    $table->unique(['user1_id', 'user2_id']);
    $table->index('user2_id');
    $table->foreign('user1_id')->references('id')->on('users')->cascadeOnDelete();
    $table->foreign('user2_id')->references('id')->on('users')->cascadeOnDelete();
});
// user1_id には小さい ID を入れる（違反すると、エラーに CHECK の名前 user_matches_user1 が出る）
DB::statement('alter table user_matches add constraint user_matches_user1 check (user1_id < user2_id)');
// 最後に、抜けていたマッチを likes の自己結合で埋める
DB::statement('insert into user_matches (user1_id, user2_id, created_at)
    select l1.from_user_id, l1.to_user_id, greatest(l1.created_at, l2.created_at)
    from likes l1
    join likes l2 on l2.from_user_id = l1.to_user_id and l2.to_user_id = l1.from_user_id
    where l1.from_user_id < l1.to_user_id
    on conflict do nothing');

大事なのは順番です。向きがそろっていない行や重なった行が残っていると、UNIQUE と CHECK を足す alter table が失敗します。PostgreSQL の update … set user1_id = user2_id, user2_id = user1_id は、右側に書き換える前の値を使うので、1本で入れ替えられます。最後の insert … select は自己結合で、「l1 が A から B、l2 が B から A」の組を探します。l1.from_user_id < l1.to_user_id で、同じ組を2回数えないようにしています。送る処理（トランザクションとロック）は、下の SQL の並びの1つ目にあります。

Eloquent が発行する SQL（レガシー版と改善版を並べる）

左がレガシー版、右が改善版です。SQL は Laravel に作らせて確かめたもので（user_matches の表はまだないので、レガシー版の送った一覧のほかは DB::pretend() で、流さずに SQL だけを取り出した）、例は会員 23（さくら）が会員 5・6 にいいねしていて、5 が 23 に送り返す場合です。中身は explanations/sql/03-matches.json にあり、explanations/tools/compare-block.py で作り直せます。

ログ（sql-*.log）では、値は ? になり、別に渡されます（プリペアドステートメント）。読みやすいよう、ここでは値を入れて、行を分けて書きました。

改善版4本＋ガード1本

DB::transaction(function () use ($me, $targetId) {
    $ids = DB::table('users')
        ->whereIn('id', [$me->id, $targetId])
        ->orderBy('id')->lockForUpdate()
        ->pluck('id');        // 2つ読めなければ 404
    $inserted = DB::table('likes')->insertOrIgnore([...]);
    // 0 なら 409
    $mutual = DB::table('likes')
        ->where('from_user_id', $targetId)
        ->where('to_user_id', $me->id)->exists();
    if ($mutual) {
        DB::table('user_matches')->insertOrIgnore([
            'user1_id' => min($me->id, $targetId),
            'user2_id' => max($me->id, $targetId),
            'created_at' => now(),
        ]);
    }
});

7. 気をつけること（罠）

  • LEFT JOIN の相手の表の条件を WHERE に書くと、INNER JOIN と同じになる：where m.created_at > … と書くと、m が null の行（マッチしていない相手）が消える。相手の条件は ON に書く
  • トランザクションで包むだけでは、マッチが抜ける：READ COMMITTED では、相手のまだコミットしていないいいねは見えない。「書いてから相手の行を読む」処理は、包むだけでは守れない。ロックで順番にするか、SERIALIZABLE にする
  • ロックの順をそろえないと、デッドロックになる：A は「A → B」、B は「B → A」の順に押さえると、待ち合って止まる。いつも ID の小さい順に押さえる（order by id … for update）
  • 組の UNIQUE だけでは、(B, A) を止められない：(user1_id, user2_id) の UNIQUE は (A, B) と (B, A) を別の値とみなす。CHECK user1_id < user2_id とセットで、向きを1つにそろえる
  • OR の片側にしかインデックスがないと、表を全部読む：user1_id = ? or user2_id = ? は、UNIQUE（user1_id が先頭）だけでは足りない。user2_id にもインデックスを足すと BitmapOr になる。または2本の SQL を union all でつなぐ
  • 正を2つ持たない：印を逆向きのいいねから、一覧を user_matches から作ると、マッチが抜けたときに画面どうしが食い違う。どちらを正にするかを決めて、そこから読む
  • マッチを作る場所を1つにする：シードや手で流す SQL でマッチを作ると、ロックの約束が守られない。そのときの最後の守りが、組の UNIQUE と CHECK
  • 02 のレガシー版の穴が、03 に広がる：自分あてのいいねが入ると、自分とのマッチもできる。前の一歩の制約の抜けは、あとの一歩の不具合として出る

8. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？

マッチは「A と B」の向きのない組なので、小さい ID を user1_id にそろえて1行で持つ。そろえておけば、組の UNIQUE が「1組に1行」をそのまま守れ、CHECK user1_id < user2_id で (B, A) と自分とのマッチも入らない。表に持つのは、05 のメッセージが user_matches.id を指せるようにするため。送るときは、2人の users の行を ID の小さい順にロックしてから「相手からのいいねがあるか」を読む。トランザクションで包むだけだと、READ COMMITTED では相手のコミット前のいいねが見えず、同時に送るとマッチが抜けるからだ。

ほかの方法は？なぜ選ばなかったか？

表を持たずに likes の自己結合で毎回求める案は、正が1つで二重もずれもないが、05 で「どのマッチか」を指す ID がなく、一覧のたびに結合が走る。向きつきで2行持つ案は、一覧が速いが、2行をいつもそろえて書き・消す必要がある。同時の守りは、SERIALIZABLE でやり直す案もあるが、失敗のやり直しを呼ぶ側すべてに書く必要があり、ここでは「同じ2人の処理を順番にする」ロックのほうが、何を守っているかがはっきりする。pg_advisory_xact_lock でも順番にできるが、会員がいるかも一緒に確かめられる FOR UPDATE を選んだ。

弱点は？

一覧が「どちらかの列が自分」の OR になり、インデックスが2つ（UNIQUE の user1_id 先頭と、user2_id）要る。相手の列を CASE で選ぶので、SQL が読みにくい。users の行のロックは、人気のある会員に同時に多くのいいねが来ると、その会員の行で待ちが並ぶ（その会員の行を書き換えるほかの処理も待つ）。FOR UPDATE は、外部キーの確かめ（いいねを入れるときに相手の users の行へかかる FOR KEY SHARE）ともぶつかるので、ほかの会員からその会員へのいいねも待たされる。FOR NO KEY UPDATE なら外部キーの確かめとはぶつからず、同じ組の処理どうしは順番になる（ロックの強さの違いは 09 で比べる）。least・greatest と CASE を忘れたコードは、正しく組を探せない。

問題が起きたら、どう調べて直すか？

「マッチしたのに一覧に出ない」と言われたら、検査の SQL（likes の自己結合に user_matches を LEFT JOIN して m.id is null）で、お互いにいいねしているのにマッチがない組を数える。あれば、同時の送信で抜けている（トランザクションだけでロックがない）。「同じ相手が2回出る」なら、least・greatest で並べ替えて group by … having count(*) > 1 で重なりを探す。直すときは、行を直してから UNIQUE と CHECK を足し、抜けた組を自己結合で埋める。デッドロック（40P01）がログに出たら、ロックを取る順がそろっているかを見る。

データが10倍・100倍になったら？

マッチは、いいねより少ないが、会員が増えるほど増える。インデックスがないと、マッチの一覧も、送った一覧の印（LEFT JOIN）も、user_matches を全部読む。user2_id のインデックスと組の UNIQUE があれば、どちらも数行を読むだけで済む。一覧の件数が増えたら、04 でページ送り（カーソル）を入れる。そのとき OR の並べ替えが重くなれば、2本の SQL を union all でつなぐ形に変えることを考える。同時に多くのいいねを受ける会員がいれば、ロックの待ちを測り、番号のロック（pg_advisory_xact_lock）で組ごとに押さえる形も比べる。
