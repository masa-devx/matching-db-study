アーキテクチャの地図（レイヤード・オニオン・クリーン・DDD ほか）

作成: 2026-11-15 ／ 状態: 解説だけ（サイクル 01「どう作るか」の資料）

このページでわかること
  • よく名前が出る設計（MVC・レイヤード（3層）・ヘキサゴナル・オニオン・クリーン・DDD・モジュラーモノリス・垂直スライス）が、それぞれ何を守るための形か
  • メリット・デメリットと、どんなサービスやプロジェクトに向いているか
  • あとで変更（決済の差し替え・プランを増やす・DB を移す・会員が100倍）が来たとき、どの形だと何か所を直すことになるか
  • このプロジェクト（会員の側は3層・管理画面はモジュール）に当てると、どこまで取り入れるのがよいか

1. 先に知っておく言葉

言葉意味（1〜2文）
層（レイヤー）受け持ちの違うコードを分けたかたまり。「HTTP の入口」「業務の判断」「DB の読み書き」など
依存A が B を使う（B のクラス名を書いている）こと。B が変わると A も直す必要が出る
依存の向きだれがだれを使うかの矢印。設計の多くは「この向きにしか矢印を引かない」という決まり
ドメイン（業務）アプリが扱う世界の決まり。このアプリなら「お互いにいいねしたらマッチ」「男性だけが有料プランを買える」
ユースケース利用者がする1つの操作。「いいねする」「プランを買う」
インターフェース（差し替え口）「こういうメソッドを持つもの」という約束だけの型。中身（本物・テスト用の偽物）を差し替えられる
依存性逆転（DIP）業務の側が差し替え口（インターフェース）を決め、DB や外のサービスの側がそれに合わせて作る形。矢印が「業務 → DB」から「DB → 業務の決めた口」に逆向きになる
ポートとアダプターポート＝業務の側が決めた差し替え口。アダプター＝その口に合わせて、DB・外の API・画面とつなぐ部品
モノリスアプリ全体が1つのプログラムとして動く形。反対はマイクロサービス（機能ごとに別のプログラムに分ける）

2. まず全体の見取り図

名前はたくさんあるが、狙いで分けると3つのグループになる。

グループ設計何を守るか
横に切る（技術の受け持ちで分ける）MVC・レイヤード（3層）HTTP・業務・DB を混ぜない
内と外に分ける（業務を真ん中に置く）ヘキサゴナル・オニオン・クリーン業務の決まりを、DB・フレームワーク・外のサービスから守る（差し替えられる）
縦に切る（機能・業務のまとまりで分ける）モジュラーモノリス・垂直スライス・DDD の戦略設計1つの機能を変えるとき、触る場所を1か所に閉じる

DDD（ドメイン駆動設計）だけは「フォルダの形」ではなく、業務をどう言葉とモデルにするかの考え方。上のどの形とも組み合わせられる（6章）。

3. 横に切る設計

3-1. MVC（今のレガシー版）

Model（データ）・View（画面）・Controller（入口）の3つに分ける。Laravel を入れたときの形。API だけなら View は JSON になる。

  • メリット：覚えることが少ない。小さいうちは最速で作れる
  • デメリット：業務の判断の置き場がないので、Controller に全部が集まる（Fat Controller）。今のコードで JWT の読み方が30か所にコピーされたのはこのため
  • 向いているもの：試作・社内の小さな道具・画面が数枚のアプリ

3-2. レイヤードアーキテクチャ（3層）

プレゼンテーション層（入口）・ビジネスロジック層（業務）・データアクセス層（DB）の3つに分け、矢印は上から下へ一方向にする。

flowchart TB
  P["プレゼンテーション層 Controller・Request・Resource"] --> B["ビジネスロジック層 Service"]
  B --> D["データアクセス層 Repository・Model"]
  D --> DB[(PostgreSQL)]
  
// プレゼンテーション層：受けて渡して返すだけ
public function store(StoreLikeRequest $request, LikeService $likes): JsonResponse
{
    $match = $likes->like($request->user(), $request->targetPublicId());
    return response()->json(new LikeResource($match), 201);
}

// ビジネスロジック層：このアプリの決まり
public function like(User $me, string $targetId): ?UserMatch
{
    return DB::transaction(function () use ($me, $targetId) {
        $target = $this->users->findActiveByPublicId($targetId);   // データアクセス層
        if ($this->likes->exists($me, $target)) {
            throw new AlreadyLiked();
        }
        $this->likes->create($me, $target);
        return $this->likes->exists($target, $me) ? $this->matches->create($me, $target) : null;
    });
}
  • メリット：分かる人がとても多い（入ってきた人がすぐ読める）。どこに何を書くかの迷いが減る。Fat Controller を直す最初の一歩として段階的に移しやすい
  • デメリット：業務の層が、下のデータアクセス層（つまり DB の形）に依存する。DB を変えると業務の層まで波が来ることがある。Repository が Eloquent を包むだけの薄いファイルになりやすい。Service が太りやすい
  • 向いているもの：中くらいまでの Web サービス・業務システム・API サーバー。チームに初めての人が多いとき

4. 内と外に分ける設計

3つとも考え方はほぼ同じで、業務を真ん中に置き、DB・フレームワーク・外のサービスを外側に置く。外側から内側へだけ矢印を引く。違いは、層の切り方と呼び方。

4-1. ヘキサゴナルアーキテクチャ（ポートとアダプター）

flowchart LR
  HTTP["HTTP の入口 アダプター"] --> IN(["入口のポート いいねする"])
  CLI["コマンド・キューの入口 アダプター"] --> IN
  IN --> CORE["業務 いいねとマッチの決まり"]
  CORE --> OUT1(["出口のポート いいねを保存する"])
  CORE --> OUT2(["出口のポート 通知を送る"])
  PG["PostgreSQL のアダプター"] -.実装する.-> OUT1
  FS["Firestore のアダプター"] -.実装する.-> OUT1
  MAIL["メールのアダプター"] -.実装する.-> OUT2
  • 考え方：業務の側が「何が要るか」を口（ポート）として決め、DB や外の API はその口に合わせた部品（アダプター）にする。入口も HTTP だけでなく、コマンドやキューから同じ業務を呼べる
  • メリット：外のものを差し替えやすい（決済の会社・メールの送り先・DB）。業務を、DB なしで速くテストできる
  • デメリット：口と部品の2つずつファイルが増える。差し替える予定のないものにまで口を作ると、読むのが遠回りになる

4-2. オニオンアーキテクチャ

flowchart TB
  subgraph 外側["外側：画面・API・DB・外のサービス（Infrastructure）"]
    subgraph アプリ["アプリケーションサービス（ユースケース）"]
      subgraph ドメインサービス["ドメインサービス"]
        M["ドメインモデル（中心）"]
      end
    end
  end
  • 考え方：玉ねぎのように、中心にドメインモデル（業務のデータと決まり）、その外にドメインサービス、その外にユースケース、いちばん外に DB・画面。依存は外 → 内だけ。Repository の口（インターフェース）は内側に置き、実装は外側に置く
  • メリット：業務の中心が、どのライブラリにも依存しない
  • デメリット：ヘキサゴナルと同じ（ファイルと決まりが増える）。Eloquent のように「Model が DB を知っている」作りとは相性が悪く、Laravel では Model を2種類（業務の Model と DB の Model）持つかどうかで悩む

4-3. クリーンアーキテクチャ

flowchart LR
  F["フレームワークとドライバ Laravel・PostgreSQL・Web"] --> A["インターフェースアダプター Controller・Presenter・Gateway"]
  A --> U["ユースケース 1つの操作ごと"]
  U --> E["エンティティ 業務の決まり"]
  • 考え方：同心円の4層（エンティティ → ユースケース → アダプター → フレームワーク）。ヘキサゴナルとオニオンをまとめ直したもので、依存は内側へだけ（依存性のルール）。ユースケースを1操作1クラス（例：LikeUser）にするのが特徴
  • メリット：フレームワークを替えても、業務とユースケースが残る。テストしやすさは最も高い
  • デメリット：ファイルの数と、層をまたぐたびのデータの詰め替え（入力の型・出力の型）が最も多い。小さなアプリでは「層を通すだけ」のコードが大半になる

4-4. 3つの違い（まとめ）

ヘキサゴナルオニオンクリーン
見方内（業務）と外（つなぐ部品）の2つ同心円の4層同心円の4層
強調すること口と部品で差し替えるドメインモデルが中心依存は内側へだけ・ユースケースが主役
Laravel での形の例Domain/・Ports/・Adapters/Domain/・Application/・Infrastructure/Entities/・UseCases/・Adapters/・Frameworks/

レイヤードとの決定的な違いは依存性逆転。レイヤードでは「業務 → DB」と矢印が下を向くが、この3つでは DB の側が業務の決めた口に合わせる（「DB → 業務の口」）。

5. 縦に切る設計

5-1. モジュラーモノリス

flowchart LR
  subgraph アプリ["1つのアプリ（モノリス）"]
    M1["会員モジュール"]
    M2["いいねとマッチモジュール"]
    M3["メッセージモジュール"]
    M4["有料プランモジュール"]
  end
  M2 -->|公開した関数だけを呼ぶ| M1
  M3 -->|公開した関数だけを呼ぶ| M2
  M4 -->|公開した関数だけを呼ぶ| M1
  • 考え方：1つのアプリのまま、機能（モジュール）ごとにフォルダを分け、モジュールどうしは決めた入口（公開した関数）だけでやり取りする。ほかのモジュールの表を直接読まない
  • メリット：1つの機能の変更が1つのフォルダに閉じる。いずれマイクロサービスに分けるとき、切り口がもうある。モジュールの中は、3層でもクリーンでも好きな形にできる
  • デメリット：モジュールの境目を最初に引き間違えると、あとで直すのが大変。境目を守る仕組み（アーキテクチャのテスト）がないと、すぐ崩れる
  • 向いているもの：機能が増え続けるサービス・チームが複数に分かれ始めたプロダクト

5-2. 垂直スライス

  • 考え方：「1つの操作（いいねする）」を、入口から DB まで1つのフォルダ（または1ファイル）にまとめる。層ではなく操作で切る
  • メリット：1つの操作を足す・消すのが、そのフォルダだけで済む。読む場所が1か所
  • デメリット：操作どうしで同じ処理が重なりやすい（重複を許す考え方）。共通の決まりをどこに置くかで迷う
  • 向いているもの：画面や操作ごとの独立が強いもの。管理画面のように「一覧・詳細・停止」が並ぶもの

6. DDD（ドメイン駆動設計）

フォルダの形ではなく、業務の専門家と同じ言葉で、業務をコードにするための考え方。2つの段がある。

段道具このアプリの例
戦略設計（大きな分け方）ユビキタス言語（チームで同じ言葉を使う）・境界づけられたコンテキスト（言葉の意味が同じ範囲で区切る）「会員」は、会員の側では「出会う相手」、管理画面では「停止できる人」、売上では「お金を払う人」。意味が違うので、別のまとまりにする
戦術設計（コードの部品）エンティティ（ID で区別するもの）・値オブジェクト（値で区別するもの）・集約（一緒に整合性を守るまとまり）・ドメインサービス・リポジトリ・ドメインイベント値オブジェクト：Price（金額と通貨）・Age。集約：「購入」と「有効期間」を一緒に守る。イベント：「マッチした」
  • メリット：業務が複雑でも、コードが業務の言葉で読める。仕様の変更が、業務の言葉の変更として1か所に効く
  • デメリット：学ぶことが多く、業務の専門家と話す時間が要る。業務が単純（データを入れて出すだけ）なら、手間に見合わない
  • 向いているもの：業務の決まりが複雑で長く育てるもの（お金・予約・物流・保険・医療など）
  • 組み合わせ：戦略設計はモジュラーモノリスの「境目」を決めるのに使える。戦術設計の部品（値オブジェクトなど）は、3層の Service の中でも使える

8. 将来の変更が来たとき、何か所を直すか

このアプリで起こりうる変更で比べる。「〇」は1か所で済む、「△」は数か所、「×」は広く直す。

来る変更MVC3層ヘキサゴナル・オニオン・クリーンモジュラーモノリス何が効くか
決済の会社を入れる・替える（08）×（Controller に直書き）△（Service が決済の SDK を直接使うと、Service まで直す）〇（決済のアダプターを1つ足すだけ）△〜〇（中身による）外のサービスとの境目に口があるか
メッセージを Firestore に移す（05c）×△（Repository を直す。Model を上に返していたら Service と Resource も）〇（保存のアダプターを差し替える）△（メッセージのモジュールの中だけ）DB の都合が上の層に漏れていないか
プランを一般とプラチナに分ける（07b）×（判定が Controller の各所にコピー）〇〜△（判定が Service に1つなら1か所）〇（ドメインの決まりを直す）〇（有料プランのモジュールの中）業務の判定が1か所にあるか（設計の形より SSoT が効く）
管理画面に機能を足す△△（層ごとにファイルを足す）△（層ごとにさらに多く足す）〇（モジュールを1つ足す）機能で縦に切れているか

会員が100倍で、メッセージだけ別のサーバーに分ける××（層で横に切ったので、機能の切り口がない）△〇（モジュールの境目で切る）機能の境目があるか
Laravel から別のフレームワークへ××（Service が Eloquent を使う）〇〜△（内側は残る）×〜△業務がフレームワークを知らないか。実際にはまれ

表から分かること：どの形でも、1つの事実（判定・定数）を1か所に書くこと（SSoT）と、外との境目に口を作ることが、変更に一番効く。形の名前よりも、この2つを守れているかの方が大事。

9. 形は育てていくもの

flowchart LR
  A["MVC Fat Controller"] -->|業務を Service に出す| B["3層"]
  B -->|外との境目だけ口を作る| C["3層と差し替え口"]
  C -->|機能の境目を引く| D["モジュラーモノリス"]
  D -->|負荷やチームの都合で切り出す| E["マイクロサービス"]
  • はじめから最終の形にしない。困りごとが出たところで、次の形へ1段だけ進む（必要になってから足す）
  • 移すときは、一気に書き換えず、触る機能から少しずつ新しい形にする（ストラングラーパターン：古いものを新しいもので少しずつ置き換える）。このプロジェクトの「触る API には先にテストを足す」は、この移し方の安全装置
  • どの段でも、決めた依存の向きをアーキテクチャのテスト（Pest の arch()）で機械で守る

10. このプロジェクトに当てると（リーダーの見立て）

場所決まった形取り入れるとよいものまだ入れないもの
会員の側（backend/client） 3層
  • 外との境目（決済・メール・Firestore・時刻）だけ、差し替え口を作る（ヘキサゴナルの考え方を一部）
  • 値オブジェクト（金額・年齢）を、Service の中で使う（DDD の部品を一部）
  • Repository は Model をそのまま上に返さない決まり、または with() を Repository の中で決める決まり（N+1 を防ぐ）
 DB の Model と業務の Model の2つ持ち・全部の表へのインターフェース
管理画面（backend/admin） モジュール
  • 画面の領域（会員・メッセージ・売上・プラン・監査ログ）ごとにモジュールを1つ
  • モジュールの中は薄く（垂直スライスに近い形）
  • 監査ログを書く処理だけは、全モジュールが使う共通の入口にする
 モジュールの中の細かい層分け

Repository の作り方・Service の単位・管理画面のモジュールの中身は、docs/cycles/01-backend-foundation/03-how.md で人と決める。

11. 罠

  • 形だけ真似る：フォルダを3つに分けても、Service が Request を受け取ったり、Repository の中で業務の判断をしたりすれば、中身は Fat Controller と同じ
  • 全部に口を作る：差し替える予定のないものにインターフェースを作ると、読む人が実装を探して迷う
  • Model が層を越えて漏れる：Eloquent の Model を Resource まで渡すと、Resource の中でリレーションを読み、N+1 になる
  • Service が太る：機能ごとに1つの Service にすると、千行を超えることがある。操作が増えてきたら、操作ごとに分ける
  • 決めっぱなし：アーキテクチャのテストがないと、急いだときに1行の近道が入り、半年で崩れる

12. 理解を確かめる問い

レイヤードとクリーンの一番の違いは？

依存の向き。レイヤードは「業務 → DB」と下を向き、業務の層が DB の層を知っている。クリーン（オニオン・ヘキサゴナルも）は依存性逆転で、業務の側が口を決め、DB の側がそれに合わせる。だから DB を替えても業務の層を直さずに済む。

なぜこのアプリの会員の側は、クリーンではなく3層にしたのか？

規模が中くらい（API 24本）で、入ってきた人がすぐ読めることを重く見たため。クリーンはテストしやすさと差し替えやすさで勝つが、ファイルと詰め替えのコードが多く、この大きさでは層を通すだけのコードが増える。差し替えが本当に要る外との境目（決済・メール・Firestore）だけ、口を作って補う。

DDD は3層と一緒に使える？

使える。DDD はフォルダの形ではなく考え方なので、戦略設計（言葉と境目）でモジュールの切り口を決め、戦術設計の部品（値オブジェクト・集約）を Service の中で使える。全部を入れる必要はない。

会員が100倍になり、メッセージだけ別のサーバーに分けたい。どの形だと楽か？

機能で縦に切っているモジュラーモノリス。モジュールの境目が、そのままサービスの境目になる。3層は層で横に切っているので、メッセージに関わるコードが3つの層に散らばり、切り出すときに集め直す必要がある。

形を決めても崩れないようにするには？

依存の向き（例：Service は Illuminate\Http を使わない、Repository は Service を使わない、管理画面のモジュールはほかのモジュールの中を直接使わない）を、Pest の arch() でテストにする。CI で落ちれば、急いでいても近道が入らない。

どの形でも、変更に一番効くのは何か？

1つの事実を1か所に書くこと（SSoT）と、外との境目に口を作ること。たとえば「有料かどうか」の判定が1か所にあれば、プランを増やすときに1か所を直せば済む。形の名前より、この2つを守れているかの方が大事。
