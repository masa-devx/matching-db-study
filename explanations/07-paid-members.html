07 有料会員

作成: 2026-11-13 ／ 状態: レガシー版まで ／ 要件: docs/requirements/paid-members.md（FR-PAID-001〜017・NFR-PAID-001〜004）・screens.md の FR-UI-038〜040

この一歩でできるようになること
  • 「買ったときの値段」を、注文の行に写して残す理由（スナップショット）を説明できる
  • 有料かどうかを、真偽値の列ではなく「期限」と「購入の記録」から決める形にできる
  • どの機能が有料かを1か所で決め、API と画面が同じ判断を使う形（出し分け）を作れる

1. 何を作るか

男性の会員が、プランの一覧（/plans）で1か月・3か月・6か月から選び、購入の画面で「購入する」と、有料会員になります（決済はせず、押したらすぐ。08 で決済の通知に置き換えます）。男性の無料の会員は、メッセージを送る・1日11回目からのいいね・検索の身長の条件が使えず、画面では「有料」の印と誘導のモーダルが出ます。女性などほかの性別の会員は、すべて無料で使えます。期限が過ぎたら、何もしなくても無料に戻ります。

レガシー版は、設計を考えずに「とりあえず使える」形で作ります。users.is_paid（真偽値）を立て、有料の機能の入口ごとに if を写します。

2. 先に知っておく言葉

言葉意味（1〜2文）
スナップショットそのときの値を、記録の行に写して残すこと。商品の値段を変えても、前の注文の金額が変わらないようにする。
有効期間始まり（starts_at）と終わり（ends_at）で、いつからいつまで効くかを持つこと。「今が期間の中か」で状態が決まるので、期限が来ても行を書き換えなくてよい。
フラグの列is_paid のような真偽値の列。期限や記録とずれやすく、「期限が過ぎたのに true」のような食い違いができる。
出し分け同じ画面・API でも、会員の状態（有料か・性別）で、使える機能を変えること。
行ロック（for update）トランザクションの中で行を読みながら押さえ、ほかのトランザクションがその行を押さえるのを、終わるまで待たせる。同じ会員の処理を1つずつにできる。
timestamptz時間帯つきの日時（PostgreSQL）。UTC で持ち、読むときに好きな時間帯に直せる。日本時間の「今日」の区切りを正しく計算できる。

4. 設計の選択肢を比べる

有料かどうかの持ち方

案良いところ弱いところ向いている場面
A. users.is_paid（真偽値）読むのも書くのも1列期限が過ぎたら、だれかが false に戻さないといけない（バッチ）。戻し忘れると有料のまま。購入の記録とずれるレガシー版（product.md の用語）
B. users.paid_until（期限だけ）「期限 > 今」で決まり、戻す処理が要らないいつ・いくらで買ったかが残らない記録が要らないとき
C. purchases の記録の max(ends_at) から決める記録が1つの事実になり、状態はそこから出す。期限が来ても書き換えない有料かを知るのに、記録を読む（索引で1回）改善版

買ったときの値段の残し方

案良いところ弱いところ向いている場面
A. purchases.plan_id だけ持ち、値段は plans を読む列が少ないプランの値段を変えると、前の記録の値段も変わって見えるレガシー版
B. purchases に値段と期間を写す（スナップショット）前の記録が変わらない。プランを読まずに記録を出せる同じ値が2か所にある（ただし「今の値段」と「買ったときの値段」は別の事実）改善版
C. 値段の履歴の表（plan_prices：いつからいつまでいくら）値段の移り変わりも残る記録を出すたびに、買った時点の値段を探す JOIN が要る値段の改定を分析したいとき

出し分け（どの機能が有料か）

案良いところ弱いところ向いている場面
A. 入口ごとに if (男性 && ! is_paid) を写す（画面にも写す）すぐ書ける有料の機能を変えるたびに、API と画面の if を探して直す。写し忘れるレガシー版
B. 有料の機能の一覧を設定（config/features.php）に置き、1つの関数で判断し、GET /api/me で画面に「使える機能」を渡す1か所を変えれば、API も画面も変わる（FR-PAID-017）。判断は純粋な関数でテストしやすい設定の変更にはデプロイが要る改善版
C. 機能の表（features・plan_features）を DB に持つデプロイなしで変えられる。プランが増えても表に行を足すだけ07 ではプランが1種類なので、表が過剰07b（一般とプラチナ）

いいねの1日の上限

案良いところ弱いところ向いている場面
A. 数えてから入れる（ロックなし）・created_at::date短い同時に送ると上限を超える。日付が UTC（日本時間の 9時に数え直す）。列に関数をかけるので索引が効かないレガシー版
B. 会員の行を for update で押さえて、日本時間の範囲で数える同じ会員だけが待つ。索引 (from_user_id, created_at) が使えるトランザクションの中で数える分、少し長く押さえる改善版
C. 日ごとの数の表（(user_id, date) の UNIQUE）を upsert … returning で1つ増やす数えない。1本で増やして確かめられる表が1つ増える。いいねを取り消すと数がずれる上限の種類が多いとき
この一歩で選ぶもの：改善版は、有料かを purchases の max(ends_at) から決め（C）、買ったときの値段と期間を写し（B）、有料の機能の一覧を設定に置いて1つの関数で判断し、GET /api/me で画面に渡す（B）。いいねの上限は行ロックで数える（B）。レガシー版は、ユーザーの言葉どおり「とりあえず使える」形（それぞれ A）で作り、何が困るかを測ります。

5. 見本：レガシー版と改善版

レガシー版（Fat Controller・テストなし）

// PurchaseController::store（JWT の処理を写す）
$plan = Plan::find($request->input('plan_id'));
Purchase::create(['user_id' => $me, 'plan_id' => $plan->id]);
$user->update(['is_paid' => true, 'paid_until' => ($user->paid_until ?? now())->addMonths($plan->months)]);

// MessageController::store・LikeController::store・UserController::index に写す
$profile = Profile::where('user_id', $me)->first();
$user = User::where('id', $me)->first();
if ($profile->gender === 'male' && ! $user->is_paid) {
    return response()->json(['message' => '有料会員になると使えます'], 403);
}
// 画面にも同じ判断を写す（TalkPage・SearchPage・UserPage）
const locked = me?.profile?.gender === 'male' && !me?.is_paid
  • 期限が効かない：is_paid だけを見るので、paid_until が過ぎても有料のまま（FR-PAID-005）
  • 値段が変わる：記録はプランを指すだけなので、値段を変えると前の記録の値段も変わる（FR-PAID-004）
  • 期限の延ばし方：期限が過ぎた人が買い直すと、過去の期限から足すので、期間が短くなる
  • 性別を変えて抜けられる：購入まわりは男性だけ（レガシー版でも確かめる）だが、性別はプロフィールの今の値で見る。プロフィールの編集は性別も書き換えるので、男性が女性に変えると無料で使え、女性が男性に変えると買える
  • いいねの上限：同時に送ると超える。日付の区切りが UTC
  • 出し分けが散らばる：同じ判断が API に3か所・画面に3か所。有料の機能を変えるには6か所を直す

改善版

// config/features.php：有料の機能の一覧（ここを変えれば、API も画面も変わる）
return ['paid' => ['send_message', 'unlimited_likes', 'advanced_search']];

// app/Support/Features.php：判断は1か所（SQL を流さない純粋な関数）
public static function allows(User $me, string $feature, CarbonImmutable $now): bool
{
    if (! in_array($feature, config('features.paid'), true)) return true;
    if ($me->gender_code !== Gender::MALE) return true;
    return $me->paid_until !== null && $me->paid_until->greaterThan($now);
}

// GET /api/me：画面はこれで出し分ける
'features' => collect(config('features.paid'))->mapWithKeys(fn ($f) => [$f => Features::allows($me, $f, now())]),

大事なのは3つです。① 有料かは purchases から出し、users に印を持たない（期限が来ても何も書き換えない）。② 買ったときの値段と期間を purchases に写す。③ 「どの機能が有料か」と「使ってよいか」を1か所に置き、画面は features を見るだけにする。

Eloquent が発行する SQL（レガシー版と改善版を並べる）

ログ（sql-*.log）では、値は ? になり、別に渡されます。読みやすいよう、ここでは値を入れて、行を分けて書きました。

改善版4本＋begin・commit

DB::transaction(function () use ($me, $plan) {
    DB::table('users')->where('id', $me->id)->lockForUpdate()->value('id');
    $plan = Plan::findOrFail($planId);
    $last = Purchase::where('user_id', $me->id)->max('ends_at');
    $start = max(now(), $last ?? now());   // 有料のあいだなら、今の期限から
    Purchase::create([
        'user_id' => $me->id, 'plan_id' => $plan->id,
        'months' => $plan->months, 'price_yen' => $plan->price,   // 買ったときの値を写す
        'starts_at' => $start, 'ends_at' => $start->copy()->addMonthsNoOverflow($plan->months),
    ]);
});

    ->selectSub(DB::table('purchases')->selectRaw('max(ends_at)')

    ->where('users.id', $id)->first();

改善版3本＋begin・commit

DB::transaction(function () use ($me, $to) {
    DB::table('users')->where('id', $me->id)->lockForUpdate()->value('id');
    [$from, $until] = Today::rangeInTokyo();   // 日本時間の0時〜次の0時（UTC に直す）
    $count = Like::where('from_user_id', $me->id)
        ->where('created_at', '>=', $from)->where('created_at', '<', $until)->count();
    if (! Features::allows($me, 'unlimited_likes') && $count >= 10) abort(403, 'paid_required');
    Like::create(['from_user_id' => $me->id, 'to_user_id' => $to->id]);
});

7. 気をつけること（罠）

  • フラグと期限の二重持ち：is_paid と paid_until を両方持つと、どちらが正しいか分からなくなる（ノートの X11「フラグの列が増え続ける」）

  • 日付の区切りと時間帯：アプリも DB も UTC。whereDate(…, today()) は UTC の日付なので、日本時間の 9時に数え直す。timestamp（時間帯なし）の列に日本時間で入れると、さらにずれる
  • 列に関数：created_at::date = ? は索引を使えない。created_at >= ? and created_at < ? の範囲にする
  • 画面だけで隠す：画面でボタンを隠しても、API を直接呼べば使える。判断は API で必ず行い、画面は同じ判断の結果（features）を見せるだけにする
  • 性別の書き換え：有料かを性別で分けるなら、性別を変えられないことが前提になる（members.md の FR-010）

8. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？（値段を写す・有料かを記録から出す・判断を1か所にする）

値段は運営が変えるので、記録がプランを指すだけだと、過去の購入の金額まで変わって見える。だから買ったときの値段と期間を記録に写す。有料かを is_paid で持つと、期限が来たときに書き換える処理が要り、忘れると有料のままになる。記録の ends_at から出せば、期限が来ても何もしなくてよい。どの機能が有料かは、変わりやすい業務の決まりなので、1か所に置き、API と画面が同じ判断を使う。

ほかの方法は？なぜ選ばなかったか？

users.paid_until だけを持つ形は、記録が残らない。値段の履歴の表は、記録を出すたびに時点で JOIN が要る。機能の表を DB に持つ形は、デプロイなしで変えられるが、プランが1種類の 07 では過剰なので 07b に回す。いいねの上限を日ごとの数の表で持つ形は、取り消しで数がずれる。

弱点は？

有料かを知るたびに max(ends_at) を読む（索引で1回なので軽い）。値段と期間がプランと記録の2か所にある（意味が違うので重複ではないが、名前で区別する）。有料の機能の一覧の変更にはデプロイが要る。いいねで会員の行を押さえるので、同じ会員の同時のいいねは並ぶ。

問題が起きたら、どう調べて直すか？

「期限が過ぎたのに使えた」なら、その API の判断が Features::allows() を通っているか、paid_until を一緒に読んでいるかを見る。「値段が違う」なら、記録の price_yen とプランの price を比べる。「上限を超えた」なら、トランザクションと for update が入っているか、範囲の時間帯が日本時間かを見る。

データが10倍・100倍になったら？

購入の記録が増えても、(user_id, ends_at) の索引で、会員ごとの最後の1件だけを読む。いいねが増えても、(from_user_id, created_at) の索引で、その日の分だけを読む。レガシー版の created_at::date は、その会員のいいねを全部読む（索引なしなら表の全部）。

Eloquent でどんな SQL が流れ、どう直したか？ Rails（ActiveRecord）・Prisma ならどう書くか？

レガシー版は、購入でプランを指すだけの行を入れ、users の印を書き換える（3本・トランザクションなし）。記録は 1＋N 本。機能の入口ごとに会員とプロフィールを読む（2本）。改善版は、行ロックのあとに値段と期間を写して入れ、会員を読むときに max(ends_at) を一緒に読む。
