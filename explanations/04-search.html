04 検索と一覧

作成: 2026-11-12 ／ 状態: レガシー版まで ／ Issue: #42 ／ 要件: docs/requirements/search.md（FR-SEARCH-001〜011・NFR-SEARCH-001）・docs/requirements/screens.md（FR-UI-015〜018）

この一歩でできるようになること
  • いくつもの条件（等しい・範囲・IN）と「いいねした相手を除く」を1本の SQL にまとめ、NOT EXISTS と whereNotIn の違いを説明できる
  • OFFSET のページ送りが、深いほど読む行が増え、途中でだれかがログインすると重なる・抜けることと、カーソル（最後の人の時刻と public_id）で直す方法を説明できる
  • 実行計画で、どの表を全部読み、何行を捨てたかを読み、インデックスを1つ足したときの違いを、2万人のデータで確かめられる

1. 何を作るか

会員が、性別・年齢の幅・都道府県（1つ以上）・身長の幅で相手を絞り込み、最近ログインした人から順に、20人ずつ見られるようにします。画面は検索のタブで、写真の2列のカードを、下までスクロールすると続きが出る形にします。03b までは、相手を URL（/users/<public_id>。#46 で UUID にした）で開くしかありませんでした。

子 Issue作るもの要件
#43 DBusers に最終ログインの列（last_login_at）・試しの会員 2万人のシーダーFR-SEARCH-011・制約（2万人）
#44 APIGET /api/users（絞り込み・除く・並び・続き）・ログインで最終ログインを書き換えるFR-SEARCH-001〜011・NFR-SEARCH-001
#45 画面検索のタブ（/search）・2列のカード・絞り込み・下までスクロールで続きFR-UI-015〜018

出さない相手：自分・もういいねした相手・メールアドレスを確認していない会員。性別を選ばなければ、自分と違う性別を出します。速さの目標は置かず、実行計画・SQL の本数・時間・画面の表示速度は記録だけします。ブロックした相手を除くのは 06 です。

2. 先に知っておく言葉

言葉意味（1〜2文）
絞り込みの条件（等しい・範囲・IN）gender_code = 1（等しい）、birthdate between … and …（範囲）、prefecture_code in (13, 14)（どれか）。インデックスがどう効くかは、条件の種類で変わる。
OFFSETlimit 20 offset 40 は「先頭から40行を飛ばして、20行を返す」。飛ばす40行も読んでから捨てるので、ページが深いほど読む行が増える。
カーソル（keyset）「前のページの最後の人」の並びの値（最終ログインと public_id）を覚えておき、次は「それよりあと」から読む方法。何ページ目でも、飛ばす行を読まない。
NOT EXISTS「サブクエリに1行もなければ、その行を残す」条件。not exists (select 1 from likes where from = 自分 and to = 相手) で「いいねしていない相手」になる。
whereHas()Eloquent で「リレーション先に条件に合う行がある」を書く方法。SQL は exists (select * from profiles where users.id = profiles.user_id and …)（相関サブクエリ）になる。
複合インデックス2つ以上の列をこの順で並べたインデックス。(last_login_at, public_id) なら、最終ログインで並べ、同じ時刻は public_id で並べたものになる。
実行計画DB が SQL をどう動かすかの手順。EXPLAIN (ANALYZE, BUFFERS) で、実際に動かして、段ごとの行数・時間・読んだページ数を見る。
NULLS FIRSTPostgreSQL は、order by … desc のとき、NULL を先頭に置く。最終ログインが NULL（一度もログインしていない）の会員が、いちばん上に出る。
シーダー試しのデータを DB に入れるプログラム（database/seeders/）。2万人を、性別・年齢・都道府県・身長をばらつかせて作る。
IntersectionObserverブラウザの仕組みで、「ある要素が画面に入った」ことを知らせる。一覧のいちばん下に目印を置き、見えたら続きを読む。
LCP・CLSLighthouse の数字。LCP はいちばん大きい要素（写真など）が出るまでの時間、CLS は読み込み中に並びがずれた量。画像の大きさを決めておかないと、CLS が増える。

4. 設計の選択肢を比べる

続きの読み方（ページ送り）

案良いところ弱いところ向いている場面
A. OFFSET（?page=2。レガシー版）書くのが簡単。何ページ目にでも飛べる深いほど、飛ばす行を読んで捨てる。途中で並びが変わると、重なる・抜ける（図3）行がほとんど変わらない一覧・管理画面のページ番号
B. カーソル（?cursor=…。改善版）何ページ目でも、読む行が同じくらい。並びが変わっても、見た人がもう一度出ない任意のページに飛べない。並びの列に、必ず並びが決まる組（時刻と ID）が要る下までスクロールで続きが出る一覧（今回）
C. ページ番号と全件の数（count(*)）「全 1,234人」と、何ページあるかを見せられる毎回、条件に合う全員を数える SQL がもう1本要る。数えるのは件数に比例して重い件数を見せたいとき。今回は見せない

もういいねした相手を除く

案良いところ弱いところ向いている場面
A. ID を PHP に持ってきて whereNotIn（レガシー版）Eloquent で素直に書けるSQL が2本になり、いいねが 1,000件なら not in (…1,000個…) の長い SQL になる除く相手が、いつも数件だけのとき
B. not exists（改善版）1本の中で済み、いいねの数が増えても SQL が変わらない。likes の UNIQUE のインデックスで1回ずつ探すクエリビルダーの書き方が少し長い今回。06 のブロック（された相手も除く）も同じ形で足せる
C. left join likes … where l.id is nullNOT EXISTS と同じ結果。JOIN に慣れていれば読みやすいつなぐ相手が2行以上あると行が増える（今回は UNIQUE で1行まで）。意図が「除く」だと読み取りにくいJOIN した相手の列も使うとき

インデックス

案良いところ弱いところ向いている場面
A. なし（レガシー版）書き込みが軽い毎回、条件に合う全員を読んで並べ替える（2万人ならまだ速い）会員が少ないとき
B. 並びのインデックス users (last_login_at, public_id)（改善版）新しい順に読みながら、条件に合う21人が見つかったら止まる。カーソルの続きにも、そのまま使える条件がきびしい（合う人が少ない）と、見つかるまでたくさん読む。0人なら最後まで読む条件がゆるく、合う人が多い検索（性別だけ・年齢の幅が広い）
C. 絞り込みの複合インデックス profiles (gender_code, birthdate)条件がきびしい検索で、合う人だけを先に集められる集めたあとに並べ替える（Sort）。並びと条件の表が違うので、両方を1つのインデックスにはできない条件がきびしい検索が多いとき
この一歩で選ぶもの：レガシー版は、OFFSET・whereNotIn・インデックスなし・文字の列のままで作る（測る問題を出すため）。改善版は、カーソル・not exists・並びのインデックス B を選ぶ。下までスクロールする一覧ではページ番号が要らず、続きで同じ人が出ないことを守れるのはカーソルだけだから。C は、2万人で「条件がきびしいとき」と「0人のとき」の実行計画を測り、B だけで足りないと分かったら足す（先に両方を張らない）。

5. 見本：レガシー版と改善版

レガシー版（Fat Controller・テストなし）

// app/Http/Controllers/UserController.php の index()（JWT を読む6行は5か所目の写し）
$me = Profile::where('user_id', $payload->sub)->first();
$gender = $request->input('gender', $me->gender === 'male' ? 'female' : 'male');
$likedIds = Like::where('from_user_id', $payload->sub)->pluck('to_user_id');

$users = User::whereNotNull('email_verified_at')
    ->where('id', '!=', $payload->sub)
    ->whereNotIn('id', $likedIds)
    ->whereHas('profile', function ($q) use ($request, $gender) {
        $q->where('gender', $gender);
        if ($request->filled('height_min')) {
            $q->where('height', '>=', $request->input('height_min'));   // 文字で比べる
        }
        // 年齢・都道府県も同じように if を並べる
    })
    ->orderBy('last_login_at', 'desc')
    ->offset(($request->input('page', 1) - 1) * 20)->limit(20)
    ->get();
foreach ($users as $user) { $user->profile; }   // 1人ずつ読む
return response()->json($users);
  • SQL が 23本：自分のプロフィール・いいねの ID・本体・20人のプロフィール（1＋N）
  • 文字で比べる：height >= '170' では '99' も通る。生年月日も、'1995/4/1' や '2026-13-45' のような形の違う値は、正しく比べられない
  • 並びが決まらない：最終ログインだけで並べるので、同じ時刻の人の順が毎回変わることがある。NULL（一度もログインしていない人）がいちばん上に出る
  • OFFSET：深いページほど読む行が増え、途中でログインした人がいると、同じ人がもう一度出る（図3）
  • 入力を確かめない：age_min=abc は subYears() で例外になり、page=0 は offset -20 で SQL のエラーになり、どちらも 500 になる見込み
  • 出しすぎ：User をそのまま返すので、メールアドレス・verification_token・生年月日が出る

改善版

// app/Http/Controllers/UserSearchController.php（入力は SearchUsersRequest、認証はミドルウェア）
public function index(SearchUsersRequest $request): JsonResponse
{
    $me = $request->user();
    $c = $request->validated();
    $cursor = SearchCursor::decode($c['cursor'] ?? null);   // 最後の人の時刻と ID

    $rows = UserSearchQuery::build($me, $c, $cursor)->limit(21)->get();   // 5章の SQL の ②

    $page = $rows->take(20);
    $next = $rows->count() > 20 ? SearchCursor::encode($page->last()) : null;

    return response()->json([
        'data' => SearchResultResource::collection($page),   // 年齢は birthdate から計算。メールは出さない
        'next_cursor' => $next,                                // null なら「これで全員」
    ]);
}

大事なのは3つです。① 21人を読んで、21人目がいるかで「続きがあるか」を知る（全員を数えない）。② 次のカーソルは、返した20人の最後の人の last_login_at と public_id から作る（カーソルにも連番の id を出さない。D-022）。③ SQL を作るところ（UserSearchQuery）を分けておくと、06 でブロックの not exists を1つ足すだけで済む。

Eloquent が発行する SQL（レガシー版と改善版を並べる）

左がレガシー版、右が改善版です。SQL は Laravel に作らせて確かめたもので（列がまだないので、どれも DB::pretend() で、流さずに SQL だけを取り出した）、例は会員 23（さくら）が、男性・25〜35歳・東京都と神奈川県・身長 170 以上で、2ページ目を見る場合です。中身は explanations/sql/04-search.json にあり、explanations/tools/compare-block.py で作り直せます。

ログ（sql-*.log）では、値は ? になり、別に渡されます（プリペアドステートメント）。読みやすいよう、ここでは値を入れて、行を分けて書きました。

相手を探す（2ページ目。GET /api/users?gender=male&age_min=25&age_max=35&prefecture[]=…&height_min=170&page=2）

↓ 発行される SQL

-- ① 自分のプロフィール（性別の既定を決める）
select * from "profiles"
where "user_id" = 23 limit 1;

-- ② いいねした相手を全部 PHP に持ってくる
select "to_user_id" from "likes"
where "from_user_id" = 23;

-- ③ 本体。②の ID を全部 not in に並べる
select * from "users"
where "email_verified_at" is not null
  and "id" != 23
  and "id" not in (5, 7)
  and exists (
    select * from "profiles"
    where "users"."id" = "profiles"."user_id"
      and "gender" = 'male'
      -- 生年月日も身長も文字として比べる
      and "birthday" <= '2001-11-12'
      and "birthday" > '1990-11-12'
      and "prefecture" in ('東京都', '神奈川県')
      and "height" >= '170')
order by "last_login_at" desc
limit 20 offset 20;

-- ④ 1人ごとにプロフィールを読む（20回）
select * from "profiles"
where "user_id" = 101 limit 1;
  • whereHas() は exists (select * from profiles …) になる。条件は profiles にあるのに、取ってくるのは users なので、表示に使うプロフィールを ④ でもう一度読む（1＋N）
  • "height" >= '170' は文字の比べ。'99' は '170' より「大きい」（先頭の 9 と 1 を比べる）ので、身長 99 の会員も出る
  • order by "last_login_at" desc だけで、同じ時刻の並びが決まらない。PostgreSQL は desc のとき NULL を先頭に置くので、まだ一度もログインしていない会員が最初に出る
  • offset 20 は、飛ばす20人も読んでから捨てる。100ページ目なら 1,980人を読んで捨てる
  • 応答は User をそのまま返すので、メールアドレスと verification_token も出る

改善版2本

$gender = $c['gender'] ?? $me->profile->oppositeGenderCode();  // ①
$rows = DB::table('users as u')                                   // ②
    ->join('profiles as p', 'p.user_id', '=', 'u.id')
    ->whereNotNull('u.email_verified_at')
    ->where('u.id', '<>', $me->id)
    ->whereNotExists(fn ($q) => $q->select(DB::raw(1))->from('likes as l')
        ->where('l.from_user_id', $me->id)->whereColumn('l.to_user_id', 'u.id'))
    ->where('p.gender_code', $gender)
    ->whereBetween('p.birthdate', [$oldest, $youngest])
    ->whereIn('p.prefecture_code', $c['prefectures'])
    ->where('p.height_cm', '>=', $c['height_min'])
    ->when($cursor, fn ($q) => $q->whereRaw(
        '(u.last_login_at, u.public_id) < (?, ?)', [$cursor['at'], $cursor['public_id']]))
    ->orderByDesc('u.last_login_at')->orderByDesc('u.public_id')
    ->limit(21)   // 1人多く読んで、続きがあるかを知る
    ->select('u.public_id', 'p.nickname', 'p.birthdate', 'p.prefecture_code',
             'p.height_cm', 'p.image', 'u.last_login_at')
    ->get();

↓ 発行される SQL

-- ① 自分のプロフィール（性別の既定を決める）
select * from "profiles"
where "user_id" = 23 limit 1;

-- ② 本体。1本で絞り込み・除く・並び・続き
select "u"."public_id", "p"."nickname", "p"."birthdate",
       "p"."prefecture_code", "p"."height_cm",
       "p"."image", "u"."last_login_at"
from "users" as "u"
inner join "profiles" as "p"
  on "p"."user_id" = "u"."id"
where "u"."email_verified_at" is not null
  and "u"."id" <> 23
  -- いいねした相手は DB の中で除く
  and not exists (
    select 1 from "likes" as "l"
    where "l"."from_user_id" = 23
      and "l"."to_user_id" = "u"."id")
  and "p"."gender_code" = 1
  -- 年齢の幅を、生年月日の幅（date）に直して比べる
  and "p"."birthdate" between '1990-11-13' and '2001-11-12'
  and "p"."prefecture_code" in (13, 14)
  and "p"."height_cm" >= 170
  -- カーソル：前のページの最後の人より「あと」
  and (u.last_login_at, u.public_id) < ('2026-11-12 08:00:00', '01a1cfd1-9822-7205-b069-c72f2d33f8a3')
order by "u"."last_login_at" desc, "u"."public_id" desc
limit 21;
  • 一覧に出す列を JOIN で一緒に取るので、1人ごとの SQL がない。件数が増えても2本のまま（NFR-SEARCH-001）
  • not exists は、いいねが何千件あっても SQL の長さが変わらない。likes の (from_user_id, to_user_id) の UNIQUE のインデックスで、1人ごとに1回探すだけで済む
  • (last_login_at, public_id) < (…) は「時刻が前、または同じ時刻で public_id が小さい」。UNIQUE の public_id で並びを必ず決めるので、続きで重ならず抜けない（FR-SEARCH-006・008）
  • users (last_login_at, public_id) のインデックスを後ろから読めば、新しい順に読みながら条件に合う21人が見つかったところで止まる。ページが深くなっても、飛ばす行を読まない
  • last_login_at は NOT NULL（登録した時刻を最初の値にする）にして、NULL が先頭に出る問題をなくす

7. 気をつけること（罠）

  • LIMIT は「見つかるまで読む」：並びのインデックスで読むとき、条件に合う人が少ない・いないと、最後まで読む。合う人が多い条件だけで測ると、遅い場合が隠れる（0人の条件でも測る）
  • 年齢の境目：「25〜35歳」は、生年月日が「今日から36年前の翌日」〜「今日から25年前」。誕生日の当日を含むかどうかで1日ずれる。「今日」は日本時間で決める（サーバーは UTC）
  • 並びには、必ず決まる列を足す：最終ログインだけだと、同じ時刻の人の順が毎回変わり、カーソルでも重なる・抜ける。public_id（UNIQUE）を2つ目に足す。連番の id にすると、カーソルの中身から会員の番号が分かる
  • NULL の位置：desc では NULL が先頭。NOT NULL にするか、nulls last を書く
  • 空の IN：都道府県を選ばなかったときに whereIn('prefecture', []) を呼ぶと、Laravel は 0 = 1（だれも出ない）を作る。選ばなかったら条件を付けない
  • カーソルは読める：base64 にした時刻と public_id は、だれでも中身を読み、書き換えられる。書き換えても、見られるのは同じ検索の結果だけなので、ここでは隠さない（入力として形だけ確かめる）
  • Lighthouse は開発サーバーで測らない：npm run dev は、ビルドしていない JS を何十本も配るので遅く出る。npm run build のあと npm run preview で測る
  • 2万人を毎回作り直さない：シーダーは開発用の DB だけに流す。テスト用の DB では、テストごとに数人だけ作る

8. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？

下までスクロールすると続きが出る一覧では、ページ番号は要らず、「一度見た人がもう一度出ない」ことのほうが大事。OFFSET は、続きを読むあいだにだれかがログインすると並びがずれ、同じ人が出る。カーソルは「前のページの最後の人よりあと」から読むので、ずれない。いいねした相手は、PHP に ID を持ってくると件数に比例して SQL が長くなるので、not exists で DB の中で除く。レガシー版で、23本の SQL・文字の比べ・NULL が先頭・OFFSET のずれを実際に起こして測ってから直す。

ほかの方法は？なぜ選ばなかったか？

ページ番号と全件の数（count(*)）は、件数を見せられるが、毎回もう1本、条件に合う全員を数える SQL が要り、今回の画面では件数を見せない。left join … is null は not exists と同じ結果になるが、「除く」という意図が読み取りにくい。絞り込みの複合インデックス profiles (gender_code, birthdate) は、条件がきびしい検索に効くが、並びの列が別の表（users）にあるので、集めたあとに並べ替えが要る。どちらが効くかは条件で変わるので、先に並びのインデックスだけを張って測る。

弱点は？

カーソルは、任意のページ（10ページ目など）に飛べない。新しくログインした人は、1ページ目を読み直すまで出ない。並びのインデックスは、条件がきびしい・0人のときに、たくさん読む。ログインのたびに users とインデックスが書き換わるので、ログインがとても多いと書き込みが重くなる。カーソルの中身（時刻と ID）は画面から読める。

問題が起きたら、どう調べて直すか？

「検索が遅い」と言われたら、遅い条件を聞き、pg_stat_statements で平均と最大を見る。その条件で EXPLAIN (ANALYZE, BUFFERS) を取り、Seq Scan・Rows Removed by Filter・Sort・Buffers の read を見る。条件に合う人が少ないのに並びのインデックスで読み続けていれば、絞り込みの複合インデックスを足して、同じ条件で前と後を比べる。「同じ人が2回出る」なら、並びに ID が入っているか、OFFSET を使っていないかを見る。

データが10倍・100倍になったら？

20万人なら、カーソルと並びのインデックスで、ゆるい条件は今と同じくらいで返る。OFFSET は深いページほど遅くなる（5,000人目なら 5,000行を読んで捨てる）。200万人になると、きびしい条件・0人の条件で並びのインデックスを読み続けるのが重くなるので、よく使う条件に合わせた複合インデックスや、部分インデックス（確認済みの会員だけ）を測って足す。それでも足りなければ、検索だけを別の仕組み（検索用の表や検索エンジン）に分ける。いいねが 1人数千件になっても、not exists は UNIQUE のインデックスで1回ずつ探すだけなので変わらない。

Eloquent でどんな SQL が流れ、どう直したか？ Rails（ActiveRecord）・Prisma ならどう書くか？
Eloquent で流れる SQL → 問題直し方Rails（ActiveRecord）Prisma
条件whereHas('profile', …) → exists (select * from profiles …)。表示用のプロフィールを、もう一度1人ずつ読む（1＋N）join で一緒に取るUser.joins(:profile).where(profiles: { gender_code: 1 })user.findMany({ where: { profile: { genderCode: 1 } }, include: { profile: true } })（既定では、プロフィールを別の SQL で取ることがある）
