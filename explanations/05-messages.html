05 メッセージ

作成: 2026-11-13 ／ 状態: 解説だけ ／ Issue: #56 ／ 要件: docs/requirements/messages.md（FR-MSG-001〜014・NFR-MSG-001〜003）・docs/requirements/screens.md（FR-UI-019〜022） ／ 決めたこと: D-023

この一歩でできるようになること
  • マッチ（関係）・トークルーム（場所）・参加者（一人ひとりの状態）・メッセージ（中身）を別の表に分ける理由と、あとから足す列がどこに入るかを説明できる
  • 「外部キーと UNIQUE はあるが、インデックスは足していない」表で何が起きるかを実行計画で示し、PostgreSQL が外部キーの列にインデックスを作らないことと、足すインデックスの選び方を説明できる
  • 「相手ごとの最新の1件」を、ループ（N+1）・DISTINCT ON・ROW_NUMBER・LATERAL で書き分け、5秒ごとのポーリングで読む量を、マッチ 1000組・メッセージ 10万件で比べられる

1. 何を作るか

マッチした2人が、文字のメッセージを送り合えるようにします。マッチしたときにトークルームを1つ作り、2人を参加者として入れます。メッセージのタブ（/messages）は、03b の「マッチした相手の一覧」を、相手ごとの最新の1件と未読の数が出るトークの一覧に変えます。相手を押すとトーク画面（/messages/<ルームの public_id>）に移ります。

送れるのは文字だけ（1〜1000文字）。相手に「既読」は見せず、自分の側の未読の数だけを出します。新しいメッセージは、WebSocket で押し出さず、画面が5秒ごとに取りに行きます（リアルタイムは 05c の Firestore と比べる）。ブロック（blocks）・通報（reports）は 06 で別の表にします。

2. 先に知っておく言葉

言葉意味（1〜2文）
外部キーとインデックス外部キーは「指す先の行があるか」を守る制約で、検索を速くするものではない。PostgreSQL は、外部キーの列にインデックスを自動で作らない（MySQL の InnoDB は作る）。作られるのは主キーと UNIQUE の分だけ。
複合インデックスの列の順(talk_room_id, user_id) のインデックスは、電話帳のように先に talk_room_id で並ぶ。talk_room_id だけ・両方での検索には効くが、user_id だけの検索には効かない。
グループごとの最新の1件「ルームごとに、いちばん新しいメッセージを1行」。group by と max(created_at) では時刻しか取れず、その行の本文が取れないので、別の書き方が要る。
DISTINCT ONPostgreSQL だけの書き方。select distinct on (talk_room_id) … order by talk_room_id, id desc で、ルームごとに並びの先頭の1行だけを残す。
ウィンドウ関数（ROW_NUMBER）行を減らさずに、グループの中での番号を付ける関数。row_number() over (partition by talk_room_id order by id desc) が 1 の行が、ルームごとの最新。どの DB でも使える。
LATERAL「左の表の1行ごとに、右のサブクエリを1回動かす」JOIN。サブクエリの中で左の列を使えるので、「このルームの最新を1件」をそのまま書ける。
ポーリング画面が決まった間隔（今回は5秒）で、API に「新しいものはあるか」を聞きに行くこと。WebSocket より簡単だが、何もなくても毎回リクエストが来る。
既読の位置「この人はこのルームでここまで読んだ」を1行で持つ方法。未読は「それより新しい、相手のもの」を数える。レガシー版は時刻（last_read_at）、改善版は ID（last_read_message_id）で持つ。
相関サブクエリ外側の行の値を使うサブクエリ。外側の1行ごとに動く。1本の SQL の中なので N+1 ではないが、行ごとの手間はかかる。

4. 設計の選択肢を比べる

表の分け方

案良いところ弱いところ向いている場面
A. マッチの行をそのままルームにする（messages.match_id）表が増えないマッチ（関係）の列と、ルーム（場所）の列が1つの表に混ざる。マッチのないルーム（運営からのお知らせ・マッチ前に送れる有料の機能）を作れない。未読の位置を「組のどちら側か」で2列に分けることになるやり取りの機能を広げる予定がないとき
B. talk_rooms と talk_room_members を分ける（選ぶ）関係・場所・一人ひとりの状態・中身が、それぞれ1つの表になる。あとから足す列の置き場所が決まっている（下の表）。持ち主の確かめが「参加者に自分の行があるか」の1つの形になる表が2つ増え、マッチしたときに書く行が3つ増える（トランザクションが要る）今回。やり取りの機能が育っていくとき
表何を表すかあとから足す列の例
user_matchesお互いにいいねした関係（03）マッチの解除（unmatched_at・unmatched_by）・どこから生まれたか
talk_roomsやり取りの場所type（マッチ・お知らせ）・closed_at（解除・ブロック・退会で読むだけにする）・last_message_at（一覧が重いと測れたら写す）。match_id は、マッチのないルームを作るときに NULL を許す
talk_room_membersルームの中の一人ひとりの状態既読の位置・通知を切る・非表示・ピン留め・入った日時
messagesやり取りの中身type（画像・スタンプ・システムの文）・edited_at・deleted_at（取り消し）・返信先・運営が隠した日時
blocks・reports（06）会員から会員への拒否・通報マッチしていない相手にも起きるので、user_matches には持たない。通報は talk_room_id・message_id（NULL を許す）で、どのやり取りかを指す

受け取った人（receiver_id）は持たない：受け取った人は「そのルームの参加者のうち、送った人でない人」なので、talk_room_members から必ず求められます（join talk_room_members tm on tm.talk_room_id = m.talk_room_id and tm.user_id <> m.sender_id）。未読の数は「自分のルームで sender_id <> 自分」、トーク画面の左右は「sender_id が自分か」で決まるので、どちらにも要りません。持つと、参加者の表の写しになり、ずれたとき（ルームにいない人・送った人と同じ人が入る）を CHECK や外部キーでは防げず、3人以上のルームでは1つの列に入りません。receiver_id を持つのは、ルームの表を作らず sender_id と receiver_id の組でやり取りを表す設計のときです。受け取った人ごとに「読んだ」を1件ずつ持ちたくなったら、messages に列を足さず、message_receipts (message_id, user_id, read_at) を別に作ります。

インデックス（レガシー版は足さない）

インデックスレガシー版で起きること改善版で効く SQL弱いところ
messages (talk_room_id, id)外部キーはあるが、履歴・5秒ごと・最新の1件・未読の数のたびに、messages を全部読む履歴（id < ?）・新しいもの（id > ?）・LATERAL の最新・未読（id > 既読の位置）。外部キー talk_room_id の検索も、先頭の列で受け持つ送るたびに書き換わる
talk_room_members (user_id, talk_room_id)UNIQUE は (talk_room_id, user_id) の順なので、「自分のルーム」（user_id = ?）で全部読むトークの一覧の起点。外部キー user_id の検索も受け持つほぼ同じ中身のインデックスが2つになる
messages (sender_id)会員を消すとき（ON DELETE CASCADE）、消す1人ごとに messages を全部読む06 の退会・12 の「この人が送ったもの」05 の画面では使わない。06 で測ってから足してもよい
（足さない）UNIQUE の4つtalk_rooms.public_id・talk_rooms.match_id・talk_room_members (talk_room_id, user_id)・messages.public_id。ルームを探す・持ち主の確かめ・カーソルの読み替えは、レガシー版からこれで効く―

9-4 では、messages (talk_room_id, id) include (sender_id) も比べます。未読の数を、表を読まずにインデックスだけで数えられる（Index Only Scan）代わりに、インデックスが大きくなります。messages (created_at) は、並びを id で決めるので作りません。

相手ごとの最新の1件

案良いところ弱いところ向いている場面
A. ループで1件ずつ（レガシー版）Eloquent で素直に書けるルームの数だけ SQL が増える（N+1）。インデックスがないので、1本ごとに messages を全部読むルームがいつも数個のとき
B. DISTINCT ON (talk_room_id)短く書ける。1回の並べ替えで済むPostgreSQL だけ。自分のルームのメッセージを全部読んでから捨てるので、やり取りが長い人ほど遅いメッセージが少なく、ルームが多いとき
C. ROW_NUMBER() OVER (PARTITION BY …)どの DB でも使える。「最新の3件」にも広げやすいB と同じく全部読んで番号を付ける。サブクエリで包む必要があるほかの DB に移す見込みがあるとき
D. LEFT JOIN LATERAL (… limit 1)（改善版）(talk_room_id, id) があれば、ルームごとに1行読んで止まる。やり取りが何万件あっても変わらないルームの数だけインデックスを探す1つのルームのやり取りが長くなる、今回の形
E. talk_rooms に最新の1件を写す一覧の SQL は JOIN だけになり、いちばん速い送るたびに2つの表を書く。正が2つになる一覧がとても多く読まれ、D で足りないと測れたとき

未読の数と、新しいメッセージの届け方

案良いところ弱いところ向いている場面
未読 A. 最後に読んだ時刻 last_read_at（レガシー版）参加者の1行を書き換えるだけ同じ秒に届いたものの境目がずれる。一度も開いていないと null で、created_at > null が当てはまらず未読が 0 に見える見込み―
未読 B. 読んだメッセージの ID last_read_message_id（改善版）境目がずれない。(talk_room_id, id) の範囲で数えられる「途中の1件だけ読んでいない」は表せない（今回は要らない）未読の数だけを出す、今回の形
未読 C. メッセージごとの read_at相手に1件ずつ既読を見せられる開くたびに未読の行をすべて書き換える既読の印を見せたいとき（対象外）
届け方 A. 5秒ごとに新しい50件を読み直す（レガシー版）履歴の API をそのまま使える何もなくても毎回50件。入れ替えるので、さかのぼって読んだものが消える作り始めの試し
届け方 B. 5秒ごとに「最後に受け取ったものより新しいもの」（改善版）何もなければ0件。インデックスを1か所見るだけ何もなくてもリクエストは来る。id の順とコミットの順のずれ（7章）今回。数秒の遅れが許せるとき
届け方 C. WebSocket・Firestore で押し出すすぐ届き、何もないときのリクエストがない常につながるサーバーか、もう1つの DB が要る。切れたときの取り直しも要る05c で比べる

履歴の古い続きは、04 と同じく、レガシー版は OFFSET（?page=2）、改善版はカーソル（?before=<メッセージの public_id>）にします。

この一歩で選ぶもの：表は B（talk_rooms・talk_room_members・messages）に分け、レガシー版から主キー・UNIQUE・外部キーを持たせる。レガシー版は、インデックスを足さない・ループ（A）・last_read_at・5秒ごとに読み直す・OFFSET・持ち主を確かめない・マッチとルームを別々に入れる、で作る。改善版は、インデックス3つ・LATERAL（D）・last_read_message_id・新しいものだけ・カーソル・持ち主の確かめ・トランザクションにする。一覧・履歴・新しいもの・未読の数を、どれも「1つのルームの中を、新しいほうから少し読む」形にそろえれば、messages (talk_room_id, id) の1つで全部に効くから。B と C（DISTINCT ON・ROW_NUMBER）は、改善したあとに同じデータで実行計画を並べる。

5. 見本：レガシー版と改善版

レガシー版（Fat Controller・テストなし）

// database/migrations/…_create_messages_table.php（外部キーはあるが、インデックスは足さない）
Schema::create('messages', function (Blueprint $table) {
    $table->id();
    $table->foreignId('talk_room_id')->constrained()->cascadeOnDelete();   // PostgreSQL では索引は作られない
    $table->foreignId('sender_id')->constrained('users')->cascadeOnDelete();
    $table->text('body');
    $table->timestamps();
});

// app/Http/Controllers/MessageController.php の index()（JWT を読む6行は6か所目の写し）
$room = TalkRoom::where('public_id', $roomId)->first();   // 自分のルームかを確かめない
$messages = Message::where('talk_room_id', $room->id)
    ->orderBy('created_at', 'desc')
    ->offset(($request->input('page', 1) - 1) * 50)->limit(50)
    ->get();
TalkRoomMember::where('talk_room_id', $room->id)->where('user_id', $payload->sub)
    ->update(['last_read_at' => now()]);   // GET の中で書き込む（5秒ごとに呼ばれる）
return response()->json($messages);       // sender_id（中の連番）がそのまま出る
  • 外部キーの列にインデックスがない：foreignId()->constrained() は制約だけを作る。履歴・最新の1件・未読の数・5秒ごとの読み直しのたびに、messages を全部読む。会員を消すと、CASCADE のために messages を全部読む
  • UNIQUE の列の順：(talk_room_id, user_id) では「自分のルーム」（user_id だけ）を探せず、参加者の表を全部読む
  • 他人のトークが読める・送れる：ルームの UUID だけで探すので、UUID を知っていれば読めて送れる。制約は「だれが読めるか」を守らない（不変条件 6・8）
  • トークの一覧が 1＋6N 本：ルームごとに、ルーム・相手・プロフィール・public_id・最新の1件・未読の数
  • マッチとルームを別々に入れる：途中で失敗すると、マッチはあるのにルームがない
  • 読み直しで消える・GET で書き込む・入力を確かめない：さかのぼって読んだものが5秒で消える。空の本文も1万文字も入る

改善版

// マイグレーション：検索に使う列の組に、インデックスを足す
Schema::table('messages', function (Blueprint $table) {
    $table->index(['talk_room_id', 'id']);   // 履歴・新しいもの・最新の1件・未読の数
    $table->index('sender_id');              // 会員を消すときの CASCADE
});
Schema::table('talk_room_members', fn ($t) => $t->index(['user_id', 'talk_room_id']));   // 自分のルーム

// app/Http/Controllers/TalkRoomMessageController.php（認証はミドルウェア、入力は FormRequest）
public function index(Request $request, string $publicId): JsonResponse
{
    $roomId = TalkRooms::idFor($publicId, $request->user());   // 参加者に自分がいなければ 404
    $rows = MessageQuery::page($roomId, before: $request->query('before'), after: $request->query('after'))
        ->limit(51)->get();

    return response()->json([
        'data' => MessageResource::collection($rows->take(50)),   // is_mine を付け、中の ID は出さない
        'has_more' => $rows->count() > 50,
    ]);
}

大事なのは3つです。① インデックスは「どの SQL の、どの条件と並びに効かせるか」から決める（外部キーだから張る、ではない）。(talk_room_id, id) は条件の talk_room_id = ? と並びの id の両方に効く。② ルームを探すときは必ず参加者の表と JOIN し、ほかの人のルームとないルームを同じ 404 にする。③ 読んだことにするのは別の API（PUT …/read）にし、GET では書き込まない。

Eloquent が発行する SQL（レガシー版と改善版を並べる）

左がレガシー版、右が改善版です。SQL は Laravel に作らせて確かめたもので（表がまだないので、どれも DB::pretend() で、流さずに SQL だけを取り出した）、例は会員 23 が、相手 5 とのルーム（中の id は 7）を使う場合です。中身は explanations/sql/05-messages.json にあり、explanations/tools/compare-block.py で作り直せます。

6. どう確かめるか

段階確かめること
① レガシー版で問題を見る
  • psql の \d messages で、外部キーはあるがインデックスがないことを見る
  • トークの一覧の SQL の本数を、ルーム 1・10・100 で数える（DB::listen）。NFR-MSG-001
  • マッチ 1000組・メッセージ 10万件で、一覧の各 SQL・履歴（1ページ目と 20ページ目）・最新の1件・自分のルームの EXPLAIN (ANALYZE, BUFFERS)。Seq Scan と Rows Removed by Filter を見る。NFR-MSG-002
  • トーク画面を開いたまま1分：CDP で GET の本数と受け取った量、DB で update の回数。NFR-MSG-003
  • メッセージの多い会員を1人消す時間（CASCADE。EXPLAIN ANALYZE delete … の Trigger の時間）
  • 他人のルームの UUID で読む・送る（FR-MSG-002・003）。空・1001文字を送る（FR-MSG-004）。一度も開いていないルームの未読の数（FR-MSG-009）
  • 上までさかのぼってから5秒待ち、古いものが消えるか。続きを読むあいだに送られたとき、OFFSET で重なるか（FR-MSG-006・FR-UI-021）
② 振る舞いを固定するテスト要件 ID を名前に入れる。例：FR-MSG-002 マッチしていない相手には送れない・FR-MSG-003 他人のルームは見られない・FR-MSG-006 さかのぼるあいだに届いても重ならない・FR-MSG-009 未読の数は相手のものだけ・FR-MSG-010 開くと未読が0になる・NFR-MSG-001 トークの一覧はルームが増えても3本以内（SQL の本数を数えるテスト）
③ 改善したあとに比べる数字一覧の SQL の本数（ルーム 100 で 601本 → 2本）・同じデータでの実行計画の時間と Buffers（一覧・履歴の深い続き・新しいもの・自分のルーム）・1分のポーリングで読んだ行と返した件数・会員を1人消す時間・インデックスの大きさ（pg_relation_size）と送る時間の変化・DISTINCT ON・ROW_NUMBER・LATERAL の3つと、include (sender_id) の有無の実行計画

7. 気をつけること（罠）

  • 外部キー＝インデックスではない：MySQL（InnoDB）は外部キーの列にインデックスを自動で作るが、PostgreSQL は作らない。同じマイグレーションでも、DB によって速さが変わる。外部キーの列で検索するか・親を消すか（CASCADE）を見て、インデックスを決める
  • 複合インデックスは列の順で効き方が変わる：(talk_room_id, user_id) は user_id だけの検索に効かない。逆の順のものがもう1つ要る
  • インデックスは書き込みを重くする：messages に4つ張れば、送るたびに4つを書き換える。読む SQL から必要なものだけを選び、測ってから足す
  • UUID は鍵ではない：ルームの ID を UUID にしても、URL は履歴やログに残る。参加者に自分がいるかの確かめを、すべての API に入れる
  • id の順とコミットの順は違う：A の送信が id 100、B が 101 を取り、B が先にコミットすると、ポーリングは 101 を受け取り、次は「101 より新しいもの」を聞くので、あとから見えた 100 を取りこぼす。少し前から読み直して画面で重なりを除くか、起きうることを記録する
  • NULL との比べ：created_at > null はどの行にも当てはまらない。まだ開いていないルームの未読が 0 に見える
  • group by で最新を取ろうとする：select talk_room_id, max(created_at), body … group by talk_room_id は PostgreSQL ではエラー、MySQL の設定によっては別の行の本文が混ざる
  • ポーリングを setInterval で回す：遅い回線では前の呼び出しが終わる前に次が飛び、返ってくる順も入れ替わる

8. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？（なぜ表を4つに分け、インデックスをこの3つにするのか）

マッチ（関係）・ルーム（場所）・参加者（一人ひとりの状態）・メッセージ（中身）は、変わる理由が違うので、あとから足す列の置き場所が決まる（解除はマッチ、閉じるはルーム、通知を切るは参加者、取り消しはメッセージ）。インデックスは、一覧・履歴・新しいもの・未読の数を、どれも「1つのルームの中を、新しいほうから少し読む」形にそろえ、messages (talk_room_id, id) の1つで全部に効かせる。一覧の起点の「自分のルーム」には (user_id, talk_room_id)、会員を消すときの CASCADE には (sender_id) が要る。

ほかの方法は？なぜ選ばなかったか？

マッチの行をそのままルームにすると表は少ないが、マッチのないルームを作れず、未読の位置を組のどちら側かで2列に持つことになる。最新の1件は DISTINCT ON と ROW_NUMBER でも書けるが、自分のルームのメッセージを全部読んでから捨てるので、やり取りが長いほど遅い（改善版で並べて測る）。talk_rooms に最新の1件を写す案はいちばん速いが、正が2つになる。外部キーの列すべてにインデックスを張る案は、使わないもの（talk_rooms.match_id は UNIQUE で足りる）まで張り、書き込みを重くする。messages に receiver_id を持つ案は、参加者の表から分かることの写しで、ずれても DB が防げず、グループのトークで形が崩れるので選ばない。

弱点は？

マッチしたときに書く行が3つ増え、トランザクションが要る。messages のインデックスは、送るたびに書き換わる。ポーリングは、何もなくても会員1人につき5秒に1回のリクエストが来る（1000人が開いていれば、毎秒200回）。id の順とコミットの順がずれると、取りこぼしが起きうる。talk_room_members の2つのインデックスは中身がほぼ同じで、容量が2倍になる。

問題が起きたら、どう調べて直すか？

「一覧が遅い」なら、まず SQL の本数を見る（同じ形の SQL が値を変えて並んでいれば N+1）。1本でも遅ければ EXPLAIN (ANALYZE, BUFFERS) で、Seq Scan on messages と Rows Removed by Filter を探し、その条件の列にインデックスがあるかを \d messages で見る。外部キーの列でも、インデックスがなければ全部読む。「退会が遅い」なら、EXPLAIN ANALYZE delete from users where id = … の Trigger の時間で、どの外部キーの CASCADE が重いかが分かる。「他人のトークが見えた」なら、ルームを探す SQL に参加者との JOIN があるかを、すべての API で見る。

データが10倍・100倍になったら？

メッセージが 100万・1000万件になっても、インデックスを片側から読む形なので、1つのルームの履歴と新しいものの速さはほとんど変わらない（レガシー版は件数に比例して遅くなり、5秒ごとの読み直しがそのまま DB の負荷になる）。インデックスは表と一緒に大きくなり、メモリに載らなくなると読む量が増えるので、pg_relation_size で大きさを見る。ルームの多い会員では、一覧の LATERAL と未読の数がルームの数だけ動くので、一覧にもページ送りを入れるか、talk_rooms.last_message_at を写して並べる（案 E）。開いている会員が多くなれば、ポーリングの間隔を延ばす・見えていないときは止める・WebSocket や Firestore に移す。古いメッセージは、月ごとに表を分ける（パーティション）ことも候補になる。

Eloquent でどんな SQL が流れ、どう直したか？ Rails（ActiveRecord）・Prisma ならどう書くか？

Eloquent では、参加者の foreach の中でルーム・相手・プロフィール・最新の1件・未読の数を読むと、ルームごとに6本ずつ増える（N+1）。foreignId()->constrained() は外部キーだけを作り、インデックスは作らない（->index() を足すか、別に $table->index([...]) を書く）。改善版は、クエリビルダーの leftJoinLateral() と selectSub() で1本にした。

ORM外部キーとインデックス最新の1件をまとめる書き方
EloquentforeignId('talk_room_id')->constrained() は制約だけ。$table->index(['talk_room_id', 'id']) を足すhasOne(Message::class)->latestOfMany() と with()・withCount()、または leftJoinLateral()
Rails（ActiveRecord）t.references :talk_room, foreign_key: true は、既定でインデックスも作る（index: true）includes(:latest_message) は全件を読むことがあるので、joins("LEFT JOIN LATERAL …") か select("DISTINCT ON …")
Prisma@relation は、PostgreSQL ではインデックスを作らない。@@index([talkRoomId, id]) を書くinclude: { messages: { take: 1, orderBy: { id: 'desc' } } }（裏では別のクエリ）。未読の数は _count に条件か、$queryRaw で LATERAL
