2. 書き方の正本はどれか

PHP の書き方の決まりは、PSR-2（2012）→ PSR-12（2019）→ PER Coding Style（2022〜）と引き継がれてきた。Laravel の contributions.md は、今も「PSR-2 に従う」と書いている。実際に Laravel 本体とアプリのコードを直しているのは、Pint の laravel の preset。

flowchart TD
  A["書き方で迷った"] --> B{"Pint が直すか？"}
  B -- "直す" --> C["Pint が直した形にする（決まり 1）"]
  B -- "直さない" --> D{"PER Coding Style 3.1 に決まりがあるか？"}
  D -- "ある" --> E["PER に合わせる（決まり 2）"]
  D -- "ない" --> F["php-style.md に決まりを足すか、人に聞く"]

Pint の laravel の preset は、PER と逆の形に直す所がある。手元の Pint 1.32.2 で確かめた。

書くものPER Coding Style 3.1Pint の laravel
引数のない newnew Box()new Box
文字をつなぐ'a' . 'b''a'.'b'
否定決まりなし! $flag
短い無名関数fn($x)fn ($x)
引数の最後の ,複数行なら必ず配列だけ足す
パイプ演算子の空白前後に1つ直さない

このリポジトリで選ぶもの：Pint が直す所は Pint の形。Pint が直さない所（パイプ演算子の空白・引数の最後の ,）は PER の形。CI の pint --test が通る形と、文書の形をそろえるため。

3. Laravel 13 の公式の文書が勧めていること

3-1. Http と Console は、業務の処理を持たない

  • Laravel の文書は、Console と Http のフォルダを「アプリの中心への API」と呼び、アプリのロジックを持たないと書いている
  • このリポジトリでは、architecture-backend.md の Controller → Service → Model の形が、これに当たる

3-2. interface に頼らないクラスは、登録しなくても注入される

  • コンストラクタに private readonly ProfileService $profiles と書けば、Laravel が ProfileService を作って渡す。AppServiceProvider に何も書かなくてよい
  • 登録（bind()）が要るのは、interface の型を書いて、本物とテスト用の偽物を差し替えたいときだけ

3-3. ファサードは便利だが、クラスが大きくなったら分ける

  • 文書は、ファサードの一番の危なさを「クラスの受け持ちが知らないうちに広がること」と書いている
  • コンストラクタで受け取る形なら、引数が増えて目に見える。ファサードは、使う所が増えても見た目が変わらない

3-4. env() は config/ の中だけ

  • php artisan config:cache をすると、.env を読まなくなり、env() は OS の環境変数しか返さない
  • アプリのコードは config('...') で読む

3-5. トランザクションの中のメールと出来事は、確定のあとに送る

  • キューのワーカーは、トランザクションの確定を待たない。確定の前に動くと、まだ見えない行を読みにいく
  • メールは afterCommit()、出来事は ShouldDispatchAfterCommit、キューの Listener は ShouldQueueAfterCommit で、確定のあとにする
  • このリポジトリの config/queue.php は 'after_commit' => false（ひな形のまま）

3-6. Laravel のメソッドに、引数を名前で渡さない

  • リリースノートに「名前付き引数は、Laravel の後方互換の約束に入らない」とある。引数の名前は、小さい版の更新で変わることがある
  • architecture-backend.md の 7章の DB::transaction(fn () => ..., attempts: 3) は、DB::transaction(fn () => ..., 3) と書くほうが、この勧めに合う

4. PHP 8.4・8.5 の新しい書き方

どれも、手元の PHP 8.5.12 で動かして確かめた。Larastan は、今は PHP 8.3 として読むので、プロパティのフックを誤りにする（6章）。

4-1. プロパティのフック（PHP 8.4）

final class Nickname
{
    // 書くときに、前後の空白を取る
    public string $value {
        set(string $value) {
            $this->value = trim($value);
        }
    }
}
  • 使う場面：Model 以外の小さなクラスで、1〜2行の整え・作り
  • 使わない場面：DB を読む・外のサービスを呼ぶ処理。呼ぶ所からは、ただの代入に見えるため
  • Eloquent の Model には使わない。手元で確かめると、フック付きのプロパティを宣言した Model は、代入しても getAttributes() が [] のままだった（列に入らない）

4-2. 非対称の可視性 private(set)（PHP 8.4）

final class LikeLimit
{
    // 読むのはだれでも、書くのはこのクラスだけ
    public private(set) int $sentToday = 0;

    public function record(): void
    {
        $this->sentToday++;
    }
}
  • getSentToday() のような、読むためだけのメソッドが要らなくなる
  • Pint は、private(set) int $x と書くと public を足す

4-3. new を括弧で包まずにつなぐ（PHP 8.4）

$label = new Box()->label;     // PHP 8.4 から
$label = (new Box)->label;     // 前からの書き方
  • Pint 1.32.2 は、どちらの形も直さなかった。どちらにするかを決めておく

4-4. パイプ演算子 |>（PHP 8.5）

$slug = $title
    |> trim(...)
    |> strtolower(...)
    |> (fn (string $s): string => str_replace(' ', '-', $s));
  • 左の値を、右の関数に1つ目の引数として渡す。入れ子の呼び出しを、上から下へ読めるようにする
  • 矢印関数は、括弧で包まないと文法の誤りになる
  • Pint は、|> の前後の空白を直さない。PER の形（前後に空白・行の始めに置く）で書く

4-5. clone with（PHP 8.5）

final readonly class Point
{
    public function __construct(public int $x, public int $y) {}

    #[\NoDiscard]
    public function withX(int $x): self
    {
        return clone ($this, ['x' => $x]);   // Pint は clone のあとに空白を入れる
    }
}
  • readonly のプロパティを、複製しながら変えられる。PHP 8.4 までは、コンストラクタに全部の値を渡し直していた
  • Pint 1.32.2 は clone($this, ...) を clone ($this, ...) に直した。動きは同じ

4-6. #[\NoDiscard]（PHP 8.5）

  • 戻り値を使わないと、PHP が警告を出す。上の $point->withX(3); と書いて、$point が変わったと思い込む誤りを見つける
  • 手元で確かめた警告：The return value of method ... should either be used or intentionally ignored by casting it as (void)
  • わざと捨てるときは (void) $point->withX(3); と書く

4-7. 配列の関数（PHP 8.4・8.5）

  • PHP 8.4：array_find()・array_find_key()・array_any()・array_all()
  • PHP 8.5：array_first()・array_last()（空の配列なら null）
  • Eloquent の結果（Collection）には、今までどおり ->first(fn ...) を使う

5. 真偽と状態の名前

#243 で、真偽を返すメソッドの名前の決まりを architecture-backend.md の3章に足した。ここでは、その根拠にした資料を並べる。資料は #243 のときに読んだもので、このページを作るときには読み直していない。

5-1. 真偽を返すメソッドは、受け取る側についての主張として読める形にする

  • Swift の API Design Guidelines は、真偽を返すメソッドやプロパティを「受け取る側についての主張」として読める名前にする（x.isEmpty）と書いている
  • .NET の Framework Design Guidelines は、肯定の形にし、Is・Can・Has を頭に付けると書いている
  • Apple の Cocoa の命名も、is・can・should と、三人称単数の動詞を使う
  • PHP の世界（PER Coding Style・Symfony・Laravel の文書）には、真偽の頭の言葉の決まりはない。Laravel 本体（手元の vendor/laravel/framework/src）の public function の頭の言葉を数えると、has が 162・is が 121・should が 30・can が 1（同じ名前を1つに数えると、108・74・22・1）

5-2. 真偽の引数で、メソッドの動きを変えない

  • Martin Fowler の「FlagArgument」：book($user, true) は、呼ぶ所で true の意味が分からない。動きごとにメソッドを分ける
  • .NET の Parameter Design：真偽の引数が2つ以上になるなら、enum にする

5-3. 状態が3つ以上なら、真偽ではなく enum で持つ

  • Robert Harper の「Boolean Blindness」：true・false の値は、何を調べた結果かを持たない。値を受け取った側は、何が分かったのかを覚えておく必要がある
  • 会員のアカウントの状態は4つある。このリポジトリでは、列は日時のまま（deleted_at・suspended_at・banned_at）にし、User::accountStatus() が PHP の enum（AccountStatus）を返す
flowchart LR
  R["users の行"] --> Q{"User::accountStatus()"}
  Q -- "banned_at がある" --> B["Banned（強制退会）"]
  Q -- "deleted_at がある" --> W["Withdrawn（退会）"]
  Q -- "suspended_at がある" --> S["Suspended（アカウント停止）"]
  Q -- "どれもない" --> U["Usable"]
  U --> T["isAccountUsable() が true"]

上から順に確かめる（戻せないものを先にする）。backend/client/app/Models/User.php の78〜92行目。

5-4. 一度だけ起きる出来事は、日時の列で持つ

  • 「You might as well timestamp it」：真偽の列（is_verified）より、日時の列（verified_at）のほうが、「いつか」も分かる。コメント欄には、列の意味が二つになるという反論もある
  • Laravel も、email_verified_at と hasVerifiedEmail()、deleted_at と trashed() の形を使っている

6. このリポジトリでの当てはめ

6-1. Larastan が PHP 8.3 として読む

  • composer.json が "php": "^8.3" で、phpstan.neon に phpVersion がない。PHPStan は composer.json の版を読む
  • 手元で確かめると、プロパティのフックだけが Property hooks are supported only on PHP 8.4 and later. になった
  • phpVersion: 80500 を書いても、composer.json を ^8.5 にしても、この誤りは消えた。今のコードは、どちらでも両方のアプリで [OK] No errors
  • 勧めるのは composer.json を ^8.5 にするほう。PHP の版を書く所が1か所で済む（下書きの larastan-version.md）

7. 気をつけること（罠）

  • Eloquent の Model に、列と同じ名前のプロパティ（フック・private(set) を含む）を宣言すると、Eloquent を通らなくなり、列に入らない
  • Larastan が PHP 8.3 として読んでいても、private(set)・パイプ演算子・clone with は誤りにならなかった。誤りにならないからといって、PHP 8.3 で動くわけではない
  • architecture-backend.md の5章は「now() は CarbonImmutable」と書いているが、手元の now() は変えられる型（Illuminate\Support\Carbon）だった。$now->addDays(7) は $now も変える
  • Laravel の contributions.md の「PSR-2」は、Laravel 本体に PR を出す人向けの古い文。アプリの書き方は Pint の preset が正

8. 理解を確かめる問い

先に自分で答えてから、開いて見る。

PER Coding Style と Pint の形が違うとき、なぜ Pint に合わせるのか？

CI の pint --test が Pint の形を確かめるので、PER の形で書いても、Pint が直す。人が覚える決まりを減らし、文書とコードの形をそろえるため。

Laravel のメソッドに名前で引数を渡すと、何が困るか？

引数の名前は後方互換の約束に入らないので、小さい版の更新で名前が変わると、名前で渡した所だけが Error になる。順番で渡せば、名前が変わっても動く。

Model にプロパティのフックを使うと、なぜ列に入らないのか？

Eloquent は、宣言していないプロパティへの読み書きを __get・__set で受けて、$attributes に入れる。プロパティを宣言すると、PHP はそちらに直接書くので、__set が呼ばれない。

phpVersion: 80500 と composer.json の ^8.5、どちらで直すか？

composer.json。PHP の版を書く所が1か所になり、Composer も 8.5 より前の PHP に入れなくなる。phpVersion だと、composer.json の ^8.3 と食い違ったまま残る。

会員のアカウントの状態を、真偽の列4つで持つと何が困るか？

退会と強制退会の両方が入っているときにどちらとするかを、読む所ごとに決めることになる。enum を1か所（User::accountStatus()）で作れば、順番の決まりが1つになる。

パイプ演算子を使わないほうがよいのはどんなときか？

通す関数が1つ・2つのとき（ふつうの呼び出しのほうが短い）と、Collection の処理（->map() でつなぐほうが Laravel の文書と同じ形になる）。
