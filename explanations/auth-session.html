1. 認証の形と、選んだもの

認証（ログインした人がだれかを確かめること）の形の違いは、「ログインしていること」をどこに覚えておくかと、どう止めるかの2つ。

形どこに覚えるか止め方向いている場面
セッション（Sanctum の SPA 認証も、この形）サーバーの DB（表 sessions）。ブラウザには、行の番号だけを入れた HttpOnly の Cookie行を消せば、次のリクエストから止まる画面と API が同じサイトにある Web のサービス
API トークン（Sanctum の API トークン）DB の表（personal_access_tokens。ハッシュ）。画面が Authorization のヘッダーで送る表の行を消すスマホのアプリ・外のプログラムから呼ぶ API
JWT と取り替え用のトークン（前の D-014）JWT は署名だけで確かめ、どこにも覚えない。取り替え用は DBJWT は期限まで止められない。取り替え用は DB で止めるいくつものサーバーが、DB を見ずに「だれか」を確かめたいとき
OAuth2 のサーバー（Laravel Passport）DBDB で止めるほかの会社のアプリに、ログインを貸すとき
外のログインのサービス（Firebase Auth・Auth0 など）外のサービス外のサービスで止めるログインの仕組みを自分で持たない・SNS でログインさせたいとき

このサービスで、セッションを選んだ理由（2026-11-20 に人が決めた）

  1. 今の形に合う：画面は Web の1つだけで、API と同じサイトに置く。スマホのアプリも、外から呼ぶプログラムもない。Laravel の公式も、この形にはセッション（Sanctum の SPA 認証）を勧めている
  2. JWT の強みが、もう消えている：JWT の強みは「DB を読まずに確かめられる」こと。しかし、止めた会員・退会した会員を毎回 DB で確かめると決めている（#243）。毎回 DB を読むなら、セッションと手間は同じで、JWT には取り替え用の表という作る部分が増える
  3. 止めるのが簡単：セッションは行を消せば止まる。ログアウトも、運営が止めた会員も、次のリクエストから効く
弱いところ

スマホのアプリを作るときは、セッションの Cookie が使いにくい。そのときは、Sanctum の API トークンを足す（同じ Sanctum の別の機能なので、作り直さずに足せる）。

2. Laravel Sanctum とは

Laravel の公式の、軽い認証のパッケージ。2つの機能を持つ。

機能中身このサービスで
SPA 認証Laravel の標準のセッション（Cookie と表 sessions）を、別のポートで動く画面（SPA：1枚のページの中で画面を切り替えるアプリ。ここでは React）からも使えるようにする。CSRF の守りも付く使う
API トークン会員ごとにトークンを作り、表 personal_access_tokens にハッシュで置く。画面やアプリが Authorization: Bearer で送る今は使わない（スマホのアプリを作るときに）

このリポジトリには、もう入っている：backend/client/composer.json の laravel/sanctum（^4.0）・設定ファイル sanctum.php・表 personal_access_tokens（行は 0）。まだ、どの API も使っていない。

Sanctum が中でしていること（SPA 認証）

部品していること
statefulApi()（bootstrap/app.php に1行足す）API のルートに、Sanctum の Middleware（EnsureFrontendRequestsAreStateful）を付ける
EnsureFrontendRequestsAreStatefulリクエストの送り元（Origin・Referer）が、設定した画面のドメイン（stateful）なら、セッションを使う形にする：Cookie の暗号化・セッションの読み込み・CSRF の確かめを付ける。違うなら、何も付けない（API トークンの形として扱う）
GET /sanctum/csrf-cookieCSRF のトークンを、Cookie XSRF-TOKEN に入れて返す。画面は、ログインの前に1回呼ぶ
auth:sanctum（ルートに付ける Middleware）セッションにログインした会員がいれば通す。いなければ、Authorization の API トークンを見る。どちらもなければ 401

4. 使う表と、列の意味

    users ||--o{ sessions : "ログインしている端末"
    users ||--o{ personal_access_tokens : "使わない（API トークン）"
    users {
        bigint id PK
        varchar email UK
        varchar password
        timestamp email_verified_at
        varchar remember_token
        timestamp last_login_at
        timestamp deleted_at
        timestamp suspended_at
        timestamp banned_at
    }
    sessions {
        varchar id PK
        bigint user_id
        varchar ip_address
        text user_agent
        text payload
        int last_activity
    }

表 sessions（もうある。Laravel の最初のマイグレーション）

列型意味
id文字・主キーセッションの番号。ブラウザの Cookie に入るのは、これ（暗号にして入れる）。ログインのたびに作り直す
user_id整数・NULL 可・インデックスログインしている会員の users.id。ログインの前（CSRF の Cookie をもらっただけ）は NULL。外部キーはない
ip_address文字（45）最後に来た IP（IPv6 も入る長さ）
user_agent文字ブラウザの名前。「ログインしている端末の一覧」を作るときに使える
payload長い文字セッションの中身（ログインした会員の番号・CSRF のトークンなど）を、文字にしたもの
last_activity整数・インデックス最後に使った時刻（UNIX の秒）。リクエストのたびに書き直す。ここから24時間（SESSION_LIFETIME=1440）たった行は期限切れとして扱われ、ときどき消される
気をつけること：sessions.user_id に外部キーがない

会員を止めたり退会させたりしても、その会員の sessions の行は残る。そのため、次のどちらか（または両方）が要る。

  • 毎回のリクエストで、会員が使えるか（退会・停止）を確かめる（#243 の Middleware）
  • 止めた・退会したときに、その会員の行を消す（delete from sessions where user_id = ?。user_id のインデックスが効く）

表 users（認証に関係する列だけ）

列認証での使い方
email（UNIQUE）・password（bcrypt のハッシュ）ログインで照合する。変えない
email_verified_at確認していない会員は、自分の情報・再送・ログアウトだけ使える（FR-AUTH-021）
remember_token「ログインしたままにする」を使うときの、長い期限の Cookie と照らし合わせる値。使わない（操作がないまま24時間で切れ、使うたびに延びる形にした。計画の5章）
last_login_atログインしたときに書く（今と同じ）
deleted_at・suspended_at・banned_at退会・停止・強制退会。毎回のリクエストで見る（#243）。どれかが入っていれば 401
verification_token確認のメールのリンクの文字。認証の Cookie とは関係ない（応答には出さない。PR #255）

使わない表・作らない表

表扱い
personal_access_tokensもうある（Sanctum の API トークン用）。今は使わない。スマホのアプリを作るときに使う
refresh_tokens作らない。前の D-014（JWT と取り替え用のトークン）で作る予定だった表

5. Cookie

Cookie中身画面から読めるか設定
セッションの Cookiesessions.id（暗号にしたもの）読めない（HttpOnly）SameSite=Lax。本番だけ Secure（https のときだけ送る）
XSRF-TOKENCSRF のトークン読める（わざと）画面が読んで、ヘッダー X-XSRF-TOKEN に入れて送る。よそのサイトのページからは、こちらの Cookie を読めないので、送れない

6. CSRF と CORS

  • CSRF（よそのサイトのページに、ログインした会員のふりをした書き込みを送らせる攻撃）：ブラウザは Cookie を自動で付けるので、Cookie で認証すると起きうる。Sanctum は、書き込みのたびに X-XSRF-TOKEN と、セッションの中のトークンが同じかを確かめ、違えば 419 で断る。SameSite=Lax も、よそのサイトからの POST に Cookie を付けない
  • GET で書き込まない：SameSite=Lax は、よそのサイトからのページの移動（GET）には Cookie を付ける。CSRF の確かめも GET にはかからない
  • CORS（ほかのオリジンのページに、応答を読ませるかの決まり）：設定ファイル cors.php を作り、許すオリジンを画面（http://localhost:5173）だけにして、supports_credentials を true にする。すべてのオリジンを許す設定と、一緒にしない

7. レガシー版との違い

レガシー版（今）改善版（これから）
ログインの応答JSON で、30日の JWT（AuthController.php:58）セッションの Cookie（HttpOnly）。JSON にトークンは入れない
画面の持ち方sessionStorage に置き、24ファイルで読んで Authorization に付ける持たない。ブラウザが Cookie を自動で付ける（credentials: 'include'）
XSS があったときトークンを持ち出せる。よその PC から30日使えるセッションの Cookie は読めないので、持ち出せない。ただし、ページが開いているあいだは、そのページの中から会員として操作できる（XSS そのものは、画面で防ぐ）
ログアウトサーバーは何もしない。トークンは30日使える行を消す。同じ Cookie は 401
止めた会員確かめるのはログインだけ。持っているトークンの期限まで使える次のリクエストから 401（#243）
だれかを確かめる所16の Controller と IdentifyUser に、JWT を読むコードをコピーSanctum と AuthenticateUser の Middleware だけ

8. はまりやすい所

  • localhost と 127.0.0.1 は別のサイト：画面を localhost:5173、API を 127.0.0.1:8000 で開くと、ブラウザは「よそのサイト」とみなし、SameSite=Lax の Cookie を送らない。手元では、どちらも localhost で開く（ポートの違いは、同じサイトのまま）
  • credentials: 'include' を付け忘れる：fetch は、ほかのオリジンへの送信に Cookie を付けない。付け忘れた画面だけ 401 になる
  • Sanctum の stateful に画面のドメインがない：EnsureFrontendRequestsAreStateful がセッションを使わず、ログインしても毎回 401 になる。環境変数 SANCTUM_STATEFUL_DOMAINS に localhost:5173 を入れる
  • ログインのときにセッションの番号を作り直さない：前もって番号を知っている人が、ログインのあとの会員になりすませる（セッションの固定という攻撃）。$request->session()->regenerate() を必ず呼ぶ
  • テスト：API テストは、今の DummyAuth::actingAs()（JWT を作る）から、セッションでログインした形に変わる。Laravel の actingAs() を使う

9. 問い

JWT をやめてセッションにすると、何が良くなり、何を手放すか？

良くなるのは、止めるのがすぐ効くこと（行を消す）と、作る部分が減ること（取り替え用の表・家族・使い回しの見つけ方が要らない）。手放すのは、DB を読まずに確かめられること。ただし、止めた会員を毎回 DB で確かめると決めているので、もともと使っていなかった。

セッションの Cookie は画面から読めないのに、XSRF-TOKEN は読めてよいのはなぜ？

XSRF-TOKEN は「同じサイトのページから送った」ことを示すためのもので、持ち出しても、セッションの Cookie がなければ会員になれない。よそのサイトのページは、こちらのサイトの Cookie を読めないので、正しい値をヘッダーに入れられない。

運営が会員を止めたのに、その会員が操作を続けられるとしたら、どこを見る？

#243 の Middleware が、毎回 suspended_at を見ているか。その API のルートに Middleware が付いているか。止めたときに、その会員の sessions の行を消しているか（sessions.user_id には外部キーがないので、自動では消えない）。

手元で、ログインできたのに次の API が 401 になる。まず何を確かめる？

画面と API を同じホスト名（どちらも localhost）で開いているか。fetch に credentials: 'include' が付いているか。SANCTUM_STATEFUL_DOMAINS に localhost:5173 があるか。ブラウザの開発者ツールで、リクエストに Cookie が付いているかを見る。
