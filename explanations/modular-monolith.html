レイヤードからモジュラーモノリスへ・フレームワークを替えられる設計

作成: 2026-11-15 ／ 状態: 将来のイメージ（サイクル 01「どう作るか」の資料。決まった計画ではない）

このページでわかること
  • レイヤードの考え方（層と依存の向き）を残したまま、モジュラーモノリスにしたときのディレクトリ
  • モジュールの境目の守り方：公開する入口・イベント・表の持ち主・JOIN できないときの読み方
  • 今のレイヤードから、どの順で移るか（いきなり作り直さない）
  • Laravel から別のフレームワークや言語へ移るときに備える設計と、その費用

1. 先に知っておく言葉

言葉意味（1〜2文）
モジュール業務のまとまり1つ分のコード（会員・マッチング・メッセージ・課金など）。中に、レイヤードの層を持つ
公開する入口（コントラクト）ほかのモジュールに使わせてよいクラスとメソッドだけを集めたもの。それ以外はモジュールの中だけで使う
モジュールのイベント「マッチした」「購入した」のような出来事の知らせ。知らせた側は、だれが受け取るかを知らない
表の持ち主その表に書いてよいモジュール。ほかのモジュールは、持ち主の公開する入口を通して読む
読むための写し（リードモデル）ほかのモジュールのデータを、読みやすい形で自分の側に写した表。JOIN の代わりに使う
共有カーネルどのモジュールも使う、小さな共通の部品（会員の ID の型・金額・時刻）。大きくしない
移植しやすさフレームワークや言語を替えるとき、書き直さずに残せるコードの多さ

2. 横に切るか、縦に切るか

レイヤードは層で横に切る。モジュラーモノリスは業務で縦に切り、その中をレイヤードの層で横に切る。つまり「縦に切ってから、中を横に切る」。

3. モジュールの切り方（このアプリなら）

切り口は「言葉の意味が同じ範囲」と「一緒に変わるもの」。DDD の境界づけられたコンテキストの考え方を使う。

モジュール受け持ち持つ表（書いてよい表）ほかに公開するもの出すイベント
Identity（認証）登録・ログイン・トークン・メールの確認・停止users の認証の列・personal_access_tokensトークンから会員 ID を出す・停止しているか登録した・停止した
Members（会員）プロフィール・検索・退会profiles・users.deleted_at会員の公開の情報・出会える相手か（退会していない）退会した・プロフィールを変えた
Matching（マッチング）いいね・マッチ・ブロックlikes・user_matches・blocks2人がマッチしているか・ブロックしているかマッチした・ブロックした
Messaging（メッセージ）トークルーム・メッセージ・Firestore への写しtalk_rooms・talk_room_members・messages未読の数送った
Billing（課金）プラン・購入・有料かどうか・期限plans・purchases・users.is_paid と paid_until有料かどうか（機能を使えるか）購入した・期限が切れた
Shared（共有カーネル）どのモジュールも使う小さな部品なしMemberId・Money・Clock（時刻）―

今は1つの users 表に、認証・退会・有料の列が同居している。モジュラーモノリスでは、列ごとに持ち主を決めるか、将来は表を分ける（users から member_subscriptions を切り出す、など）。

  • モジュールの中はレイヤード（Presentation → Application → Infrastructure、全部が Domain を使う）。今のレイヤードで覚えた決まりが、そのまま中で生きる
  • モジュールの外に見せるのは Contracts/ だけ。ほかのモジュールの Application/・Infrastructure/・Model を直接使わない
  • ルート・マイグレーション・テストもモジュールの中に置き、ServiceProvider で読み込む。モジュールを1つ足すとき、フォルダ1つと登録1行で済む
  • Laravel で動かすには、composer.json の autoload に "Modules\\": "modules/" を足し、各モジュールの ServiceProvider を登録する（パッケージを使う方法もあるが、自分で書いても数十行）

5. モジュールどうしのやり取り

5-1. 3つのやり方

やり方いつ使うか例気をつけること
公開する入口を呼ぶ（同期）答えがすぐ要るときメッセージを送る前に、Matching の isMatched() と isBlocked() を聞く呼ぶ側が相手に依存する。依存が輪にならないように（A → B → A は禁止）
イベントを出す（非同期でもよい）知らせるだけで、結果を待たないときMatching が「マッチした」を出し、Messaging がトークルームを作る受け取った側が失敗したときのやり直し。順番が入れ替わることがある
読むための写しほかのモジュールのデータを、自分の検索や一覧で JOIN したいときMembers の検索が、Billing の「有料か」と Matching の「ブロック」で絞りたい → 検索用の表に写しておく写しは少し遅れる（数秒）。どこまで遅れてよいかを決める

5-2. 「いいね → マッチ → トークルーム」をモジュールで分けると

sequenceDiagram
  participant LC as Matching の LikeController
  participant LS as Matching の LikeService
  participant BA as Billing の Contracts
  participant DB1 as Matching の表
  participant EV as イベント
  participant MS as Messaging の Listener
  participant DB2 as Messaging の表
  LC->>LS: like(me, target)
  LS->>BA: canUseUnlimitedLikes(me)
  BA-->>LS: false（無料の男性）
  LS->>DB1: 今日の数・insert likes・逆向きを探す・insert user_matches
  LS->>EV: Matched(me, target) をコミットのあとに出す
  EV->>MS: Matched を受ける
  MS->>DB2: insert talk_rooms・talk_room_members
  MS->>MS: Firestore へ写す

今のレガシー版は、いいねの Controller がトークルームの表と Firestore まで直接書いている。モジュールにすると、Matching はトークルームのことを知らず、「マッチした」と知らせるだけになる。メッセージの仕組みを替えても、Matching は直さずに済む。

// modules/Matching/Contracts/Events/Matched.php
// 中身は ID と時刻だけ（Model を渡さない。受け取る側が Matching の Model を知らずに済む）
final readonly class Matched
{
    public function __construct(
        public int $matchId,
        public int $memberA,
        public int $memberB,
        public DateTimeImmutable $matchedAt,
    ) {}
}

// modules/Messaging/Application/Listeners/OpenRoomWhenMatched.php
final class OpenRoomWhenMatched implements ShouldQueue
{
    public function handle(Matched $event): void
    {
        $this->rooms->openFor($event->matchId, [$event->memberA, $event->memberB]);
    }
}

5-3. 表と JOIN

決まり理由
表は1つのモジュールだけが書くほかのモジュールが勝手に書くと、持ち主の決まり（制約・業務の判断）を通らない
モジュールをまたぐ JOIN は、最初は読み取りだけ許す。育ったら写しに変えるいきなり JOIN を全部禁止すると、検索（会員 × 有料 × ブロック）が書けない。移る途中は「読むだけなら許す」を例外の一覧で管理する
モジュールをまたぐ外部キーは付けない（または付けても削除の連鎖をしない）将来サービスに切り出すとき、DB が別になる
PostgreSQL のスキーマ（名前空間）をモジュールごとに分ける案もあるmatching.likes・billing.purchases のように、持ち主が名前で分かる。DB の権限で、ほかのモジュールからの書き込みを止められる

6. 境目を機械で守る

// tests/Arch/ModulesTest.php
$modules = ['Identity', 'Members', 'Matching', 'Messaging', 'Billing'];

foreach ($modules as $module) {
    $others = array_diff($modules, [$module]);

    arch("{$module} は、ほかのモジュールの公開する入口だけを使う")
        ->expect("Modules\\{$module}")
        ->not->toUse(array_merge(
            array_map(fn ($m) => "Modules\\{$m}\\Application", $others),
            array_map(fn ($m) => "Modules\\{$m}\\Infrastructure", $others),
            array_map(fn ($m) => "Modules\\{$m}\\Domain", $others),
        ));

    arch("{$module} の中はレイヤード：業務と DB の層は HTTP を知らない")
        ->expect(["Modules\\{$module}\\Application", "Modules\\{$module}\\Infrastructure"])
        ->not->toUse(['Illuminate\Http', "Modules\\{$module}\\Presentation"]);
}

arch('共有カーネルはどのモジュールも使わない')
    ->expect('Modules\Shared')
    ->not->toUse(array_map(fn ($m) => "Modules\\{$m}", $modules));

依存の輪（A → B → A）を見つけるには、PHP の依存を図にして検査する道具（Deptrac など）を足す案もある。

7. 今のレイヤードから、どの順で移るか

いきなりモジュールに作り直さない。今のうちに「層の中を機能ごとのフォルダで分ける」をしておくと、あとで同じ名前のフォルダを集めるだけで済む（レイヤードの詳細設計で、層の中を Likes/・Members/ に分けたのは、この準備でもある）。

段すること終わったと言える条件
0 今レイヤード。層の中を機能ごとのフォルダで分ける機能のフォルダの名前が、全部の層でそろっている
1 境目を決める3章の表（モジュール・持つ表・公開するもの）を決め、表と列の持ち主を書く全部の表に持ち主がいる
2 依存を見る機能のフォルダどうしの依存を数える（だれがだれの Model を使っているか）。アーキテクチャのテストを「今の依存は例外」として足す例外の一覧＝直す一覧ができた
3 公開する入口を作るほかの機能の Model を直接使っている所を、相手の Contracts を呼ぶ形に直す。1か所ずつ、例外の一覧を減らす例外の一覧が空になる
4 イベントに変える「Aが終わったらBもする」を、イベントに変える（いいね → トークルームなど）モジュールをまたぐ書き込みがない
5 フォルダを移す各層の同じ名前のフォルダを、modules/<名前>/ の下に集める。中身は変えない（名前空間だけ）API テストが全部通る（中身を変えていないので）
6 表を分ける（必要なら）同居している列を表に分ける。スキーマを分ける止めずに変えるマイグレーション（10）の手順で移せた

どの段でも、API テストが安全装置になる。外から見える振る舞いだけを確かめているので、中のフォルダを動かしても落ちない（落ちたら本当に壊した）。

8. Laravel から別のフレームワークや言語へ移るときに備える

8-1. 先に知っておくこと：実際にはまれで、費用が大きい

  • フレームワークを替えることは、実務では数年に1回もない。替える理由の多くは「採用（書ける人が集まらない）」「性能（特定の機能だけ）」「サポートの終わり」
  • 全部を最初からフレームワークに依存しない形で書くと、ファイルも詰め替えのコードも倍近くになる。「全部を備える」より「境目だけを固くする」方が、費用に見合う
  • 言語を替えるときは、ほとんどの場合、一気に書き換えず、API の入口で少しずつ新しい方へ流す（ストラングラーパターン）。この移し方ができるかが、備えの本体

8-2. 備えの3段

段すること費用移るときに残るもの
段 1：境目を固くする（勧める）
  • API の形を文書と言語に依存しないテストで固める（HTTP を送って応答を見るだけのテスト。どの言語の実装にも同じテストを流せる）
  • DB の表の作りを、フレームワークの外でも読める形で残す（マイグレーションの結果の SQL・docs/data-model.md）
  • トークン（JWT）の形・ID（UUID）・時刻（ISO 8601・UTC）・エラーの形を、標準の書き方にそろえる
  • イベントの中身を、JSON にできる形（ID と値だけ）にする
小API・DB・データ・トークン・テストがそのまま使える。新しい言語でも、同じテストが通れば同じ振る舞い
段 2：業務の中心を切り離す（大事なモジュールだけ）
  • Domain と Application を、Laravel の機能（ファサード・Eloquent・now()・config()）なしで書く
  • DB・時刻・設定・外のサービスは、差し替え口（ポート）を通す（ヘキサゴナル）
  • Laravel は、外側のアダプター（Controller・Eloquent の Repository・ServiceProvider）にだけ出てくる
中〜大業務の決まりが、そのまま別の言語に1対1で写せる（読んで訳すだけ）。テストも写せる
段 3：全部を切り離す全モジュールを段 2 の形にする大ほぼ全部。ただし費用に見合うことはまれ

8-3. 段 2 のディレクトリ（大事なモジュールだけ。例：課金）

// modules/Billing/Core/Domain/Subscription.php
// Eloquent を継承しない。DB の形を知らない。別の言語にもそのまま訳せる
final class Subscription
{
    public function __construct(
        public readonly MemberId $memberId,
        private ?DateTimeImmutable $paidUntil,
    ) {}

    public function isActive(DateTimeImmutable $now): bool
    {
        return $this->paidUntil !== null && $now < $this->paidUntil;   // 今のレガシー版は is_paid だけを見ている（既知のリスク）
    }
}

// modules/Billing/Core/Application/Ports/SubscriptionStore.php
interface SubscriptionStore
{
    public function find(MemberId $id): Subscription;
    public function save(Subscription $subscription): void;
}

// modules/Billing/Adapters/Persistence/EloquentSubscriptionStore.php
// Laravel が出てくるのはここ。Eloquent の Model と、業務の Subscription を詰め替える
final class EloquentSubscriptionStore implements SubscriptionStore

    {
        $row = SubscriptionModel::query()->findOrFail($id->value);
        return new Subscription($id, $row->paid_until?->toDateTimeImmutable());
    }

}

8-4. 別の言語に移すときの流れ（イメージ）

flowchart LR
  U[画面とアプリ] --> P["入口（リバースプロキシ）"]
  P -->|まだ移していない API| OLD["Laravel の本体"]
  P -->|移した API（例：課金）| NEW["新しい言語の課金サービス"]
  OLD --> DB[(PostgreSQL)]
  NEW --> DB
  T["言語に依存しない API テスト"] -.同じテストを両方に流す.-> OLD
  T -.-> NEW
  1. 移すモジュールを1つ選ぶ（境目がきれいで、得が大きいもの）
  2. そのモジュールの API テスト（言語に依存しないもの）を、新しい実装に向けて流し、全部通るまで作る。Core があれば、訳すだけで済む
  3. 入口（リバースプロキシ）で、そのモジュールの API だけを新しい方へ流す。最初は一部の会員だけ（割合で切り替える）
  4. 問題がなければ全部を流し、Laravel の側のモジュールを消す
  5. DB は最初は共有のまま。落ち着いたら、そのモジュールの表だけ別の DB に移す（11 の引っ越しの手順）

この流れで必要なのは、段 1 の「境目を固くする」こと（API の形・言語に依存しないテスト・DB の作り・トークンの形）。段 2 は、移すモジュールの中身を訳しやすくする追加の備え。

8-5. フレームワークを知らない書き方の決まり（段 2 にする場所だけ）

使わない代わりに
now()・Carbon::now()Clock の口から受け取る（テストで時刻を固定でき、時間帯の扱いも1か所）
ファサード（DB::・Cache::・Log::）コンストラクタで受け取る口
Eloquent の Model を業務の中で使うふつうのクラス（業務の型）。詰め替えはアダプターで
config()・env()必要な値だけをコンストラクタで受け取る
Laravel のコレクション・ヘルパー（collect()・Str::）PHP の配列と標準の関数（使うなら、アダプターの中だけ）
例外を HTTP の形で投げる（abort(403)）業務の例外を投げ、アダプターで HTTP の形に変える

これもアーキテクチャのテストで守れる：arch()->expect('Modules\Billing\Core')->not->toUse('Illuminate')。

10. 理解を確かめる問い

モジュラーモノリスにしても、中をレイヤードにするのはなぜ？

モジュールは「業務で縦に切る」決まり、レイヤードは「受け持ちで横に切る」決まりで、狙いが違うから両立する。モジュールの中でも入口・業務・DB が混ざれば Fat Controller に戻る。今のレイヤードで覚えた層の決まりが、そのままモジュールの中で使える。

いいねでマッチしたとき、トークルームを Matching が直接作らず、イベントにするのはなぜ？

Matching がトークルームの表を直接書くと、Matching が Messaging の作りを知ることになり、メッセージの仕組み（Firestore など）を替えると Matching も直す必要が出る。「マッチした」と知らせるだけにすれば、Matching は受け取る側を知らない。代わりに、受け取る側が失敗したときのやり直し（キュー）と、少し遅れて作られることを受け入れる。

検索で「有料の人だけ・ブロックした人を除く」をしたい。モジュールをまたぐ JOIN をしないなら、どうする？

Members のモジュールに、検索用の写し（読むための表）を持ち、Billing の「購入した・期限が切れた」と Matching の「ブロックした」のイベントで更新する。数秒遅れることを受け入れる。移る途中は、読み取りだけの JOIN を例外として許し、例外の一覧で管理する。

Laravel から別の言語に移るとき、一番の備えは何？

境目を固くすること。特に、言語に依存しない API テスト（HTTP を送って応答を見るだけ）と、DB の作り・トークン・ID・時刻の形。これがあれば、新しい実装に同じテストを流して、同じ振る舞いかを確かめながら、入口で少しずつ流す先を替えられる。業務の中心をフレームワークから切り離すのは、移すモジュールの中身を訳しやすくする追加の備え。

全部のモジュールをフレームワークに依存しない形（段 3）にしないのはなぜ？

費用に見合わないから。ファイルと詰め替えのコードが倍近くになり、Laravel の便利さ（Eloquent・生成のコマンド）を外側でしか使えなくなる。フレームワークを替えることはまれで、替えるとしても少しずつ移すので、まず移す大事なモジュール（課金など）だけを段 2 にすれば足りる。
