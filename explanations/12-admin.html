12 管理画面

作成: 2026-11-13 ／ 状態: 解説だけ ／ 要件: docs/requirements/admin.md（FR-ADMIN-001〜012・NFR-ADMIN-001〜004）

この一歩でできるようになること
  • 会員の側と管理画面を、別のアプリ（別の Laravel と別の React）に分け、表は共通にして、表の作り（マイグレーション）を1か所にまとめる理由を説明できる
  • 管理者と会員の権限の分け方（別の表・役割）と、「だれが何を見たか」を残す監査ログの持ち方が分かる
  • 大量のデータの一覧（N+1・offset・count(*)）と、日ごとの集計を、1本の SQL と索引で速くできる
  • サイドバーの項目を「1か所の一覧」から作り、ドメインを足すときに直す場所を1つにできる

1. 何を作るか

運営の人（管理者）が使う画面です。よくある管理画面の形にします。左にサイドバー（ダッシュボード・会員・メッセージ・有料会員と売上・監査ログ）、上に帯（管理者の名前と役割・ログアウト）、真ん中に中身です。

  • ダッシュボード：会員・今日の登録・マッチ・メッセージ・有料会員・今月の売上の数（カード）と、直近30日の日ごとの折れ線（登録・マッチ・メッセージ）、直近12か月の売上の棒グラフ
  • 会員：探す（メールアドレス・ニックネーム・状態）→ 詳細（プロフィール・いいね・マッチ・購入・ブロック）→ 利用を止める／解く
  • メッセージ：10万件の一覧を、送った会員・期間・本文の語で絞る
  • 有料会員・売上：購入の一覧・月ごとの売上（表とグラフ）・プランの値段の変更
  • 監査ログ：だれが・いつ・どの会員の何を見た／変えたか

管理者は会員とは別にログインし、役割は「すべてできる（owner）」と「見るだけ（viewer）」の2つです。

2. 先に知っておく言葉

言葉意味（1〜2文）
境界（バウンダリ）どこまでが1つのアプリ（チーム）の持ち物かの線。ここでは「会員の側」と「管理画面」の線で、越えるのは DB だけにする。
表の持ち主その表の作り（列・制約・マイグレーション）を決めて変えてよい場所。ここでは、管理者と監査ログの表も含めて、すべての表の作りを backend/ にまとめる（ユーザーが決めた）。管理画面は表を読み書きするだけ。
役割による権限（RBAC）人に役割（owner・viewer）を付け、役割ごとにできる操作を決めること。人ごとに決めるより、増えても管理しやすい。
監査ログだれが・いつ・何に・何をしたかを、あとから確かめるための記録。書き足すだけで、消さない・書き換えない（追記だけ）。
集計の表（ロールアップ）日ごと・月ごとの数を、あらかじめ数えて別の表に入れておくこと。ダッシュボードは、その小さな表を読むだけになる。PostgreSQL のマテリアライズドビューも同じ考え。
generate_seriesPostgreSQL で、日付や数の並びを作る関数。登録が0件の日も、グラフに0として出せる。
pg_trgm文字を3文字ずつに分けて索引にする PostgreSQL の拡張。like '%語%'（前にも % がつく部分一致）を索引で速くできる。
レジストリ（1か所の一覧）「どの項目があり、どの画面を出し、どの役割が見られるか」を1つの配列に書き、サイドバーもルートもそこから作る形。

4. 設計の選択肢を比べる

構成（他の機能と干渉しない形）

案良いところ弱いところ向いている場面
A. admin/backend（別の Laravel）と admin/frontend（別の React）。共有は DB だけ会員の側を変えても管理画面のコードは壊れない（API の形に頼らない）。デプロイ・権限・依存を別にできる。どこまでが管理画面かがフォルダで分かる同じ表を読む Model を2か所に書く（会員の側が列の名前を変えると、管理画面の SQL も直す）。コンテナが2つ増える今回（ユーザーが選んだ）。管理画面と会員の画面を別の人が作るとき
B. 今の Laravel に app/Admin と routes/admin.php、画面だけ別Model を共有でき、書く量が少ない会員の側の変更（Model・ミドルウェア）の影響を受けやすい。管理者の権限の穴が会員の API に広がりやすい小さく始めたいとき
C. 管理画面は会員の側の API を呼ぶDB に直接さわらない会員の API に管理用の入口を足すことになり、境界がかえってにじむ。集計の API も会員の側に要るDB を共有できないとき（別の会社・別のサービス）

管理者のアカウントと権限

案良いところ弱いところ向いている場面
A. admins の表・role の列（owner・viewer）。トークンの鍵も会員と別会員のトークンでは管理画面に入れない（FR-ADMIN-001）。役割で操作を分けられるログインの仕組みが2つになる今回
B. users.is_adminログインが1つ会員のトークンが盗まれると管理画面にも入れる。会員の検索などに管理者が混ざる選ばない（分け方の弱い形として知る）
C. 役割と権限の表（roles・permissions）細かく分けられる2つの役割には重い役割が増えたとき（次の段階）

サイドバーの増やし方

案良いところ弱いところ向いている場面
A. 画面の「1か所の一覧」（レジストリ）：{ path, label, icon, roles, element } の配列から、サイドバーとルートを作るドメインを足すのは、フォルダ1つと一覧に1行（FR-ADMIN-002・NFR-ADMIN-004）。役割で見せる項目も同じ一覧で決まる一覧の書き方を決めておく必要がある今回
B. サイドバーとルートを別々に手で書くすぐ書ける足すたびに2か所を直し、片方を忘れる選ばない
C. サーバーが「見せる項目」を返す役割を変えても画面を作り直さなくてよい画面の部品はどのみち画面にある。仕組みが重い項目や役割が運用で変わるとき

画面の部品とグラフ

案良いところ弱いところ向いている場面
A. 部品のライブラリ Mantine（AppShell・Table・Modal）と、そのグラフ（@mantine/charts。中は Recharts）よくある管理画面の形（サイドバー・帯・表・カード）がそろう。グラフも同じ見た目依存が増え、バンドルが大きくなる（会員の画面とは別なので、会員の数字には響かない）今回。部品が多く、見た目の作り込みより機能を先にしたいとき
B. Tailwind と shadcn/ui（部品を写して使う）よく使われている。部品を自分のコードとして直せるTailwind の設定から入る。写した部品の量が多い見た目を細かく決めたいとき
C. 03c と同じく自分で書く（グラフは SVG）依存なし表・グラフ・サイドバーを全部書く量が多い。グラフの軸や吹き出しを作るのが大変部品が少ないとき

ダッシュボードの数え方

案良いところ弱いところ向いている場面
A. 開くたびに、日ごとに1本ずつ数えるすぐ書ける30日 × 3種類で 90本。1本ごとに表を全部読むレガシー版
B. 開くたびに、generate_series と group by で1本1本で済み、0件の日も出る。いつも最新データが増えると、開くたびの集計が重くなる改善版の最初
C. 日ごとの数を集計の表（またはマテリアライズドビュー）に作っておくダッシュボードは小さな表を読むだけ作り直すまで少し古い。作り直す仕組みが要るデータが大きくなったとき（測ってから選ぶ）

監査ログの守り方

案良いところ弱いところ向いている場面
A. コントローラで、思い出した操作のあとに insertすぐ書ける書き忘れる。書き換え・削除を止められないレガシー版
B. ミドルウェアで、決めた操作は必ず残す。DB では、管理画面の DB ユーザーに監査ログの update・delete の権限を与えない（または止めるトリガー）書き忘れない。アプリのバグでも書き換えられない（DB が守る）DB ユーザーを分ける設定が要る改善版
この一歩で選ぶもの：構成は A（別の Laravel と別の React・共有は DB だけ）、管理者は A（admins と役割）、サイドバーは A（1か所の一覧）、部品とグラフは A（Mantine と @mantine/charts。版は入れるときに、出てから2週間以上のものを決め打ちにする）。レガシー版は構成と一覧を最初から整え、中の API は Fat Controller で作ります（集計は A・監査ログは A）。測ってから、集計は B（必要なら C）、監査ログは B に直します。

5. 見本：レガシー版と改善版

レガシー版（構成は整え、中は Fat Controller）

// admin/frontend/src/domains.tsx：サイドバーとルートの「1か所の一覧」（ここは最初から整える）
export const DOMAINS = [
  { path: '/', label: 'ダッシュボード', icon: 'chart', roles: ['owner', 'viewer'], element: <DashboardPage /> },
  { path: '/members', label: '会員', icon: 'users', roles: ['owner', 'viewer'], element: <MembersPage /> },
  { path: '/messages', label: 'メッセージ', icon: 'chat', roles: ['owner', 'viewer'], element: <MessagesPage /> },
  { path: '/sales', label: '有料会員・売上', icon: 'yen', roles: ['owner', 'viewer'], element: <SalesPage /> },
  { path: '/audit-logs', label: '監査ログ', icon: 'log', roles: ['owner'], element: <AuditLogsPage /> },
]
// 足すときは、domains/<名前>/ を作って、ここに1行足すだけ
// admin/backend：DashboardController（中は Fat Controller）
public function index(Request $request): JsonResponse
{
    $admin = $this->adminFromToken($request);        // 管理者の JWT（会員と別の鍵）
    $days = [];
    foreach (range(29, 0) as $i) {
        $d = now()->subDays($i)->toDateString();
        $days[] = ['day' => $d,
            'registrations' => DB::table('users')->whereDate('created_at', $d)->count(),
            'matches' => DB::table('user_matches')->whereDate('created_at', $d)->count(),
            'messages' => DB::table('messages')->whereDate('created_at', $d)->count()];
    }
    // 監査ログは書かない（ダッシュボードは個人の情報を出さないので、と思って書き忘れる）
    return response()->json(['days' => $days, /* カードの数・月ごとの売上 */]);
}
  • 集計の本数：30日 × 3種類で 90本。どれも created_at::date で表を全部読む（メッセージは10万行を30回）
  • 一覧の N+1：会員は 2＋2N 本、メッセージは 2＋3N 本。offset と毎回の count(*)
  • 出しすぎ：select * で、パスワードのハッシュや確認用の文字まで管理画面に返る
  • 監査ログの抜け：コントローラで思い出したところにだけ書く。メッセージの一覧を見ても残らない
  • 役割の抜け：viewer の確かめもコントローラごとに写すので、写し忘れたところで viewer が止める・値段を変えるができる
  • 売上がずれる：07 のレガシー版の記録は値段を持たないので、プランの値段を変えると過去の売上も変わる
  • 止めても使える：会員の側が suspended_at を見ない場所（JWT を読むだけの API）では、止めた会員がそのまま使える

改善版

// 役割と監査ログは、ルートで決める（コントローラに書かない）
Route::middleware(['admin.auth', 'audit:member.view'])->get('/members/{publicId}', [MemberController::class, 'show']);
Route::middleware(['admin.auth', 'role:owner', 'audit:member.suspend'])->post('/members/{publicId}/suspension', …);

// 監査ログの表は、管理画面の DB ユーザーに insert と select だけを許す（書き換え・削除は DB が断る）
// grant select, insert on admin_audit_logs to admin_app;   -- update・delete は与えない

大事なのは3つです。① 役割の確かめと監査ログは、ルートのミドルウェアで決め、コントローラに写さない（足し忘れたら、ルートの一覧で見つけられる）。② 一覧は JOIN とカーソルで1本、集計は generate_series と group by で1本にし、必要なら集計の表に移す。③ 会員の利用の停止は、会員の側の入口（会員を読むところ）で見る。管理画面だけでは守れない。

Eloquent が発行する SQL（レガシー版と改善版を並べる）

左がレガシー版、右が改善版です。SQL は Laravel に作らせて確かめたもので（管理画面の表と、07 の改善版の列はまだないので、すべて DB::pretend() で、流さずに SQL だけを取り出した。管理画面の Laravel はまだないので、会員の側の Laravel で同じ書き方をして作らせた）、例は会員の検索の語が search001 の場合です。中身は explanations/sql/12-admin.json にあり、explanations/tools/compare-block.py で作り直せます。

ログ（sql-*.log）では、値は ? になり、別に渡されます。読みやすいよう、ここでは値を入れて、行を分けて書きました。

ダッシュボード：直近30日の日ごとの登録（GET /admin/api/dashboard の一部）

レガシー版30本（1日1本）

$days = [];
foreach (range(29, 0) as $i) {
    $d = now()->subDays($i)->toDateString();   // アプリの時計（UTC）の日付
    $days[$d] = User::whereDate('created_at', $d)->count();
}
// マッチ・メッセージも同じ形で30本ずつ（合わせて90本）

↓ 発行される SQL

-- 日の数だけくり返す（ここでは2日分だけ見せる）
select count(*) as "aggregate" from "users"
where "created_at"::date = '2026-11-12';
select count(*) as "aggregate" from "users"
where "created_at"::date = '2026-11-13';
-- …を30回。日付は UTC で区切る
  • 表がまだない列・表もあるので、どれも DB::pretend() で作らせた（以下も同じ）
  • created_at::date は列に関数をかけるので、索引があっても使えず、1本ごとに users を全部読む（30本 × 2万行）
  • 退会した会員も数える。日本時間の0時〜9時の登録は、前の日に入る

改善版1本

DB::select("
  select d::date as day, count(u.id) as registrations
  from generate_series(今日 - 29, 今日, interval '1 day') as d
  left join users u on 日本時間の日付(u.created_at) = d::date
                   and u.deleted_at is null
  group by d order by d");

↓ 発行される SQL

select d::date as day, count(u.id) as registrations
from generate_series(
       (now() at time zone 'Asia/Tokyo')::date - 29,
       (now() at time zone 'Asia/Tokyo')::date,
       interval '1 day') as d
-- 登録がない日も 0 で出す（left join）
left join users u
  on (u.created_at at time zone 'UTC' at time zone 'Asia/Tokyo')::date = d::date
 and u.deleted_at is null
group by d
order by d;
  • generate_series で30日を作り、left join で登録のない日も 0 にする（グラフの線が途切れない）
  • 日本時間に直してから日付にする。さらに速くするなら、日ごとの数を別の表（集計の表・マテリアライズドビュー）に夜のうちに作っておく（解説の選択肢）

会員の一覧（50人ずつ。メールアドレスの部分一致）

レガシー版2＋2N 本（50人で 102本）

$users = User::where('email', 'like', "%{$q}%")
    ->orderBy('created_at', 'desc')
    ->offset(($page - 1) * 50)->limit(50)->get();
$total = User::where('email', 'like', "%{$q}%")->count();
foreach ($users as $u) {
    $u->nickname = Profile::where('user_id', $u->id)->first()?->nickname;   // 1人ごとに1本
    $u->purchases = DB::table('purchases')->where('user_id', $u->id)->count(); // もう1本
}

↓ 発行される SQL

select * from "users"
where "email"::text like '%search001%'
order by "created_at" desc
limit 50 offset 0;

select count(*) as "aggregate" from "users"
where "email"::text like '%search001%';

-- 1人ごとに
select * from "profiles" where "user_id" = 1 limit 1;
select count(*) as "aggregate" from "purchases" where "user_id" = 1;
  • select * なので、パスワードのハッシュや確認用の文字まで管理画面の API に出る
  • 前に % が付く like は、普通の索引を使えない（全部読む）
  • ページが進むと offset の分を読んで捨てる

改善版1本（＋件数の1本）

DB::table('users as u')
    ->leftJoin('profiles as p', 'p.user_id', '=', 'u.id')
    ->select('u.public_id', 'u.email', 'u.created_at', 'u.last_login_at',
             'u.is_paid', 'u.deleted_at', 'p.nickname')   // 要る列だけ
    ->where('u.email', 'like', "%{$q}%")
    ->orderBy('u.created_at', 'desc')->orderBy('u.id', 'desc')
    ->limit(51)->get();   // 51件目があれば「続きあり」

↓ 発行される SQL

select "u"."public_id", "u"."email", "u"."created_at",
       "u"."last_login_at", "u"."is_paid", "u"."deleted_at",
       "p"."nickname"
from "users" as "u"
left join "profiles" as "p" on "p"."user_id" = "u"."id"
where "u"."email"::text like '%search001%'
order by "u"."created_at" desc, "u"."id" desc
limit 51;
  • JOIN で1本にし、要る列だけを返す
  • 部分一致を速くするなら、pg_trgm の GIN 索引（3文字ずつに分けた索引）を使う（解説の選択肢）

7. 気をつけること（罠）

  • 2つのアプリで同じ表を読む：会員の側が列の名前を変えると、管理画面の SQL が動かなくなる。会員の側の表を変えるときは、管理画面が読む列の一覧（data-model.md）を見る
  • マイグレーションを2か所に置く：2つの Laravel がそれぞれマイグレーションを持つと、同じ DB の migrations の表で記録が混ざり、どちらで流したかが分からなくなる。表の作りは backend/ の1か所にまとめ、管理画面では migrate を流さない（Laravel の雛形のマイグレーションは、会員の側の users などの表とぶつかるので消す）
  • 画面で隠すだけ：viewer にボタンを出さなくても、API を直接呼べば変えられる。役割は API で必ず確かめる
  • count(*) は速くない：PostgreSQL は件数を持っていないので、毎回数える。10万件の一覧の「全部で何件」を毎回出すのは重い
  • 個人の情報の出しすぎ：管理者でも、要る列だけを返す。メッセージの本文を見たことは監査ログに残す
  • グラフの日付：UTC で区切ると、日本時間の 0時〜9時の分が前の日になる（07 と同じ罠）。0件の日を抜かすと、線が途切れて見える
  • 監査ログを消せる：アプリで消さないと決めても、DB の権限で止めなければ、手で消せる

8. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？（別のアプリに分ける・役割と監査ログ）

管理画面は、会員の画面と使う人も、見せてよい情報も、変える速さも違う。同じアプリに入れると、会員の側の変更で管理画面が壊れ、管理者の権限の穴が会員の API に広がる。だから別のアプリにし、共有を DB だけにして、どこまでが管理画面かを線で分ける。管理者は会員の個人の情報を見られるので、役割で操作を絞り、だれが何を見たかを監査ログに残して、あとから確かめられるようにする。

ほかの方法は？なぜ選ばなかったか？

今の Laravel に同居させる形は書く量が少ないが、会員の側の影響を受けやすい。管理画面が会員の API を呼ぶ形は、会員の API に管理用の入口が増えて、かえって境界がにじむ。users.is_admin は会員のトークンで管理画面に入れてしまう。部品を自分で書く形は、表・グラフ・サイドバーの量が多い。

弱点は？

同じ表を2つのアプリが読むので、会員の側の表の変更が管理画面に響く（API の形ではなく、表の形に頼っている）。Model や接続の設定が2か所になる。会員の利用の停止のように、管理画面の操作でも、守るのは会員の側の仕事になるものがある。Mantine を入れるので、管理画面のバンドルは大きくなる。

問題が起きたら、どう調べて直すか？

「ダッシュボードが遅い」なら、管理画面の API のクエリログで本数と時間を見て、EXPLAIN (ANALYZE, BUFFERS) で全部読んでいる SQL を探す。「viewer が変えられた」なら、ルートの一覧で、その操作に役割のミドルウェアが付いているかを見る。「だれが見たか分からない」なら、監査ログに残す操作の一覧と、ルートの一覧を突き合わせる。

データが10倍・100倍になったら？

メッセージが 1,000万件になると、毎回の count(*) と offset は使えない。カーソルにして件数は出さない（または概数）。ダッシュボードは、開くたびの集計から、夜のうちに作る集計の表やマテリアライズドビューに移す。監査ログは増え続けるので、月ごとのパーティションや、古い分を別の置き場に移すことを考える。

Eloquent でどんな SQL が流れ、どう直したか？ Rails（ActiveRecord）・Prisma ならどう書くか？

レガシー版は、日ごとに whereDate() で1本ずつ（90本）、一覧は1件ごとに Model を読む N+1。改善版は、generate_series と group by の1本、一覧は JOIN とカーソルの1本。
