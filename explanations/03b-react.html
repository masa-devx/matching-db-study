03b React を足す

作成: 2026-11-12 ／ 状態: 解説だけ ／ Issue: #34 ／ 要件: docs/requirements/screens.md（FR-UI-001〜014・NFR-UI-001〜003）

この一歩でできるようになること
  • Vite で React＋TypeScript を入れ、ブラウザの画面から API を呼ぶまでの流れ（開発サーバー・CORS・環境変数）を説明できる
  • React Router で画面を分け、「ログインが要る画面」をどこで守るかを説明できる
  • 素の CSS がなぜ崩れやすいか（名前のぶつかり・読み込む順・どこで使うか分からない）と、CSS Modules と CSS の変数（デザイントークン）で何が良くなるかを説明できる

1. 何を作るか

01〜03 で作った API を、ブラウザの画面から使えるようにします。まずレガシー版で、必要な6画面だけを作ります。会員を探す一覧はまだない（04）ので、相手は URL（/users/5）で開きます。

2. 先に知っておく言葉

言葉意味（1〜2文）
Vite画面の開発サーバーと、配る形にまとめる道具（ビルド）。npm run dev で、保存するとすぐ画面に出る。npm run build で dist/ に HTML・JS・CSS を作る。
SPA（シングルページアプリケーション）HTML は最初の1枚だけで、画面の切り替えはブラウザの中の JavaScript が行う作り方。データは API から JSON で取る。
React RouterURL（/users/5）と、出す部品を結びつける道具。URL の :id を取り出したり、別の画面に移したりできる。v7 から react-router の1つのパッケージになった。
オリジン・CORSオリジンは「方式＋ホスト＋ポート」の組（http://localhost:5173）。ブラウザは、別のオリジンの API の応答を、API が許したとき（Access-Control-Allow-Origin）だけ画面に渡す。この決まりが CORS。
プリフライトAuthorization の見出しや JSON を送るとき、ブラウザが本番の前に OPTIONS で「送ってよいか」を聞くこと。API が許さなければ、本番は送られない。
sessionStorageブラウザのタブごとの小さな保存場所。タブを閉じると消える。JavaScript から読めるので、XSS（悪いスクリプトが画面で動くこと）があると、中のトークンを持ち出される。
useEffect画面を描いたあとに動かす処理を書く React の仕組み。レガシー版は、ここで fetch する。開発中は StrictMode が、わざと2回動かす。
カスケードと詳細度CSS で、同じ要素に当たる決まりが2つあるとき、どちらが勝つかの決め方。より詳しい書き方（#id ＞ .class ＞ 要素）が勝ち、同じならあとに読み込んだほうが勝つ。
CSS ModulesButton.module.css のように書くと、クラス名が部品ごとに別の名前（Button_primary_x7a2）に変わる仕組み。ほかの部品の .primary とぶつからない。Vite はそのまま使える。
CSS の変数（デザイントークン）--color-primary: #d6336c; のように、色・余白・文字の大きさに名前を付けて1か所で決めたもの。部品は var(--color-primary) で使う。色を変えるときは1か所を直せばよい。
container と presentercontainer は「データを取る・持つ」部品、presenter は「props で受け取って見せるだけ」の部品。presenter は API がなくても描けるので、テストしやすい（改善版で分ける）。

4. 設計の選択肢を比べる

CSS の書き方

案良いところ弱いところ向いている場面
A. 素の CSS を1〜2枚（index.css・App.css。レガシー版）何も入れずに書ける。ひな形のままクラス名がすべての画面で共有され、.button を2か所で書くとぶつかる。勝ち負けが読み込む順で決まる。消してよいかが分からず、増える一方になる小さな1画面だけのとき
B. CSS Modules＋CSS の変数（改善版）クラス名が部品ごとに閉じ、ぶつからない。部品を消せば CSS も消える。色や余白は変数で1か所に決める。Vite に入っていて、道具が増えない部品ごとにファイルが1つ増える。同じ見た目を2か所で書かないよう、共通の部品（ボタンなど）を作る必要がある素の CSS を知っていて、部品ごとに整理したいとき
C. Tailwind CSS決まった段階の値（余白・色）をクラスで書くので、ばらつかない。仕事でよく使われる道具が1つ増える。クラス名が長く、JSX が読みにくくなる。素の CSS の理解がなくても書けてしまうチームで値をそろえたいとき・速く作りたいとき
この一歩で選ぶもの：レガシー版は A、改善版は B。A で「名前がぶつかる・消せない」を実際に起こしてから B に直すと、なぜ分けるかを事実で話せる。C は B の考え方（決まった値を使う）を道具で強くしたもの、と説明できるようにする。

見た目の決め方（デザイントークン）

見た目は、まず「使ってよい値」を少なく決めてから作ります。値がばらばらだと、画面ごとに少しずつずれて、直すときにすべての画面を探すことになります。改善版は次の値を src/styles/tokens.css に変数として置き、レガシー版は同じ値を index.css に直接書きます（同じ見た目のまま、書き方の違いだけを比べるため）。

種類決める値理由
色主な色1つ（いいね・ボタン。#d6336c）・文字（#212529）・薄い文字（#6c757d）・線（#dee2e6）・背景（#ffffff・#f8f9fa）・成功（#2b8a3e）・失敗（#c92a2a）色が増えると、何が押せるかが分かりにくくなる。主な色は「押せるもの」だけに使う。文字と背景の差は、読みやすさの目安（4.5:1）を満たす組にする
余白4px 刻み（4・8・12・16・24・32）決まった刻みにすると、画面ごとの隙間がそろう
文字端末の文字（system-ui）。大きさは 14・16（本文）・20・24px の4つ文字を読み込まないので速い。日本語でも端末の読みやすい文字が出る
角と影角の丸みは 8px と、丸いボタンの 999px。影はカードの1種類種類を増やさない
幅中身の幅は最大 480px で真ん中に置く。スマホ（375px）を先に作るマッチングアプリはスマホで使う前提。広い画面でも1列で読みやすい（NFR-UI-001）

置き場所（改善版）

案良いところ弱いところ
A. 種類で分ける（pages/・components/・api/）ひと目で分かる。小さいうちは迷わない1つの機能を直すのに、3つのフォルダを行き来する
B. 機能で分ける（features/auth/・features/profile/・features/likes/）＋共通（shared/）1つの機能を変えるときに、触るフォルダが1か所にまとまる（architecture.md の「機能ごとに縦に切る」）どこまでを共通にするかを決める必要がある
この一歩で選ぶもの：レガシー版はひな形のまま、src/ の下に画面のファイルを並べる（LoginPage.tsx など）。改善版は B。API を呼ぶところ（shared/api/client.ts）と見た目の変数（shared/styles/tokens.css）だけを共通にし、ほかは機能のフォルダに置く。

ログインが要る画面の守り方

案良いところ弱いところ
A. 画面ごとに、トークンがあるかを確かめる（レガシー版）その画面を見れば分かる新しい画面で書き忘れる。401（期限切れ）の扱いも画面ごとにばらつく
B. ルートで包む部品（<RequireAuth>）＋API を呼ぶところで 401 を受ける（改善版）守りが1か所。ルートの表を見れば、どの画面が守られているか分かる画面の側の守りは見た目のためで、本当の守りは API（401・403）だと分かっている必要がある
この一歩で選ぶもの：改善版は B。ただし画面の守りは「見せない」ためで、データを守るのは API の認証と認可（01b）。画面の守りを外しても、API が 401 を返せばデータは漏れない。

レガシー版（1画面に1つの大きな部品・素の CSS）

// src/UserPage.tsx（相手のプロフィール。取る・持つ・見せる・決まりを全部ここに書く）
import { useEffect, useState } from 'react'
import { useParams } from 'react-router'
import './App.css'

export default function UserPage() {
  const { id } = useParams()
  const [user, setUser] = useState<any>(null)
  const [message, setMessage] = useState('')

  useEffect(() => {
    // 送り先もトークンも画面ごとに書く。読み込み中・失敗・401 は考えない
    fetch(`http://127.0.0.1:8000/api/users/${id}/profile`, {
      headers: { Authorization: `Bearer ${sessionStorage.getItem('token')}` },
    })
      .then((r) => r.json())
      .then(setUser)   // すぐ別の人に移ると、前の人の応答があとから上書きする
  }, [id])

  const like = () => {
    fetch('http://127.0.0.1:8000/api/me/likes', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${sessionStorage.getItem('token')}` },
      body: JSON.stringify({ user_id: Number(id) }),
    })
      .then((r) => r.json())
      // 2回目は API が 500 を返すが、ステータスを見ないので「いいねしました」と出る
      .then((d) => setMessage(d.matched ? 'マッチしました' : 'いいねしました'))
  }

  // 年齢の計算もここに書く（年の引き算なので、誕生日の前だと1歳多い）
  const age = user?.profile?.birthday
    ? new Date().getFullYear() - Number(user.profile.birthday.slice(0, 4)) : ''

  return (
    <div className="card">
      <img src={user?.profile?.image} />
      <h1>{user?.profile?.nickname}（{age}）</h1>
      <button className="button" onClick={like}>いいね</button>
      <p>{message}</p>
    </div>
  )
}
/* src/App.css（すべての画面で共有される） */
.card { padding: 16px; border: 1px solid #dee2e6; border-radius: 8px; }
.button { background: #d6336c; color: #fff; padding: 8px 16px; border-radius: 999px; }

/* …200行あと。ログインの画面のために書き足した。
   あとに書いたほうが勝つので、いいねのボタンも灰色になる */
.button { background: #f8f9fa; color: #212529; }
  • API の送り先とトークン：http://127.0.0.1:8000 と sessionStorage.getItem('token') を、画面ごとに書く。送り先を変えるときは、すべての画面を直す
  • 読み込み中・失敗・401：考えない。API が止まると、画面は空のまま何も出ない（FR-UI-013）
  • 古い応答の上書き：/users/5 から /users/6 にすぐ移ると、5 の応答があとから来て、6 の画面に 5 の名前が出ることがある
  • XSS に弱い：トークンが sessionStorage にあるので、画面で動いたスクリプトは sessionStorage.getItem('token') で持ち出せる
  • CSS：.button がすべての画面で共有される。ある画面のために .button を直すと、ほかの画面も変わる
  • 型：応答を any で受けるので、キーの名前を間違えても（nick_name）、ビルドは通る

改善版（container／presenter・API を1か所・CSS Modules）

// shared/api/client.ts（API を呼ぶところは、ここだけ）
export async function apiFetch<T>(path: string, init: RequestInit = {}): Promise<T> {
  const res = await fetch(`${import.meta.env.VITE_API_URL}${path}`, {
    ...init,
    credentials: 'include',   // 改善版のトークンは HttpOnly の Cookie
    headers: { 'Content-Type': 'application/json', ...init.headers },
  })
  if (res.status === 401) throw new UnauthorizedError()   // 呼ぶ側で /login に移す
  if (!res.ok) throw new ApiError(res.status, await res.json())
  return (await res.json()) as T
}

// features/profile/UserProfilePage.tsx（container：取る・持つ）
export function UserProfilePage() {
  const id = Number(useParams().id)
  const { profile, error, loading, retry } = useProfile(id)   // AbortController で古い応答を捨てる
  const { liked, matched, sendLike } = useLike(id)
  if (loading) return <p>読み込み中…</p>
  if (error) return <ErrorMessage onRetry={retry} />
  return <ProfileCard profile={profile} liked={liked} matched={matched} onLike={sendLike} />
}

大事なのは3つです。① API を呼ぶところを apiFetch() の1つにまとめ、送り先・Authorization（改善版は Cookie）・401・失敗をそこで扱う。② ProfileCard は props だけで描くので、API がなくてもテストできる。③ styles.likeButton は Vite が別の名前に変えるので、ほかの部品の .likeButton とぶつからない。色は var(--color-primary) を使い、値は tokens.css の1か所で決める。

6. どう確かめるか

段階確かめること
① レガシー版で問題を見る
  • 要件の受け入れ条件（FR-UI-001〜014）を、画面で1つずつ試し、できる・できないを記録する
  • 開発者ツールの Network で、1画面を開くと何本の API が呼ばれるか（StrictMode で2回になるか）、プリフライト（OPTIONS）が出るか
  • 開発者ツールの Console で sessionStorage.getItem('token') を打つ → トークンが読めるか（XSS で持ち出せることの確かめ）
  • API を止める（docker compose stop app）・遅くする → 画面がどうなるか
  • /users/5 と /users/6 をすばやく行き来する → 違う人の名前が出るか（開発者ツールで通信を遅くして試す）
  • 2つの画面で同じクラス名（.button）を使い、片方だけ直す → もう片方が崩れるか
  • 1つの画面の部品の行の数・any の数・npm run build の dist/ の大きさ
  • 幅 375px で横にはみ出さないか（開発者ツールの端末の表示）
② 振る舞いを固定するテストVitest＋Testing Library で、要件 ID を名前に入れる。例：FR-UI-002 ログインに失敗したら分かる・FR-UI-007 いいねを送れる。マッチしたらその場で分かる（API は仮の応答に差し替える）・FR-UI-011 ログインしていないと、ログイン画面に移る・FR-UI-013 読み込み中と失敗が分かる。E2E の道具は改善する段階で決める
③ 改善したあとに比べる数字1つの部品の最大の行の数・any の数・同じクラス名の数（→ 0）・API の送り先を書いた場所の数（→ 1）・守れている要件の数（○/17 → 17/17）・dist/ の大きさ。表示速度（Lighthouse）は 04 の一覧で測る

7. 気をつけること（罠）

  • CORS は API を守る仕組みではない：ブラウザが「別のオリジンに応答を渡すか」を決めるだけ。curl なら、CORS に関係なく API を呼べる。API を守るのは認証と認可
  • localhost と 127.0.0.1 は別のオリジン：http://localhost:5173 の画面から見ると、http://127.0.0.1:8000 は別のサイト。改善版で Cookie を使うと、ここで送られない問題が出る（SameSite）。改善版は名前をそろえる
  • Cookie を送るなら * は使えない：Laravel の標準の設定は allowed_origins: ['*']・supports_credentials: false。改善版で Cookie を送るときは、画面のオリジンを名前で許し、supports_credentials を true にする
  • VITE_ で始まる環境変数は、画面のだれにでも見える：ビルドした JS に値が入る。秘密の値（鍵・パスワード）は入れない。入れてよいのは API の送り先だけ
  • 開発中は useEffect が2回動く：StrictMode がわざと2回動かす。Network に同じ API が2本出ても、本番（ビルド）では1本。いいねを送るような書き込みを useEffect に書くと、開発中に2回送る
  • 画面の守りは見た目のため：RequireAuth を外しても、API が 401 を返せばデータは漏れない。逆に API に守りがなければ、画面でいくら隠しても漏れる（01b の「他人のプロフィールを書き換えられる」は、画面では防げない）
  • 素の CSS は、読み込む順で勝ち負けが変わる：同じ詳細度なら、あとに読み込んだ CSS が勝つ。画面を足すと、前の画面の見た目が変わることがある
  • SPA の URL を直接開くと、サーバーにそのファイルがない：開発サーバーは index.html を返してくれるが、本番で静的に置くときは、どの URL でも index.html を返す設定が要る（今はデプロイしない）

8. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？

レガシー版は、Vite のひな形のまま、1画面に1つの大きな部品で、API の呼び出し・状態・見た目・CSS を全部その中に書く。こうすると、送り先の書き散らし・401 の扱いの抜け・古い応答の上書き・CSS の名前のぶつかりが、実際に起きる。それを測ってから、API を1か所にまとめ、container と presenter に分け、CSS Modules と CSS の変数に直す。前と後の数字（部品の行の数・送り先を書いた場所の数・同じクラス名の数）で、なぜ分けるのかを話せるようにするため。見た目は、使ってよい色・余白・文字の値を先に少なく決めておくと、画面ごとのずれがなくなる。

ほかの方法は？なぜ選ばなかったか？

CSS は Tailwind も候補だった。決まった値をクラスで使うので値はそろうが、道具が増え、素の CSS（カスケード・詳細度）を知らなくても書けてしまう。この学習では、素の CSS の困りごとを先に体験し、CSS Modules と変数で直すほうが、理由を説明しやすい。UI の部品のライブラリ（MUI など）は、見た目はすぐ整うが、部品の設計を自分で考える場面が減るので選ばなかった。画面の切り替えを useState で持つ案は、URL が変わらず、相手のプロフィールを URL で開けないので選ばなかった。

弱点は？

CSS Modules は、部品ごとに CSS のファイルが増える。共通の見た目（ボタン・カード）を部品にしないと、同じ CSS を何か所にも書くことになる。CSS の変数は、値の名前の付け方（--color-primary か --color-like か）を決めないと、変数が増えすぎる。レガシー版の sessionStorage は XSS に弱く、改善版の Cookie は CSRF（ほかのサイトから送らせる攻撃）を考える必要がある（SameSite=Lax で弱める）。画面の守りは見た目のためで、データの守りにはならない。

問題が起きたら、どう調べて直すか？

画面が真っ白なら、開発者ツールの Console で、JavaScript のエラー（undefined のキーを読んだなど）を見る。データが出ないなら、Network で API の呼び出しを見る。赤い OPTIONS や「CORS」のエラーなら、API の CORS の設定（config/cors.php）と、画面のオリジンを見比べる。401 ならトークンがあるか、403 ならメールアドレスを確認したか。見た目が崩れたら、要素を選んで、どの CSS の決まりが勝っているか（取り消し線が付いた決まり）を見る。

データが10倍・100倍になったら？

画面に出す件数が増えると、一覧の描き直しと、画像の読み込みが重くなる。レガシー版は全部を一度に取って全部を描くので、100件・1000件で遅くなる。04 で、API のページ送り（カーソル）と、画面の長い一覧（見えているところだけ描く）・画像の遅延読み込み（loading="lazy"）を入れ、Lighthouse の LCP・INP で前と後を測る。部品が増えると、素の CSS は名前のぶつかりが増えるので、CSS Modules の効き目が大きくなる。

Eloquent でどんな SQL が流れ、どう直したか？ Rails（ActiveRecord）・Prisma ならどう書くか？

03b は画面の一歩なので、新しい SQL はない。画面から呼ぶ API の SQL は、01〜03 のページのとおり（送った一覧は 1＋2N 本、マッチの一覧は 1＋N 本）。画面から見ると、N+1 は「1回の API の応答が遅い」として出る。代わりに、画面の側で同じ形の問題を比べる。

React（この学習）Rails の画面（Hotwire など）Next.js など
データの取り方ブラウザから API を fetch（SPA）。CORS とトークンを考えるサーバーで HTML を作って返す。同じオリジンなので CORS がない。セッションの Cookie で認証サーバーの部品で取ってから HTML にできる（API を通さずに DB を読むこともできる）
画面の「N+1」一覧の1件ごとに API を呼ぶ部品を作ると、件数の分だけ通信が増える部分テンプレートの中でリレーションを読むと、SQL の N+1 になる（includes で直す）サーバーの部品の中で1件ずつ取ると、同じことが起きる
