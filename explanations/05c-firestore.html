05c Firestore と比べる

作成: 2026-11-13 ／ 状態: 解説だけ ／ 要件: docs/requirements/messages.md（05 と同じ FR-MSG-001〜014・NFR-MSG-001〜003）／ 決めたこと: D-008（手元の Firebase Emulator で比べる）

この一歩でできるようになること
  • 「なぜ NoSQL を使うのか・RDB ではだめなのか」に、RDB でも作れることを認めたうえで、「何を DB に任せたくて、代わりに何を払うのか」で答えられる
  • 「画面がどう読むか」から形を決めるドキュメント DB の設計（コレクション・サブコレクション・会員ごとの受信箱・写して持つ）を、05 の RDB（正規化・JOIN）と並べて説明できる
  • 読んだドキュメントの数で料金が決まる仕組みを、レガシー版（最低限の形）と改善版で画面ごとに数え、どこでふくらむかを数字で言える

1. 何を作るか

05 のメッセージ（トークの一覧・トーク画面・送る・未読の数）を、もう1つ、Firestore で作ります。本物の Firestore（Google Cloud）は使わず、手元の Docker の中で動く Firebase Emulator を使います。クラウドのアカウントを作らないので、料金はかかりません（D-008）。それでも設計を比べるために、「本番ならドキュメントを何件読むか」を画面ごとに数えます。

だれが何をするか
Laravel（今の API）マッチしたら、PostgreSQL のトークルームに加えて、Firestore にもルームと2人の受信箱を作る（REST を直接呼ぶ）。画面が Firebase にログインするためのトークン（カスタムトークン）を出す
画面（React）Firebase の JS SDK で、Firestore を直接読み書きする。リスナーで、新しいものは押し出しで届く。05 の画面（/messages）は残し、/messages-fs を足して並べる
Firestore（Emulator）メッセージと、会員ごとの「自分のルームの一覧」を持つ。だれが読めるかを、セキュリティルールで守る

会員・いいね・マッチ・ルームの正は PostgreSQL のままです。Firestore が持つのは「やり取り」とその表示に要るものだけです。ルームの ID は PostgreSQL の talk_rooms.public_id、会員の ID は users.public_id（D-022）を、そのまま使います。

05 と同じく、まずレガシー版（必要な情報だけを持つ最低限の形）で作って測り、そのあと改善版（写して持つ・limit・厳しいルール）に直します。

2. なぜ NoSQL を使うのか（RDB ではだめなのか）

結論：RDB でもチャットは作れる（05 で作った）。NoSQL を選ぶのは、RDB が足りないからではなく、「リアルタイムに届ける仕組み・画面からの直接の読み書き・広げること」を、DB ごと任せたいとき。代わりに、JOIN・表をまたいだトランザクション・自由な集計・正が1つであること、を手放す。

RDB でチャットを作るとき、自分で用意するもの

要るものRDB（05）での作り方Firestore での作り方
新しいものを届けるポーリング（05 のレガシー版。何もなくても5秒ごとにリクエスト）か、WebSocket のサーバー（Laravel Reverb・API Gateway など）を足すリスナー（onSnapshot）。DB が押し出す
つながりの管理だれがどのルームを開いているか・切れたら付け直す・取りこぼしたら取り直す、をサーバーで書く。何台にも広げるなら Redis などでつなぐSDK が受け持つ（切れても、つながったら差分が届く）
だれが読めるかAPI のコントローラで確かめる（05 のレガシー版はここが抜けた）セキュリティルールに書く（画面が DB を直接読むので、ここが唯一の守り）
API のサーバー読むのも書くのも、Laravel を通る（サーバーに負荷が来る）画面が直接読み書きする（Laravel はルームを作るだけ）
電波が切れたとき画面で自分で書くSDK が手元に残し、つながったら送る（オフラインの保存）
書き込みが増えたときDB のサーバーを大きくする・分ける（パーティション・読み取りの複製）Google が広げる（設計で「1つのドキュメントに書き込みを集めない」だけ守る）

代わりに払うもの

手放すものチャットで困る場面
JOIN一覧に相手の名前や最新の1件を出すには、書くときに写しておく（非正規化）。名前を変えたら写しを全部直す
正が1つであること会員・マッチ・ブロック（06）は RDB、やり取りは Firestore。2つの DB をまたぐトランザクションはないので、片方だけ失敗するとずれる
自由なクエリと集計「先月いちばん送った会員」「この言葉を含むメッセージ」は、そのままでは書けない。管理画面（12）では別の仕組みが要る
列の決まり（型・NOT NULL・CHECK）古い形のドキュメントが混ざっても、DB は止めない。ルールとアプリで守る
料金の見通しRDB はサーバーの大きさで決まる（ほぼ固定）。Firestore は読んだ数で決まり、書き方の誤り（limit なし・付け直し）がそのまま請求になる
乗り換えやすさSDK とルールは Firebase だけのもの。ほかの DB に移すときは書き直しになる

チャットが NoSQL に向く理由（データの使われ方）

  • 足すだけで、ほとんど直さない：メッセージは送ったら終わりで、更新や削除が少ない
  • 読み方が決まっている：「このルームの新しいもの」と「自分のルームの一覧」の2つがほとんど。いろいろな条件で探さない
  • ほかの表と組み合わせることが少ない：一覧に出す名前と写真だけを写せば、JOIN がなくても困らない
  • 件数が多く、届く速さが大事：1人が1日に何十件も送り、相手にすぐ届いてほしい

判断の物差し

こういうとき向くもの
リアルタイムに届けたい・リアルタイムのサーバーを持つ人手がない・画面から直接読ませたいFirestore などのリアルタイムの NoSQL
お金・在庫・予約など、表をまたいで必ずそろっていてほしいRDB
いろいろな条件で探す・集計する（04 の検索・12 の管理画面）RDB
小さく始めて、数秒の遅れが許せるRDB ＋ ポーリング（05 の改善版）。DB を増やさない
DB は1つのまま、すぐ届けたいRDB ＋ WebSocket（Reverb・AppSync Events など）

「RDB ではだめなのか？」と聞かれたときの答え方

「だめではない」から始め、何を優先し、何を払ったかを言います。

  1. 事実：会員とマッチは RDB、メッセージは Firestore に分けた
  2. 優先したこと：リアルタイムに届けることと、そのためのサーバーを持たないこと。チャットは読み方が決まっていて JOIN が要らない
  3. 払ったもの：正が2つになり、名前の変更・ブロック・退会で2つの DB を直す。集計が苦手。料金は読んだ数で決まる
  4. 今ならどうするか：規模が小さいうちは RDB ＋ ポーリングか WebSocket で始め、届く速さやサーバーの手間が問題になってから分ける。分けるなら、何を正にし、写しをどう直すかを先に決める

3. 先に知っておく言葉

言葉意味（1〜2文）
ドキュメント・コレクションFirestore の1件がドキュメント（JSON に近い入れもの。上限は 1MiB）で、ドキュメントの集まりがコレクション。表と行に近いが、列の決まり（型・NOT NULL）はない。
サブコレクションドキュメントの下に置くコレクション。rooms/{roomId}/messages のように、ルームの下にメッセージを置ける。親を消しても、子は自動では消えない。親のドキュメントがなくても、子は置ける。
受信箱（会員ごとのルームの一覧）users/{uid}/rooms/{roomId} のように、会員ごとに「自分から見たルーム」を1件ずつ持つ形。05 の talk_room_members の1行に当たる。
非正規化（写して持つ）JOIN がないので、一覧に出したいもの（最新の1件・相手の名前・未読の数）を、書くときに一覧のドキュメントへ写しておくこと。読むのは速く安くなるが、写しがずれないように書く側が気をつける。
リスナー（onSnapshot）クエリを聞きっぱなしにして、結果が変わったら DB から押し出しで届く仕組み。最初に結果の全部が届き、あとは変わったドキュメントだけが届く。
セキュリティルール画面が DB を直接読み書きするので、「だれが何を読める・書けるか」を DB の側に書く決まり。ルールは絞り込みではないので、クエリが読めないものを含みうるなら、全体が拒まれる。
読み取りの課金本番の料金は、読んだ・書いた・消したドキュメントの数で決まる。リスナーは、結果に足された・変わったドキュメントごとに1件。0件のクエリも最低1件。ルールの中の get() も1件。offset は飛ばした分も1件ずつ。
複合インデックス2つ以上のフィールドで絞り込みと並べ替えをするクエリに要るインデックス。本物の Firestore では、なければクエリがエラーになる。Emulator は複合インデックスを見ずに、どのクエリも通す。
カスタムトークン自分のサーバー（Laravel）が「この人は uid X」と保証して出すトークン。画面はこれで Firebase にログインする。本番はサービスアカウントの鍵で署名するが、Auth の Emulator は署名のないトークンを受け付ける。
serverTimestamp()・increment()時刻を DB の時計で入れる値と、数を読まずに足す値。画面の時計（new Date()）は端末ごとにずれ、「読んでから +1 して書く」は同時に送られたときに数がずれる。
EmulatorFirebase のサービスを手元で動かすプログラム。プロジェクトの ID を demo- で始めると、本物のプロジェクトにつながらない。止めるとデータが消える（書き出しと読み込みで残せる）。

5. 設計の選択肢を比べる

コレクションの形

案良いところ弱いところ向いている場面
A. rooms だけ（members の配列で自分のルームを探す）コレクションが少ない。送るときの書き込みは2件（メッセージ・ルーム）一覧のクエリが array-contains ＋ orderBy で、複合インデックスが要る。未読などの一人ひとりの状態を、ルームの中に人ごとの map で持つので、ルールが長くなる一人ひとりの状態がないとき
B. users/{uid}/rooms（受信箱）と rooms（選ぶ）一覧は自分の受信箱を読むだけ（インデックスは自動）。一人ひとりの状態（未読・通知を切る・非表示）を足しやすい。ルールが「本人だけ」と短く書ける。05 の talk_rooms と talk_room_members の分け方（D-023）とそろう送るときの書き込みが3件（メッセージ・2人の受信箱）に増える今回。2人のトークで、一覧を開く回数が多い
C. ルームのドキュメントの中に、メッセージを配列で持つ1件読めば全部あるドキュメントの上限（1MiB）にすぐ届く。1件足すたびに、大きなドキュメントを丸ごと書き直す件数が少なく決まっているとき（チャットには向かない）

受信箱に何を持つか（レガシー版と改善版の違いの中心）

案良いところ弱いところ向いている場面
A. 必要な情報だけ（partnerUid・lastReadAt。レガシー版）写しがないので、ずれない。名前を変えても何も直さない。作るのが簡単一覧を開くたびに、ルームごとに最新の1件・未読のメッセージ・相手の名前を読む（05 のレガシー版と同じ N+1 が、そのまま読み取りの課金になる）ルームが数個のとき。まず動かすとき
B. 一覧に出すものを写す（partnerInfo・lastMessage・lastActivityAt・unread。改善版）一覧は受信箱を読むだけ（20件なら20件分）。リスナーなら変わった受信箱だけが届く送るたびに2人の受信箱を書く。相手が名前を変えたら、その人のルームの数だけ書き直す一覧を開く回数が、名前を変える回数よりずっと多いとき（ふつうのチャット）

トーク画面の読み方と、だれが読めるか

項目レガシー版改善版
新しいものorderBy(createdAt) のリスナーで、limit なし（開くたびに、そのルームの全部を読む。2万件なら2万件）orderBy(sentAt, 'desc').limit(50) のリスナー（開いたときに50件、あとは届いた分だけ）
古い続き要らない（全部読んでいるので）カーソル（startAfter(いちばん古いもの)）で50件ずつ
時刻画面の時計（new Date()。端末ごとにずれる）serverTimestamp()（DB の時計）
未読の数lastReadAt より新しいメッセージを全部読んで、画面で相手のものを数える受信箱の unread を increment(1)、開いたら 0
セキュリティルールallow read, write: if request.auth != null;（ログインしていればだれでも）受信箱は本人だけ。メッセージはルームの members だけが読め、senderId は自分・本文は 1〜1000文字だけ書ける
Laravel から作るREST で3件を別々に書く（途中で失敗すると、片方の受信箱がない）REST の commit で3件を一緒に書く

Laravel から Firestore への書き込み

案良いところ弱いところ
A. REST を直接呼ぶ（Laravel の Http。選ぶ）拡張も SDK も要らない。送る中身（ドキュメントの JSON）がそのまま見えるJSON が冗長（{"stringValue": "…"}）。本番では、サービスアカウントでトークンを取る処理が要る
B. Admin SDK（kreait/firebase-php）本番の書き方に近いFirestore の部分は PHP の grpc の拡張が要る（今の app にはない。作るのに時間がかかる）
C. Cloud Functions（Node）に任せるFirebase でよくある形動かすものが増え、DB の学習から離れる
この一歩で選ぶもの：形は B（users/{uid}/rooms の受信箱と rooms/{id}/messages）。レガシー版は受信箱に必要な情報だけ（partnerUid・lastReadAt）を持ち、limit のないリスナー・画面の時計・ゆるいルールで作る（測る問題を出すため）。改善版は、一覧に出すものを受信箱に写し、limit とカーソル・serverTimestamp()・increment()・本人だけのルールにする。一覧を開く回数は、名前を変える回数よりずっと多いので、「書くときに組み立て、読むときは読むだけ」にするのが、読み取りの数でも速さでも得だから。Laravel からは REST を直接呼ぶ。

6. 見本：レガシー版と改善版

Docker の構成（compose.yaml に足す。両方で同じ）

  firebase:
    build: ./docker/firebase          # Node と JDK 21 の上に firebase-tools（出てから2週間以上の版）を入れる
    working_dir: /app/firebase        # firebase.json・firestore.rules・firestore.indexes.json を置く
    command: firebase emulators:start --project demo-matching --only firestore,auth
             --import /data --export-on-exit /data   # 止めてもデータを残す（最初の1回は --import を外す）
    ports:
      - "127.0.0.1:8080:8080"   # Firestore（画面が直接つなぐ）
      - "127.0.0.1:9099:9099"   # Auth

レガシー版（必要な情報だけ）

// ルール（firestore.rules）：ログインしていれば、だれでも何でも読み書きできる
//   match /{document=**} { allow read, write: if request.auth != null; }

// 一覧：自分の受信箱を全部読み、ルームごとに3回読みに行く（N+1）
const inbox = await getDocs(collection(db, 'users', uid, 'rooms'))          // limit なし
const rows = await Promise.all(inbox.docs.map(async (r) => {
  const msgs = collection(db, 'rooms', r.id, 'messages')
  const last = await getDocs(query(msgs, orderBy('createdAt', 'desc'), limit(1)))
  const after = await getDocs(query(msgs, where('createdAt', '>', r.data().lastReadAt ?? new Date(0))))
  const unread = after.docs.filter((m) => m.data().senderId !== uid).length   // 読んだ全部を画面で数える
  const partner = await fetch(`${api}/api/users/${r.data().partnerUid}`, { headers }).then((x) => x.json())   // 名前は RDB から
  return { id: r.id, last: last.docs[0]?.data(), unread, partner }
}))

// トーク画面：limit のないリスナー。開くたびに、そのルームのメッセージを全部読む
onSnapshot(query(collection(db, 'rooms', roomId, 'messages'), orderBy('createdAt')), (snap) => setMessages(snap.docs.map((d) => d.data())))
updateDoc(doc(db, 'users', uid, 'rooms', roomId), { lastReadAt: new Date() })   // 画面の時計

// 送る：メッセージを1件足すだけ（受信箱は直さない）
addDoc(collection(db, 'rooms', roomId, 'messages'), { senderId: uid, body, createdAt: new Date() })
  • だれでも読める：ルールが「ログインしていれば」だけなので、ほかの会員のルームの ID が分かれば読めて書ける。senderId を他人にもできる（05 のレガシー版の「参加者を確かめない」と同じ穴が、DB の側にある）
  • 一覧の N+1：ルーム 100 なら、受信箱 100件 ＋ 最新の1件 100回（0件でも1件分）＋ 未読のメッセージの全部 ＋ Laravel への API 100回。まだ開いていないルームは、相手のメッセージを全部読む
  • limit のないリスナー：2万件のルームを開くたびに、2万件分の読み取り。画面も2万個の吹き出しを描く
  • 画面の時計：端末の時計が進んでいる人のメッセージは、いつも下に並ぶ。lastReadAt も端末の時計なので、未読の境目がずれる
  • 一覧の並び：受信箱に時刻がないので、Firestore では並べられず、全部読んでから画面で並べる

段階確かめること
① レガシー版で問題を見る

  • 画面ごとの読み取りの数（一覧・2万件のルームを開く・送る・名前を変える）を、画面の中で数える（docChanges() と取った件数・キャッシュから来たか metadata.fromCache）。Laravel への API の本数も数える

③ 改善したあとに比べる数字同じ操作の読み取り・書き込みの数（レガシー版と改善版）と、05 の SQL の本数。数えた数を、本番の料金表の単価で「1日に 1,000人なら月にいくら分か」に直す（払わない。比べるための物差し）。届くまでの時間（05 のポーリングの5秒と押し出し）。名前を変えたとき・ブロックしたとき（06）に直す場所の数

8. 気をつけること（罠）

  • Emulator は複合インデックスを見ない：本物では、2つ以上のフィールドの絞り込みと並べ替えに、インデックスがないとエラーになる。必要なものを firestore.indexes.json に書く
  • orderBy したフィールドがないドキュメントは、結果に出ない：lastMessage.sentAt で並べると、まだやり取りのないルームが一覧から消える。作るときに入る lastActivityAt で並べる
  • ルールは絞り込みではない：クエリが読めないものを含みうるなら、全体が拒まれる。クエリに同じ条件を書く（受信箱なら、パスに自分の uid が入っているので満たせる）
  • リスナーの付け直し・止め忘れ：useEffect の依存の書き方を誤ると、描き直しのたびに聞き直し、そのたびに最初の結果を読み直す。止める関数（unsubscribe）を必ず返す
  • 長くつながらないと読み直し：30分より長くオフラインだったあとにつなぎ直すと、新しいクエリと同じだけ課金される
  • serverTimestamp() は、送ったばかりのときは null：自分の画面には先に届くが、時刻がまだ決まっていない（{ serverTimestamps: 'estimate' } で見込みを出す）
  • 写しのずれ：名前の変更・退会・ブロック（06）は PostgreSQL で起きるので、Firestore の受信箱とルームも直す必要がある。直し忘れると、古い名前が残り、ブロックした相手のルームが開ける
  • 親を消しても子は消えない・親がなくても子は置ける：rooms/{id} を消しても messages は残る。users/{uid} に中身がなくても受信箱は置けるが、Emulator の画面では親が斜体（ないドキュメント）で出る
  • 署名のないトークンは Emulator だけ：本番は、サービスアカウントの鍵で署名したカスタムトークンが要る。鍵は秘密の値なので、Laravel の外に出さない

9. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？（なぜチャットに NoSQL を使い、なぜ受信箱に写しを持つのか）

チャットは、足すだけで読み方が決まっていて、JOIN が要らず、すぐ届いてほしい。Firestore なら、届ける仕組み（リスナー）・画面からの直接の読み書き（ルール）・広げることを DB ごと任せられ、WebSocket のサーバーを持たずに済む。そのうえで JOIN がなく、料金も速さも「何件読むか」で決まるので、一覧に出すものを書くときに受信箱へ写し、一覧は受信箱を読むだけにする。チャットは一覧を開く回数が、名前を変える回数よりずっと多いので、書くときに手間をかけるほうが得になる。

ほかの方法は？なぜ選ばなかったか？（RDB ではだめなのか）

RDB でも作れる（05）。数秒の遅れが許せるならポーリング、すぐ届けたいなら WebSocket（Laravel Reverb・AppSync Events）を足せば、DB は1つのままにできる。ただ、つながりの管理・切れたときの取り直し・広げ方を自分で持つことになる。Firestore の中でも、rooms だけで members の配列から探す形は、複合インデックスが要り、一人ひとりの状態の置き場所がない。メッセージをルームの配列に入れる形は、ドキュメントの上限（1MiB）にすぐ届く。写しを持たずに毎回集める形（レガシー版）は、写しがずれない代わりに、一覧の N+1 がそのまま課金になる。

弱点は？

正が2つになる（会員・マッチ・ブロックは PostgreSQL、やり取りは Firestore）。名前の変更・退会・ブロックのたびに2つの DB を直す必要があり、片方だけ失敗するとずれる（2つの DB をまたぐトランザクションはない）。画面が DB を直接書くので、守りはルールに頼り、ルールの1行の誤りがそのまま穴になる。送るたびの書き込みが3件に増える。集計や全文検索は苦手で、管理画面（12）では別の仕組みが要る。列の決まりがないので、古い形のドキュメントが混ざっても DB は止めない。

問題が起きたら、どう調べて直すか？

「料金が急に増えた」なら、まず画面ごとの読み取りの数を見る（本番なら Cloud Monitoring の使用量、05c では画面の中の数）。よくある原因は、limit のないリスナー・一覧の N+1・offset・描き直しのたびのリスナーの付け直し。「一覧が拒まれる」なら、Emulator の画面の Requests でルールのどの行で止まったかを見て、クエリに同じ条件があるかを確かめる。「本番でだけクエリが失敗する」なら、複合インデックスがない（Emulator は見ない）かを疑う。「古い名前が出る」なら、名前を変えたときの書き直しが失敗していないかを見る。

データが10倍・100倍になったら？

Firestore は、読むのも書くのも「返す件数」だけで速さが決まるので、メッセージが 100万・1億件になっても、1つのルームの50件を読む速さは変わらない（RDB のようにインデックスを足して計画を見る必要がない代わりに、使えるクエリが限られる）。料金は使った分だけ増えるので、会員が 100倍なら読み取りもほぼ 100倍になる。RDB はサーバーの大きさで決まる費用なので、多くなると RDB のほうが見通しやすいことがある。レガシー版の limit のないリスナーは、件数に比例して読み取りが増えるので、データが増えるほど請求がふくらむ。名前を変えたときの書き直しは、ルームの数に比例して重くなる。

RDB の SQL と、Firestore の書き方は何が違うか？ ほかのツールならどう書くか？

05 では Eloquent が SQL を作り、SQL の本数と実行計画で設計を確かめた。05c では SDK がクエリを送り、「読んだドキュメントの数」で確かめる。どちらも「一覧で1件ごとに読みに行かない」ことが大事だが、RDB は読むときに JOIN でまとめ、Firestore は書くときに写してまとめる。
