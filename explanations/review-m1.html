7. 振り返りの問い

今の表で、DB だけで「1人にプロフィールは1つ」を守るには、何を足すか？

profiles.user_id に UNIQUE（と、users.id への外部キー）。UNIQUE があれば、2つ目の行の insert を DB が断る。今は外部キーもないので、会員を消してもプロフィールが残る。ON DELETE CASCADE を付ければ、一緒に消える。

JWT を読む処理が4か所にあると、何が困るか？

直すときに4か所を同じように直す必要があり、1つ直し忘れると、その API だけ 500 のまま・確認していない会員が通る、のように振る舞いがそろわない。ミドルウェアにすると、ルートに付けるだけで、だれかの決まり方が全部の API で同じになる。

02 で「10本同時」に送っても問題が起きなかったのは、なぜか？

compose の app は PHP の組み込みサーバーで、ワーカーを指定していないので、リクエストを1つずつ順に処理していた。同時に送っても、サーバーの中では1本ずつ確定するので、競合が起きなかった。03 では、ワーカー8つのサーバーを別に立てて、初めて同時に処理させた。

CORS を直さずに画面から呼べたのは、安全だということか？

違う。CORS はブラウザが「応答を画面に渡すか」を決めるだけで、curl など、ブラウザでないところからは何でも呼べる。今の API は、だれでも呼べるルートに、認証と認可がコントローラの中にしかない。API を守るのは CORS ではなく、認証（だれか）と認可（してよいか）。

M2 で、なぜ「直す前に、今の振る舞いを固定するテスト」を足すのか？

直したあとに、直したところ以外が変わっていないことを確かめるため。レガシー版にはテストがないので、先に要件 ID の名前で今の動き（守れていないものは、守れていないことも）をテストにし、直すたびに、そのテストが「赤 → 緑」に変わるのを見る。数字（SQL の本数・守れている要件）も、同じテストの中で測れる。
