00 環境を作る

作成: 2026-11-11 ／ 状態: 解説だけ ／ Issue: #1

この一歩でできるようになること
  • 手元で PostgreSQL（開発用とテスト用）とメールの受信箱（Mailpit）を Docker で動かせる
  • Laravel の API から PostgreSQL につなぎ、マイグレーションで表を作れる
  • API を1回叩いたときに流れた SQL と、その数・時間をログで見られる

作るもの置き場何のため

2. 先に知っておく言葉

言葉意味（1〜2文）
Docker・コンテナアプリを、手元の PC から切り離した箱（コンテナ）の中で動かす仕組み。PostgreSQL を手元に入れずに、決まった版で動かせる
Docker Compose複数のコンテナ（DB・Mailpit）を compose.yaml 1つに書いて、まとめて起動・停止する道具
ボリュームコンテナを消してもデータを残すための置き場。消すと DB の中身も消える
マイグレーション表の作り方・変え方を、順番つきのファイルで残す仕組み。どこまで流したかは migrations という表に記録される
artisanLaravel のコマンド（php artisan migrate など）
EloquentLaravel の ORM。PHP のコードから SQL を組み立てて流す
クエリログ（DB::listen）Laravel が SQL を流すたびに、その SQL・値・時間を受け取れる仕組み。これをログに出す
EXPLAINPostgreSQL が SQL をどう実行するか（実行計画）を見る命令。EXPLAIN (ANALYZE, BUFFERS) は実際に実行して、時間と読んだページ数も出す
pg_stat_statementsPostgreSQL の拡張。クエリごとの回数・合計時間を集める。04 から先で「どのクエリが重いか」を探すのに使う
テスト用の DBテストのたびに中身を消して作り直す DB。開発用と分けないと、テストで開発のデータが消える
pdo_pgsqlPHP から PostgreSQL につなぐための拡張。これがないと Laravel は PostgreSQL につなげない

4. 設計の選択肢を比べる

テスト用の DB をどう用意するか

案良いところ弱いところ向いている場面
A. 1つのコンテナに DB を2つ（matching_dev・matching_test）コンテナが1つで軽い。版が必ず同じ。起動のときの SQL で2つ目の DB を作るだけテストが重くなると、開発の DB と同じ箱の力を取り合う1人で学ぶ・テストが少ないうち
B. コンテナを2つ（開発用・テスト用）完全に分かれる。テスト用をメモリの上（tmpfs）に置いて速くできるコンテナとポートが増えるテストが増えて遅くなったとき
C. テストは SQLite のメモリ DB速い。Docker が要らないロック・UNIQUE・型・EXPLAIN の動きが PostgreSQL と違い、確かめたいことが確かめられない（D-010）DB の動きに関係しないテストだけのとき
この一歩で選ぶもの：A。1人の学習でテストも少ないうちは、軽くて版がそろう形がよい。テストが遅くなったら B に移す（そのときに decisions.md に1行足す）。

流れた SQL をどう見るか

案良いところ弱いところ向いている場面
A. DB::listen でログに出すLaravel だけで書ける。1回の API で流れた SQL の数を数えられる。どの環境でも同じ自分で書く。値（バインド）に個人情報が入るので、手元だけにするAPI だけのうち（00〜03）
B. Telescope画面でリクエストごとの SQL・時間が見える入れるものが増える。記録用の表ができるあとで、画面で追いたくなったとき
C. PostgreSQL のログ（log_min_duration_statement）と pg_stat_statementsどのアプリから来た SQL も見える。遅いもの・回数の多いものを集計できるどの API から来たかが分かりにくい04 から先の、重いクエリを探すとき
この一歩で選ぶもの：A を作り、C の pg_stat_statements も最初から有効にしておく。A は「この API で何本流れたか」、C は「全体でどれが重いか」を見るので、両方あると 04 から先で困らない。

5. 見本（小さく）

00 は環境なので、素朴な版と直した版に分けません。要点だけです。

# compose.yaml（要点）
services:
  db:
    image: postgres:18
    ports: ["55432:5432"]          # 手元の 5432 とぶつからないように
    environment:
      POSTGRES_DB: matching_dev
    command: postgres -c shared_preload_libraries=pg_stat_statements
    volumes:
      - db-data:/var/lib/postgresql
      - ./docker/db/init:/docker-entrypoint-initdb.d   # matching_test を作る SQL
  mailpit:
    image: axllent/mailpit
    ports: ["51025:1025", "58025:8025"]  # 1025・8025 は手元でもう使われている
volumes:
  db-data:
// backend/app/Support/Logging/QueryLogger.php（要点）
public static function register(): void
{
    if (! app()->environment('local')) {
        return;                     // 値に個人情報が入るので、手元だけ
    }
    DB::listen(function (QueryExecuted $query) {
        Log::channel('sql')->debug('sql', [
            'sql' => $query->sql,
            'ms' => $query->time,
            'count' => ++self::$count,  // 1回のリクエストで何本目か
        ]);
    });
}

読み方：ports の左が手元の PC のポート、右がコンテナの中のポート。docker-entrypoint-initdb.d の SQL は、ボリュームが空のとき（最初の1回）だけ流れる。DB::listen は、Laravel が SQL を流すたびに呼ばれる。値（bindings）はログに出さず、SQL の形・時間・本数だけを出す。

7. 気をつけること（罠）

  • 新しい Laravel は、最初から SQLite につながる設定になっている。接続先を pgsql に変えないと、PostgreSQL を使っているつもりで SQLite に書いてしまう
  • テストが開発用の DB を消す：テストの設定（phpunit.xml とテスト用の環境変数のファイル）で接続先を matching_test にしないと、RefreshDatabase が開発の DB を作り直してしまう
  • php artisan config:cache を手元で使わない：設定が固まり、テストのときもテスト用の接続先に切り替わらなくなる
  • 手元の PHP に pdo_pgsql がない：今の Homebrew の PHP には入っていない。mise で入れる PHP に入っているかを、最初に php -m で確かめる
  • ポートがぶつかる：1025・8025 は手元ですでに使われているので、Mailpit は 51025・58025 にする。PostgreSQL も手元の 5432 と分けて 55432 にする
  • docker compose down -v は DB の中身を消す（-v がボリュームも消す）。止めるだけなら down か stop
  • SQL のログに値を出さない：メールアドレスやパスワードのハッシュが入る。値は出さず、手元だけで動かす
  • 秘密の値のファイル（Laravel の環境変数のファイル）はコミットしない。AI は中身を読まない。見本のファイルには名前だけを書く

8. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？（なぜ DB を Docker で、しかもテスト用を分けるのか）

版を決めて、だれの PC でも同じ PostgreSQL を動かすため。テスト用を分けるのは、テストが毎回 DB を作り直すので、開発のデータを消さないため。SQL のログを最初から入れるのは、01 から先で「Eloquent の裏で何本の SQL が流れたか」を毎回見るため。

ほかの方法は？なぜ選ばなかったか？

手元に PostgreSQL を直接入れる方法は、版がずれやすく、消して作り直すのが面倒。Laravel Sail（すべて Docker）は手元を汚さないが、コマンドが長く遅くなる。テストを SQLite にする方法は速いが、ロックや UNIQUE の動きが違い、この学習で確かめたいことが確かめられない。

弱点は？

Docker が動いていないと何もできない。1つのコンテナに DB を2つ置くので、テストが重くなると開発の DB も遅くなる。DB::listen は自分で書くので、書き方を間違えると本番で個人情報をログに出すおそれがある（手元だけにして防ぐ）。

問題が起きたら、どう調べて直すか？

つながらない → docker compose ps で動いているか、ポートが 55432 か、接続先が pgsql か、php -m に pdo_pgsql があるかの順に見る。テスト用の DB ができていない → 初期化の SQL はボリュームが空のときだけ流れるので、ボリュームを作り直すか、手で CREATE DATABASE する。SQL がログに出ない → 環境が local か、ログのチャンネルの設定を見る。

データが10倍・100倍になったら？

00 ではデータはほぼない。ただ、04 で大量のデータを入れると、1つのコンテナの DB を開発とテストで取り合う。そのときは案 B（テスト用のコンテナを分けて tmpfs に置く）に移す。pg_stat_statements は、データが増えたときに重いクエリを探す入口になる。

Eloquent でどんな SQL が流れ、どう直したか？ Rails（ActiveRecord）・Prisma ならどう書くか？

00 では直すものはない。「流れた SQL を見る方法」を ORM ごとに並べる。

ORM流れた SQL を見る1本の SQL の形を見る実行計画
EloquentDB::listen・Telescope・Debugbar->toSql()・->toRawSql()->explain()
Rails（ActiveRecord）ログ（ActiveRecord::Base.logger）・bullet（N+1 の検知）.to_sql.explain（7.1 以降は :analyze も）
Prismalog: ['query'] の設定（ない。ログで見る）生の SQL で EXPLAIN を流す
