01b 認証と認可

作成: 2026-11-11 ／ 状態: 解説だけ ／ Issue: #13 ／ 要件: docs/requirements/auth.md（FR-AUTH-001〜032）／ 決めたこと: D-014 ／ 図解: 認証とトークンの絵本

この一歩でできるようになること
  • 認証（だれか）と認可（何をしてよいか）を分けて説明できる
  • JWT の中身・弱いところ（期限まで止められない・権限が古いまま）と、短い期限＋取り替え用のトークンで補う理由を説明できる
  • 確認のリンク・取り替え用のトークンを、DB にどう持つか（平文か・ハッシュか・持たないか）を選べる

1. 何を作るか

会員が自分で登録し、メールアドレスを確認して、ログインできるようにします。画面は 03b からなので、01b では curl と Mailpit（手元の受信箱）で確かめます。

API（案）中身要件子 Issue
登録メールアドレス・パスワード・性別・生年月日・表示名で登録し、確認のメールを送るFR-AUTH-001〜004#15
メールアドレスの確認・再送メールのリンクで確認済みにする。確認のメールをもう一度送るFR-AUTH-005〜007#15
ログイン・自分の情報・ログアウトメールアドレスとパスワードで JWT をもらう。JWT で自分の情報を見るFR-AUTH-010〜017#16

API の入力と応答の細かい形は、子 Issue の最初に docs/api/01b-auth.md に書いて、確かめてもらってから作ります。だれが何をできるか（認可。FR-AUTH-020〜023）は、素朴な版では作らず、直す段階で足します。

2. 先に知っておく言葉

言葉意味（1〜2文）
認証「あなたはだれか」を確かめること。メールアドレスとパスワードで本人だと確かめ、ログイン済みの証拠（トークン）を渡す
認可「その人が、それをしてよいか」を決めること。ログインしていても、他人のプロフィールは編集できない、など
トークンログイン済みの証拠（入場券）。API を呼ぶたびに見せる
JWT「だれか・いつまで」を書いて、サーバーの鍵で署名したトークン。中身は暗号化されておらず、だれでも読める。サーバーは DB を見ずに、署名と期限だけで確かめられる
署名サーバーだけが知る鍵で作る「書き換えられていない」印。1文字でも変えると合わなくなる
取り替え用のトークン（リフレッシュトークン）短い JWT が切れたときに、新しい JWT をもらうための、長めのトークン。DB にハッシュで持ち、使うたびに新しいものに取り替える
HttpOnly・Secure・SameSiteCookie の印。HttpOnly は JavaScript から読ませない、Secure は HTTPS のときだけ送る、SameSite はほかのサイトからのリクエストに付けるかを決める
XSS・CSRFXSS は画面に悪いスクリプトを埋め込まれること（トークンを盗まれる）。CSRF は、ほかのサイトから、ログイン中の人として勝手に操作されること（Cookie は自動で送られるため）
署名つきのリンクURL に有効期限と署名を付けたもの。期限が切れたり、書き換えたりすると使えない。Laravel の URL::temporarySignedRoute()
回数制限（429）決まった時間に決まった回数より多く呼ばれたら断ること。パスワードの総当たりを防ぐ
IDORURL の ID を変えるだけで、他人のデータを見たり変えたりできてしまうこと。01 の素朴な版がこの形

4. 設計の選択肢を比べる

① トークンを、どこに置くか

案良いところ弱いところ向いている場面
A. JSON で返し、画面が sessionStorage に置く（素朴な版）作るのが簡単。CSRF が起きないXSS で盗まれる。新しいタブでログインが消えるなし（ブラウザでは勧められない）
B. HttpOnly の Cookie に置くJavaScript から読めないので、XSS で持ち出されにくい。すべてのタブで同じ自動で送られるので CSRF の守りが要る。画面と API を同じサイトに置く必要があるブラウザの SPA
C. BFF がトークンを預かるブラウザにトークンがないサーバーが1つ増える大きめのサービス
この一歩で選ぶもの：直した版は B（D-014）。BFF は作らない。01b では画面がないので、curl の Cookie の保存（-c・-b）で確かめる。

② JWT を、どうやって止められるようにするか

案良いところ弱いところ向いている場面
A. 止めない（期限を長く。素朴な版）何も作らなくてよいログアウトしても、盗まれても、期限まで使える。権限が古いままなし
B. 短い期限（15分）＋取り替え用のトークン（DB）JWT は DB を見ずに確かめられる。止めたいときは、取り替え用のトークンを止めれば、最大15分で切れる表と取り替えの仕組みを作るJWT のよさを残したいとき
C. 止めた JWT の番号（jti）を表に入れ、毎回確かめるすぐ止められる毎回 DB を見るので、JWT のよさ（DB を見ない）がなくなるすぐ止める必要が強いとき（B と組み合わせる）
この一歩で選ぶもの：直した版は B。取り替え用のトークンは、使うたびに取り替え、使ったものがもう一度来たら「盗まれた」と考えて家族ごと止める（FR-AUTH-015）。

③ 確認のリンクを、どう持つか

案良いところ弱いところ向いている場面
A. 乱数を users の列に平文で持つ・期限なし（素朴な版）分かりやすいDB が漏れると、だれのメールアドレスでも確認済みにできる。いつまでも使えるなし
B. 乱数のハッシュと期限を、別の表に持つ漏れても使えない。期限で切れる表が1つ増える1回だけ使うことを、DB で厳しく守りたいとき（パスワードの再設定など）
C. 署名つきのリンク（DB に持たない）表が要らない。期限と書き換えの確かめは、署名で済む期限内なら何度でも開ける（ただし確認は1回で済み、2回目は何も変えない）メールアドレスの確認
この一歩で選ぶもの：直した版は C（Laravel の標準）。確認は「済んだかどうか」だけを email_verified_at に持てば足りる。

④ ログインの回数を、何で数えるか

案弱いところ
IP だけ同じ IP（会社・学校）の人をまとめて締め出す。IP を変えれば何度でも試せる
メールアドレスだけ悪い人がわざと失敗して、本人を締め出せる
メールアドレスと IP の組み合わせ両方を変えないと試し続けられない。本人は別の場所からならログインできる
この一歩で選ぶもの：直した版は、メールアドレスと IP の組み合わせで 1分に5回まで（FR-AUTH-012）。Laravel の RateLimiter を使う。

5. 見本：素朴な版と直した版

素朴な版（Fat Controller・テストなし）

// 登録
public function register(Request $request)
{
    $user = User::create($request->all() + [
        'verification_token' => Str::random(40),   // 平文・期限なし
    ]);
    Mail::to($user->email)->send(new VerifyMail($user));
    return $user;
}

// ログイン
public function login(Request $request)
{
    $user = User::where('email', $request->email)->first();
    if (! $user || ! Hash::check($request->password, $user->password)) {
        return response()->json(['message' => 'メールアドレスが違います'], 401);
    }
    return ['token' => JWT::encode([
        'sub' => $user->id, 'email' => $user->email, 'is_paid' => false,
        'exp' => time() + 60 * 60 * 24 * 30,      // 30日
    ], $key, 'HS256')];
}
  • 登録：18歳未満も入れる。A@example.test と a@example.test が別の人になる。$request->all() で email_verified_at まで送れて、確認を飛ばせる
  • 確認のリンク：平文で DB にあり、期限がない
  • ログイン：ないメールアドレスのときだけ「メールアドレスが違います」になり、登録されているかが分かる。何回でも試せる。ないメールアドレスのときはパスワードの照合を飛ばすので、返るまでの時間で見分けられる
  • JWT：30日使え、止められない。中身（メールアドレス）はだれでも読める。is_paid が古いまま残る

直した版

// ログイン：Cookie で渡す。JSON にトークンは入れない
$jwt = $issuer->accessToken($user);                 // sub・exp(15分)・jti・iss・aud だけ
[$plain, $row] = $refresh->issue($user);            // DB には hash('sha256', $plain)
return response()->noContent(200)
    ->cookie('access', $jwt, 15, '/', null, $secure, true, false, 'Lax')
    ->cookie('refresh', $plain, 60 * 24 * 30, '/api/auth', null, $secure, true, false, 'Lax');

// 取り替え：使った印のあるものが来たら、家族ごと止める
DB::transaction(function () use ($plain) {
    $row = RefreshToken::where('token_hash', hash('sha256', $plain))->lockForUpdate()->first();
    if (! $row || $row->expires_at->isPast() || $row->revoked_at) abort(401);
    if ($row->used_at) { RefreshToken::where('family_id', $row->family_id)->update(['revoked_at' => now()]); abort(401); }
    $row->update(['used_at' => now()]);
    // 同じ家族で、新しい取り替え用のトークンを作る
});

読み方：cookie() の引数の true が HttpOnly、'Lax' が SameSite、$secure は本番だけ true にする（設定で切り替える）。取り替えでは、同じ取り替え用のトークンが同時に2回来ても1回だけ通るように、lockForUpdate() で行をロックする（09 で詳しく学ぶ）。

6. どう確かめるか

段階確かめること
① 素朴な版で問題を見る
  • 17歳の生年月日で登録して、通ることを見る
  • a@example.test と A@example.test で2人登録できることを見る
  • 登録のときに email_verified_at を送り、確認を飛ばせることを見る
  • DB の確認用の文字が平文で、何日たっても使えることを見る。確認のメールを何回でも送れることを見る
  • ないメールアドレスと、違うパスワードで、返る言葉と時間が違うことを見る
  • 1分に何回ログインを試せるかを数える
  • JWT の真ん中を base64 で戻して、メールアドレスが読めることを見る
  • 「ログアウト」のあとも、同じ JWT で自分の情報が見られることを見る
  • ログインしていなくても、01 のプロフィールを他人のものまで編集できることを見る（IDOR）
② 振る舞いを固定するテスト要件 ID ごとにテストを足す（例：FR-AUTH-002 18歳未満は登録できない・FR-AUTH-015 使ったあとの取り替え用のトークンが、もう一度使われたら止める）。素朴な版でも守れているもの（パスワードのハッシュなど）は、素朴な版のまま通ることを確かめる
③ 直したあとに比べる数字守れている要件の数（素朴な版 ○/22 → 直した版 22/22）・JWT が使える時間（30日 → 15分）・1分に試せるログインの回数（数えきれない → 5回）・ないメールアドレスと違うパスワードの返る時間の差・ログアウトのあと JWT が使える時間

7. 気をつけること（罠）

  • bcrypt は 72バイトより後ろを見ない：日本語なら 24文字くらいで切れ、そこから後ろが違っても同じパスワードになる。パスワードは 64文字まで（FR-AUTH-004）
  • メールアドレスの大文字と小文字：users_email_unique は、大文字と小文字を別のものとして扱う。小文字にそろえて保存するか、lower(email) の UNIQUE のインデックス（式のインデックス）を作る
  • トランザクションの中でメールを送らない：送ったあとでロールバックすると、ない会員に確認のメールが届く。コミットのあとに送る（database.md）
  • ないメールアドレスのときも、照合の時間をそろえる：ないときだけすぐ返すと、時間で登録の有無が分かる。決まったハッシュで Hash::check() を1回する（NFR-AUTH-002）
  • JWT の鍵は、秘密の値のファイルで渡す：リポジトリに入れない。AI は秘密の値のファイルを読まない・書かないので、鍵はあなたが作って入れる
  • JWT の方式（alg）はサーバーで決め打ちにする：ヘッダーの alg を信じない（none を通さない）
  • 確認のリンクの URL がログに残る：00 で作った SQL のログの db.summary は、パスをそのまま書く。確認のリンクのパスに署名が入るなら、ルートのひな形を書く形に変える（00 のレビューの P2）
  • 18歳の境目は日本の時間帯で：01 と同じく、Laravel の設定は UTC
  • curl で Cookie を確かめる：-c cookie.txt で保存し、-b cookie.txt で送る。HttpOnly でも curl は読めるので、「JS から読めない」ことは 03b の画面で確かめる

8. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？（なぜ JWT を短くして、取り替え用のトークンを DB に持つのか）

JWT は DB を見ずに確かめられるかわりに、一度渡すと期限まで止められない。期限を15分に短くすれば、盗まれても使える時間は短い。そのままだと15分ごとにログインし直すことになるので、取り替え用のトークンで新しい JWT をもらう。取り替え用のトークンは DB に持つので、ログアウトや「盗まれた」と分かったときに止められる。

ほかの方法は？なぜ選ばなかったか？

セッション（Sanctum の SPA 認証）は、毎回 DB を見るかわりに、すぐ止められて仕組みも小さい。この学習では JWT の形と弱いところを学ぶために JWT にした（D-014）。止めた JWT の番号を毎回確かめる方法は、JWT のよさ（DB を見ない）がなくなる。BFF は、ブラウザにトークンを置かず最も守りやすいが、サーバーが1つ増える。

弱点は？

ログアウトしても、JWT は最大15分は使える。取り替え用のトークンの表と、取り替え・家族ごと止める仕組みを作る手間がある。Cookie なので CSRF の守りが要り、画面と API を同じサイトに置く必要がある。JWT の鍵が漏れると、だれの JWT でも作られる。

問題が起きたら、どう調べて直すか？

「ログインが続かない」→ ブラウザの開発ツールで Cookie が保存されているか（SameSite・Secure・ドメイン）、API が Access-Control-Allow-Credentials を返しているかを見る。「急に全員ログアウトした」→ JWT の鍵が変わっていないか、取り替え用のトークンの家族ごとの停止が誤って起きていないか（同時に2回の取り替え）を refresh_tokens の used_at・revoked_at で見る。盗まれた疑いがあれば、その会員の取り替え用のトークンを全部止め、必要なら JWT の鍵を取り替える（全員がログインし直しになる）。

データが10倍・100倍になったら？

アクセストークンの確かめは DB を見ないので、会員が増えても重くならない。重くなるのは refresh_tokens：端末ごと・取り替えのたびに行が増える。token_hash の UNIQUE のインデックスで探すので速いが、期限切れの行を定期的に消す仕組み（バッチ）が要る。ログインの回数制限は、手元はキャッシュの表で数えるが、数が増えたら Redis に移す。

Eloquent でどんな SQL が流れ、どう直したか？ Rails（ActiveRecord）・Prisma ならどう書くか？

素朴な版のログインは select * from users where email = ? limit 1 の1本で、大文字のメールアドレスでは見つからない（または別の人として登録できる）。直した版は、メールアドレスを小文字にそろえ、取り替えのときに select ... for update で行をロックしてから update する。
