1. 決まったこと

項目会員の側（backend/client）管理画面（backend/admin）
形DIP を使ったレイヤード（4層）同じ4層の骨組み。読み取りは Controller から QueryService を直接、書き込みだけ UseCase と Domain
理由中くらいの規模。いろいろな現場で使われていて、入った人がすぐ読める。依存性の少ない設計にしたい（ファイルが増えてもよい）API が少なく（14本）、読み取りと集計が中心。形を会員の側と1つにして、読む・レビューする・AI が真似する手間を減らす
業務の決まりの置き場Domain 層（Laravel を使わない）Domain 層（運営の権限と監査：役割・停止・値段・監査ログ）
Laravel の機能Http と Infrastructure だけで使う。Application と Domain では使わない（トランザクションと日時も interface 越し）会員の側と同じ
読み取りの専用の道QueryService（必要なときだけ）QueryService（読み取りは全部ここ。画面ごと）
守り方アーキテクチャのテスト（Pest の arch()）と API テスト
方針今の段階に合う形にする。機能・会員・ファイルが増えて問題が出たら、そのときにやり直す（11章のきっかけ）

2. 先に知っておく言葉

言葉意味（1〜2文）
依存性逆転（DIP）業務の側（Domain）が「こういう保存や取り出しが要る」という約束（interface）を決め、DB の側（Infrastructure）がそれに合わせて作る形。業務が DB を知らずに済む
エンティティID で区別する業務のもの（会員・いいね）。中身が変わっても同じもの
値オブジェクト値そのもので区別する小さな型（会員の ID・金額）。作るときに正しい値かを確かめ、あとから変えない
集約一緒に整合性を守るまとまり。保存と取り出しは集約ごとに Repository で行う
ドメインサービス1つのエンティティに置くと不自然な業務の決まり（「2人がお互いにいいねしたらマッチ」）
UseCase利用者の1つの操作の手順（いいねする）。1操作1クラス
DTO層の間でデータを運ぶだけの型（入力・出力）。連想配列の代わりに使い、型で間違いを止める
Repository集約を保存・取り出す。interface は Domain、実装（Eloquent を使う）は Infrastructure
QueryService一覧・検索・集計のような読み取り専用の処理。画面に出す形の DTO を直接返し、エンティティへの詰め替えを省く
詰め替え（マッピング）Eloquent の Model（DB の形）と Domain のエンティティ（業務の形）を、お互いに作り直すこと。Repository の実装の中で行う

② ApplicationDomainHttp・Infrastructure使わない（DB::・now()・config() も）

矢印が Domain に集まっているのがポイント。Domain はだれにも依存しないので、DB・Firestore・Laravel が変わっても、業務の決まりは直さずに済む。

// app/Http/Middleware/AuthenticateMember.php
// トークンを読むのはここだけ。読めたら会員 ID をリクエストに載せる
final class AuthenticateMember
{
    public function __construct(private JwtTokenService $tokens) {}

    public function handle(Request $request, Closure $next): Response
    {
        $memberId = $this->tokens->memberIdFrom($request->bearerToken());   // 読めなければ null
        if ($memberId === null) {
            return response()->json(['message' => 'ログインしてください'], 401);
        }
        $request->attributes->set('member_id', $memberId);

        return $next($request);
    }
}
// app/Http/Requests/Matching/StoreLikeRequest.php
// 形だけを確かめる（UUID か）。「相手がいるか」は業務の話なので Domain で
final class StoreLikeRequest extends FormRequest
{
    /** @return array<string, list<string>> */
    public function rules(): array
    {
        return ['user_id' => ['required', 'uuid']];
    }

    public function toInput(): LikeMemberInput
    {
        return new LikeMemberInput(
            memberId: new MemberId((int) $this->attributes->get('member_id')),
            targetPublicId: $this->string('user_id')->toString(),
        );
    }
}
// app/Http/Controllers/Matching/LikeController.php
// 受け取る → UseCase を呼ぶ → 形にして返す。判断も SQL も書かない
final class LikeController extends Controller
{
    public function store(StoreLikeRequest $request, LikeMemberUseCase $useCase): JsonResponse
    {
        $output = $useCase->execute($request->toInput());

        return (new LikeResultResource($output))->response()->setStatusCode(201);
    }
}
// app/Http/Resources/Matching/LikeResultResource.php
// 返してよい項目だけを並べる（今は Model を丸ごと返している）
final class LikeResultResource extends JsonResource
{
    /** @return array<string, mixed> */
    public function toArray(Request $request): array
    {
        /** @var LikeMemberOutput $output */
        $output = $this->resource;

        return [
            'matched' => $output->matched,
            'talk_room_id' => $output->talkRoomPublicId,
        ];
    }
}

// app/Application/Transaction/TransactionManagerInterface.php
interface TransactionManagerInterface
{
    /**
     * 中の処理を1つのトランザクションで実行する。例外が出たら巻き戻して、その例外を投げ直す
     *
     * @template T
     * @param callable(): T $callback
     * @return T
     */
    public function run(callable $callback): mixed;
}
// app/Application/UseCases/Matching/LikeMemberUseCase.php
// 手順だけを書く。決まりは Domain、保存は Repository、外への書き込みはコミットのあと
final class LikeMemberUseCase
{
    public function __construct(
        private MemberRepositoryInterface $members,
        private LikeRepositoryInterface $likes,
        private UserMatchRepositoryInterface $matches,
        private TalkRoomRepositoryInterface $talkRooms,
        private MatchingService $matching,
        private ChatSyncInterface $chatSync,
        private TransactionManagerInterface $transaction,
        private ClockInterface $clock,
    ) {}

    public function execute(LikeMemberInput $input): LikeMemberOutput
    {
        $me = $this->members->findById($input->memberId);
        $target = $this->members->findByPublicId($input->targetPublicId);   // いなければ MemberNotFoundException
        $now = $this->clock->now();

        // 無料の男性は1日10回まで（日付の境目は今のまま UTC。既知のリスク：07 の 9-2）
        LikeQuota::assertNotExceeded($me, $this->likes->countSentOn($me->id, $now));

        $room = $this->transaction->run(function () use ($me, $target, $now): ?TalkRoom {
            $this->likes->save(Like::create($me->id, $target->id, $now));

            if (! $this->matching->isMutual($me->id, $target->id)) {
                return null;
            }
            $match = UserMatch::create($me->id, $target->id, $now);
            $this->matches->save($match);
            $room = TalkRoom::openFor($match);
            $this->talkRooms->save($room);

            return $room;
        });

        if ($room !== null) {
            $this->chatSync->openRoom($room);   // DB が確定してから外へ書く
        }

        return new LikeMemberOutput(matched: $room !== null, talkRoomPublicId: $room?->publicId);
    }
}

// app/Domain/Matching/Like/Like.php（エンティティ）
// 新しく作るときの create と、DB から作り直すときの reconstruct を分ける
final class Like
{
    private function __construct(
        public readonly ?int $id,
        public readonly MemberId $from,
        public readonly MemberId $to,
        public readonly DateTimeImmutable $likedAt,
    ) {}

    public static function create(MemberId $from, MemberId $to, DateTimeImmutable $now): self
    {
        // 自分へのいいねを止める決まりは、改善のチケットでここに足す（今は止めていない）
        return new self(null, $from, $to, $now);
    }

    public static function reconstruct(int $id, MemberId $from, MemberId $to, DateTimeImmutable $likedAt): self
    {
        return new self($id, $from, $to, $likedAt);   // DB の値は正しい前提で、確かめを省く
    }
}
// app/Domain/Matching/Like/LikeQuota.php
// 決まりを1か所に。DB を知らない純粋な関数なので、単体テストで境目を確かめられる
final class LikeQuota
{
    public const FREE_MALE_DAILY_LIMIT = 10;

    public static function assertNotExceeded(Member $member, int $sentToday): void
    {
        if ($member->gender === Gender::Male && ! $member->isPaid && $sentToday >= self::FREE_MALE_DAILY_LIMIT) {
            throw new PaidPlanRequiredException();
        }
    }
}

final class MatchingService

// app/Infrastructure/Repositories/Matching/EloquentLikeRepository.php
// Eloquent が出てくるのは、ここから下だけ。詰め替えもここ
final class EloquentLikeRepository implements LikeRepositoryInterface
{
    public function save(Like $like): void
    {
        LikeModel::query()->create([
            'from_user_id' => $like->from->value,
            'to_user_id' => $like->to->value,
            'created_at' => $like->likedAt,
        ]);
    }

    public function exists(MemberId $from, MemberId $to): bool
    {
        return LikeModel::query()
            ->where('from_user_id', $from->value)
            ->where('to_user_id', $to->value)
            ->exists();
    }

    public function countSentOn(MemberId $from, DateTimeImmutable $day): int
    {
        return LikeModel::query()
            ->where('from_user_id', $from->value)
            ->whereDate('created_at', $day->format('Y-m-d'))   // 列を包むのでインデックスが効かない（04 の 9-2）
            ->count();
    }
}

7-5. 読み取りの道（QueryService）

一覧と検索は、エンティティに詰め替えると遅く、手間も大きい。QueryService が画面の形の DTO を直接返す。SQL は自由に書けるので、JOIN・with()・カーソルをここで決める（N+1 を防ぐ場所が1か所になる）。

// app/Infrastructure/QueryServices/Members/SearchMembersQueryService.php
final class SearchMembersQueryService
{
    /** @return list<MemberSummary> */
    public function search(MemberId $me, SearchCriteria $criteria): array
    {
        return UserModel::query()
            ->join('profiles', 'profiles.user_id', '=', 'users.id')
            ->whereNull('users.deleted_at')
            ->where('profiles.gender', $criteria->gender->value)
            ->whereNotExists(fn ($q) => $q->from('blocks')->whereColumn('blocks.blocked_id', 'users.id')->where('blocks.blocker_id', $me->value))
            ->orderByDesc('users.last_login_at')
            ->limit($criteria->limit)
            ->get(['users.public_id', 'profiles.nickname', 'profiles.birthday'])
            ->map(fn ($row) => new MemberSummary($row->public_id, $row->nickname, $row->birthday))
            ->all();
    }
}

// app/Http/Controllers/Members/SearchController.php（読み取りは UseCase を通さなくてよい）

// app/Domain/Members/MemberSuspension.php
// 停止の決まり：理由は必須・もう停止している会員は止めない
final class MemberSuspension
{
    private function __construct(
        public readonly int $memberId,
        public readonly ?DateTimeImmutable $suspendedAt,
        public readonly ?string $reason,
    ) {}

    public static function reconstruct(int $memberId, ?DateTimeImmutable $suspendedAt, ?string $reason): self
    {
        return new self($memberId, $suspendedAt, $reason);
    }

    public function suspend(string $reason, DateTimeImmutable $now): self
    {
        if ($this->suspendedAt !== null) {
            throw new AlreadySuspendedException();
        }
        if (trim($reason) === '') {
            throw new InvalidArgumentException('停止の理由は必須');
        }

        return new self($this->memberId, $now, $reason);
    }
}

// app/Application/UseCases/Members/SuspendMemberUseCase.php
// 役割の確かめ → 停止 → 監査ログを、1つのトランザクションで（今は監査ログに漏れがある：12 の 9-2）
final class SuspendMemberUseCase
{
    public function __construct(
        private AdminRepositoryInterface $admins,
        private MemberSuspensionRepositoryInterface $suspensions,
        private AuditLogRepositoryInterface $auditLogs,
        private TransactionManagerInterface $transaction,
        private ClockInterface $clock,
    ) {}

    public function execute(SuspendMemberInput $input): void
    {
        $admin = $this->admins->findById($input->adminId);
        $admin->assertCan(Permission::SuspendMember);   // 見るだけの人なら PermissionDeniedException → 403
        $now = $this->clock->now();

        $this->transaction->run(function () use ($input, $admin, $now): void {
            $current = $this->suspensions->findByPublicIdForUpdate($input->memberPublicId);   // 行をロックして読む
            $suspended = $current->suspend($input->reason, $now);
            $this->suspensions->save($suspended);

            $this->auditLogs->save(new AuditLog(
                adminId: $admin->id,
                action: AuditAction::SuspendMember,
                targetType: 'users',
                targetId: $suspended->memberId,
                detail: ['reason' => $input->reason],
                at: $now,
            ));
        });
    }
}

{
    public function findByPublicIdForUpdate(string $publicId): MemberSuspension
    {
        $row = User::query()->where('public_id', $publicId)->lockForUpdate()->first()
            ?? throw new MemberNotFoundException();

            'suspended_reason' => $suspension->reason,
        ]);
    }
}

11. メリットとデメリット

11-1. 会員の側（DIP を使ったレイヤード）

メリットデメリット
  • 業務の決まりが Domain の1か所に集まる（回数の上限・マッチの決まりが、今のように3か所にコピーされない）
  • Domain と UseCase を DB なしでテストできる（速い・時刻を固定できる）
  • DB・Firestore・JWT・将来の決済や AI を、実装を替えるだけで差し替えられる
  • Eloquent の Model が外に漏れないので、N+1 と項目の漏れ（パスワードのハッシュ）が起きにくい
  • フォルダを見れば層と機能が分かる。AI も見本を真似しやすい
  • 各層の中が機能ごとなので、将来モジュラーモノリスへ移りやすい
  • ファイルが増える（いいね1つで15〜20ファイル）
  • Eloquent の Model とエンティティの詰め替えが要る（Repository の実装が長くなる）
  • Eloquent の便利さ（リレーション・遅延読み込み）を、Infrastructure の中でしか使えない
  • interface から実装を探す一手間がある（エディタの「実装へ移動」を使う）
  • 「どこまでを Domain に置くか」の判断に慣れが要る
  • 層で横に切っているので、どの表をどの機能が持つかは、別に決めて守る必要がある

11-2. 管理画面（同じ4層・読み取りは QueryService を直接）

メリットデメリット
  • 会員の側と形が1つ。覚えるのも、AI が真似するのも、アーキテクチャのテストも1種類
  • 役割・停止・監査の決まりが Domain の1か所にあり、DB なしで単体テストできる（12 の 9-2 の問題が起きた場所）
  • 読み取りは QueryService を直接呼ぶので、詰め替えがなく、SQL を自由に書ける（集計と N+1 の直しに強い）
  • 画面の領域のフォルダ名が frontend/admin とそろい、画面を足すときに迷わない
  • 書き込みの API 1本で、会員の側と同じくらいファイルが増える
  • 会員の側の Domain（会員）と、管理画面の Domain（停止・値段）が、同じ表を別々の形で持つ。決まりがずれる心配がある → 10章の表で約束する
  • 読み取りが QueryService に集まるので、QueryService が太りやすい → 画面ごとに分ける

12-1. 今のコードからの移し方

flowchart LR
  T[その API を触るチケットが来た] --> FT[先に API テストで今の振る舞いを固める]
  FT --> MV[その API の処理を、新しい形の層へ移す]
  MV --> RUN[固めたテストが全部通る]
  RUN --> ARCH[アーキテクチャのテストの例外の一覧から、その API を消す]
  ARCH --> FIX[必要なら、ここで改善 不具合の直し・性能]
  FIX --> PR[PR とレビュー]
  • 一気に移さない。触るチケットが来た API から1本ずつ移す（ストラングラーパターン）
  • 移すことと、振る舞いを変えることを、別のコミットにする。移すコミットでは API テストが1本も変わらない。変わったら、移すときに壊した
  • 古いコントローラーは、移し終わるまで app/Http/Controllers の直下に残る。新しい形は app/Http/Controllers/<機能>/ に置くので、フォルダで見分けられる
  • アーキテクチャのテストでは、移していない古いファイルを例外として並べる。この一覧が、そのまま移行の地図になる

13. 理解を確かめる問い

LikeRepositoryInterface を Domain に置き、EloquentLikeRepository を Infrastructure に置くのはなぜ？

依存の向きを Domain に向けるため。interface が Domain にあれば、Domain は「何が要るか」だけを知り、Eloquent や SQL を知らずに済む。Infrastructure が Domain の約束に合わせて作るので、DB の都合が変わっても Domain と UseCase は直さない。逆に interface を Infrastructure に置くと、Domain が Infrastructure を使うことになり、矢印が元に戻る。

読み取り（検索）だけ、UseCase を通さず QueryService を直接呼んでよいのはなぜ？

読み取りには業務の決まり（守るべき整合性）がほとんどなく、画面の形で速く返すことが大事だから。エンティティに詰め替えてから DTO に詰め直すと、遅く手間も大きい。そのかわり、「出してはいけない人（退会・ブロック）」の条件は QueryService の中に1か所で書き、API テストで守る。

Firestore への書き込みを、TransactionManager の run の外（コミットのあと）にするのはなぜ？

トランザクションの中で外へ書くと、そのあと DB が巻き戻ったときに、外にだけ「ないはずのトークルーム」が残るから。外への書き込みは DB の巻き戻しに含まれない。DB が確定してから外へ書き、外が失敗したら DB は戻さずにやり直す（将来はキューで）。

管理画面の読み取りは Domain を通さないのに、書き込みだけ UseCase と Domain を通すのはなぜ？

書き込みには、役割の確かめ・停止の決まり・監査ログという「必ず守ること」があるから。Controller ごとに書くと漏れる（今のレガシー版で、見るだけの人が停止を解けた・監査ログに漏れがあった）。UseCase で手順を固め、決まりを Domain（AdminRole・MemberSuspension）に置けば、DB なしで単体テストでき、書き込みの API を足しても漏れにくい。読み取りには守る決まりが少ないので、QueryService で速く返す。

今のコードを新しい形に移すとき、移すコミットと直すコミットを分けるのはなぜ？

移すコミットでは振る舞いが変わらないので、API テストが1本も変わらずに通るはず。テストが落ちたら、移すときに壊したと分かる。直すコミット（不具合の直し・性能）を混ぜると、テストが変わった理由が「移したから」か「直したから」か分からなくなる。

このアプリの会員が10倍になったとき、この設計で最初に触るのはどこ？

遅くなった読み取りの QueryService の SQL と EXPLAIN。足りなければ、QueryService の中で読む先を読み取り専用の DB に変える。それでも足りなければ、検索の interface を作って検索エンジンの実装を足す。どれも UseCase・Controller・Domain は直さずに済むのが、層に分けた効果。
