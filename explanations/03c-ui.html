03c 画面の見た目と動き

作成: 2026-11-13 ／ 状態: 解説だけ

この一歩でできるようになること
  • モーダル・トースト・スケルトン・マッチの演出を、ライブラリを入れずにブラウザの標準で作れる
  • 「応答を待たずに先に見せる」（楽観的な表示）の良いところと、失敗したときの扱いを説明できる
  • 動きを足しても表示速度（CLS・バンドルの大きさ）を悪くしない作り方を、前と後の数字で説明できる

1. 何を作るか

今の画面は、押しても反応が返らず、読み込み中は真っ白で、マッチしても1行の文字が出るだけです。03c では、色・文字・余白をそろえ直し、押したとき・待つとき・うれしいときに動きで返す画面にします。値と部品の決まりは docs/design.md、受け入れ条件は screens.md の FR-UI-023〜033 です。

下は、決めた値で作った見本です。ボタンを押して動きを試せます（ここで動くのは見本だけで、アプリのコードではありません）。

2. 先に知っておく言葉

言葉意味（1〜2文）
モーダル画面の上に重ねて出し、閉じるまで後ろを触れなくする箱。確認や大事なお知らせに使う。
<dialog>モーダルを作るための HTML の標準の要素。showModal() で開くと、Esc で閉じる・後ろを触れなくする・一番上に出す、をブラウザが受け持つ。
トースト画面の端に少しだけ出て、数秒で消えるお知らせ。操作を止めない。
スケルトン読み込み中に、中身と同じ形の灰色の枠を出すこと。待つ時間が短く感じられ、中身が出たときに位置がずれない。
楽観的な表示（optimistic UI）応答を待たずに、成功したものとして先に画面を変えること。失敗したら元に戻す。React 19 では useOptimistic で書ける。
View Transitions画面が切り替わる前と後の様子をブラウザが写して、その間をなめらかにつなぐ仕組み。React Router は <Link viewTransition> で使える。
CLSCumulative Layout Shift。表示の途中で、もう出ていたものがどれだけ動いたかの数字。0.1 以下が良い。04 で測った Web Vitals の1つ。
prefers-reduced-motionOS で「動きを減らす」を選んだ人を見分ける CSS の条件。動きで酔う人のために、動きを止める。
フォーカスキーボードで今操作している場所。モーダルを開いたら中に移し、閉じたら開いたボタンに戻す。

4. 設計の選択肢を比べる

案良いところ弱いところ向いている場面
A. ブラウザと React の標準だけ（<dialog>・CSS の @keyframes・View Transitions・useOptimistic）依存が増えず、バンドルが大きくならない。Esc やフォーカスの閉じ込めをブラウザが受け持つ。04 の数字とそのまま比べられる閉じるときの動きや、指で引っぱる動きは自分で書く。View Transitions は古いブラウザで動かない（動かなくても困らない）部品が少なく、動きが決まった形のとき
B. 動きのライブラリ（Motion）消えるときの動き・指の動き・ばねの動きが楽に書けるバンドルが数十 KB 増える。動きの書き方がライブラリに縛られる指で操作する動きが多いアプリ（スワイプでいいね など）
C. 部品のライブラリ（Radix・shadcn/ui）読み上げ・キーボード操作がよくできた部品がそろう入れる量が多く、レガシー版の「1画面に1つの部品」の形と合わない。何をブラウザが受け持つかが見えにくい部品が多く、何人かで作る画面（12 の管理画面で考える）
この一歩で選ぶもの：A。依存を増やさずに作ると、動きを足した前と後で、バンドルの大きさと CLS の変化を動きそのものの分だけで測れます。標準の <dialog> を使うと、読み上げとキーボードの扱いを自分で作らずにすみます（D-024）。

5. 見本：レガシー版と改善版

レガシー版（1画面に1つの大きな部品）

03c のレガシー版は、見た目と動きだけを足します。モーダルやトーストは、使う画面ごとに書きます。

// HomePage.tsx の中。ログアウトの確認を、この画面のためだけに書く（いいねの画面にも、ほぼ同じものをもう1つ書く）
const [confirmOpen, setConfirmOpen] = useState(false)
const [toast, setToast] = useState('')
const dialogRef = useRef<any>(null)
useEffect(() => {
  if (confirmOpen) dialogRef.current?.showModal()
  else dialogRef.current?.close()
}, [confirmOpen])

const save = () => {
  fetch(`${api}/api/users/${me.public_id}`, { method: 'PUT', headers, body: JSON.stringify(form) })
    .then(() => {
      setToast('保存しました')
      setTimeout(() => setToast(''), 3000) // 3秒を、画面ごとに書く。続けて押すと、前のタイマーが新しいトーストを消す
    }) // 失敗は考えない（FR-UI-013 は守れていないまま）
}
同じモーダル・トーストが画面ごとにコピーされます。3秒・250ms などの値もあちこちに書くので、1つ直すと全部を探して直すことになります。タイマーを止めないので、続けて出すと新しいトーストが早く消えます。失敗・401・連打の扱いはこれまでどおり直しません（改善する段階で測って直すため）。

改善版

// 部品を1つにして、どの画面からも同じ形で呼ぶ
const toast = useToast()               // 1つだけ出す・新しいものが来たらタイマーごと入れ替える
const confirm = useConfirm()           // <dialog> を開き、押されたほうを Promise で返す

const onLogout = async () => {
  if (await confirm({ title: 'ログアウトしますか？', danger: 'ログアウトする' })) logout()
}

// いいね：応答を待たずに済みに見せ、失敗したら元に戻る
const [liked, setOptimisticLiked] = useOptimistic(user.liked)
const like = () => startTransition(async () => {
  setOptimisticLiked(true)
  const res = await api.like(user.id)  // 失敗したら、transition が終わると liked は元の値に戻る
  if (res.ok) res.data.matched ? openMatch(user) : toast.show('いいねしました')
  else toast.show('いいねできませんでした', 'error')
})

大事なのは useOptimistic の行です。先に見せた値は、処理が終わると元の値（サーバーから来た値）に戻るので、成功したときは元の値も true に変え、失敗したときは何もしなければ自然に戻ります。

この一歩は画面だけで、流れる SQL は変わらないので、SQL を並べる節はありません。

6. どう確かめるか

段階確かめること
① 作る前に今を測るLighthouse（スマホ・シークレットウィンドウ）で /search・/messages の LCP・INP・CLS。npm run build の JS と CSS の大きさ（gzip）。今の画面のスクリーンショット
② レガシー版で作ったあとFR-UI-023〜033 を手で試す。DevTools の Network を「Slow 4G」にしてスケルトンと送信中のボタンを見る。OS の「視差効果を減らす」を入れて動きが止まるか（NFR-UI-004）。Tab キーだけでモーダルを開いて閉じ、フォーカスが戻るか。① と同じ数字をもう一度測る
③ 改善する段階で固定するテストVitest＋Testing Library で FR-UI-023 ログアウトの前に確かめる（Esc で閉じる・フォーカスが戻る）・FR-UI-027 いいねを押すと、すぐ返ってくる（応答の前に済みになる・失敗で戻る）・FR-UI-024（続けて出しても3秒出る）
④ 比べる数字CLS（0.1 以下を保つ）・バンドルの大きさの増え方・モーダルとトーストのコードがいくつの画面にコピーされているか（レガシー版）と、部品1つ（改善版）

7. 気をつけること（罠）

  • height・top・margin を動かすと、まわりの並べ直しが毎回起きて重くなり、CLS も悪くなる。動かすのは transform と opacity だけ
  • スケルトンの大きさが中身と違うと、出た瞬間に下のものが押し出される（CLS が上がる）。写真は aspect-ratio で枠を先に取る
  • 送信中のボタンで文字をスピナーに替えるとき、幅が変わると隣のものが動く。文字は visibility: hidden で残し、幅を保つ
  • <dialog> を open 属性だけで開くと、モーダルにならない（後ろが触れる・Esc で閉じない）。showModal() で開く
  • トーストのタイマーを止めずに次を出すと、前のタイマーが新しいトーストを早く消す
  • 楽観的な表示は、失敗したときに戻すところまでで1つ。戻さないと、画面とサーバーで違う状態が残る（レガシー版はわざと戻さない）
  • StrictMode では、開発中に effect が2回動く。開いた・閉じたを effect の中で数えると、2回になる
  • View Transitions の名前（view-transition-name）は、同じ画面に同じ名前が2つあると、動きが出ない。カードごとに会員の ID を名前に入れる

8. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？

押しても反応がない画面は、会員が「押せたのか」を分からず、もう一度押す（いいねの二重送信・409 につながる）。読み込み中に真っ白だと、壊れていると思われる。動きは飾りではなく、「受け付けた」「待っている」「うまくいった」を伝えるために使う。だから時間は短く、動かす場所はマッチの演出に絞る。

ほかの方法は？なぜ選ばなかったか？

Motion（動きのライブラリ）や Radix・shadcn/ui（部品のライブラリ）がある。選ばなかったのは、バンドルが増えて 04 の数字と比べにくくなることと、今の画面に要る動き（開く・閉じる・弾む・光る）は CSS と <dialog> で足りるため。指で引っぱる動きや部品の数が増えたら、12 の管理画面で考え直す。

弱点は？

閉じるときの動き（消える前に縮む）は、CSS だけだと書きにくい（@starting-style や transitionend を使う）。View Transitions は古いブラウザで動かない。楽観的な表示は、失敗したときに一度「済み」に見えてから戻るので、会員がまぎらわしく感じることがある。レガシー版は部品がコピーされるので、直す場所が増える。

問題が起きたら、どう調べて直すか？

カクつくなら、DevTools の Performance で記録し、Layout（並べ直し）が動きの間に出ていないかを見る。出ていれば、動かしている性質を transform に替える。CLS が上がったら、Lighthouse の「レイアウトのずれ」でずれた要素を見て、スケルトンや写真の枠の大きさを中身に合わせる。モーダルが閉じないなら、showModal() で開いているか、close のイベントで状態を戻しているかを見る。

データが10倍・100倍になったら？

一覧が長くなると、行ごとに動き（入ってくるフェード）を付けると、描く量が増えて重くなる。最初に見える行だけに付けるか、04 の改善で考える長い一覧（見えている行だけ描く）と合わせる。トークの吹き出しが数千になっても、動かすのは足した1つだけにする。スケルトンの数は、画面に入る分（4〜6個）で止める。

Eloquent でどんな SQL が流れ、どう直したか？ Rails（ActiveRecord）・Prisma ならどう書くか？

03c は画面だけなので、流れる SQL は変わらない。ただし未読のバッジ（FR-UI-032）を出すために、レガシー版はどの画面でもトークの一覧（GET /api/me/talk-rooms）をもう1回呼ぶ。05 のレガシー版のこの API は、ルームごとにルーム・相手・プロフィール・public_id・最新の1件・未読の数を1本ずつ読む（1＋6N 本）ので、バッジの数字1つのために、どの画面を開いても 1＋6N 本が流れる。

流れる SQL問題直し方
Eloquent（レガシー版）一覧の API を丸ごと呼ぶ。未読はルームごとに select count(*) from messages where talk_room_id = ? and sender_id != ? and created_at > ?バッジの合計1つのために 1＋6N 本合計だけを返す API（1本の count）にするか、一覧の応答を画面で使い回す
Rails（ActiveRecord）同じ形で room.messages.where("created_at > ?", last_read_at).count を回すと 1＋N同じMessage.joins(:talk_room_members).where(...).count で1本にする
Prismaprisma.message.count をルームごとに呼ぶと 1＋N同じprisma.$queryRaw で1本の count、または groupBy
