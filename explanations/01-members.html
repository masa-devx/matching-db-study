01 会員とプロフィール

作成: 2026-11-11 ／ 状態: 解説だけ ／ Issue: #8 ／ 要件: docs/requirements/members.md（FR-001〜FR-014）

この一歩でできるようになること
  • 主キー・データの型・NOT NULL・CHECK・UNIQUE を、「何を DB に守らせるか」で選んで説明できる
  • 1対1 の表の分け方（profiles.user_id を主キー兼外部キーにする）と、分ける理由を説明できる
  • 素朴な表（全部を文字で持つ）に、おかしな値が入ることを確かめ、データを壊さずに直す手順を知る

1. 何を作るか

会員が相手のプロフィールを見て、自分のプロフィールを編集できるようにします。01 ではまだ登録の API がないので、会員はシードで 20人 用意します（プロフィール画像は、シードで作る頭文字のデモ画像）。

API中身要件
GET /api/users/{id}/profile相手のプロフィールを見る。年齢を返し、生年月日・メールアドレス・パスワードは返さないFR-001〜004
PUT /api/users/{id}/profileプロフィールを編集する。表示名・都道府県・身長・自己紹介・画像だけ。性別と生年月日は変わらないFR-005〜010

API の入力と応答の細かい形は、子 Issue #10 の最初に docs/api.md に書き、確かめてもらってから作ります。

だれが編集できるか（自分だけ）は 01b で直します。01 の素朴な版では、URL の会員 ID さえ分かれば、だれでも書き換えられます。

2. 先に知っておく言葉

言葉意味（1〜2文）
主キー（PK）表の中で1行を必ず1つに決める列。重なりも空も許されない。メールアドレスのような業務の値ではなく、意味のない番号（サロゲートキー）にすると、値が変わっても困らない
外部キー（FK）「この列の値は、あの表のどれかの主キー」という約束。ない会員を指すプロフィールを作れなくする
1対11人の会員に、プロフィールがちょうど1つ（か、なし）。2つ目を作れないようにするのが大事
NULL と NOT NULLNULL は「分からない・ない」。NOT NULL は「必ず値がある」。NULL は = NULL で比べても真にならないので、扱いに気をつける
CHECK 制約「身長は 120〜220」のような、値の範囲の決まりを DB に持たせる。アプリを通らない書き込み（手で流す SQL・バグ）でも断る
マスタの表選べる値の一覧を持つ表（例：性別の表・都道府県の表）。ほかの表は、外部キーでこの表の値を指す。値を足すときは、行を足すだけで済む
UNIQUE 制約その列（の組み合わせ）に、同じ値が2つ入らないようにする。同時に2つ登録されても、DB が片方を断る
データの型列に入る値の種類。smallint（小さな整数）・date（日付）・varchar(n)（n 文字までの文字）・timestamptz（時間帯つきの日時）など。型が合わない値は、DB が入れない
マイグレーション表の作り方・変え方を、順番つきのファイルで残す仕組み（00 で使った）。流したものは書き換えず、直すときは新しいファイルを足す
ファクトリ・シードファクトリは「それらしい会員」を作る決まり、シードはそれを使って DB に入れる処理。01 の会員は、これで用意する
ハッシュ化パスワードを、元に戻せない形に変えて保存すること。暗号化（鍵があれば戻せる）とは違う。Laravel は bcrypt（わざと遅く作られた方式）を使う
一括代入（mass assignment）$user->fill($request->all()) のように、送られてきた値をまとめて Model に入れること。送ってはいけない列（性別・メールアドレスなど）まで書き換えられてしまうことがある
バリデーションアプリで入力を確かめること。誤りなら 422 を返し、保存しない

4. 設計の選択肢を比べる

① 1対1 をどう作るか

案良いところ弱いところ向いている場面
A. 1つの表（users）に全部入れる（素朴な版）JOIN が要らない。作るのが速いログインに使う列と、相手に見せる列が混ざる。一覧で読むたびに全部の列を読む。見せてはいけない列を返しやすい列が少なく、見せ方も1つのとき
B. profiles に分け、user_id を主キー兼外部キーにする1人に2つのプロフィールを、表の作りとして作れない（主キーは重ならないため）。余計な列がない読むときに JOIN か、もう1本の SQL が要る1対1 がずっと変わらないとき
C. profiles に分け、自分の id と、UNIQUE の user_id を持つあとで「1人に複数」に変えやすい（UNIQUE を外すだけ）列が1つ余計。UNIQUE を付け忘れると、1対1 が壊れる将来、1対多になりそうなとき
この一歩で選ぶもの：直した版は B。プロフィールは会員ごとに1つで、増えることはない。主キーで1対1 を守るので、UNIQUE の付け忘れも起きない。

② 選べる値（性別・都道府県）をどう持つか

案良いところ弱いところ向いている場面
A. 文字で持つ（'male'・'東京都'）・制約なし（素朴な版）SQL を読むと意味がすぐ分かる書き方のゆれ（'M'・'東京'）がそのまま入る。インデックスが大きくなるなし（制約を付けるなら CHECK と組み合わせる）
B. 小さな整数（smallint）＋CHECK決めた値しか入らない。小さく、04 の検索のインデックスも小さい番号の意味は、アプリの定数で持つ（1＝男性 など）。SQL だけ見ても意味が分からない値が少なく、ほとんど変わらないとき
C. PostgreSQL の ENUM 型決めた値しか入らず、意味も読める値を足すのは簡単だが、消す・並べ替えるのが重い。Laravel のマイグレーションで扱いにくい値がずっと変わらず、DB だけで意味を読みたいとき
D. マスタの表（prefectures）＋外部キー名前・並び順・地方なども持てる。値を足すのは行を足すだけ表と JOIN が増える値が増える・名前を DB で持ちたいとき
この一歩で選ぶもの：直した版は D（D-012）。性別は男性・女性のほかに「その他」「回答しない」も選べるようにし、あとから値が増えても行を足すだけで済むようにする。都道府県も同じ形にそろえ、CHECK で範囲を書かずに、外部キーで守る。名前と並び順も DB に持てる。相手に求める性別（複数選べる）は、04 で中間の表にする。

③ おかしな値を、どこで断るか

案良いところ弱いところ向いている場面
A. どこでも断らない（素朴な版）書くことが少ないおかしな値がたまり、あとで集計・検索・表示が壊れるなし
B. アプリだけ（バリデーション）利用者に分かる言葉で 422 を返せるシード・手で流す SQL・別の API の書き忘れでは守れない見た目の決まり（入力の形）だけのとき
C. アプリと DB の両方利用者には 422、どの書き込みでも DB が最後に断る決まりを2か所に書く（範囲を変えるときは両方を直す）壊れたら困る決まり（範囲・必須・重なり）
この一歩で選ぶもの：直した版は C。「アプリを通らない書き込みでも壊れてはいけないか」が Yes のもの（範囲・必須・1対1・メールアドレスの重なり）は DB にも持たせる（database.md の決まり）。身長の範囲（120〜220）は、ありえない値が入っても表示が変になるだけなので、DB では型（smallint）だけを守り、範囲はバックエンドで守る（D-013）。18歳以上は、CHECK に「今日の日付」が使えないので、アプリ（01b の登録）で確かめる。フロントエンドの確かめだけでは、curl で API を直接呼べば通ってしまうので守れない。

5. 見本：素朴な版と直した版

素朴な版（Fat Controller・テストなし）

// マイグレーション：users に文字の列を足す（制約なし）
$table->string('gender')->nullable();
$table->string('birthday')->nullable();
$table->string('height')->nullable();

// User.php
protected $guarded = [];   // どの列でも一括代入できる

// routes/api.php
Route::get('/users/{id}/profile', function ($id) {
    return User::findOrFail($id);          // 全部の列を返す
});
Route::put('/users/{id}/profile', function (Request $request, $id) {
    $user = User::findOrFail($id);
    $user->fill($request->all())->save();  // 送られた値を全部入れる
    return $user;
});
  • おかしな値が入る：height = "abc"・gender = "M"・birthday = "2026-13-45" がそのまま保存される（FR-006〜009・012）
  • 見せてはいけないものを返す：生年月日とメールアドレスが応答に入る（FR-002）。パスワードは Laravel の $hidden で隠れるが、たまたま隠れているだけ
  • 変えてはいけないものが変わる：gender・birthday・email、password まで送れば書き換わる（FR-010）
  • 年齢が出せない：生年月日が文字なので、'1995/4/1' と '1995-04-01' が混ざり、年齢で絞る・並べる SQL が書けない

直した版

// マイグレーション：profiles を分け、型と制約を DB に持たせる
Schema::create('profiles', function (Blueprint $table) {
    $table->foreignId('user_id')->primary()->constrained()->cascadeOnDelete();
    $table->string('nickname', 20);
    $table->smallInteger('prefecture_code')->nullable();
    $table->foreign('prefecture_code')->references('code')->on('prefectures');
    $table->smallInteger('height_cm')->nullable();      // 範囲はアプリで守る（D-013）
    $table->timestampsTz();
});
DB::statement("ALTER TABLE profiles ADD CONSTRAINT profiles_nickname_length_check
               CHECK (char_length(nickname) BETWEEN 1 AND 20)");

// 編集：決めた項目だけを、確かめてから入れる
$data = $request->validate([
    'nickname'  => ['required', 'string', 'min:1', 'max:20'],
    'prefecture_code' => ['nullable', 'integer', 'exists:prefectures,code'],
    'height_cm' => ['nullable', 'integer', 'between:120,220'],
]);
$user->profile()->update($data);   // 性別・生年月日は受け取らない

読み方：foreignId('user_id')->primary() が「主キー兼外部キー」で、1対1 を表の作りで守る。foreign('prefecture_code')->references('code')->on('prefectures') が都道府県の表への外部キー（列は表の code と同じ smallint にそろえる）。Laravel のマイグレーションには CHECK を書く道具がないので、表示名の長さは DB::statement で SQL を書く。validate() で通った項目だけを保存するので、送られてきたほかの列（性別など）は無視される。直した版では、応答は年齢を出す形（API Resource）にして、生年月日は返さない。

直すときは、素朴な版の表に入ってしまったおかしな値を、先に見つけて直してから制約を付けます（database.md の「違反する行がないか、先に読み取りの SQL で確かめる」）。データを消さずに、表を足す → 写す → 古い列を消す、の順に進めます。

6. どう確かめるか

段階確かめること
① 素朴な版で問題を見る
  • curl で height="abc"・gender="M"・birthday="2026-13-45" を送り、保存されることを見る
  • curl で email・password を送り、書き換わることを見る
  • GET の応答に、生年月日とメールアドレスが入っていることを見る
  • psql で直接、同じ会員のプロフィールの重なり・おかしな値を入れてみて、入ってしまうことを見る
  • SQL のログで、GET・PUT の1回に何本流れるかを数える
  • 要件 FR-001〜014 のうち、いくつ守れていないかを数える
② 振る舞いを固定するテスト直す前に、要件 ID ごとにテストを足す。素朴な版でも守れているもの（FR-001・004・005・014 など）は、素朴な版のまま通ることを確かめる。守れていないもの（FR-002・006〜013）は、素朴な版では落ちることを確かめてから直す。テストの名前は FR-006 表示名は 1〜20文字 のように要件 ID を入れる
③ 直したあとに比べる数字守れている要件の数（例：素朴な版 ○/14 → 直した版 14/14）・おかしな値を DB に直接入れたときに断られた数・GET 1回の SQL の本数（NFR-001：2本以内）・表を直したときに見つかったおかしな行の数

7. 気をつけること（罠）

  • CHECK に「今日の日付」は書けない：CHECK (birthdate <= current_date - interval '18 years') は PostgreSQL が断る。CHECK はいつ確かめても同じ答えになる式（immutable）しか使えないため。18歳以上はアプリで確かめる
  • 年齢の境目は時間帯でずれる：今の Laravel の時間帯の設定は UTC。日本の 0時〜9時は、UTC ではまだ前の日なので、誕生日の当日の朝に、年齢が1つ少なく出る。年齢を出すときは日本の時間帯（Asia/Tokyo）の「今日」を使う
  • Laravel の timestamps() は時間帯なし（timestamp without time zone。00 で確かめた）。直した版は timestampsTz() で timestamptz にする
  • string() は何も言わないと 255 文字：表示名の 20文字は string('nickname', 20) と書く。PostgreSQL の varchar(n) は、バイトではなく文字の数で数えるので、日本語でも 20文字
  • $guarded = [] と $request->all()：送られた値が全部の列に入る。素朴な版の大きな穴（FR-010）
  • 文字の列を数の列に変えるとき：'170cm' のような値が残っていると、型を変える SQL が失敗する。先に読み取りの SQL でおかしな行を探して直してから変える
  • マスタの表の行は、マイグレーションで入れる：性別と都道府県の行がないと、会員もプロフィールも作れない。シード（開発用のデータ）ではなく、どの環境にも必ず入るマイグレーションで入れる
  • foreignId() は bigint になる：マスタの表の code を smallint にするなら、外部キーの列も smallInteger() にそろえる（PostgreSQL は整数どうしなら型がずれていても外部キーを作れてしまうので、ずれに気づきにくい）
  • パスワードは2回ハッシュ化しない：casts() で 'hashed' にしたうえで、自分でも Hash::make() すると、ハッシュのハッシュになり、ログインできなくなる（Laravel は、すでにハッシュなら2回目はかけない作りだが、頼らずにどちらか一方にする）

8. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？（なぜ表を分け、型と制約を DB に持たせるのか）

ログインに使うもの（メールアドレス・パスワード・変えない性別と生年月日）と、相手に見せて自分で変えるもの（表示名・身長など）は、使う場面も変える人も違うので分ける。型と制約を DB に持たせるのは、アプリを通らない書き込み（シード・手で流す SQL・別の API の書き忘れ）でも、おかしな値を入れないため。利用者に分かる言葉で返すのはアプリのバリデーション、最後の守りは DB、と役目を分ける。

ほかの方法は？なぜ選ばなかったか？

1つの表のまま（案 A）は JOIN が要らないが、見せてはいけない列を返しやすく、列が増えるほど一覧が重くなる。profiles に自分の id を持たせる案（案 C）は、1対多 に変えやすいが、プロフィールは増えないので、UNIQUE の付け忘れの危険のほうが大きい。性別・都道府県を smallint＋CHECK にする案は小さく速いが、性別は値が増える見込みがあり、増やすたびに CHECK を変えるマイグレーションが要る。ENUM 型は値を消す・並べ替えるのが重い。そこでマスタの表にした。身長の範囲は、壊れても困らないので DB の CHECK にしなかった。

弱点は？

読むときに JOIN か2本目の SQL が要る（一覧で会員ごとにプロフィールを読むと N+1 になる。05 で扱う）。身長の範囲はアプリにしかないので、シードや手で流す SQL では、ありえない値が入りうる。性別・都道府県の名前を出すには、マスタの表との JOIN（か、もう1本の SQL）が要る。

問題が起きたら、どう調べて直すか？

おかしな値が見つかったら、まず読み取りの SQL で、同じような行がどれだけあるかを数える（例：height が数字だけでない行）。原因の書き込み（どの API・シード・手の SQL か）を SQL のログと laravel.log で探す。直すときは、データを直す → 制約を足す、の順に、新しいマイグレーションで進める（流したマイグレーションは書き換えない）。制約に断られたときは、エラーの制約の名前（profiles_prefecture_code_foreign・profiles_nickname_length_check）から、どの決まりかが分かる。

データが10倍・100倍になったら？

会員が 20人 → 2000人 → 2万人 になっても、主キーで1人を引く SQL は、インデックスで一瞬で終わる。重くなるのは一覧と検索（04）で、そのときに smallint で持っていることが効く（インデックスが小さい）。文字で持っていたら、検索のたびにゆれ（'東京' と '東京都'）を吸収する重い SQL が要る。表を直すマイグレーションは、行が多いほど時間がかかり、その間ロックがかかる（10 で扱う）。

Eloquent でどんな SQL が流れ、どう直したか？ Rails（ActiveRecord）・Prisma ならどう書くか？

素朴な版の User::findOrFail($id) は select * from users where id = ? limit 1 の1本で、全部の列を返す。直した版でプロフィールを一緒に読むと、$user->profile を読んだときに select * from profiles where user_id = ? がもう1本流れる（合わせて2本。NFR-001）。

ORM1対1 の書き方CHECK 制約決めた項目だけを保存する
EloquenthasOne(Profile::class)・belongsTo(User::class)マイグレーションに道具がない。DB::statement で SQL を書く$request->validate() の結果だけを入れる。$fillable を決める
Rails（ActiveRecord）has_one :profile・belongs_to :useradd_check_constraint がある（6.1 以降）Strong Parameters（params.require(:profile).permit(:nickname)）
Prismaprofile Profile? と、userId Int @id ＋ @relationスキーマに書けない。マイグレーションの SQL を手で直す型で受ける項目を決める（data: { nickname }）
