02 いいね

作成: 2026-11-12 ／ 状態: レガシー版まで ／ Issue: #24 ／ 要件: docs/requirements/likes.md（FR-LIKE-001〜009・NFR-LIKE-001〜002）

この一歩でできるようになること
  • 中間テーブルで多対多（会員と会員）をつなぎ、「同じ組は1行だけ」を UNIQUE で守る理由を、同時に送ったときの事実で説明できる
  • 「あるか調べてから入れる」が同時のリクエストで破れること（check-then-act）と、DB に断らせる直し方（UNIQUE＋ON CONFLICT DO NOTHING）を説明できる
  • 一覧の N+1 を、流れた SQL の本数で見つけ、with() で直せる

1. 何を作るか

会員が、気になる相手にいいねを送れるようにします。自分が送った相手の一覧も見られます。お互いにいいねするとマッチになりますが、マッチは 03 で作ります。もらったいいねの一覧は有料の会員だけに見せるので、07 で作ります。

作るもの中身要件子 Issue
いいねの表だれから・だれへ・いつFR-LIKE-003・009・NFR-LIKE-002#25
いいねを送る自分には送れない。同じ相手には1回だけ。いない会員には送れないFR-LIKE-001〜004・007・008#26
送った相手の一覧新しい順に、相手の ID・ニックネーム・年齢・画像・日時FR-LIKE-005・006・NFR-LIKE-001#26

API のパスと応答の形は、子 Issue #26 の最初に docs/api/02-likes.md に書き、確かめてもらってから作ります。

2. 先に知っておく言葉

言葉意味（1〜2文）
多対多1人が何人にもいいねでき、1人が何人からももらえる関係。2つの表の列だけでは持てないので、間に表を置く。
中間テーブル多対多の「組」を1行ずつ持つ表。ここでは likes。「いつ」などの、組についての情報も持てる。
自分の表どうしの多対多両側が同じ users の多対多。from_user_id（送った人）と to_user_id（もらった人）の2つの列で、向きを持つ。
UNIQUE 制約指定した列の組み合わせが、表の中で1つだけになるように DB が守る決まり。裏でインデックスが作られる。
複合主キー2つ以上の列の組を主キーにすること。中間テーブルでは (from_user_id, to_user_id) を主キーにして、id を持たない作り方もある。
check-then-act「あるか調べてから、なければ入れる」という書き方。調べてから入れるまでの間に別のリクエストが入ると、両方が「ない」と見て、両方が入れてしまう。
ON CONFLICT DO NOTHINGPostgreSQL の書き方。UNIQUE に当たる行を入れようとしたら、エラーにせず、何もしない。入った行の数（0 か 1）で、二重だったかが分かる。Laravel では insertOrIgnore()。
N+1一覧を1本の SQL で取り、そのあと1件ごとに関連するものを1本ずつ取ること。N 件なら 1＋N 本になる。Eloquent では、リレーションをループの中で読むと起きる。

4. 設計の選択肢を比べる

中間テーブルのキー

案良いところ弱いところ向いている場面
A. id だけで、組に制約なし何も考えずに作れる。Eloquent の Model がそのまま使える同じ組が何行でも入る（アンチパターン「IDリクワイアド」）。いない会員を指せるなし
B. id＋(from_user_id, to_user_id) に UNIQUE（レガシー版もこの形）二重を DB が断る。Eloquent の Model（Like）を使い続けられる。A から制約を足すだけで移れる使わない id と、そのインデックスが1つ増えるあとで「いいね」そのものを別の表から指したい（通知など）とき。今の表から直すとき
C. (from_user_id, to_user_id) を複合主キー余分な列とインデックスがない。主キーがそのまま「A は B にいいねしたか」の検索に効くEloquent は複合主キーの Model が苦手（find()・save() が使いにくい）。A から移るには、id と主キーを作り直す初めから作るとき。ORM を使わないとき
この一歩で選ぶもの：レガシー版も改善版も B。レガシー版は UNIQUE だけで、外部キー・CHECK・to_user_id のインデックスがない。改善版は、自分あて・いない会員を指す行を先に直してから、それらを足す（01 と同じ「先に直してから制約」の手順）。Eloquent の Like の Model も使い続けられる。C との違いは、6つの問いの「ほかの方法」で話せるようにする。

二重の防ぎ方

案良いところ弱いところ向いている場面
A. アプリで「あるか」調べてから入れる分かりやすい。409 の言葉を出しやすい同時に来ると両方が入る（check-then-act）。制約がなければ防げない使わない（UNIQUE の上での、言葉を出すための前の確かめとしてならよい）
B. UNIQUE に当てて、例外（23505）をつかまえて 409（レガシー版は UNIQUE だけあって、つかまえないので 500）同時でも1行になるPostgreSQL では、エラーになったトランザクションは、そのあとの SQL が全部失敗するトランザクションの外で1本だけ入れるとき
C. UNIQUE＋ON CONFLICT DO NOTHING（insertOrIgnore()）で、入った行の数を見る同時でも1行になる。エラーにならないので、トランザクションが止まらない二重のとき、どの行とぶつかったかは返らない（ここでは要らない）「あれば何もしない」でよいとき
この一歩で選ぶもの：改善版は C。土台は UNIQUE（DB が守る）。03 でマッチを同じトランザクションで作るときにも、エラーでトランザクションを止めずに済む。

自分へのいいね・一覧の取り方

決めること改善版理由
自分へのいいねバリデーションで 422＋DB の CHECK（from_user_id <> to_user_id）不変条件 4。API を通らない書き込み（シード・手で入れる SQL）でも壊れてはいけない（database.md の判断）
いない会員404＋外部キー消えた会員を指す行を残さない（FR-LIKE-009 は ON DELETE CASCADE）
送った一覧with('toUser.profile') でまとめて読む（3本）NFR-LIKE-001。件数が増えても本数が増えない
to_user_id のインデックス足すUNIQUE の (from_user_id, to_user_id) は、ふつうは from_user_id から探すときに効く。PostgreSQL 18 の skip scan は、先頭の列の種類が少ないときだけ to_user_id でも使えるが、送る人が多いと使われない（9-2 で測った）。03 のマッチ（逆向きを探す）と 07 のもらった一覧で、to_user_id から探す

5. 見本：レガシー版と改善版

レガシー版（Fat Controller・テストなし）

// いいねを送る
public function store(Request $request): JsonResponse
{
    // 01b の me() から写した JWT の処理（ほかのコントローラにも同じものが増える）
    $payload = JWT::decode($request->bearerToken(), new Key(config('app.key'), 'HS256'));
    $like = Like::create([
        'from_user_id' => $payload->sub,
        'to_user_id' => $request->input('user_id'),   // 自分でも・いない会員でも入る。2回目は UNIQUE の違反で 500
    ]);
    return response()->json($like, 201);
}

// 送った相手の一覧
public function index(Request $request): JsonResponse
{
    $payload = JWT::decode($request->bearerToken(), new Key(config('app.key'), 'HS256'));
    $likes = Like::where('from_user_id', $payload->sub)->orderBy('created_at', 'desc')->get();
    $result = [];
    foreach ($likes as $like) {
        $profile = Profile::where('user_id', $like->to_user_id)->first();   // 1件ごとに1本
        $result[] = ['user_id' => $like->to_user_id, 'nickname' => $profile?->nickname,
                     'birthday' => $profile?->birthday, 'liked_at' => $like->created_at];
    }
    return response()->json($result);
}
  • 二重：UNIQUE があるので行は1つのまま。ただし2回目は、違反の例外をつかまえないので 500（409 にならない）。同時に送ると、1つ以外は 500
  • 自分・いない会員：user_id が自分でも、ない会員でも入る（CHECK・外部キーがない）。会員を消すと、いいねが残る
  • もらった側から探す：UNIQUE は from_user_id が先頭なので、to_user_id から探すと表を全部読む（03 のマッチ・07 のもらった一覧で困る）
  • N+1：送った数が N なら、SQL は 1＋N 本。100人に送れば 101本
  • 写した JWT の処理：01b と同じく、トークンがないと 500。直すときは、写したすべての場所を直す
  • 年齢：生年月日をそのまま返す（FR-LIKE-005 は年齢）

改善版

// マイグレーション：UNIQUE はレガシー版にある。先に自分あて・いない会員の行を直してから、残りを足す
Schema::table('likes', function (Blueprint $table) {
    $table->foreign('from_user_id')->references('id')->on('users')->cascadeOnDelete();
    $table->foreign('to_user_id')->references('id')->on('users')->cascadeOnDelete();
    $table->index('to_user_id');
});
DB::statement('ALTER TABLE likes ADD CONSTRAINT likes_not_self CHECK (from_user_id <> to_user_id)');

// いいねを送る（だれかはガードが決める。自分あては FormRequest で 422）
$target = User::findOrFail($request->integer('user_id'));            // いなければ 404
$inserted = DB::table('likes')->insertOrIgnore([                       // on conflict do nothing
    'from_user_id' => $request->user()->id, 'to_user_id' => $target->id, 'created_at' => now(),
]);
if ($inserted === 0) {
    return response()->json(['message' => 'もういいねしています'], 409);
}

// 送った相手の一覧（何件でも3本：likes・users・profiles）
$likes = $request->user()->sentLikes()->with('toUser.profile')->latest()->get();
return LikedUserResource::collection($likes);

大事なのは、二重を「アプリが調べる」のではなく「DB に断らせる」こと、そして DB が断ったことを 500 ではなく 409 として返すことです。insertOrIgnore() は UNIQUE に当たっても例外にせず 0 を返すので、トランザクションを止めずに 409 を返せます。外部キーや CHECK の違反は、無視されずにエラーになります（MySQL の INSERT IGNORE は、こうした違反も警告にして飲み込むので、同じではありません）。

Eloquent が発行する SQL（レガシー版と改善版を並べる）

同じ「いいね」でも、書き方で SQL の本数と中身が変わります。左がレガシー版、右が改善版です。SQL は Laravel に作らせて確かめたもので（改善版の書き込みは DB::pretend() で、流さずに SQL だけを取り出した）、例は会員 23 が会員 5・6 にいいねしている場合です。中身は explanations/sql/02-likes.json にあり、explanations/tools/compare-block.py で作り直せます。

ログ（sql-*.log）では、値は ? になり、別に渡されます（プリペアドステートメント）。読みやすいよう、ここでは値を入れて、行を分けて書きました。

いいねを送る（POST /api/me/likes）

レガシー版1本

// $payload->sub が 23、user_id が 5 のとき
Like::create([
    'from_user_id' => $payload->sub,
    'to_user_id' => $request->input('user_id'),
]);

↓ 発行される SQL

insert into "likes"
  ("from_user_id", "to_user_id",
   "updated_at", "created_at")
values (23, 5,
  '2026-11-12 05:27:23',
  '2026-11-12 05:27:23')
returning "id";
-- 2回目は UNIQUE の違反（23505）
-- の例外 → 500
  • 相手がいるかも、自分あてかも調べない。DB が止めるのは UNIQUE と NOT NULL だけ
  • create() は Model の日時（updated_at・created_at）を自分で入れ、returning "id" で新しい ID を受け取る
  • 自分（sub）が会員としているかも読まない。消えた会員の JWT でも送れるのは、このため

改善版2本＋ガード1本

$me = $request->user();
$target = User::findOrFail(
    $request->integer('user_id')
);
$inserted = DB::table('likes')->insertOrIgnore([
    'from_user_id' => $me->id,
    'to_user_id' => $target->id,
    'created_at' => now(),
]);
// $inserted が 0 なら 409

↓ 発行される SQL

-- ① 相手がいるか（いなければ 404）
select * from "users"
where "users"."id" = 5 limit 1;

-- ② 入れる。UNIQUE に当たれば何もしない
insert into "likes"
  ("from_user_id", "to_user_id", "created_at")
values (23, 5, '2026-11-12 13:00:00')
on conflict do nothing;
-- 入った行が 1 なら 201、0 なら 409
  • findOrFail() は limit 1 で1行だけ読み、なければ例外（404）にする
  • insertOrIgnore() は PostgreSQL では on conflict do nothing。例外にならないので、トランザクションも止まらない
  • これとは別に、ガードが「自分」を読む1本がある（形は 01b の改善版で決める）

送った相手の一覧（GET /api/me/likes）

レガシー版1＋N 本

$likes = Like::where(
        'from_user_id', $payload->sub
    )
    ->orderBy('created_at', 'desc')
    ->get();
foreach ($likes as $like) {
    $profile = Profile::where(
        'user_id', $like->to_user_id
    )->first();
}

↓ 発行される SQL

-- ① 送ったいいね（1本）
select * from "likes"
where "from_user_id" = 23
order by "created_at" desc;

-- ② いいね1件ごとに1本（first()）
select * from "profiles"
where "user_id" = 6 limit 1;
select * from "profiles"
where "user_id" = 5 limit 1;
-- いいねが100件なら、②が100本
-- （測ったら合計101本）
  • ループの中で SQL を呼ぶと、件数の分だけ往復が増える（N+1）
  • profiles.user_id にインデックスがないので、②の1本ずつが表を全部読む
  • first() は limit 1 を付けるだけで、並びを決めない（プロフィールが2つあると、どちらが出るか決まらない）

改善版（with）3本＋ガード1本

$likes = $request->user()
    ->sentLikes()
    ->with('toUser.profile')
    ->latest()
    ->get();

↓ 発行される SQL

-- ① 送ったいいね
select * from "likes"
where "likes"."from_user_id" = 23
  and "likes"."from_user_id" is not null
order by "created_at" desc;

-- ② 相手の会員をまとめて（toUser）
select * from "users"
where "users"."id" in (5, 6);

-- ③ プロフィールをまとめて（.profile）
select * from "profiles"
where "profiles"."user_id" in (5, 6);
-- いいねが100件でも、3本のまま
  • with() は、①の結果から相手の ID を集めて、in (…) で1本にまとめる（Eager Loading）
  • is not null は、リレーション（hasMany）から呼ぶと Laravel が足す条件
  • latest() は order by "created_at" desc の短い書き方
  • in (5, 6) のように、整数の ID は ? ではなく SQL に直接入る（Laravel が整数だと確かめてから入れる）
  • 今のモデルでは名前が likes()。改善版で sentLikes() にする予定（SQL は同じ）

ほかの書き方（JOIN）1本＋ガード1本

DB::table('likes')
    ->join('users', 'users.id', '=', 'likes.to_user_id')
    ->leftJoin('profiles', 'profiles.user_id', '=', 'users.id')
    ->where('likes.from_user_id', $me->id)
    ->orderByDesc('likes.created_at')
    ->get(['users.id as user_id', 'profiles.nickname',
           'profiles.birthday', 'profiles.image',
           'likes.created_at as liked_at']);

↓ 発行される SQL

select "users"."id" as "user_id", "profiles"."nickname",
       "profiles"."birthday", "profiles"."image",
       "likes"."created_at" as "liked_at"
from "likes"
inner join "users" on "users"."id" = "likes"."to_user_id"
left join "profiles" on "profiles"."user_id" = "users"."id"
where "likes"."from_user_id" = 23
order by "likes"."created_at" desc;
  • 1本で済む。inner join users なので、消えた会員のいいねは結果に出ない（FR-LIKE-009 の見え方）
  • left join profiles なので、プロフィールのない相手も null で出る（inner にすると消える）
  • 弱いところ：返るのは Model ではなくただの行。列を自分で選ぶ。プロフィールが2つある相手は、行が2つに増える
操作レガシー版改善版（with）JOIN違いのもと
送る1本（何も確かめない）2本＋ガード1本―相手がいるかを読む・on conflict do nothing
一覧（いいね N 件）1＋N 本3本＋ガード1本1本＋ガード1本ループの中の first() → with() の in (…) → JOIN
要確認：NFR-LIKE-001 は「一覧の SQL は3本以内」。with('toUser.profile') は3本で、ガードが自分を読む1本を足すと4本になる。「3本」にガードを含めるか、users を飛ばして profiles だけを読むか（2本）、JOIN にするか（1本）は、改善する段階で決める。

6. どう確かめるか

段階確かめること
① レガシー版で問題を見る
  • 同じ相手に2回送る → ステータスと行の数（UNIQUE で1行のまま・2回目は 500 か）。xargs -P 10 などで同じいいねを10本同時に送る → ステータスの内わけと行の数
  • 自分に送る・いない会員に送る → 入るか。会員を消す → いいねが残るか（DB で、トランザクションの中で試して取り消す）
  • 送った数を 1・10・100 にして一覧を呼ぶ → SQL のログの本数（1＋N 本になるか）
  • EXPLAIN (ANALYZE, BUFFERS) で、「A は B にいいねしたか」（UNIQUE が効くか）と「B はだれからもらったか」（to_user_id だけ。Seq Scan になるか）を比べる。シードでいいねを1万件ほど入れて、読んだ行と時間を見る
② 振る舞いを固定するテストFR-LIKE-001 いいねを送れる・FR-LIKE-002 自分にはいいねできない・FR-LIKE-003 同じ相手へのいいねは1回だけ（続けて・同時に）・FR-LIKE-004 いない会員にはいいねできない・FR-LIKE-005 送った相手の一覧を見られる・FR-LIKE-009 会員が消えたら、その会員のいいねも消える・NFR-LIKE-001 一覧の SQL は3本以内（いいねを 1件と 20件にして、本数が同じか）
③ 改善したあとに比べる数字10本同時の応答の内わけ（201 が1つ・500 が9つ → 201 が1つ・409 が9つ）・一覧の SQL の本数（1＋N → 3）・to_user_id から探すときの EXPLAIN の段と読んだ行（Seq Scan → Index Scan）と時間・守れている要件の数（○/11 → 11/11）

7. 気をつけること（罠）

  • 「あるか調べてから入れる」だけでは、同時のリクエストで破れる：アプリの確かめは、言葉を出すためのもの。守るのは UNIQUE
  • UNIQUE があっても、違反を扱わなければ 500：データは守れても、使う人には「サーバーのエラー」に見える。DB が断ったことを、API の言葉（409）に直すのはアプリの役目
  • PostgreSQL では、UNIQUE の違反でトランザクションが止まる：例外をつかまえても、同じトランザクションの次の SQL は current transaction is aborted で失敗する。ON CONFLICT DO NOTHING か、セーブポイントを使う
  • 複合のインデックスは、ふつうは先頭の列から探すときに効く：(from_user_id, to_user_id) は「A が送った一覧」には効くが、「B がもらった一覧」（to_user_id だけ）には、ふつうは効かない。PostgreSQL 18 の skip scan は、先頭の列の値ごとに索引を探し直すので、送る人が数人なら使われる。会員が増えて送る人が多くなると使われず、表を全部読む（9-2）
  • 制約を足す前に、違反している行を直す：重なった行・自分あての行・いない会員を指す行が1つでもあると、ALTER TABLE が失敗する。先に読み取りの SQL で数える（database.md）
  • いいねには向きがある：A から B と、B から A は別の行。「お互い」（マッチ）は 03 で、向きが逆の行を探す
  • ON DELETE CASCADE で消える範囲：会員を消すと、送ったいいねも、もらったいいねも消える。06 の退会で論理削除（行を残して印を付ける）にするなら、CASCADE は働かないので、別の扱いを考える

8. 理解を確かめる6つの問い

先に自分で答えてから、開いて見る。

なぜそうするのか？

不変条件 5（同じ相手へのいいねは1回）を、アプリではなく DB の UNIQUE で守るため（レガシー版も UNIQUE は持つ）。アプリで「あるか」調べるだけだと、同時に2つ来たときに両方が「ない」と見て、2行入る。UNIQUE なら、何本同時に来ても1行になる。ただ、レガシー版は違反をそのまま 500 にしている。改善版は入れ方を ON CONFLICT DO NOTHING にして、エラーでトランザクションを止めずに 409 を返す。自分あてを CHECK、いない会員を外部キーで止めるのも、API を通らない書き込みでも壊れないようにするため。

ほかの方法は？なぜ選ばなかったか？

中間テーブルを (from_user_id, to_user_id) の複合主キーにする案（C）は、余分な id がなく、本来はきれい。選ばなかったのは、Eloquent が複合主キーの Model を苦手にすることと、レガシー版の表（id あり）から制約を足すだけで移れることのため。二重を例外（23505）で受ける案は、PostgreSQL ではトランザクションが止まり、03 でマッチを同じトランザクションで作るときに困る。

弱点は？

使わない id と、そのインデックスの分だけ、表と書き込みが少し重い。インデックスは UNIQUE の (from_user_id, to_user_id) と to_user_id の2つが増え、いいねを入れるたびに両方を書き直す。ON CONFLICT DO NOTHING は、二重のときにどの行とぶつかったかを返さない。CASCADE は、06 で論理削除にすると働かなくなる。

問題が起きたら、どう調べて直すか？

「いいねを押すとエラーになる」と言われたら、laravel.log で 23505（UNIQUE の違反）を探す。あれば、2回目のいいねを 500 にしている（レガシー版）。insertOrIgnore() にして 409 を返す。UNIQUE のない表なら、select from_user_id, to_user_id, count(*) from likes group by 1, 2 having count(*) > 1 で重なりを数え、1つに減らしてから UNIQUE を足す。一覧が遅いと言われたら、SQL のログで本数（N+1 か）を見て、EXPLAIN (ANALYZE, BUFFERS) で Seq Scan を探す。

データが10倍・100倍になったら？

いいねは会員の数より速く増える（1人が何十人にも送る）。インデックスがないと、「A は B にいいねしたか」も、送った一覧も、表を全部読む。UNIQUE の (from_user_id, to_user_id) があれば、どちらも数行を読むだけで済む。一覧は件数が増えるので、04 でページ送り（カーソル）を入れる。N+1 のままだと、送った数に比例して SQL が増える。

Eloquent でどんな SQL が流れ、どう直したか？ Rails（ActiveRecord）・Prisma ならどう書くか？
