2. 変わる要件と決定

場所今変えたあと
docs/decisions.md の D-014JWT（15分）と取り替え用のトークン（30日）「置き換え」にする。新しい決定を足す：会員の認証は、Sanctum の SPA 認証（セッション）
FR-AUTH-010（ログイン）access と refresh の Cookieセッションの Cookie が付く。ログインのたびに、セッションの番号を作り直す
FR-AUTH-013（15分で切れる）アクセストークンは15分操作がないまま24時間で切れる。使うたびに、期限が24時間先に延びる（5章の1）
FR-AUTH-014・015（取り替え・使い回し）取り替え用のトークン外す。番号は欠番にし、理由を1行残す
FR-AUTH-016（ログアウト）取り替え用のトークンを使えなくする204。セッションの行を消し、Cookie を消す。同じ Cookie は 401
新しい要件（CSRF）―書き込みは、CSRF のトークン（Sanctum の XSRF-TOKEN）がなければ 419 で断る（5章の2）
NFR-AUTH-001確かめに DB を使わない毎回、セッションと会員の状態（退会・停止）を DB で確かめる

5. 決めたこと（2026-11-20 に人が決めた）

#問い決めたこと理由・中身
1ログインが切れる時間操作がないまま 24時間 で切れる。使っているあいだは延び続ける頻繁に切れると使いにくいため。セッションは、リクエストのたびに sessions.last_activity と Cookie の期限を書き直すので、取り替え用のトークン（refresh_token）がなくても、ページを開くたびに期限が24時間先に延びる。設定は SESSION_LIFETIME=1440（分）。「ログインしたままにする」（remember_token）は使わない
2CSRF の守り方Sanctum の CSRF のトークン（XSRF-TOKEN）を使う。前に選んだ「JSON だけを受ける」の代わりにするLaravel の標準の仕組みで、自分で書く所がない。画面は、書き込みのたびに X-XSRF-TOKEN を付ける（client.ts の1か所）
3移すあいだの形(a) 一度に切り替えるセッションと JWT の両方を受けるあいだ、XSS で持ち出される穴が残るのを避ける。そのために、先に API と画面の「読む所」を1か所にし（2）、メンテナンスの中で中身だけを替える（4）

6. 手元での確かめ方

  1. 画面は http://localhost:5173、API は http://localhost:8000 で開く（どちらも localhost。127.0.0.1 を混ぜると、Cookie が届かない）
  2. ログインし、ブラウザの開発者ツールの「アプリケーション」で、セッションの Cookie に HttpOnly の印が付いていること、sessionStorage にトークンがないことを見る
  3. DB で select id, user_id, last_activity from sessions; を流し、行ができていることを見る
  4. ログアウトし、行が消えること、同じ画面の API が 401 になることを見る
  5. 管理画面で会員を止め、その会員の次の操作が 401 になることを見る

7. 戻し方

  • マイグレーションはない（表 sessions は前からある）。PR を戻せば、元の JWT に戻る
  • 戻すときは、API と画面を一緒に戻す（片方だけ戻すと、ログインできなくなる）
  • 残った sessions の行は、使われずに期限で消えるので、害はない
